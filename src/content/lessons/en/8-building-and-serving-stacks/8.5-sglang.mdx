Your traffic is not what [lesson 8.4](/lessons/8-building-and-serving-stacks/8.4-vllm/) assumed. Instead of independent users asking independent questions, you are running an agent. One task fans out into forty model calls. Each call begins with the same system prompt, the same tool schemas, and the same few-shot examples (sample question-and-answer pairs that show the model the expected format): about three thousand tokens of identical preamble. The calls differ only in the last paragraph, and every one must return a JSON object your code will parse. On a general-purpose engine this workload wastes memory and compute without any error to warn you, and understanding why is the whole reason SGLang exists.

## What does a repeated preamble cost?

Price the waste with the number you already have. [Lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/) established 64 KiB of KV per token for Qwen3.8-27B (the keys and values the model caches for each token so later tokens can attend to it). A three-thousand-token preamble therefore occupies

$$
3{,}000 \times 64\ \text{KiB} = 187.5\ \text{MiB}
$$

of cache. Forty concurrent calls each holding their own copy come to roughly 7.3 GiB of duplicate KV. That is substantial pressure in any realized pool, whose complete budget belongs to [lesson 9.3](/lessons/9-hardware-and-infrastructure/9.3-kv-cache-sizing-and-memory-budgets/).

The compute is just as bad. Prefill, the phase that processes the prompt before the first new token, runs on the preamble forty times. That is one hundred and twenty thousand tokens of attention work to produce a prefix the engine already computed thirty-nine times that second.

## How RadixAttention stores a shared prefix once

RadixAttention is the fix, and its design follows from what the cache actually is. KV blocks are a function of the token ids that produced them and of their positions. So two sequences that begin with the identical run of tokens have identical blocks for that run.

SGLang therefore organizes the block pool as a **radix tree** keyed on token ids. A radix tree is a tree in which each path from the root spells out a sequence, so sequences with a common beginning share the same path. (If you have met a trie for autocompleting words, it is the same idea with token ids in place of letters.) Three rules make it work:

1. An arriving request walks the tree from the root and reuses every block along the longest matching path.
2. It allocates new blocks only for the suffix where it diverges.
3. Eviction is least-recently-used (LRU) over the tree: when memory runs short, the blocks touched longest ago go first. Hot prefixes, such as your system prompt, stay resident while one-off conversations age out.

In our example the preamble is stored once, at about 188 MiB, and prefilled once. That recovers roughly seven gibibytes of pool and thirty-nine fortieths of the preamble's prefill cost.

:::warning
Teams often enable prefix sharing, measure no improvement, and conclude the feature does not work. Almost always the prompt begins with something volatile: a timestamp, a request or trace id, a per-user greeting, a tool list serialized in a different order each time, or a retrieved-document block whose ordering is not stable. Matching is exact and anchored at position one, so a single differing token at the top collapses the shared prefix to zero. Restructure the prompt so everything stable comes first and everything variable comes last. Then measure the cache hit rate the engine reports, rather than inferring it from latency.
:::

## Scheduling a program, not a pile of requests

The second thing SGLang treats as first-class is that your forty calls are a *program*, not forty unrelated requests. They have dependencies. They fork and join. Some of them are speculative branches you will discard.

When the runtime knows the program structure, it can schedule with that knowledge. It can keep a branch's prefix pinned in memory while its children run, batch the siblings together, and order the work so that a shared parent is computed once before the fork rather than forty times after it. An engine that only sees independent HTTP requests can recover some of this after the fact, through prefix matching, but it cannot plan for it in advance.

## How constrained decoding guarantees the JSON shape

Structured output is the third piece, and it turns the JSON requirement into a guarantee rather than a hope. [Lesson 7.4](/lessons/7-inference-and-efficiency/7.4-sampling/) described sampling as drawing the next token from the model's probability distribution over the vocabulary. Constrained decoding adds one step before that draw:

1. Your JSON schema or grammar is compiled into a state machine, which tracks what may legally come next.
2. At every step, the engine masks the logits (the raw scores) of every token that cannot legally follow the text so far, setting their probability to zero.
3. Sampling then happens over the tokens that remain.

So the model cannot emit a stray prose apology in front of the opening brace, cannot close an array it did not open, and cannot invent a field name outside the schema. That holds because those tokens had their probability set to zero, not because the prompt asked nicely.

Two practical notes. Compiling a grammar costs real time, so reuse and cache schemas rather than building one per request. And the constraint applies only to shape.

:::caveat
Schema-valid is not correct. A constrained decode will happily produce a perfectly formed object whose fields are wrong, invented, or contradictory. It will even look more confident than free-form text, because the usual sign of a confused model, rambling, has been masked away. Keep semantic validation downstream. Constrained decoding removes parse errors from your incident list; it does not remove hallucination.
:::

## Sharing a prefix in a hybrid model

The hybrid architecture complicates prefix sharing, and this is the deepest point in the lesson, so here it is step by step.

- Only the 16 full-attention layers store per-token KV blocks, and those blocks are exactly what a radix tree can share.
- The 48 Gated DeltaNet layers hold a fixed-size recurrent state that is a *summary* of everything processed so far. It has no per-token structure, so it cannot be indexed into or partially reused.
- So for a request to resume from a shared prefix, the engine must also have saved a checkpoint of the recurrent state at that prefix boundary, and must be able to restore it.

That checkpoint is not small. The reference implementation stores about 144 MiB per sequence when that state is fp32, the same order as the 188 MiB of shared KV in this example, not a negligible add-on. A serving runtime may use another state dtype or layout, so inspect its realized allocation.

Checkpointing state is a different mechanism from sharing blocks. Whether a given release implements it is a per-version question to verify, not to assume. The alternatives are a fallback to full recomputation that gives no warning, or, worse, blocks reused against a stale state. SGLang publishes an official cookbook page for this exact model. That page is the right starting point because it pins the versions and settings the maintainers have exercised.

## Who is allowed to share a prefix?

One boundary rule survives all of this unchanged. Reuse is exact-match on token ids, so no content crosses between requests that did not already share it word for word. But a cache hit is faster than a miss, and timing is observable: another user can learn something from how fast a response arrives. Treat prefix sharing across tenants (separate customers on the same server) as a decision to make deliberately. Keep tenants in separate pools when the prompt itself is confidential, and re-read lesson 7.2's warning that cached keys and values are a rich record of what a user said.

The map in [lesson 7.11](/lessons/7-inference-and-efficiency/7.11-serving-stacks-vllm-sglang-tensorrt-llm/) sent you to SGLang for traffic made of programs rather than prompts. Now you can say why in numbers: seven gibibytes of pool and thirty-nine redundant prefills recovered from one workload, and a JSON contract enforced at the sampler instead of hoped for in the prompt.
