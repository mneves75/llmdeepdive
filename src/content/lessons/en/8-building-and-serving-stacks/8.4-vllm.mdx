You have one 80 GB GPU, a copy of Qwen3.8-27B, and a request to stand up an internal chat API for perhaps forty engineers. Two numbers decide whether that works: how much of the card the engine is allowed to claim, and how long a single conversation may become. Get them wrong in one direction and the server refuses to start. Get them wrong in the other and it dies under the first real burst of traffic.

This lesson shows the operational sizing loop. Everything else about vLLM (the OpenAI-shaped API, the scheduler, the metrics) is documentation you can read. The part people get wrong is mistaking a configured ceiling for realized capacity, meaning the memory the engine actually managed to set aside.

## What vLLM does with the memory you give it

vLLM exists because of [lesson 7.8](/lessons/7-inference-and-efficiency/7.8-pagedattention-and-continuous-batching/), and it uses both of that lesson's ideas:

- **Continuous batching.** The scheduler admits and retires requests at iteration boundaries (between one decode step and the next) rather than holding a fixed batch until the slowest member finishes.
- **A paged KV cache.** The cache of keys and values is split into fixed-size blocks handed out as tokens are produced. A session that stops after four thousand tokens never paid for the thirty-two thousand it was permitted.

At startup, the engine has to decide how large that block pool should be. It does so by subtraction rather than by asking you: it takes what it is allowed to use and removes everything else that must live on the card.

## The utilization flag is a ceiling, not the KV pool

Treat `--gpu-memory-utilization` as a ceiling on everything the engine allocates. Before any cache capacity appears, the engine pays for:

- resident weights,
- activation peaks (the largest temporary tensors a forward pass needs),
- CUDA graph pools (memory reserved for the captured graphs of [lesson 8.3](/lessons/8-building-and-serving-stacks/8.3-torch-compile-and-cuda-graphs/)),
- allocator fragmentation (free memory split into pieces too small to use),
- and architecture-specific state.

[Lesson 9.3](/lessons/9-hardware-and-infrastructure/9.3-kv-cache-sizing-and-memory-budgets/) owns that full accelerator budget, while [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/) owns this model's cache and recurrent-state derivation. In the reference implementation, the 48 Gated DeltaNet layers keep about 144 MiB of recurrent state per sequence when that state is fp32 (32-bit floats). Another runtime can choose a different dtype or layout. So copying that byte count into a vLLM capacity claim without checking the implementation would be just as wrong as ignoring the state.

## Reading the pool the engine actually allocated

The source of truth is therefore the launch you will serve. Pin the checkpoint and the vLLM release, and leave deliberate headroom. Then read the startup lines that report two things: the KV pool actually allocated, and the maximum concurrency that pool implies at your chosen context length.

`--max-model-len` must fit at least one request inside that realized pool. If it does not, the engine should reject the configuration at startup. Your choices are to lower the limit, change to a validated memory format, or add capacity, and then measure again.

Once that safety condition is met, paging changes how many requests you can admit. Blocks are allocated for tokens actually present, not for every token a request is allowed to reach. So ordinary shorter conversations can coexist at much higher concurrency than dividing the pool by the worst-case maximum length suggests. Size the hard limit from realized allocation; then size traffic from the measured distribution of prompt and completion lengths.

```
vllm serve Qwen/Qwen3.8-27B \
  --max-model-len 32768 \
  --gpu-memory-utilization 0.90
```

Do not trust any paper estimate over the engine. vLLM prints the size of the KV pool it actually allocated and the maximum concurrency that implies at your chosen context length. Read that line, compare it with your arithmetic, and reconcile any large gap before you benchmark anything. A mismatch usually means the workspace reserve or the recurrent-state accounting differs from what you assumed.

## Why not raise the fraction to 0.98?

:::warning
When the pool looks small, it is tempting to raise `--gpu-memory-utilization` toward 0.98. It appears to work: the pool grows, the startup log looks better, and short tests pass. Then a burst arrives. Prefill hits its peak activation width on a long prompt while graph capture pools are pinned, and the process is killed for running out of memory, taking every in-flight session with it. Those last few percent are not waste; they are the headroom that absorbs the difference between average and peak. Note too that the runtime reports less than the number on the box once ECC (error-correcting memory) and reserved regions are taken out. Lesson 9.3 does that subtraction. So several percent of apparent slack was never there.
:::

## When the pool cannot hold the context you need

If the realized pool cannot admit the full native context, no flag can turn that failed allocation into usable capacity. The honest options are:

- more memory;
- sharding across GPUs with tensor parallelism, which splits each weight matrix across cards ([lesson 5.8](/lessons/5-pretraining-at-scale/5.8-model-parallelism/) for the mechanics, [lesson 9.9](/lessons/9-hardware-and-infrastructure/9.9-interconnects-and-clusters/) for the interconnect cost);
- a runtime-supported lower-precision memory format that has passed the correctness canary from [lesson 8.1](/lessons/8-building-and-serving-stacks/8.1-pytorch-the-reference-runtime/) (the token-by-token comparison against eager PyTorch).

Measure the new realized pool rather than projecting a multiplier from bit width.

:::caveat
Everything here assumes your vLLM release actually supports this architecture, and support is version-specific in a way it is not for ordinary models. A hybrid model needs a block manager that handles two kinds of memory at once: paged per-token blocks for 16 layers and fixed per-sequence recurrent state for 48. Engines gained that capability at different times for different layer types. Verify on your exact version before reading any benchmark: confirm the model loads, then run the differential test from lesson 8.1 against eager PyTorch on a short deterministic prompt. An engine that mishandles the recurrent state without raising an error produces fluent, wrong text at excellent throughput.
:::

Carry the measurement chain, not a memorized set of flags. The utilization fraction bounds the engine. The startup log reports the pool it actually realized. And `--max-model-len` bounds the largest single claim against that pool. Lessons 7.2 and 9.3 own the arithmetic behind those quantities; this lesson owns how vLLM exposes and enforces them.
