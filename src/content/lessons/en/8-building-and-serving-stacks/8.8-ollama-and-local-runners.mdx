Two people run the same pinned 17.1 GB Qwen3.8-27B Q4_K_M GGUF on the same laptop and ask the same question. Their answers have visibly different temperaments: one is crisp and literal, the other discursive and prone to inventing detail. Neither edited a config file. The difference is that one of them runs the engine from [lesson 8.7](/lessons/8-building-and-serving-stacks/8.7-llama-cpp-and-gguf/) directly, with explicit flags. The other runs it through a convenience layer that supplied sampling parameters on their behalf. This lesson is about that layer: what it genuinely gives you, and the one configuration habit that keeps it from changing your model behind your back.

## What a runner adds on top of llama.cpp

A local runner such as Ollama is not an inference engine. It is a distribution, configuration and lifecycle layer wrapped around one, in this case the llama.cpp and ggml stack. It contributes three things a bare engine binary does not offer out of the box:

- A **registry.** Models are addressed by name and tag rather than by a URL to a specific file. Pulling a model is one command, and the runner resolves which quantization variant to fetch for your hardware.
- A **Modelfile.** This small declarative recipe binds a GGUF to a chat template, a system prompt, stop sequences and sampling parameters. It can be built into a new named model that inherits from another.
- A **local server.** A long-lived process on the loopback interface (a network address only programs on the same machine can reach) exposes a chat API, including OpenAI-compatible routes. It loads a model on the first request, keeps it resident for a keep-alive interval, and evicts it to make room for another.

That last piece is not unique to the runner: llama.cpp already ships a server, `llama-server` ([lesson 8.7](/lessons/8-building-and-serving-stacks/8.7-llama-cpp-and-gguf/)). What the runner adds is the model-management layer on top of a server, which is why a runner feels different from the engine: you stop thinking about processes and start thinking about model names.

## Whose defaults are you running?

The cost of that convenience is that defaults now exist where previously there were only your flags, and defaults you did not choose are the ones that cause trouble. Qwen3.8-27B publishes two sampling presets on its model card (the knobs of [lesson 7.4](/lessons/7-inference-and-efficiency/7.4-sampling/)):

- Thinking mode, the default behaviour, expects temperature 1.0, top_p 0.95, top_k 20.
- Instruct mode, the non-thinking path, expects temperature 0.7, top_p 0.80, top_k 20.

These are not stylistic suggestions. They are the settings under which the vendor's reported behaviour was produced. A registry entry ships whatever its packager put in the Modelfile, and nothing guarantees that matches the card. If you deploy an assistant on top of unexamined defaults, you are evaluating a configuration nobody documented.

## Pinning the preset in a Modelfile

So pin it. Write a Modelfile that inherits from the pulled tag and states every parameter you care about. Then build a named local model and use only that name from your application.

```
FROM qwen3.8:27b
PARAMETER temperature 0.7
PARAMETER top_p 0.80
PARAMETER top_k 20
PARAMETER min_p 0
PARAMETER repeat_penalty 1.0
PARAMETER presence_penalty 1.5
PARAMETER num_ctx 16384
```

Build it with `ollama create qwen3.8-27b-instruct -f Modelfile` and point your client at `qwen3.8-27b-instruct`. The sampling configuration is now a versioned artifact in your repository rather than a property of whichever machine happens to be serving.

Walk through what each line buys. Alongside temperature, top_p and top_k, Ollama exposes min_p, repeat_penalty and presence_penalty. Pin all six sampling options as shown, and verify the effective request and backend, so the configuration follows the card's instruct preset. If you want thinking mode instead, build a second named model with the full thinking preset (1.0, 0.95, 20, min_p 0, repeat_penalty 1.0, presence_penalty 0) rather than toggling only temperature and top_p by hand and forgetting the rest. Sampling does not switch the mode: also turn thinking on with the runner's thinking toggle (next section), then inspect the rendered prompt the runner sends to confirm the template produced the mode you meant.

## How large should the context window be?

The `num_ctx` line is the one people omit, and it has the largest consequences. Ollama currently defaults to 4K below 24 GiB VRAM, 32K from 24 to 48 GiB, and 256K at 48 GiB or more, against this model's 262,144-token native context.

That default is not laziness. The window is a memory promise: context length times 64 KiB per token from [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/) is KV cache the runner must reserve. At 16,384 tokens the cache is 1 GiB. On the lesson's 24 GiB-class machine that is a deliberate cap below the current 32K default, chosen to leave headroom beside the pinned 17.1 GB Q4_K_M artifact. At 262,144 tokens it is 16 GiB, which is not. Choose the window your workload actually uses, and pay for exactly that.

:::warning
A truncated prompt does not announce itself. When your input exceeds the configured window, the runner drops the overflow (typically the oldest content) and generates a perfectly fluent answer from what remains. There is no error, no warning in the response, and nothing in the output that reads as damage. A model that "ignores the instructions at the top of my document" is almost never a reasoning failure; it is a context window nobody set.
:::

## Two more traps from the layering

First, per-request options sent through the API override Modelfile parameters for that request. That is useful, and it also means a stray client-side default can undo your careful pinning. Audit what your SDK sends when you pass nothing.

Second, this model ships a thinking mode controlled by the chat template and a per-request toggle, not by sampling alone. The model card's own switch is `enable_thinking`, and the runner exposes its own equivalent flag, so check the current documentation for its name. Do not assume that lowering the temperature disabled reasoning. It did not. It only made the reasoning less varied.

:::caveat
Convenience layers move faster than the engines beneath them, and support for a new architecture appears in the engine first. If a hybrid model like this one loads under a runner, the runner's bundled engine build already implements Gated DeltaNet. But a runner version that predates that support will fail on the same GGUF that works under a current llama.cpp binary. When a pull fails inexplicably, upgrade the runner before blaming the file.
:::

The habit to keep is small: treat the runner as packaging, never as policy. It decides where the file lives and how the server behaves. You decide the sampling preset, the context window and the system prompt, and you write those decisions down in a Modelfile that ships with your code. [Lesson 8.12](/lessons/8-building-and-serving-stacks/8.12-choosing-your-stack/) puts this stack beside the server-class ones and asks when the convenience is worth its ceiling.
