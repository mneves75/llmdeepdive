Your vLLM deployment from lesson 8.4 works, the pool arithmetic checks out, and the product team now wants the ninety-fifth-percentile time between tokens cut by a third on hardware you already own. You have exhausted the settings that are free. What remains is the option lesson 7.11 described as NVIDIA-maximal: stop interpreting the model at run time and compile it into an executable engine before the first request ever arrives.

That single change of tense is the whole lesson. vLLM and SGLang build their execution plan while serving; TensorRT-LLM builds it beforehand, with full knowledge of the exact shapes, precisions, and hardware it will meet. Knowing everything in advance is what lets a compiler pick tiling for a specific GPU's memory hierarchy, fuse an entire attention block into one kernel, select FP8 paths on the Tensor Cores that support them, and lay out weights in the format those kernels want rather than the format the checkpoint had. What it costs is exactly what it gained: the assumptions are baked in.

Read that as a list of things you are freezing. Precision. Tensor-parallel and pipeline layout. Maximum batch size. Maximum input length. Maximum total sequence length. The GPU architecture. The library and driver versions the engine was compiled against. The artifact is a serialized engine file, and it is not portable across any of them.

```
trtllm-build --checkpoint_dir ./qwen38-fp8 \
  --max_batch_size 32 --max_input_len 8192 --max_seq_len 16384
```

Flag names move between releases, so treat that as the shape of the decision rather than a command to copy. The decision is what matters: those three numbers are a contract with production, not hints. A request with a nine-thousand-token prompt against that engine is not slow, it is rejected.

Now the payoff, and it is larger than it first looks. Lesson 7.9 introduced eight-bit quantization; FP8 is the variant Hopper-class hardware executes natively, and because it keeps an exponent field it tolerates the activation outliers that make INT8 delicate, needing only per-tensor scales derived from a short calibration pass. Apply it to Qwen3.8-27B and work through the memory, reusing lesson 8.4's subtraction. The weights fall from 54 GB in bf16 to roughly 27 GB. On an 80 GB card at a 0.90 utilization budget of about 72 GB, subtracting 27 GB of weights and about 4 GB of workspace leaves roughly 41 GB, call it 38 GiB of pool — against the 14 GiB we had at bf16. Then apply the same eight-bit format to the cache: lesson 7.2's 64 KiB per token is two bytes per element, so an eight-bit KV format halves it to about 32 KiB per token. The pool now holds

$$
\frac{38\ \text{GiB}}{32\ \text{KiB per token}} \approx 1{,}245{,}000\ \text{tokens}
$$

against roughly 229,000 before. That is not a factor of two, it is a factor above five, and the reason is worth internalizing: the weights are a fixed cost subtracted before anything else, so halving them releases memory disproportionately, and the halved cache then stretches the released memory twice as far. Quantization compounds against a fixed overhead. This is the same structure that will decide every hardware question in track 9.

Serving is otherwise familiar. In-flight batching is TensorRT-LLM's name for the iteration-level scheduling of lesson 7.8: requests join and leave between decode steps rather than waiting for a fixed batch to drain. Paged KV, chunked prefill, and speculative decoding all have counterparts here. The programming model differs — engine plus runtime rather than a Python engine you configure — but the concepts transfer intact, which is why this lesson can spend its space on the parts that do not.

:::warning
The classic wrong turn is the benchmark that proves what you wanted. Someone builds an engine at maximum batch size 1 and maximum input length 2048, measures a beautiful latency curve, and reports that TensorRT-LLM beats vLLM by a wide margin. The comparison is void: production sends variable prompts up to 32K at real concurrency, and that engine cannot accept them at any speed. A fair comparison builds the engine for the shapes production actually sends, then replays the same trace — same prompt and output length distributions, same arrival pattern, same decoding parameters — against both stacks. Compare goodput under a latency objective, not a peak number.
:::

The operational bill arrives later and is the reason many teams choose otherwise. Your build matrix is the product of precision, parallel layout, shape buckets, GPU architecture, and library version, and every cell is an artifact to build, store, validate, and roll out. Engines do not survive a GPU generation change. A base-image security patch that moves the library version can invalidate the lot. Builds take minutes to hours, so a shape change is a scheduled event rather than a flag flip, and an urgent capacity change on a Friday evening is a build, not a restart. None of this is a defect — it is the price of the tailoring — but it is a standing commitment of engineering time, and it is why lesson 7.11 gated this option behind having an ops team that can own it.

:::caveat
Architecture support decides everything above, and for this model it must be verified per version rather than assumed. Qwen3.8-27B's 48 Gated DeltaNet layers need explicit implementation: kernels for the delta-rule update and the short convolution, and a runtime that manages a per-sequence recurrent state alongside the paged KV of the 16 attention layers. Compiled stacks typically gain support for a new architecture later than eager and Python-engine stacks do, because a plugin or kernel must be written rather than a module. Before planning any migration, confirm the exact release builds and runs this model, then run the differential test from lesson 8.1 against eager PyTorch. An engine that compiles cleanly and mishandles the recurrent state will be fast, confident, and wrong.
:::

Weigh it as a trade rather than a ranking. TensorRT-LLM buys the tightest latency available on NVIDIA silicon and, through FP8, a capacity multiplier that compounds against fixed costs; it sells you flexibility, portability, and the ability to change your mind quickly. If your traffic shape is stable, your fleet is homogeneous, and someone owns the build pipeline, that is a good trade. If any of the three is untrue, lesson 8.4's engine will serve you better than an engine you are afraid to rebuild.
