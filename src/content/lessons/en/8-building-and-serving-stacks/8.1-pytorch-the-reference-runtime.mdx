Picture two engines answering the same prompt with the same weights, the same seed and greedy decoding (always picking the single most likely next token, so nothing is random). They give you different text. One of them is wrong, but which one? A speed benchmark cannot tell you, because it measures how fast an engine answers, not whether the answer is right. Reading the source cannot tell you either, because each engine is thousands of lines of scheduling and kernel selection (a **kernel** is a function that runs on the GPU). You settle the argument with a **reference**: a definition of what this model computes that is slow, boring and easy to inspect. That reference is eager PyTorch running the model's own modeling code.

## What does "eager" mean?

Eager means each operation runs at the moment its Python line runs. Faster runtimes do two things eager does not. They capture a **graph**: they record the whole sequence of operations once and replay it later without going back through Python. And they **fuse** operations: they merge several small steps into one kernel, so intermediate results never leave the GPU's fast memory. Eager does neither. A matrix multiply is a matrix multiply, in the order written, on tensors you can print.

That is why [lesson 7.11](/lessons/7-inference-and-efficiency/7.11-serving-stacks-vllm-sglang-tensorrt-llm/) sent you here. Before you compare serving stacks, you need an oracle, something whose answer counts as correct by definition. The best oracle is the runtime with the fewest moving parts between the parameters and the logits (the raw scores the model gives every possible next token).

## Walking Qwen3.8-27B's module tree

PyTorch organizes a model as a tree of modules, each holding its own weights and its own submodules. Printing that tree is the quickest way to see the architecture as it really is. From the bottom up:

- An embedding table with 248,320 rows of width 5120, one row per token in the vocabulary. This is [lesson 1.5](/lessons/1-text-to-tensors/1.5-embeddings-meaning-as-geometry/)'s geometry: roughly 1.271B parameters of pure lookup.
- 64 decoder layers.
- A final RMSNorm (the step that rescales each vector to a standard size) and an lm_head, the matrix that turns the last hidden vector into logits. The lm_head is *not* tied to the embedding, meaning it does not reuse the embedding matrix, so it contributes another 1.271B parameters of its own.
- Alongside all of it, for image and video input, a vision tower of 27 layers at hidden size 1152 with patch size 16. Its output is projected to 5120 so that visual patches join the same sequence the text tokens live in ([lesson 4.17](/lessons/4-transformer/4.17-multimodal-vision-encoder/)).

Inside a decoder layer, two things never change. The first is a pre-norm residual stream: the running vector each layer adds its result to, with an RMSNorm at eps 1e-6 applied before the mixer and again before the FFN ([lessons 2.8](/lessons/2-neural-network-fundamentals/2.8-initialization-normalization-residuals/) and [4.10](/lessons/4-transformer/4.10-residuals-pre-norm-post-norm/)). The second is a gated feed-forward network (FFN) that projects 5120 up to 17408 and back down ([lesson 4.9](/lessons/4-transformer/4.9-feed-forward-block/)). That FFN is where most of the model physically is.

The third slot is the token mixer, the part that lets one position read from other positions, and it is the slot that changes. The config exposes `full_attention_interval: 4`. The layout is sixteen repetitions of three Gated DeltaNet layers followed by one gated attention layer. That gives 48 mixers that carry a fixed-size recurrent state ([lesson 4.15](/lessons/4-transformer/4.15-gated-deltanet/)) and 16 that do full quadratic attention, with 24 query heads sharing 4 KV heads at head dimension 256 ([lessons 4.2](/lessons/4-transformer/4.2-self-attention/) and [4.7](/lessons/4-transformer/4.7-rope/)).

Why read the tree instead of a spec sheet? Loop over the 64 layers, ask each one what kind of mixer it holds, and count: 16 attention, 48 DeltaNet. That count is the input to [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/)'s cache derivation. Sixteen layers store keys and values for every token; forty-eight hold a state whose size does not depend on how long the conversation gets. So the 64 KiB per token that every capacity plan in this track and the next depends on is something you can *verify* by walking this tree, instead of taking it on faith.

## Why is the query projection not square?

The shapes hold one surprise that trips many readers. In [lesson 4.11](/lessons/4-transformer/4.11-full-transformer-block/)'s uniform block, the hidden size equals the number of heads times the head dimension, so you expect every attention projection to be square: 5120 in, 5120 out. Print the shapes, though, and the query projection maps 5120 to 12288. Your first guess will be a corrupt checkpoint or a misread config. It is neither.

Do the multiplication: 24 query heads × 256 head dimension = 6144, which is not 5120. Then double it, because these layers are gated and `q_proj` carries the gate in the same matrix (lesson 4.2). Qwen's designers decoupled the attention width from the residual width. So `q_proj` widens to 12288 and splits per head into a 6144 query state and a 6144 gate. `o_proj` narrows the 6144 back to 5120. `k_proj` and `v_proj` produce 4 × 256 = 1024 each.

:::warning
Do not "fix" the non-square projections. Reshaping the query projection to 5120 to match the residual stream, or assuming head dimension must equal hidden size divided by head count, destroys the model without raising any error. Three kinds of code tend to make that assumption: tensor-parallel splitting (cutting each weight matrix across several GPUs), LoRA target selection (choosing which matrices get small trainable adapters), and conversion scripts. When your own code asserts the projections are square, the assertion is what is wrong.
:::

## How do you check an engine against the reference?

With a reference in hand, comparing engines becomes an experiment instead of an opinion:

1. Feed the same token ids to eager PyTorch and to the engine under test.
2. Decode greedily on both, and find the first position where the chosen token differs.
3. Ask where the divergence came from: the tokenizer, the chat template, the sampling configuration, or the kernels.

What you must not demand is bitwise equality. In bf16 (16-bit floating point), a sum of many numbers depends on the order they are added in. Any change in tiling (how a kernel cuts a matrix into blocks) or in which requests share a batch changes that order, and so perturbs the last bits. The bar is the same tokens under greedy decoding and matching distribution statistics under sampling, not identical floats.

:::caveat
"Reference" is a moving target. The modeling code lives in a specific `transformers` release, or in the model repository itself when the architecture is newer than the library. Pin both, and record the pair alongside any comparison you publish. For a hybrid model this matters more than usual: an older release may load the weights and produce output that looks plausible but is garbage, because it treats the DeltaNet layers as something they are not.
:::

## Why nobody serves from eager PyTorch

Eager is deliberately the wrong tool for serving. Each operation pays for a Python frame and a dispatch (PyTorch choosing and launching the kernel). Nothing fuses. Memory is allocated per request. There is no paged KV cache and no continuous batching, the memory and scheduling machinery of [lesson 7.8](/lessons/7-inference-and-efficiency/7.8-pagedattention-and-continuous-batching/). So batch-1 decode, one request producing one token at a time, spends much of its life waiting on that overhead rather than on arithmetic. That overhead is exactly the problem [lesson 8.3](/lessons/8-building-and-serving-stacks/8.3-torch-compile-and-cuda-graphs/) attacks.

Keep this picture. The parameters are a dictionary of tensors. The module tree is tracks 1 through 4 made executable. And every faster stack in this track is a claim that it computes what this runtime computes slowly and in plain view.
