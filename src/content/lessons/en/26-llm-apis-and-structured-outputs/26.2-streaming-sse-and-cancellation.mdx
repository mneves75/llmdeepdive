Hit send on a non-streaming LLM call that writes a 400-token explanation and the browser sits frozen for eight seconds. Users assume the app crashed and click submit a second time. Streaming does not make the GPU generate tokens any faster, yet it transforms perceived responsiveness by exposing the two distinct phases you learned in [Prefill vs Decode: Two Different Machines](/lessons/7-inference-and-efficiency/7.3-prefill-vs-decode-two-different-machines/).

## Why streaming changes UX without shrinking compute

Consider a concrete request against the stateless API from [Stateless LLM APIs & Conversation State](/lessons/26-llm-apis-and-structured-outputs/26.1-stateless-apis-and-conversation-state/): prefill processes the prompt in `300 ms`, and decode emits `400` output tokens at a steady rate of `50` tokens per second (`20 ms` per token).

- **Without streaming**, the HTTP server holds the response open until token 400 finishes. The user waits `300 ms + 8,000 ms = 8,300 ms` (`8.3 s`) staring at a spinner.
- **With streaming**, the first token arrives at `300 ms`—the **time to first token (TTFT)**—and each subsequent token arrives `20 ms` later—the **inter-token latency (ITL)**. Humans read roughly 4 to 6 tokens per second, so `50` tokens per second already outpaces reading speed.

In general, for prefill latency $\text{TTFT}$, output length $N_{\text{out}}$, and decode throughput $r_{\text{decode}}$ (tokens per second), total generation duration is:

$$T_{\text{total}} = \text{TTFT} + \frac{N_{\text{out}}}{r_{\text{decode}}}$$

Plugging in $\text{TTFT} = 0.3\text{ s}$, $N_{\text{out}} = 400$, and $r_{\text{decode}} = 50\text{ tokens/s}$ gives $0.3 + 8.0 = 8.3\text{ s}$. Streaming lowers *wait time before reading* from $8.3\text{ s}$ to $0.3\text{ s}$ while $T_{\text{total}}$ stays unchanged.

:::note
Always measure and log TTFT and total duration separately. A spike in TTFT points to long prompts, cache misses, or queue backlog before prefill; a spike in ITL points to decode-phase GPU saturation or proxy buffering.
:::

## How Server-Sent Events works on the wire

Most LLM providers stream over **Server-Sent Events (SSE)**, defined by the WHATWG HTML Living Standard, rather than WebSockets. The reason is simplicity: LLM generation is strictly unidirectional once the `POST` body is sent, so SSE rides over ordinary HTTP/1.1 or HTTP/2 connections, passes through corporate firewalls, and works with standard load balancers.

The server answers with `Content-Type: text/event-stream` and flushes UTF-8 text blocks separated by a blank line (`\n\n`). Each event carries optional `event:` and `id:` lines plus one or more `data:` lines containing a JSON delta:

```text
event: content_block_delta
data: {"delta":{"text":"Prefill "}}

event: content_block_delta
data: {"delta":{"text":"runs once."}}

event: message_stop
data: {"finish_reason":"stop","usage":{"input_tokens":512,"output_tokens":400}}
```

Three wire-level details trip up first-time parsers:

- **TCP chunks do not align with SSE frames.** One network read may deliver half a JSON line or three complete events glued together. Buffer incoming bytes until you see the `\n\n` frame delimiter before calling `JSON.parse`.
- **Keep-alive comments happen.** Providers send lines starting with a colon (`: ping`) during long prefill or reasoning pauses so idle proxies do not kill the socket. Your parser must ignore comment lines silently.
- **Reverse proxies buffer by default.** Nginx, cloud gateways, and gzip middleware often accumulate 4 KB to 32 KB before flushing to the client, turning your stream back into a blocking wait. Disable response buffering (`X-Accel-Buffering: no`, `Cache-Control: no-cache`, and no buffered compression on `text/event-stream`).

## Cancellation, backpressure, and partial billing

A major practical win of streaming is early cancellation: if the user sees on token 30 that they asked the wrong question and clicks Stop, your frontend calls `AbortController.abort()`, which signals your backend to close the upstream HTTP stream. When the inference engine detects the closed socket, it evicts the sequence from the active decode batch so GPU slots free up immediately.

Be clear about what cancellation does and does not save. Prefill already completed before token 1 was emitted, so every input token is billed in full. Every output token generated before the close reaches the provider—often a few tokens beyond what reached the browser due to network buffers—is also billed. Because an abrupt socket close usually prevents the provider's terminal `usage` event from arriving, your backend needs a local tokenizer fallback to record estimated output tokens whenever a stream ends by cancellation or network drop.

:::warning
Never assume a stream completed cleanly just because the TCP connection closed without an exception. Inspect the terminal `finish_reason`: `stop` means natural completion, `length` means the reply hit `max_tokens` and was cut off mid-sentence, and a missing terminal event means the stream died mid-flight.
:::

## Persisting partial output without corrupting state

Half-finished responses create subtle downstream bugs if you treat them like ordinary turns.

- **Conversational text.** If the user clicked Stop intentionally, either discard the aborted turn pair or save the partial assistant text with an explicit `status: "cancelled"` marker so the UI renders it honestly and the model knows it was cut short on the next turn.
- **Structured JSON or tool calls.** Never feed a truncated JSON delta into your application parser or persist half a tool invocation in the conversation log. Buffer structured deltas until the closing frame confirms `finish_reason: "stop"` (or `tool_calls`), and fail or retry cleanly if the stream terminates early.
- **Mid-stream errors.** Once HTTP headers return `200 OK` for an SSE stream, the server can no longer switch the status code to `500` or `429` mid-flight. Providers instead emit an `event: error` frame inside the stream. Your SSE parser must treat in-band error frames as failures and route them to your error classifier instead of saving an empty reply.
