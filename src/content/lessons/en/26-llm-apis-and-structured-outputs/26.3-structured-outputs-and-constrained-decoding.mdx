When an LLM talks to code instead of a human, one stray markdown fence (` ```json `) or missing brace crashes the downstream pipeline. Prompting the model with "Reply ONLY in valid JSON, no preamble" gets you to roughly 95% to 99% syntactic reliability, which still means dozens of broken parses per ten thousand requests. Constrained decoding replaces polite prompting with a mathematical guarantee inside the sampling loop.

## Why prompt-only JSON breaks in production

In [Sampling](/lessons/7-inference-and-efficiency/7.4-sampling/), you saw that at every decode step the model produces a vector of raw scores—**logits**—across its entire vocabulary, converts them into probabilities with softmax, and draws one token. Even when the prompt demands strict JSON, conversational training data still gives non-zero probability to tokens like `"Sure"`, backticks, trailing commas, or unescaped quotes inside string values. Over thousands of calls against the stateless API from [Stateless LLM APIs & Conversation State](/lessons/26-llm-apis-and-structured-outputs/26.1-stateless-apis-and-conversation-state/), a 1% tail probability turns into constant retry noise and parser exceptions.

## Masking logits with a finite-state machine

Constrained decoding—often exposed as "Structured Outputs" or grammar-guided generation—fixes the failure right before sampling. Before generation starts, the server compiles your **JSON Schema** (a declarative specification of allowed keys, types, enums, and nesting) into a **finite-state machine (FSM)** or pushdown automaton that tracks which characters are syntactically legal next.

Walk through a tiny 4-token vocabulary at step 0, right before the opening brace of a JSON object:

- Token `{"` has raw logit `2.0` (legal next token).
- Token `true` has raw logit `3.5` (illegal at object start).
- Token `123` has raw logit `1.0` (illegal).
- Token `}` has raw logit `-0.5` (illegal).

Without constraints, softmax turns those logits into weights proportional to $e^{2.0} \approx 7.39$, $e^{3.5} \approx 33.12$, $e^{1.0} \approx 2.72$, and $e^{-0.5} \approx 0.61$. Token `true` wins with `75.6%` probability (`33.12 / 43.83`), producing invalid JSON on step 1.

With constrained decoding, the FSM supplies the allowed token set $\mathcal{A}(s) = \{\text{\texttt{\{"}}\}$ for current state $s$ and adds a mask $m_i$ to every logit before softmax:

$$p_i = \frac{\exp(z_i + m_i)}{\sum_{j=1}^{V} \exp(z_j + m_j)}, \qquad m_i = \begin{cases} 0 & \text{if } i \in \mathcal{A}(s) \\ -\infty & \text{if } i \notin \mathcal{A}(s) \end{cases}$$

Because $\exp(-\infty) = 0$, the three illegal tokens drop to probability `0`, and `{"` gets probability `7.39 / 7.39 = 1.0`. After sampling `{"`, the FSM transitions to the "expecting key name" state and loads the next allowed mask.

Naive grammar checking at decode time would inspect every token in a 100,000-entry vocabulary on every step, stalling generation. As Willard and Louf (2023) showed in *Efficient Guided Generation*, precomputing a mapping from each FSM state to its allowed token bitmask reduces per-step overhead to an $O(1)$ table lookup during decode. You pay a one-time compilation cost the first time a provider sees a new schema (often tens to hundreds of milliseconds), and subsequent requests reuse the compiled artifact from cache.

## Syntax validity is not semantic truth

Constrained decoding eliminates `JSONDecodeError`—provided generation does not hit `max_tokens` mid-object—yet teams routinely confuse valid syntax with valid data. The grammar mask enforces *shape*, never *meaning*.

- **Cross-field invariants still break.** A schema with `start_date`, `end_date`, and `total_usd` cannot prevent `end_date` from preceding `start_date` or `total_usd` from disagreeing with the sum of line items.
- **Enums force a choice even when unsure.** If your schema restricts `category` to `["billing", "shipping", "cancel"]` with no escape hatch, an unrelated question still gets forced into one of those three labels. Always include an explicit `"other"` or `"insufficient_evidence"` option plus nullable fields where data may genuinely be absent.
- **Tight schemas can distort reasoning.** If the model cannot express uncertainty or intermediate arithmetic before emitting a boolean `approved` flag, masking forces it to commit early.

:::caveat
Keep a real application validator (such as Pydantic or Zod) after every structured LLM call. Let constrained decoding guarantee parseable JSON and types, and let your validator enforce domain math, foreign-key existence, and policy rules.
:::

## Practical schema design rules

Good schemas work *with* autoregressive left-to-right decoding instead of fighting it:

- **Order keys deliberately.** Place short `evidence` or `reasoning` fields before `label` or `action` fields. Because every emitted token conditions subsequent tokens, the model inspects its own extracted evidence before picking the final classification.
- **Avoid recursive or wildly dynamic schemas.** Keep objects flat, set `additionalProperties: false`, and cap nesting depth; deeply recursive schemas or complex regex patterns inflate FSM compile latency and hit provider subset limits.
- **Handle refusal and truncation.** Check `finish_reason` and any provider `refusal` field before parsing. A `length` truncation still produces broken JSON even under strict constrained decoding because decoding stopped before the FSM reached its terminal state.
