Access control from [lesson 30.1](/lessons/30-rag-security-privacy-and-governance/30.1-rag-access-control-and-tenant-isolation/) decides *which users* may read a chunk. Privacy engineering answers a second, independent question: *which bytes* are allowed to enter an embedding index, cross an external API boundary, or land in an observability trace in the first place. A single leaked API key in an indexed Slack thread or a patient's tax ID logged in a prompt trace turns a routine RAG feature into a reportable data breach (OWASP LLM02: Sensitive Information Disclosure).

## Where sensitive data leaks in a RAG stack

Sensitive data does not travel along one wire. Every production RAG application copies text across at least five storage or network hops:

- **Ingestion and chunking:** Raw PDFs, emails, and tickets carry Personally Identifiable Information (PII, any information that identifies a specific person such as names, emails, phone numbers, or national IDs) and credentials such as bearer tokens or private keys.
- **Embedding APIs and vector stores:** Text sent to a hosted embedding endpoint leaves your network, and the resulting vectors plus chunk text sit in the vector database indefinitely unless scrubbed.
- **Inference APIs and prompt caches:** Prompt text crosses to a model provider, where abuse-monitoring logs or shared prefix caches may retain payloads unless governed by explicit contractual bounds.
- **Observability and eval pipelines:** Tracing tools capture full prompts, retrieved chunks, and completions for debugging, often piping production PII into third-party SaaS dashboards with wide internal read access.
- **Model outputs:** The LLM synthesizes retrieved text and can accidentally surface hidden fields (such as an internal email address inside JSON metadata) to an end user who should only see an aggregate summary.

Because leaks occur at every hop, waiting until output generation to scrub text is too late.

## Layered detection: regex, checksums, entropy, and NER

No single detector catches every sensitive token with acceptable precision and recall. Production redaction gateways run a fast two-stage pipeline before indexing or calling an external model:

1. **Deterministic detectors (sub-millisecond):** Regular expressions paired with mathematical validation catch structured secrets and IDs cleanly. A 16-digit number is validated with the Luhn checksum before flagging it as a payment card; national IDs (such as Brazilian CPF check digits) verify their checksums; credentials (AWS keys, GitHub tokens, JWTs) match known prefixes plus Shannon entropy thresholds so normal English words are not misclassified.
2. **Contextual Named Entity Recognition (NER, 10–30 ms on CPU):** Lightweight token-classification models detect unstructured PII—person names, street addresses, dates of birth, medical diagnoses—that no regular expression can specify.

Work through a concrete error-budget calculation. Suppose your support pipeline processes $10{,}000$ tickets per day, each containing an average of $2$ sensitive entities ($20{,}000$ total entities daily). Compare two redaction configs:

- A **regex-only** pipeline achieves $99\%$ recall on structured IDs (half of all entities) and $0\%$ on unstructured names/addresses (the other half), yielding an overall recall of $50\%$—leaving $10{,}000$ raw PII entities unredacted every day.
- A **hybrid regex + NER** pipeline achieves $99\%$ recall on structured IDs and $94\%$ on unstructured entities, raising overall recall to $96.5\%$:

$$
\text{Missed Entities} = 20{,}000 \times (1 - 0.965) = 700\ \text{entities/day}.
$$

That remaining $3.5\%$ miss rate explains a critical engineering rule from NIST AI 600-1: automated PII redaction is a **risk-reduction control**, never a license to send regulated records to an unapproved vendor without legal and contractual safeguards.

## Masking vs. reversible pseudonymization vaults

Once a detector flags an entity, you choose between two transformations depending on whether downstream reasoning needs entity identity:

- **Irreversible masking** replaces every instance with a generic tag (`[REDACTED_SECRET]` or `[REDACTED_CARD]`). Always use irreversible redaction for API keys, passwords, private keys, and payment card numbers; an LLM never needs a real secret to answer a question.
- **Reversible pseudonymization (tokenization)** replaces recurring entities with consistent, scoped placeholders inside a single request or session (`Alice Silva` becomes `<PERSON_1>`, `alice@corp.example` becomes `<EMAIL_1>`). The mapping table lives in an encrypted, short-lived vault inside your own infrastructure, keyed by session ID and TTL (for example, 15 minutes). The LLM reasons accurately over `<PERSON_1>` and `<EMAIL_1>`, and your application gateway substitutes the real values back only when returning the response to an authorized caller.

:::note
Never reuse the same pseudonym token (`<PERSON_1>`) across different sessions or store the lookup vault in the same database as the unencrypted traces. Cross-session reuse lets an attacker correlate identities across logs, defeating pseudonymization.
:::

## Zero Data Retention, training opt-outs, and right to erasure

Contractual data boundaries close the gap that automated redactors cannot eliminate. Verify four concrete terms before sending production data to any model or embedding vendor:

- **Zero Data Retention (ZDR):** The provider commits not to store prompts or completions on disk after returning the HTTP response, disabling even standard 30-day abuse-monitoring logs. Note that ZDR often disables provider-hosted batch files, persistent thread APIs, or cross-request prompt-logging dashboards.
- **No training on customer data:** Explicitly verify in the enterprise Data Processing Agreement (DPA) that neither prompts nor completions feed model pretraining, fine-tuning, or human review queues.
- **Regional residency:** Pin inference and embedding endpoints to approved geographic regions (for example, EU-only endpoints for GDPR-governed workloads) and verify where failover traffic routes when a primary region degrades.
- **Right to erasure (GDPR Article 17):** Deleting a user's record from your primary SQL database does not erase their data if their chunks remain in the vector store, BM25 index, semantic cache, or fine-tuned adapters. Track a `subject_id` or `source_doc_id` on every chunk so a deletion request purges the vector store, lexical index, and caches atomically.

When you combine pre-ingestion secret stripping, hybrid regex + NER pseudonymization, redacted observability traces, and verified ZDR endpoints, sensitive bytes stay inside boundaries you control and can audit.
