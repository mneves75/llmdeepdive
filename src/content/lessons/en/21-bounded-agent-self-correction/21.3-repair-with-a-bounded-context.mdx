The failure is now precise: `test_ten_units_get_the_bulk_discount` expects `Decimal('114.00')` and gets `Decimal('120.00')`, at line 9 of `test_pricing.py`. A model could answer with a new version of the whole pricing module, a change to the test, or one character in one line. All three might turn the test green. Only one of them is a repair you would want to merge. This lesson defines what one repair attempt may contain, checks it before anything runs and proves the fix with the same tests that failed.

## What goes into one attempt?

Each attempt carries four things, and the loop supplies or checks each one:

- **A hypothesis**: one sentence about the cause, such as "the discount condition uses > where the rule says 10 or more units". It is required, at least 10 characters, and recorded with the attempt. A person reading an escalation later sees what each attempt believed.
- **A failing test**: the test id and relevant frame from [lesson 21.2](/lessons/21-bounded-agent-self-correction/21.2-read-a-failure/). The repair must turn that test green without turning another one red.
- **An affected-file scope**: the files a patch may replace. For this task it is `pricing.py` alone. The model sees that file's source and no other.
- **A clean starting snapshot**: the original files, exactly as the initial failing run saw them.

Bounding the context is a choice with a cost. The model cannot read a file outside the scope, so a bug whose cause lives elsewhere, say in a rates table another module loads, cannot be fixed by this loop. Every attempt fails and the loop escalates, which is the right outcome for a task scoped too narrowly. In exchange, the first prompt stays small, 355 tokens by [lesson 19.3](/lessons/19-agent-memory-and-context/19.3-token-budgets-and-compression/)'s four-characters-per-token approximation. The model also has fewer places to make an unrelated change, and the reviewer knows in advance which file can differ.

A *patch* in this exercise is the full new text of one file plus the hypothesis. The patch's `path` field must be a bare module name such as `pricing.py`, so `../pricing.py` or `/tmp/pricing.py` fail validation before any policy runs. SWE-bench (Jimenez et al., 2023) gives a model an issue and a whole codebase, and represents its edits as patch files that are applied with the Unix `patch` program before the tests run. The authors note that solving its tasks means finding the relatively small number of lines that need editing. The exercise keeps the same shape at a smaller scale.

## The patch policy

`check_patch` runs before the patched code ever executes and returns the reason for a refusal, or `None`:

```python
# file: examples/agent-engineering/src/agentlab/repair/patch.py
def check_patch(patch: Patch, project: Mapping[str, str], allowed: Collection[str], seen: Collection[str] = ()) -> str | None:
    """Why ``patch`` is refused, or None if it may run."""
    if is_test(patch.path):
        return f"tests are read-only: {patch.path}"
    if patch.path not in allowed:
        return f"outside the allowed files: {patch.path}"
    before = project.get(patch.path, "")
    if patch.content == before:
        return "changes nothing"
    if patch.sha256 in seen:
        return "repeats an earlier attempt"
    changed = changed_lines(before, patch.content)
    if changed > MAX_CHANGED_LINES:
        return f"too large: {changed} changed lines, at most {MAX_CHANGED_LINES}"
    return None
```

The order matters. The test check comes first, so a test stays read-only even if a task's allowed list includes it by mistake. Editing a test, weakening an expected value or deleting an assertion are all the same refusal: the repair changed the check it was supposed to pass. Qi et al. (2015) analysed patches earlier repair systems reported as successful and found that the overwhelming majority were equivalent to a single change that simply deletes functionality. A patch that guts a test is the same move aimed at the test instead of the code.

`changed_lines` counts removed plus added lines in a `difflib` unified diff. The real fix is 2: one line removed, one added. `MAX_CHANGED_LINES` is 10. A ten-line cap does not prove a patch minimal, but it makes a rewrite impossible to slip in and keeps every accepted patch small enough for a person to read in seconds. A patch identical to an earlier one is refused without running, because the answer would be the same.

:::warning
The policy runs on the patch's text. A patch inside the allowed file can still change behaviour far from the bug, for example by calling `sys.exit(0)` when it is imported. That is why [lesson 21.1](/lessons/21-bounded-agent-self-correction/21.1-what-counts-as-corrective-feedback/)'s runtime checks exist: no summary, a skip or fewer tests than the baseline means the run did not pass.
:::

## Why every attempt starts from the clean snapshot

If attempt 1 breaks `invoice_total` and attempt 2 is applied on top of it, attempt 2 is judged on two changes, one of them known to be bad. Its result says nothing clear about its own hypothesis. So the loop never edits the original:

```python
# file: examples/agent-engineering/src/agentlab/repair/patch.py
def apply(project: Mapping[str, str], patch: Patch) -> dict[str, str]:
    """A new snapshot; the original is never modified, so every attempt starts clean."""
    return {**project, patch.path: patch.content}
```

The runner then writes that snapshot into a new, empty temporary directory, the same discipline [lesson 17.2](/lessons/17-sandboxed-agent-execution/17.2-resource-and-filesystem-limits/) applied to sandbox working directories. An attempt cannot see files an earlier attempt wrote, and nothing it writes survives it. The model still learns from earlier attempts through their recorded hypotheses and results, which [lesson 21.4](/lessons/21-bounded-agent-self-correction/21.4-budget-the-repair-loop/) puts in its context.

## Fails before, passes after, with the same tests

The proof of a repair is a pair of runs on the same tests. Before the patch, `test_pricing` runs 3 tests: two pass and `test_ten_units_get_the_bulk_discount` fails with an assertion. After the `>=` patch, the same 3 tests run and all pass. The count matters as much as the result: `classify` takes the baseline's 3 as `minimum_tests`, so a patched run that ran 2 would not count. These are the visible tests, the ones the loop saw while repairing. [Lesson 21.5](/lessons/21-bounded-agent-self-correction/21.5-evaluate-a-correction/) asks what they cannot tell you.

## Run the exercise

The module is `src/agentlab/repair/patch.py`; the tests are in `tests/test_repair_patch.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_repair_patch -v`. Expect `Ran 10 tests` and `OK`.

`PlantedBug` runs the bug before and after the one-line fix and checks the test count is unchanged. `PatchPolicy` covers each refusal next to the accepted fix: a weakened expected value, deleted assertions with the test file wrongly allowed, a new file outside the scope, a rewrite, a no-op, a repeat and three paths with directories. `CleanSnapshot` checks that a second patch never carries the first one's change.

To see a test catch a policy hole, change `if is_test(patch.path):` in `check_patch` to `if False and is_test(patch.path):`. `test_editing_a_test_is_refused` and `test_deleting_assertions_is_refused_even_when_the_file_is_allowed` fail, and so does lesson 21.2's obedient-model test: the refusal now rests on the allowed list alone, so one wrong entry in that list would let the note's request through. Restore the line before moving on.
