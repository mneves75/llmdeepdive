The repair loop from [lesson 21.3](/lessons/21-bounded-agent-self-correction/21.3-repair-with-a-bounded-context/) could, in principle, ask the model for patches forever. Each attempt costs a model call, a test run and a little time, and a loop stuck on a bug it cannot fix keeps paying. How many attempts should it get, what does that cost on average and in the worst case, and how does the limit survive the process crashing halfway through? This lesson sets the budget, works out its arithmetic and makes the counters durable.

## What does "three attempts" mean?

The loop begins with one *initial run*: the tests on the original code, which measure the failure. It asks the model for nothing. After that come at most three *repair attempts*. Each attempt is one model call proposing one patch, the policy check and, if the patch is allowed, one test run. A patch refused by the policy still counts as an attempt, because the model call was made and paid for. The loop stops at the first attempt whose tests pass, or after the third.

Anthropic's guidance on building agents notes that a task usually ends when it is done, but that it is also common to include stopping conditions, such as a maximum number of iterations, to keep control. Three is this course's choice, not a rule from a source; the calculator below shows what it buys.

## What the arithmetic says

Suppose each repair attempt passes the tests with probability 0.4, independently of the others, and costs USD 0.12. All three fail with probability 0.6 × 0.6 × 0.6 = 0.216, so the loop escalates 21.6% of the time and succeeds 78.4% of the time.

The *expected attempts* count repair attempts only, including the successful one, and never the initial run. Attempt 1 always runs. Attempt 2 runs only if attempt 1 failed, with probability 0.6. Attempt 3 runs only if both failed, with probability 0.36. So the expected number is 1 + 0.6 + 0.36 = 1.96, and the expected cost is 1.96 × USD 0.12 = USD 0.2352. The worst case is all three attempts, USD 0.36. Budget for the worst case: an average does not tell you what one bad run costs.

The calculator starts from these numbers. Change the success chance or the number of attempts and watch how fast the extra attempts stop paying for themselves.

:::caveat
Every number above assumes independent attempts. Real ones are rarely independent. If the bug sits outside the allowed files, or the failing test itself is wrong, every attempt fails for the same reason and the true success chance is zero. Huang et al. (2023) found that models revising their own reasoning without outside feedback often fail to correct it. A model writing its third patch from the same evidence is in a similar position. Correlated failures make escalation more likely than the calculator says, which is why the loop also stops on repeated failures.
:::

## Three limits, checked before every attempt

Attempts are one limit. Tokens and wall-clock time are the other two, because one huge prompt or one hung test run can blow a budget without using many attempts. The loop checks all three before it starts an attempt:

```python
# file: examples/agent-engineering/src/agentlab/repair/budget.py
    def exhausted(self, spent: Spent) -> str | None:
        """Why no further attempt may start, or None."""
        if spent.attempts >= self.max_attempts:
            return f"budget: {spent.attempts} of {self.max_attempts} repair attempts used"
        if spent.tokens >= self.max_tokens:
            return f"budget: tokens {spent.tokens} of {self.max_tokens}"
        if spent.seconds >= self.max_seconds:
            return f"budget: wall time {spent.seconds:.0f} of {self.max_seconds:.0f} seconds"
        return None
```

The defaults are 3 attempts, 20,000 tokens and 600 seconds. Tokens are counted with the same approximation [lesson 19.3](/lessons/19-agent-memory-and-context/19.3-token-budgets-and-compression/) labels as one, about four characters per token, over every repair prompt and reply. In the exercise, three wrong patches spend 1,793 approximate tokens; with a 1,000-token budget the loop stops after two attempts, at 1,178. A limit is checked between attempts, so one attempt can overshoot it; the per-run limits of [lesson 17.2](/lessons/17-sandboxed-agent-execution/17.2-resource-and-filesystem-limits/) bound how far. Time comes from an injected clock, so the test of the wall-time limit runs instantly: with a clock that advances 100 seconds per reading and a 150-second budget, the second attempt is the last.

## Counters that survive a restart

A budget held in a variable resets when the process dies, and a loop that crashes on every model call would then retry forever. The counters therefore live in SQLite, one row per run, written with the compare-and-swap of [lesson 14.3](/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/): an update matches only if nobody committed since the writer read the row. The order of writes is the point:

```python
# file: examples/agent-engineering/src/agentlab/repair/loop.py
    while (reason := budget.exhausted(spent)) is None:
        messages = repair_messages(task, original, spent.history)
        number = spent.attempts + 1
        # Charged before the model call, so a crash from here on still counts this attempt.
        spent = store.charge(run_id, spent, attempts=1, tokens=sum(approx_tokens(m["content"]) for m in messages))
        started = clock()
        reply = model.complete(messages, tools=[PATCH_TOOL])
```

The attempt and its prompt tokens are committed before the call. If the process dies inside the call, the attempt is spent; what is lost is only that attempt's reply tokens and elapsed time, which were never measured. The exercise kills a run inside attempt 2, opens the database again as a new process would and finds `attempts` at 2. The resumed loop calls the model once more, for attempt 3, and then escalates.

The same row keeps the history: each attempt's number, hypothesis, patch hash, result and failure signature. The next prompt lists earlier hypotheses and their results, much as Reflexion (Shinn et al., 2023) stores verbal reflections on earlier trials in an episodic memory buffer for later ones. Here the history also feeds two rules: a patch identical to an earlier one is refused, and a repeated failure stops the loop.

## Stop when the same failure comes back

A failure's *signature* is the failing test, the error type and the relevant frame's file and line, which stay the same when only the values change. If two consecutive patches that ran produce the same signature, neither patch touched the cause, and a third is likely to miss it too:

```python
# file: examples/agent-engineering/src/agentlab/repair/loop.py
        if previous is not None and previous.signature == feedback.signature:
            return RepairOutcome("escalated", f"repeated failure: attempts {previous.number} and {number} failed the same way ({feedback.signature})", original, spent)
```

Changing the discount rate to 0.5 and then to 0.25 leaves ten units without a discount both times, so the loop escalates after two attempts instead of three. Escalation is the designed exit, not a crash: the outcome carries the original failure, every attempt's hypothesis and result, and the counters, which is what a person needs to start where the loop stopped.

To watch the restart test catch a real regression, move the `store.charge(... attempts=1 ...)` line below `reply = model.complete(...)`.
