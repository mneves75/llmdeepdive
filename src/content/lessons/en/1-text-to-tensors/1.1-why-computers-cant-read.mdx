A language model works on numbers, not letters. This lesson follows one word from your keyboard into Qwen3.8-27B and back out, and names what each step along the way promises. That matters because each step can change or drop information, and when something breaks in production you need to know which step did it.

## Why can the same word arrive as different bytes?

Type the word *café* into a chat box and send it to Qwen3.8-27B. A perfectly ordinary thing to do, and it hides a problem that has broken production systems.

Unicode, the standard that gives every character a number, calls each of those numbers a **code point**. There are two standard ways to write *café* in code points. One uses four, ending in a single precomposed character for the accented e. The other uses five, ending in a plain e followed by a separate combining acute accent. On screen they are indistinguishable.

Computers store code points as bytes, and **UTF-8** is the standard rule for doing so: each code point becomes one to four bytes. Serialized to UTF-8, the first spelling occupies five bytes and the second occupies six. The accented character costs two bytes in the first form, while the bare e plus the combining mark cost three in the second.

The model never sees your screen. Its public tokenizer receives a Unicode string and, for this pinned release, first applies **NFC** (Normalization Form C). NFC is a Unicode rule that rewrites spellings Unicode declares equivalent, called **canonically equivalent**, into one standard composed form. Only then does byte-level processing begin. The two spellings of *café* therefore converge to the same normalized string and the same token ids.

Other distinctions survive normalization. An ordinary space and a non-breaking space are not canonically equivalent, so they still produce different sequences. The point is not that every visual twin differs. It is that the tokenizer's declared normalization policy decides which distinctions reach the model.

## What does encoding guarantee?

Follow the whole path, naming what each stage promises and what it does not. The first boundary is **encoding**: Unicode assigns code points to a vast repertoire of text elements, and UTF-8 turns each code point into bytes. A byte value on its own means nothing until you know which encoding produced it.

Even the idea of one visible character is slippery. An emoji with a skin-tone modifier and a zero-width joiner (an invisible code point that glues neighbours into one symbol) can occupy several code points while drawing as one glyph. And the *café* example shows that even a Latin word with one accent has more than one legal spelling in bytes.

Normalization can force canonically equivalent forms into agreement, and Qwen3.8-27B's pinned tokenizer explicitly applies NFC. That is a choice with a cost: identifiers, passwords, and source code often must preserve distinctions that natural-language text is happy to lose. Whitespace carries the same hazard. An ordinary space, a non-breaking space, and a narrow no-break space look nearly identical and are entirely different bytes. Every one of these choices is made before any model is involved.

## What does the tokenizer turn text into?

The second boundary is **tokenization**. A tokenizer cuts text into **tokens**, the small units a model reads and writes (the term from [lesson 0.1](/lessons/0-orientation-and-foundations/0.1-what-is-a-language-model/)), and gives each one an integer id. Qwen3.8-27B's tokenizer takes the normalized text, turns it into UTF-8 bytes, and applies byte-level **BPE** (byte-pair encoding), a method that builds tokens by merging frequent neighbouring pieces. [Lesson 1.2](/lessons/1-text-to-tensors/1.2-tokenization-i/) examines what that vocabulary contains and [lesson 1.3](/lessons/1-text-to-tensors/1.3-bpe-step-by-step/) shows how it was built.

Qwen3.8-27B's artifacts expose 248,077 mapped ids. Those ids index tensors (multi-dimensional arrays of weights) with 248,320 rows, and the remaining 243 rows have no tokenizer mapping in the published artifacts.

The ids themselves are labels, not quantities. Token 900 is not larger, later, or more important than token 12, in the same way that a hash map key carries no meaning of its own.

Because this tokenizer works on bytes, it has one very useful consequence. Its byte-level alphabet can represent every UTF-8 byte produced from a valid normalized Unicode string, so it needs no "unknown" token for such text. That statement does not make the public text API an interface for arbitrary binary data.

## Following one word through the model and back

Run the round trip in your head. After NFC normalization, either spelling of *café* becomes the same UTF-8 byte sequence and then the same short list of ids.

1. Each id selects a row of the **embedding table**, a big lookup table with one learned vector per id. The result is a 5120-dimensional vector, as [lesson 0.4](/lessons/0-orientation-and-foundations/0.4-vectors-matrices-dot-products/) described.
2. Those vectors pass through 64 layers, each rewriting the state.
3. The final layer emits 248,320 **logits** for the next position: raw scores, one per row, that softmax turns into probabilities.
4. A token is chosen, and the decoder maps chosen ids back to bytes and then to text you can read.

For ids produced by encoding this normalized input, decoding reconstructs that normalized text. That includes every distinction normalization kept. It cannot recover a canonically equivalent spelling that NFC replaced, because that spelling never reached the model.

Generated text is a different case. Arbitrary ids sampled from the model have no corresponding encoded input, so they carry no NFC guarantee. They can even form malformed byte fragments, which the decoder then has to handle with replacement characters.

:::caveat
This lesson deliberately does not print the specific integer ids that Qwen assigns to *café*, and you should be suspicious of any course that does from memory. [Lesson 0.8](/lessons/0-orientation-and-foundations/0.8-how-to-read-ml-paper/) made the rule: architectural facts are stated only when a primary artifact declares them. The vocabulary size is in the configuration file and is safe to quote. Individual token ids are a property of the tokenizer files, which you can load and query in seconds, and which no one should paraphrase from recollection.
:::

## Where does meaning come from, then?

An embedding table maps ids to vectors, and at initialization those vectors contain no definitions. Training reshapes them, along with everything downstream, so that the representations become useful for predicting the next token.

Notice that the *same* row serves every occurrence of a token. The word *bat* in a cave and *bat* in baseball begin at one identical row. The surrounding tokens, mixed in by the layers above, are what pull the two states apart. So meaning, insofar as the word applies at all, belongs to a state that depends on context, not to a vocabulary entry.

Syntax and semantics are therefore delivered by neither Unicode nor the tokenizer. They emerge, imperfectly, from three sources: patterns in the training data, biases built into the architecture, and the training objective. A model can learn that an opening quotation mark predicts a later closing one, that a subject constrains a verb, or that certain names co-occur with certain professions. Those regularities can support useful behavior without amounting to an explicit grammar or a checked knowledge base.

:::warning
A common mistake is to treat a stable normalized round trip as proof of comprehension. It demonstrates that the tokenizer consistently transports its normalized representation. That is a property of tokenizer code, and it would hold just as perfectly if the 64 layers in between were replaced with random numbers. A faithful transport tells you nothing about the quality of what happened in transit.
:::

## Which failures does each boundary explain?

The layered view explains a catalogue of real failures:

- Corrupted bytes break decoding before the model is reached.
- Visually confusable characters can hide a substituted identifier in what looks like ordinary text.
- An unlucky tokenizer can shatter one language into many more positions than another, which [lesson 1.4](/lessons/1-text-to-tensors/1.4-sentencepiece-byte-level-token-counts/) turns into money.
- Rare spellings receive weakly trained representations.
- A fluent model can still attach the wrong real-world referent, because its objective rewarded probable continuation rather than checking facts against the world.

Computers process text with great sophistication, and every stage of that processing has a contract narrow enough to write on one line. Normalization picks one spelling among equivalent ones. UTF-8 maps normalized symbols to bytes. Tokenizers map that representation to ids. Embeddings map ids to vectors. Layers transform vectors. Decoding maps scores back to tokens. Keeping those six boundaries distinct stops the vague verb *reading* from hiding where information entered, changed, or was lost without any error.
