At 09:00 the approver opens the request from [lesson 20.1](/lessons/20-human-approval-and-durable-pauses/20.1-decide-when-approval-is-needed/), reads `Submit INV-0042 version 1 to Supplier Gamma for 10000.00 USD`, and clicks Approve. At 09:05 the assistant reads the injected supplier message from [lesson 16.2](/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) and changes the payee to Supplier Omega. It still holds an approval. What does that approval cover?

If the answer is "invoice INV-0042", the attacker has won: the approval follows the invoice through every later edit. The answer this lesson builds is narrower. An approval covers one *operation*: one exact draft, approved by one person who is not the requester, before a deadline, used once.

## What exactly does a person approve?

List what the approver saw: invoice id, version, payee, amount and currency, plus the tenant the invoice belongs to. Each of those fields is part of the decision, so each must be part of the binding. Five more facts complete it:

- an *operation id*, naming the effect the approval allows (here `run-1:submit_invoice`, built the way [lesson 14.4](/lessons/14-agent-architecture-and-state/14.4-replay-and-side-effects/) builds idempotency keys);
- the user id of the *requester*, the trusted principal on whose behalf the run asked;
- an *expiry*, a moment after which the approval is void;
- the *approver*, recorded when the decision arrives;
- whether the approval was already *used*.

The shared record `ApprovalRequest` in `agentlab/domain.py` holds the first group: the operation id, the draft, a content hash, `requested_by` and `expires_at`. Its `expires_at` is a timezone-aware datetime, so comparing it with "now" compares two instants, not two wall clocks in different zones. The approver and the used status are deliberately absent. Both arrive later and change over time, so they live in the store of [lesson 20.3](/lessons/20-human-approval-and-durable-pauses/20.3-durable-waits-and-callbacks/).

## Why a hash rather than the invoice id?

A *hash* such as SHA-256 maps any input to a 64-character digest that changes completely when one byte of the input changes; [lesson 15.3](/lessons/15-tool-contracts-and-mcp/15.3-tools-resources-prompts-and-discovery/) used one to pin tool definitions. Hashing the draft turns "is this still the document the person approved?" into a comparison of two short strings.

Why not compare invoice id and version? Because labels can stay the same while content changes. A bug, or the injected message, could edit the payee without bumping the version. The hash notices anyway. The version is still inside the hash, for the opposite case: if a corrected draft happens to return to the old amount, its version differs, so an old approval cannot cover it by coincidence.

A hash is only useful if equal drafts always produce equal bytes. JSON allows the same object in many spellings: keys in any order, spaces or none. So the exercise first writes the draft in one *canonical* form, sorted keys and no spaces, and hashes that:

```python
# file: examples/agent-engineering/src/agentlab/approval/binding.py
def content_sha256(draft: InvoiceDraft) -> str:
    """Hash of the draft as sorted, compact JSON, so equal drafts always hash equal."""
    canonical = json.dumps(draft.model_dump(mode="json"), sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

`model_dump(mode="json")` writes the `Decimal` amount as a string, `"10000.00"`, so no float rounding enters the hash. This canonical form is the project's own convention. Two systems written in different languages would need a form both implement identically, which is a contract to agree on, not something sorted keys guarantee on their own.

## Who may approve?

The approver must be a different person, in the same tenant, holding the approver role:

```python
# file: examples/agent-engineering/src/agentlab/approval/binding.py
def check_approver(request: ApprovalRequest, approver: Principal) -> Decision:
    """Someone else, in the same tenant, holding the approver role."""
    if approver.user_id == request.requested_by:
        return Decision(False, f"{approver.user_id} requested this approval and cannot grant it")
    if approver.tenant_id != request.invoice.tenant_id:
        return Decision(False, f"{approver.user_id} belongs to another tenant")
    if APPROVER_ROLE not in approver.roles:
        return Decision(False, f"{approver.user_id} does not hold {APPROVER_ROLE}")
    return Decision(True, f"{approver.user_id} may approve")
```

The first check is *separation of duties*: the person who asks cannot also grant. It runs before the role check on purpose, so a buyer who also holds `invoice_approver` still cannot approve their own invoice.

The model cannot self-approve, for two independent reasons. First, the approver is a `Principal`, a record the runtime builds from an authenticated callback ([lesson 20.4](/lessons/20-human-approval-and-durable-pauses/20.4-slack-and-teams-approval-adapters/) builds it from a Slack click). The run's own principal is the requester, so a decision made under the run's identity fails the first check. Second, there is nowhere for model output to put an approver. `ApprovalRequest` is strict and forbids unknown fields, so JSON carrying `"approved_by": "u-approver"` fails validation; one test checks exactly that. And no agent grant in [lesson 16.4](/lessons/16-agent-security-and-guardrails/16.4-enforce-least-privilege/) contains an approve tool. OWASP's guidance on excessive agency asks for the same shape: actions taken for a user run "in the context of that specific user", with a human approving high-impact ones.

## Does the approval still cover what is about to run?

Just before the effect, one function answers that:

```python
# file: examples/agent-engineering/src/agentlab/approval/binding.py
def covers(request: ApprovalRequest, draft: InvoiceDraft, now: datetime) -> Decision:
    """Does the approval still cover the draft about to be executed?"""
    if now >= request.expires_at:
        return Decision(False, f"the approval expired at {request.expires_at.isoformat()}")
    if content_sha256(draft) != request.content_sha256:
        return Decision(False, "the draft changed after it was approved")
    return Decision(True, "the approved draft, unchanged and in time")
```

Back to 09:05. The draft now names Supplier Omega, its canonical JSON differs, its hash differs, and `covers` refuses. The assistant would need a new request, and a person would read the new payee in the preview. Notice that `now` is a parameter. The function never reads the clock, so a test can ask what happens three days later without waiting three days.

:::caveat
`covers` cannot know whether the approval was already used. That is state, and a pure function has no memory. The store in lesson 20.3 records each use with a compare-and-swap, and [lesson 20.5](/lessons/20-human-approval-and-durable-pauses/20.5-deny-expire-revoke-and-resume/) shows why `covers` must run again inside the same transaction that queues the effect.
:::

## Run the exercise

The code is in `src/agentlab/approval/binding.py` and the tests in `tests/test_approval_binding.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest discover -s tests -p "test_approval_binding.py"`. Expected output ends with `Ran 11 tests` and `OK`.

The tests edit the amount, the payee and the version separately and expect each edit to void the approval. They try the requester as approver (holding the role too), a colleague without the role and an approver from another tenant. The positive controls are the exact draft before expiry and a distinct approver with the role; without them, a function that refused everything would pass. Now break the binding. Change `if content_sha256(draft) != request.content_sha256:` to `if False:` and run again. Three tests go red, among them `test_editing_the_payee_voids_the_approval`: an approval would follow the invoice to Supplier Omega. Restore the line.
