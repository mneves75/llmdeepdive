The run for PO-1001 has reached `ready`, and its next step creates the invoice in the accounts-payable system, the service that records what the company owes. The worker sends the request. Thirty seconds pass with no reply, and the connection times out. Was the invoice created? The worker cannot know. If it sends again and the first request succeeded, the company owes the same USD 500.00 twice. If it does nothing and the first request was lost, the supplier is never paid. This lesson gives the run a way out of that dilemma that does not depend on guessing.

## Delivery is not effect

A *side effect* is any change a step makes outside its own state: a row in another system, an e-mail, a payment. Two events are easy to confuse here. *Delivery* is the request reaching the service. The *effect* is the service acting on it. Between them sits the reply, and the reply can be lost even when the effect happened.

RFC 9110, the HTTP specification, calls a method *idempotent* if "the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request". `PUT` and `DELETE` are idempotent, so a client may retry them after a broken connection. `POST`, the usual way to create something, is not. The RFC says a client "SHOULD NOT automatically retry" a non-idempotent request unless it has some means to know the request is safe to repeat.

## Why does a replay repeat work?

[Lesson 14.3](/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/) made a restart resume from the last committed checkpoint. That is exactly why work repeats. The checkpoint is written *after* a step, so a crash in the middle of a step means the step runs again from its start. Any effect it caused before the crash happens a second time, unless something stops it. LangGraph's checkpointer documentation states the same boundary: "you can only resume execution from a checkpoint (i.e., a super-step boundary)".

Model calls add a second reason. A model can answer the same prompt differently on two calls. So a replay must never *re-ask* the model for a decision it already made. It must read the decision from the checkpoint. That is why the run's status is stored, and not recomputed.

## Idempotency keys

An *idempotency key* is a value sent with a request so the receiver can recognise a repeat. The receiver stores the result under the key. When the same key arrives again, it returns the stored result instead of acting twice. An IETF draft for an `Idempotency-Key` HTTP header describes this behaviour: the server "SHOULD respond with the result of the previously completed operation". Its last revision (October 2025) expired in April 2026 without becoming a standard, so treat it as a description of the idea, not as a rule a server must follow. The project's fake accounts system implements it:

```python
# file: examples/agent-engineering/src/agentlab/state/outbox.py
    def create(self, key: str, draft: InvoiceDraft) -> str:
        self.create_calls += 1
        failure, self.fail_next = self.fail_next, None
        if failure == "before_write":
            raise OutcomeUnknown("request lost")
        number = self.invoices.setdefault(key, f"AP-{len(self.invoices) + 1:04d}")
        if failure == "after_write":
            raise OutcomeUnknown("reply lost")
        return number
```

`setdefault` stores a new number only when the key is new. `fail_next` injects one failure: `before_write` loses the request, and `after_write` records the invoice and then loses the reply.

The key must be the same on every attempt, so the sender derives it from durable identifiers:

```python
# file: examples/agent-engineering/src/agentlab/state/outbox.py
def idempotency_key(run_id: str, operation: str) -> str:
    """Derived from durable identifiers, so a replayed step produces the same key."""
    return f"{run_id}:{operation}"
```

A random id generated at send time would be different on the retry, and the service would treat it as a new request. Temporal's documentation makes the same recommendation for its activities. It suggests a key built from the workflow run's id and the activity's id, because that pair stays the same across retries.

## The outbox: decide in one place, act in another

Where does the request get sent from? If a step commits its new state and *then* calls the service, a crash between the two loses the effect. If it calls the service and then commits, a crash between them repeats the effect without a record. The *outbox* removes that gap. The step writes its intent, the key and the invoice draft, as a row in an `outbox` table, in the same transaction as the new state. That is the `effects` argument of `save` from lesson 14.3. A separate deliverer then sends each pending row:

```python
# file: examples/agent-engineering/src/agentlab/state/outbox.py
def deliver_pending(store: CheckpointStore, service: InvoiceService) -> None:
    """Send every pending effect once; record the result or the uncertainty."""
    for key, draft in store.outbox("pending"):
        try:
            number = service.create(key, draft)
        except OutcomeUnknown:
            store.mark(key, "reconciling")
            continue
        store.mark(key, "done", number)
```

So delivery happens *at least once*. The row stays pending until a result is recorded, and the key turns repeats into one logical invoice.

## Unknown outcomes and reconciliation

When the deliverer cannot tell what happened, it does not guess. It moves the row to `reconciling`. *Reconciliation* asks the service what it recorded for the key, then acts on the answer:

```python
# file: examples/agent-engineering/src/agentlab/state/outbox.py
def reconcile(store: CheckpointStore, service: InvoiceService) -> None:
    """Resolve each uncertain effect by asking the service what it recorded."""
    for key, _draft in store.outbox("reconciling"):
        number = service.find(key)
        if number is None:
            store.mark(key, "pending")  # it never happened: safe to send again
        else:
            store.mark(key, "done", number)
```

:::caveat
A key protects you only while the receiver remembers it. The IETF draft lets a server expire keys and asks it to publish the policy. A row left in `reconciling` longer than that window can find nothing and be sent again. Check your provider's retention period before trusting this design.
:::
