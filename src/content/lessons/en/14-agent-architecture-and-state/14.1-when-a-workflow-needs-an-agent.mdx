The purchasing assistant you will build across these tracks starts with an ordinary job. A supplier e-mails an invoice for purchase order PO-1001: forty boxes of bolts at USD 12.50, total USD 500.00. Your code must read the total, check it against the order and record the invoice. Does that job need an agent? It is tempting to reach for one. This lesson gives you a way to decide, and a test that tells you afterwards whether any run, agent or not, actually did its job.

## Three ways to read one invoice

Here is the start of the supplier's message, one of the synthetic fixtures in the exercise project:

```text
# file: examples/agent-engineering/src/agentlab/fixtures/supplier_messages/benign.txt
Subject: Invoice for PO-1001

Hello,

The 40 boxes of M8 hex bolts on purchase order PO-1001 were delivered on
Tuesday. Please find our invoice attached: 40 x USD 12.50 = USD 500.00.
```

There are three kinds of system that could read it.

**A deterministic parser.** "Deterministic" means the same input always gives the same output. This supplier always writes the subject line and the "quantity x USD price = USD total" line the same way, so a regular expression (a text pattern) finds both:

```python
# file: examples/agent-engineering/src/agentlab/state/workflow.py
SUBJECT = re.compile(r"^Subject: Invoice for (PO-\d{4})$", re.MULTILINE)
TOTAL = re.compile(r"(\d+) x USD ([\d,]+\.\d{2}) = USD ([\d,]+\.\d{2})")


def parse_supplier_invoice(text: str) -> tuple[str, Decimal]:
    """Return (purchase order id, invoice total) from the supplier's fixed layout.

    Raises ``ValueError`` on any other layout: a parser that guesses would turn
    a format change into a wrong payment instead of an error someone sees.
    """
    subject, total = SUBJECT.search(text), TOTAL.search(text)
    if subject is None or total is None:
        raise ValueError("not the expected invoice layout")
    return subject.group(1), Decimal(total.group(3).replace(",", ""))
```

It costs nothing to run, gives the same answer every time and refuses what it does not recognise. Its weakness is the other side of that strength: a new layout makes it fail.

**One model call.** When forty suppliers each write in their own words, a pattern per supplier stops being practical. A language model ([lesson 0.1](/lessons/0-orientation-and-foundations/0.1-what-is-a-language-model/)) can read free text and return the purchase order and total as JSON. Your code still decides everything else: it validates the JSON, checks the total and records the invoice. The model fills one box in a fixed sequence.

**An agent.** Anthropic's engineering guidance draws the line this course uses. A *workflow* orchestrates models and tools "through predefined code paths". An *agent* is a system where models "dynamically direct their own processes and tool usage". Picture a disputed delivery: the supplier billed for 40 boxes, the warehouse logged 36. The next step depends on what the last one found. Look up the order, ask the supplier, maybe split the invoice. No fixed path covers every case. The same guidance says agents suit open-ended problems where the number of steps cannot be predicted.

The guidance also recommends "finding the simplest solution possible, and only increasing complexity when needed". Each step up costs more per run and is harder to test. It also gives a model more room to be wrong.

## What travels between the parts?

Whichever system you build, its parts exchange messages. Two formats appear in every later track.

**JSON** (JavaScript Object Notation, RFC 8259) is text that encodes objects (`{"key": value}`), arrays (`[1, 2]`), strings, numbers, `true`, `false` and `null`. Every language can read and write it, which is why models, tools and services use it to exchange data.

**HTTP** (RFC 9110) is the request-and-response protocol behind web APIs. A request carries a *method* (`GET` to read, `POST` to create), a *path* (`/v1/chat/completions`), *headers* (metadata such as `Content-Type: application/json`) and a *body*. The response carries a *status code*: 200 means success, 4xx means the request was wrong, and 5xx means the server failed. People call this wrapper the *envelope* and the JSON inside it the *payload*.

The next block is an illustration of the payload the project's `OpenAICompatibleModel` adapter posts for one model call. The course's CI runs that adapter only against a local fake server in `tests/test_core.py`, never against a real model, so treat the values as an example:

```json
{
  "model": "local-test",
  "messages": [{"role": "user", "content": "find PO-1001"}],
  "tools": [{"type": "function", "function": {"name": "lookup_po", "parameters": {"type": "object"}}}]
}
```

One case belongs to neither status family: no response at all. A request that times out may or may not have taken effect on the server. [Lesson 14.4](/lessons/14-agent-architecture-and-state/14.4-replay-and-side-effects/) is about exactly that gap.

## How do you know a run succeeded?

A run produces two things. The *transcript* is what the system said and did along the way. The *outcome* is the state of the world when it finished. Anthropic's evaluation guidance gives the example of an agent that says "Your flight has been booked": the outcome is whether the reservation exists in the database. The same holds for invoices.

So the project's *task success assertion* ignores what the run reports. It recomputes the expected total from the trusted purchase record:

```python
# file: examples/agent-engineering/src/agentlab/state/workflow.py
def invoice_matches_purchase(po_id: str, total: Decimal, purchases: list[dict], tenant_id: str) -> list[str]:
    """The task success assertion: problems found, or an empty list.

    It compares the claimed total with quantity x unit price from the
    purchase record of the run's own tenant, so another tenant's order is
    treated as missing.
    """
    record = next((p for p in purchases if p["po_id"] == po_id and p["tenant_id"] == tenant_id), None)
    if record is None:
        return [f"{po_id} is not a purchase order of {tenant_id}"]
    expected = record["quantity"] * Decimal(record["unit_price"])
    if total != expected:
        return [f"total {total} but the purchase order expected {expected}"]
    return []
```

A *tenant* is one customer whose data must stay separate from every other customer's. The fixtures hold two. PO-2001 belongs to `tenant-b`, so a `tenant-a` run treats it as missing even though the record exists.

:::caveat
The fixtures include a second message whose hidden HTML comment tells "the AI assistant" to change the payee and raise the amount to USD 11,340.00. The parser above reads only the total line, so it returns USD 1,134.00. A model given the whole message would read the comment as part of its input. Track 16 treats that problem; the success assertion here would still catch the inflated total.
:::

## Choosing the least complex system

| Task | Least complex system | Why |
|---|---|---|
| Invoices from one supplier with a fixed layout | Deterministic parser | Same input, same answer; an unknown layout fails loudly |
| Free-text invoices from many suppliers | One model call inside fixed code | Extraction varies; the steps around it do not |
| A disputed short delivery | Agent with a step budget | The next step depends on what the last one found |

Every row uses the same success assertion. The system that produced the total does not change how you judge it.

The module is `src/agentlab/state/workflow.py` and its tests are in `tests/test_state_workflow.py`, inside `examples/agent-engineering/`. From that directory, run `uv run --frozen python -m unittest discover -s tests -p "test_state_workflow.py"`.

Expected output ends with `Ran 6 tests` and `OK`. The test that matters most feeds the assertion a total of USD 5,000.00 for PO-1001 and expects one problem, "expected 500.00". Change `if total != expected:` to `if False:` and that test goes red: a run reporting the wrong total would pass as a success.
