Purchase order PO-1003 is for 25 packs of safety gloves. The supplier's invoice arrives without a quantity, so the assistant asks for it, the supplier replies, the invoice is checked again and this time it passes. That run went `received → checked → needs_info → checked → ready → completed`. The question for this lesson is how to write those moves down so that code can refuse a move that makes no sense and stop a loop that never settles. The word you will hear for this is "graph", and it hides three different ideas.

## Which kind of graph is a run?

A *directed graph* is a set of nodes joined by arrows. It allows any arrows, including ones that lead back to where you started.

A *DAG* (directed acyclic graph) is a directed graph "with no path that starts and ends at the same vertex", in the words of NIST's Dictionary of Algorithms and Data Structures. This course's lessons form one: each lesson lists its prerequisites, and the repository's `content:graph` check, which runs in CI, fails if those links ever form a cycle. A cycle there would mean some lesson could never be reached.

The run above is not a DAG. The path `checked → needs_info → checked` returns to its start. That is a *cycle*, and it is fine: an execution graph may loop, while the prerequisite graph must not. Keep the two apart: calling a looping workflow a "DAG" hides the one property you most need to control.

The third idea is the one the run uses. A *finite-state machine* is, in NIST's definition, a model with "a set of states, a start state, an input alphabet, and a transition function". Here the states are the run's statuses, the start state is `received`, and the transition function is a table that says which status may follow which. A DAG's nodes are usually separate pieces of work, each done once. A state machine's nodes are the conditions of one run, and a run may visit the same one many times.

## The run's transition table

The project writes the table as a dictionary from each status to the set of statuses allowed next:

```python
# file: examples/agent-engineering/src/agentlab/state/transitions.py
TERMINAL = frozenset({"completed", "failed", "cancelled"})

# No row leads to ``awaiting_approval``: track 20 keeps approval status on its own row (agentlab.approval.store).
TRANSITIONS: dict[str, frozenset[str]] = {
    "received": frozenset({"checked", "cancelled", "failed"}),
    "checked": frozenset({"needs_info", "ready", "cancelled", "failed"}),
    "needs_info": frozenset({"checked", "cancelled", "failed"}),
    "ready": frozenset({"completed", "cancelled", "failed"}),
    "completed": frozenset(),
    "failed": frozenset(),
    "cancelled": frozenset(),
}
```

Four features are visible in it. The *branch* is the `checked` row: the run goes to `needs_info` or to `ready`. The *loop* is `needs_info`, whose row leads back to `checked`. The *pause* is `needs_info` too, because the run waits there for the supplier. The *terminal states* have empty rows, so nothing ever leaves `completed`, `failed` or `cancelled`. Every live status can also move to `cancelled`, for a person who stops the run, or to `failed`, for an error.

Why a table and not a chain of `if` statements spread through the code? Because the table is data you can read in one screen. A reviewer can see every legal move at once, and a change to the rules shows up as a one-line difference in review. A test can also walk every row, which is much harder when the rules hide inside the functions that do the work. Later tracks build on the same idea. Track 23, for example, judges a run by whether its path was a permitted one, rather than by whether it matched one fixed "golden" sequence of steps.

## Why does a loop need a budget?

A loop with an exit is sound code. The risk is a loop whose exit depends on something outside your control, such as a supplier who never answers or a model that keeps proposing `needs_info`. Anthropic's guidance notes that agents commonly include "stopping conditions (such as a maximum number of iterations) to maintain control". The project's `RunState` record carries a `step` counter and a `max_steps` limit, and `advance` enforces both:

```python
# file: examples/agent-engineering/src/agentlab/state/transitions.py
def advance(state: RunState, to: str) -> RunState:
    """Return the next state, or raise ``IllegalTransition``.

    The new record is validated again, because ``model_copy`` would accept a
    status the record does not allow.
    """
    if to not in TRANSITIONS.get(state.status, frozenset()):
        raise IllegalTransition(f"{state.status} -> {to} is not in the table")
    step = state.step + 1
    if step >= state.max_steps and to not in TERMINAL:
        to = "failed"  # the budget is spent and the run has not finished
    return RunState.model_validate({**state.model_dump(), "status": to, "step": step})
```

Read the budget rule as: the move that would use the last step without finishing the run ends it in `failed` instead. With `max_steps=5` and a supplier who never answers, moves 1 to 4 go `checked`, `needs_info`, `checked`, `needs_info`. Move 5 proposes `checked`, but the run cannot finish on that move, so it fails at step 5.

## The model proposes and the table decides

In an agent, the model chooses the next status. In this project it never sets the status directly. The driver loop asks for a proposal and passes it through `advance`:

```python
# file: examples/agent-engineering/src/agentlab/state/transitions.py
def run_until_terminal(state: RunState, decide: Callable[[RunState], str]) -> RunState:
    """Ask ``decide`` for each next status until the run reaches a terminal state.

    The loop always ends: every move adds a step, and the budget turns the
    last one into ``failed``.
    """
    while state.status not in TERMINAL:
        state = advance(state, decide(state))
    return state
```

In the tests, `decide` reads the reply of a `ScriptedModel`, the project's offline model that replays fixed answers. When the script answers `completed` while the run is `checked`, `advance` raises `IllegalTransition`. The table cannot judge whether `ready` is a *wise* choice when information is missing. It only guarantees that the run moves along routes someone wrote down and reviewed.
