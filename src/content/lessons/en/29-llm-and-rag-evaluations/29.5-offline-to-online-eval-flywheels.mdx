A well-crafted offline evaluation suite—combining retrieval metrics from [lesson 29.2](/lessons/29-llm-and-rag-evaluations/29.2-retrieval-and-generation-metrics/), calibrated binary judges from [lesson 29.3](/lessons/29-llm-and-rag-evaluations/29.3-llm-as-a-judge-and-calibration/), and private domain cases from [lesson 29.4](/lessons/29-llm-and-rag-evaluations/29.4-benchmarks-leaderboards-and-contamination/)—still ages the moment real users arrive. New product policies enter the search index, seasonal queries shift wording, and model providers ship updated snapshots. Connecting offline Continuous Integration (CI, automated checks on every code change) replay from [lesson 23.5](/lessons/23-agent-evaluation-and-ci/23.5-ci-replay-and-live-trials/) with live production monitoring turns evaluation from a one-off launch checklist into a self-reinforcing *evaluation flywheel*.

## Three-tier budget: PR gate, release suite, and online sampling

Running every slow large language model (LLM) judge on every git commit (saved code change) makes developers bypass CI; running zero checks on production lets regressions linger unnoticed for weeks. Split evaluation into three tiers with explicit latency and dollar budgets—keeping Tier 1 fast on every pull request (PR, a proposed code change waiting for merge) with deterministic schema, citation-ID, Recall@5, and abstention checks, reserving Tier 2 for full retrieval metrics plus calibrated judges ($\kappa \ge 0.70$) before rollout, and running Tier 3 asynchronously (in the background, adding zero wait time for the user) on live traffic:

Check the online cost arithmetic for a service handling 20,000 queries per day where one LLM-judge evaluation costs USD 0.002. Judging 100% of live traffic costs $20{,}000 \times 0.002 = 40\ \text{USD/day}$ (USD 1,200/month), mostly spent confirming that routine happy-path queries still pass.

Instead, log deterministic telemetry (automated code measurements such as citation validity, latency, top reranker score, and abstention rate) on 100% of requests at near-zero cost, and run the calibrated judge asynchronously on a *stratified 2% sample* (a sample intentionally split across groups rather than purely random, totaling 400 traces/day): 200 uniformly random traces to track unbiased baseline quality, plus 200 risk-weighted traces drawn from user thumbs-down clicks, low reranker scores, multi-turn retries, and newly ingested documents. Daily judge spend drops 50-fold to:

$$
400 \times 0.002 = 0.80\ \text{USD/day}\ (24\ \text{USD/month}),
$$

while surfacing regressions in hours instead of weeks.

## Multi-trial reliability: pass@k versus pass^k

Language models are stochastic (their outputs vary slightly across runs) even at low temperature because servers group requests into batches and parallel floating-point arithmetic rounds slightly differently depending on batch layout. Running a 250-case release suite once can turn a flaky workflow green by luck. Anthropic's 2026 evaluation guide contrasts two multi-trial metrics over $k$ independent runs of the same case, where $p$ is the single-trial pass probability:

- **Capability (`pass@k`):** probability that *at least one* of $k$ trials succeeds:
  $$
  \text{pass@}k = 1 - (1 - p)^k.
  $$
- **Consistency (`pass^k`):** probability that *all* $k$ consecutive trials succeed:
  $$
  \text{pass}^k = p^k.
  $$

Plug in $p = 0.90$ and $k = 3$ trials:

$$
\text{pass@3} = 1 - (1 - 0.90)^3 = 1 - 0.001 = 0.999\ (99.9\%),
$$

$$
\text{pass}^3 = 0.90^3 = 0.729\ (72.9\%).
$$

Notice the gap: a 90% workflow looks almost flawless under `pass@3` (99.9%) yet fails at least once across three runs more than a quarter of the time (`pass^3 = 72.9%`). Use `pass@k` during early prototyping to check whether a model *can* solve a task at all; use `pass^k` (or tight confidence bounds on mean pass rate) in Tier-2 release gates when customers expect consistent answers on every single click.

## Closing the flywheel from live incidents to CI

Telemetry only improves quality when live findings flow back into offline tests through the four-stage loop in the second panel of the figure above. When online sampling or user feedback surfaces a new failure cluster, export the full trace (query, rewrite, chunks, prompt version, model version, and reply) and redact (remove) personal data before storage. A domain reviewer then assigns the trace to a taxonomy bucket, confirms the expected answer, and adds it to the versioned golden dataset (the curated, human-verified regression suite) alongside the fix. Every month—or whenever online alert rates jump unexpectedly—pull 50 freshly sampled traces, label them with humans, and recompute Cohen's kappa (Cohen, 1960; Zheng et al., 2023) to confirm the judge itself has not drifted. Finally, prune golden cases whose underlying policies were deleted or superseded so the offline suite stays fast and trustworthy instead of turning into a graveyard of false failures.

## Setting merge thresholds without alert fatigue

Avoid blocking every pull request on a 0.3% wiggle in a noisy LLM-judge metric, which causes alert fatigue (developers ignoring warnings because false alarms fire too often). Enforce **hard zero-regression gates** on deterministic invariants (rules that must always hold, including JSON schema validity, valid citation IDs, security and Access Control List—ACL—permission filters, and explicit safety controls) and **paired statistical gates** on stochastic quality metrics (blocking only when a change drops Recall@5, NDCG@5, or calibrated faithfulness beyond a measured margin, or fails a paired check against the baseline commit). In track 32, these exact release gates tie directly into coupled prompt-model-index versioning and canary rollbacks (testing a release on a small slice of live traffic and reverting automatically if metrics drop).

:::note
Version your evaluation dataset, judge prompts, and retrieval fixtures in the same repository (or immutable artifact store, where saved versions cannot be overwritten) as your prompts and index configs. Comparing Tuesday's score against last month's score only holds meaning when both numbers were measured on the same frozen test split.
:::
