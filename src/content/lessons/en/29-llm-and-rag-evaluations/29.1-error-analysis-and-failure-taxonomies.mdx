Most teams start evaluating a large language model (LLM) backwards. They install a dashboard with six off-the-shelf 1-to-5 scores—"helpfulness", "coherence", "conciseness", "toxicity", "relevance", "fluency"—watch every chart hover around 4.2 out of 5, and wonder why customers still report broken answers. Generic metrics measure generic qualities, not the specific ways *your* system breaks. Before computing retrieval ratios or writing an automated judge prompt, read real traces and build a failure taxonomy (an organized list of defect types) grounded in observed bugs.

## A 50-trace audit that exposes a misleading score

Take a customer-support assistant built with Retrieval-Augmented Generation (RAG, which searches company documents and passes matching passages into the prompt) using the grounding pipeline (tying claims to cited passages) from [lesson 28.5](/lessons/28-production-rag-architectures/28.5-grounding-citations-abstention-and-graph-rag/) and trace logging from [lesson 23.1](/lessons/23-agent-evaluation-and-ci/23.1-define-success-and-capture-traces/). Suppose its generic helpfulness metric averages 4.2/5, yet customer escalations stay stubbornly high.

A domain expert sits down for ninety minutes and reads 50 complete traces—saved step-by-step records holding the user question, query rewrite (the search-friendly rephrasing of the question), retrieved chunks (short text passages split from source documents) with relevance scores, assembled prompt, and final cited reply. For each trace, the expert notes the *first* upstream defect that triggered the failure. Tallying those 50 flagged traces produces a sharp Pareto distribution (a skewed pattern where a few causes produce most failures), shown in the first panel below:

Look at the arithmetic from the top two failure buckets:

$$
\frac{21 + 13}{50} = \frac{34}{50} = 68\%\ \text{of failures happen before the generator writes a single word}.
$$

No amount of prompt polishing could fix those 34 traces. Those failures happened during ingestion (loading documents with metadata such as region and active-version tags), retrieval filtering, or reranking (re-sorting candidate passages by relevance) and context assembly. The 4.2/5 helpfulness rubric never flagged them because an outdated policy written in polite prose still looks "helpful" to a generic rater.

## Open coding, axial coding, and the first-upstream rule

Qualitative research gives this audit four disciplined habits, summarized in the second panel of the figure above, that fit into one afternoon sprint:

- **Open coding:** read 50 to 100 real traces (or realistic test queries before launch) without pre-built categories. Write short, concrete notes on what went wrong—for example, `"retrieved 2024 EU PDF instead of 2026 PDF"` or `"answered pricing question even though top chunk scored 0.21"`.
- **Axial coding:** group those raw notes into 5 to 8 distinct failure categories, each owned by one pipeline stage (ingestion, query transform, retrieval, reranking and assembly, generation and grounding, or abstention, meaning refusing to answer when evidence is missing).
- **First-upstream attribution:** when a stale chunk causes both a wrong answer and a wrong citation, charge the trace to *stale retrieval*, not generation. Attributing downstream fallout to the generator sends teams chasing prompt tweaks for database bugs.
- **Stop when categories saturate:** once reading 20 new traces reveals zero new failure categories (theoretical saturation), your initial taxonomy is complete enough to turn into automated checks.

## Why binary checks outperform 1-to-5 scores

Once a failure category has a name, resist scoring it on a 1-to-5 Likert scale (a numbered rating slider). What separates a 3 from a 4 on "grounding quality"? Two experienced engineers will score the same trace differently on Tuesday and Friday, and an LLM judge (Zheng et al., 2023) inherits that ambiguity and clusters around middle scores.

Convert every recurring failure mode into a narrow *binary pass/fail check* (a yes-or-no rule) with explicit inclusion and exclusion criteria:
- `policy_version_fresh`: **Pass** if every cited chunk carries the active version tag for the user's region; **Fail** otherwise (100% deterministic code, meaning fixed rules that always produce the same output for the same input).
- `abstention_on_empty_evidence`: **Pass** if the assistant returns `abstained: true` (an explicit refusal flag) whenever no supplied chunk answers the query; **Fail** if it states an unsupported answer.
- `claim_entailed_by_citation`: **Pass** if every factual claim is directly supported by its cited chunk IDs; **Fail** if any claim goes beyond them.

Notice the split that Anthropic's 2026 eval guide emphasizes: deterministic code checks handle metadata, schemas (fixed data-field layouts), latency (wait time), and citation ID existence first. Narrow binary LLM judges evaluate only the remaining semantic (meaning-based) questions that fixed code cannot read.

## Turning the taxonomy into a prioritized eval backlog

Your taxonomy serves as both an engineering roadmap and a test specification. Sort categories by frequency multiplied by business severity: fixing the 42% stale-policy retrieval defect and writing a regression test (an automated test saved to make sure a fixed bug never returns) takes priority over a 4% tone defect. Every time you ship a fix, freeze the failing traces into your regression set so the bug cannot return unnoticed when a model, embedding version (numeric vector representation of text), or chunker (the tool that splits documents into passages) changes next quarter.

:::note
Error analysis is never a one-time ceremony. Schedule a lightweight 30-trace review after every major model upgrade, corpus ingestion change, or shift in user traffic—new capabilities always introduce new failure modes that old metrics were never written to see.
:::
