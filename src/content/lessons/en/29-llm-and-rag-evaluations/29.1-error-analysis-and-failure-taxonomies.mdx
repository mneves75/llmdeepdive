Most teams start LLM evaluation backwards. They install a dashboard with six off-the-shelf 1-to-5 metrics—"helpfulness", "coherence", "conciseness", "toxicity", "relevance", "fluency"—watch every chart hover around 4.2 out of 5, and feel surprised when real customers complain the assistant gives broken answers. Generic metrics measure generic qualities, not the specific ways *your* system breaks. Before computing retrieval ratios or writing an LLM-judge prompt, read real traces and build a failure taxonomy grounded in observed defects.

## A 50-trace audit that exposes a misleading score

Take a production RAG support assistant built with the grounding pipeline from [lesson 28.5](/lessons/28-production-rag-architectures/28.5-grounding-citations-abstention-and-graph-rag/) and trace logging from [lesson 23.1](/lessons/23-agent-evaluation-and-ci/23.1-define-success-and-capture-traces/). Suppose its generic helpfulness metric averages 4.2/5, yet customer escalations stay stubbornly high.

A domain expert sits down for ninety minutes and reads 50 complete traces—each containing the user question, query rewrite, retrieved chunks with scores, assembled prompt, and final cited reply—and notes the *first* upstream defect that caused each failure. Tallying those 50 flagged traces produces a sharp Pareto distribution:

| Failure mode (axial category) | Count (of 50) | Share | Owning pipeline stage |
|---|---|---|---|
| Retrieved superseded policy version | 21 | 42% | Ingestion metadata & retrieval filter |
| Missed exception sitting in chunk `#4` | 13 | 26% | Reranking & context assembly |
| Guessed instead of abstaining on unindexed topic | 9 | 18% | Abstention gate & prompt |
| Cited chunk ID contradicted the claim | 5 | 10% | Grounding & citation verifier |
| Overly stiff wording or formatting slip | 2 | 4% | Prompt tone & post-processing |

Look at the arithmetic:

$$
\frac{21 + 13}{50} = \frac{34}{50} = 68\%\ \text{of failures happen before the generator writes a single word}.
$$

No amount of prompt polishing could fix those 34 traces, and the 4.2/5 helpfulness rubric never flagged them because an outdated policy written in polite prose still looks "helpful" to a generic rater.

## Open coding, axial coding, and the first-upstream rule

Qualitative research gives this workflow two crisp steps that fit cleanly into an afternoon engineering sprint:

- **Open coding:** read 50 to 100 real traces (or realistic synthetic queries before launch) without preconceived categories. Write short, concrete notes on what went wrong—for example, `"retrieved 2024 EU PDF instead of 2026 PDF"` or `"answered pricing question even though top chunk scored 0.21"`.
- **Axial coding:** group those raw notes into 5 to 8 mutually distinct failure categories, each tied to one architectural stage (ingestion, query transform, retrieval, reranking/assembly, generation/grounding, or abstention).
- **First-upstream attribution:** when a stale chunk causes a wrong answer and a wrong citation, charge the trace to *stale retrieval*, not generation. Attributing downstream fallout to the generator sends teams chasing prompt tweaks for database bugs.
- **Stop when categories saturate:** once reading 20 new traces adds zero new failure categories (theoretical saturation), your initial taxonomy is complete enough to turn into automated evaluators.

## Why binary checks outperform 1-to-5 scores

Once a failure category is named, resist scoring it on a 1-to-5 Likert scale. What separates a 3 from a 4 on "grounding quality"? Two senior engineers will score the same trace differently on Tuesday and Friday, and an LLM judge (Zheng et al., 2023) inherits that ambiguity and drifts toward middle scores.

Convert every recurring failure mode into a *narrow binary pass/fail predicate* with explicit inclusion and exclusion rules:
- `policy_version_fresh`: **Pass** if every cited chunk carries the active version tag for the user's region; **Fail** otherwise (100% deterministic code).
- `abstention_on_empty_evidence`: **Pass** if the assistant returns `abstained: true` whenever no supplied chunk answers the query; **Fail** if it states an unsupported answer.
- `claim_entailed_by_citation`: **Pass** if every factual claim is directly supported by its cited chunk IDs; **Fail** if any claim extrapolates beyond them.

Notice the split that Anthropic's 2026 eval guide emphasizes: deterministic code checks handle metadata, schemas, latency, and citation ID existence first; narrow binary LLM judges evaluate only the residual semantic questions that code cannot read.

## Turning the taxonomy into a prioritized eval backlog

Your taxonomy table doubles as both an engineering roadmap and an evaluation spec. Sort categories by frequency multiplied by business severity: fixing the 42% stale-policy retrieval defect and writing a regression test for it takes priority over a 4% tone defect. Every time you ship a fix, freeze the failing traces into your regression set so the bug cannot silently return when a model, embedding version, or chunker changes next quarter.

:::note
Error analysis is never a one-time ceremony. Schedule a lightweight 30-trace review after every major model upgrade, corpus ingestion change, or shift in user traffic—new capabilities always introduce new failure modes that old metrics were never written to see.
:::
