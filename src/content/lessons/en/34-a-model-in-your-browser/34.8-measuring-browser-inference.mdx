Anyone can publish a headline number like "133.7 tokens per second in the browser!" and leave out the three facts that make the number honest: which chip ran it, whether the GPU shaders were already warm, and whether the measurement came from a real browser or a mocked unit test. Because browser inference varies by a factor of nearly fifty across devices, threads, and warm states, sloppy measurement turns engineering into wishful thinking.

This final lesson in Track 34 inspects how `examples/qwen-local-lab/` calculates latency and throughput in code, how `VERIFICATION.md` separates four distinct classes of evidence, what real Chromium runs measured on two very different machines, and which parts of the matrix remain unverified.

## Separating time to first token from decode throughput

A single "average tokens per second" figure blurs two completely different phases of inference:

- **Time to first token (TTFT):** how long generation waits inside the worker from receiving the request ($t_0$) until the very first token appears ($t_1$). TTFT covers message normalization, tokenization, prompt prefill, and generating token 1:

$$
\text{TTFT} = t_1 - t_0
$$

- **Decode throughput (tok/s):** how quickly subsequent tokens stream after token 1 has arrived. Because token 1 marks the start of the decode clock ($t_1$), the elapsed window $t_N - t_1$ spans exactly $N - 1$ inter-token intervals:

$$
\text{decode tok/s} = \frac{(N - 1) \times 1{,}000}{t_N - t_1}
$$

Plug in concrete numbers. Suppose a CPU turn starts at $t_0 = 1{,}000\ \text{ms}$, emits token 1 at $t_1 = 1{,}650\ \text{ms}$, and emits token 6 at $t_6 = 1{,}775\ \text{ms}$. Then:

$$
\text{TTFT} = 1{,}650 - 1{,}000 = 650\ \text{ms}
$$

$$
\text{decode tok/s} = \frac{(6 - 1) \times 1{,}000}{1{,}775 - 1{,}650} = \frac{5{,}000}{125} = 40.0\ \text{tok/s}
$$

Dividing all 6 tokens by 125 ms would wrongly inflate the rate to 48.0 tok/s, while dividing 6 tokens by total elapsed time (775 ms) would hide decode speed behind prefill latency and report 7.7 tok/s.

The `observedMetrics` function in `src/inference-worker.js` implements that exact split using `performance.now()` on CPU, while accepting WebLLM's own `usage.extra.decode_tokens_per_s` when running on GPU (`op.decodeTps ?? ...`).

```js
// file: examples/qwen-local-lab/src/inference-worker.js
function observedMetrics(op) {
  const now = performance.now();
  const duration = op.firstTokenAt === null ? 0 : now - op.firstTokenAt;
  return {
    tokens: op.tokens,
    ttftMs: op.firstTokenAt === null ? null : op.firstTokenAt - op.startedAt,
    totalMs: now - op.startedAt,
    decodeTps: op.decodeTps ?? (op.tokens > 1 && duration > 0 ? (op.tokens - 1) * 1000 / duration : null),
    promptTokens: op.promptTokens,
  };
}
```

Two timing details keep those formulas honest. First, `op.startedAt` begins inside the worker once generation starts, so worker-reported TTFT excludes main-thread `postMessage` serialization and dispatch overhead. Second, on CPU the final `decodeTps` uses `performance.now()` at the moment `observedMetrics()` is called (which can include post-last-token work after generation resolves, whereas GPU mode prefers WebLLM's `usage.extra.decode_tokens_per_s`).

## Four grades of evidence—and why mixing them misleads

Passing unit tests feels reassuring, yet a mocked worker test that swaps `hash-wasm` for Node's `crypto` module never proves that Chromium can allocate 639.45 MB in Cache API or compile Metal-3 shaders. `VERIFICATION.md` therefore sorts every claim into one of four evidence classes:

- **Source-reviewed:** checked by reading code and vendored runtime APIs (for example, confirming `app.js` renders with `textContent` and the wllama patch touches only URL resolution).
- **Fixture-tested:** proven by automated tests with small stand-in models or synthetic tarballs (`node --test tests/*.test.cjs` and `python3 -m unittest`), ideal for negative paths such as refusing a tampered SHA-256 digest or a patch that matches twice.
- **Environment-tested:** executed end to end with real Qwen3-0.6B weights in a named browser on named hardware, recording exact dates, versions, headers, and console/network counts.
- **Unverified:** implemented in code but not exercised on that browser, device, or condition.

## Apple M5 Pro vs one-thread cloud Chromium

On **26 November 2026**, the same single-file `dist/index.html` running **Qwen3-0.6B** at 2,048-token context was measured across two contrasting environments documented in `VERIFICATION.md`:

- **Apple M5 Pro (64 GiB unified memory, macOS 27.3, Chromium `156.0.8078.4`, COOP/COEP enabled, 4 WASM threads):** CPU cold load (639.45 MB download + streaming SHA-256 + Cache API save + init) took **40.93 s**; warm reload from Cache API with full 639.45 MB SHA-256 re-verification took **1.89 s** with zero HTTP requests. Decode ran at **43.7 tok/s** on turn 1 (TTFT **0.65 s**), **44.2 tok/s** on turn 2 (TTFT **0.44 s** via prefix-cache reuse), and **52.1 tok/s** on a post-reload arithmetic turn (`17 + 25 -> 17 + 25 = 42`).
- **Cloud Chromium (no WebGPU adapter, no cross-origin isolation, 1 WASM thread):** the same Q8_0 CPU file loaded and ran, but cache write returned `QuotaExceededError` (disclosed cleanly in the UI). Decode dropped to **2.8 tok/s** as the two-turn rate on `ORBIT-731` (TTFT **10.91 s** on turn 1, **6.92 s** on turn 2) and **3.4 tok/s** on the Portuguese arithmetic turn (`17 + 25`).

<Figure id="browser-decode-rates" />

That **>15×** gap—from 44.2 tok/s on Apple M5 Pro (4 WASM threads, COOP/COEP enabled) down to 2.8 tok/s on cloud Chromium (1 WASM thread, no COOP/COEP)—confounds both hardware and thread count. Because these are short, single-device runs on two different machines, they do **not** isolate COOP/COEP thread scaling on their own.

## Why cold WebGPU shaders look ten times slower than warm ones

On the same Apple M5 Pro Chromium session, switching to **WebGPU (`Metal-3`, `shader-f16`)** loaded the pinned 6.56 MB `model_lib` WASM (verified by SHA-256 and passed via `blob:` URL) plus the Q4 MLC shards in **26.87 s** cold and **1.22 s** warm with zero external requests.

The two consecutive generation turns revealed a sharp split:

- **Turn 1 (cold shaders):** **14.0 tok/s** decode and **1.82 s** TTFT—slower than 4-thread CPU on both metrics.
- **Turn 2 (warm shaders):** **133.7 tok/s** decode and **0.18 s** TTFT—a $133.7 / 14.0 \approx 9.6\times$ jump in decode rate and a $10.1\times$ drop in TTFT.

A major driver of that gap is first-turn WebGPU Shading Language (WGSL) shader compilation and pipeline warm-up on Metal-3 before later turns reuse compiled pipelines—yet two short turns on one device do **not** isolate shader-compilation overhead on their own, nor do they establish steady-state GPU throughput over long generations. Reporting only turn 1 can severely understate warm turns, while reporting only turn 2 hides the first-turn stall a visitor feels immediately after clicking Load; honest reporting publishes both alongside what those short runs leave unproven.

## Why native llm.asm numbers do not transfer—and what remains unverified

`qwen-local-lab` was inspired by the local-chat experience of `llm.asm`, a 24,252-byte bare-metal x86 operating system kernel paired with 613.66 MiB `.asmbin` weights. It does **not** compile, boot, or emulate that kernel. `llm.asm` runs directly on x86 hardware with AVX2, FMA, and F16C instructions and physical memory mapping, whereas `qwen-local-lab` runs `llama.cpp` inside WebAssembly on CPU and `MLC/WebLLM` on WebGPU with different quantizations and runtime layers. Native assembly speed or bit-exact parity claims never transfer across that boundary.

Equally important is stating what `VERIFICATION.md` leaves open:

- **Other browsers and mobile devices:** Safari, Firefox, iOS/Android memory ceilings, and direct `file://` reopening were not tested end to end.
- **Offline local GGUF import:** implemented with GGUF magic and Qwen3-0.6B architecture checks (rather than the official SHA-256, so other compatible quantizations work), but not exercised end to end in this browser session.
- **WebLLM weight hashes and packet capture:** WebLLM's GPU weights, tokenizer, and config are pinned to a Hugging Face commit rather than re-hashed byte-by-byte by the wrapper worker, and no OS packet capture or airplane-mode test was run.

Running a model in one browser tab is no longer a trick or a rumor—you now have the full architecture, from GGUF bytes and streaming hashes through Web Workers, single-file packaging, and reproducible measurements, plus the discipline to claim only what your evidence actually proves.
