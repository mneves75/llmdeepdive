When a browser tab receives a 639.45 MB binary file—either downloaded from a remote host or picked from a user's laptop—passing blind bytes straight to a WebAssembly runtime is a recipe for wasted memory and cryptic crashes. A network proxy might return an HTML error page instead of weights, a download might stop halfway, or a user might accidentally select a different model family. Because the **GGUF** format ([lesson 8.7](/lessons/8-building-and-serving-stacks/8.7-llama-cpp-and-gguf/)) packs a fixed signature, structured metadata, and quantized weights into one file, the browser worker can check what it holds before spending compute.

## How a GGUF binary file is laid out

A **binary file** is a flat sequence of raw bytes (numbers from 0 to 255) rather than human-readable text. Per the GGUF specification, Qwen Local Lab's official CPU file, `Qwen3-0.6B-Q8_0.gguf` (**639,446,688 bytes**, or 639.45 MB), packs five consecutive sections: a **header** (beginning with the four ASCII **magic bytes** `71, 71, 85, 70` spelling `"GGUF"`, format version, and counts), **metadata key-value pairs** (architecture, hyperparameters, and the tokenizer table so `wllama` needs no separate JSON files), a **tensor info directory** (each tensor's name, shape, quantization type, and offset), **alignment padding**, and finally the **quantized tensor data** itself.

The stack below collapses that layout into the three coarse regions the browser worker acts on. Nearly all 639.45 MB are compressed neural network weights: as covered in [lesson 7.9](/lessons/7-inference-and-efficiency/7.9-quantization-i-int8-int4-the-basics/) and [lesson 7.10](/lessons/7-inference-and-efficiency/7.10-quantization-ii-gptq-awq-gguf-qat/), 8-bit `Q8_0` **quantization** shrinks each weight into smaller integers plus block scale factors, landing just over 1 byte per parameter across ~0.6 billion weights once scales and embedding tables are included.

## Two checks: four bytes before load, identity after load

Before allocating WebAssembly memory, the worker runs `validateGguf()`. It verifies that the input is a browser **Blob** (a handle to raw binary data that may live on disk or in memory), checks that it has at least 16 bytes and matches `expectedSize` when one is supplied, and reads only bytes 0 through 3 via `blob.slice(0, 4)` to confirm `"GGUF"`. Reading four bytes costs virtually zero memory even on a 639 MB file.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
async function validateGguf(blob, expectedSize = null) {
  if (!(blob instanceof Blob) || blob.size < 16 ||
      (expectedSize !== null && blob.size !== expectedSize)) {
    throw new AppError("The model file is incomplete or has an unexpected size. Download the GGUF again.", "INVALID_MODEL");
  }
  const magic = new Uint8Array(await blob.slice(0, 4).arrayBuffer());
  if (magic[0] !== 71 || magic[1] !== 71 || magic[2] !== 85 || magic[3] !== 70) {
    throw new AppError("The selected file is not a GGUF model. Select a Qwen3-0.6B .gguf file.", "INVALID_MODEL");
  }
}
```

Passing the magic-byte check proves only that the file is *some* GGUF model—not that it is Qwen3-0.6B. A user could pick a Llama model or a 4-billion-parameter Qwen checkpoint that expects a different chat template or would exhaust browser memory. After `runtime.loadModel()` returns, `validateCpuIdentity()` reads the parsed metadata from `wllama`, checks three fields, and throws `WRONG_MODEL` if any one differs.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
function validateCpuIdentity(engine) {
  const metadata = engine.getModelMetadata();
  if (metadata.meta?.["general.architecture"] !== "qwen3" ||
      Number(metadata.hparams?.nLayer) !== 28 ||
      Number(metadata.hparams?.nEmbd) !== 1024) {
    throw new AppError("This page supports Qwen3-0.6B GGUF models. The selected model has a different architecture or size.", "WRONG_MODEL");
  }
}
```

Notice the deliberate difference between an official download and a user-imported local file. When the worker downloads `Qwen3-0.6B-Q8_0.gguf` from Hugging Face (or reads it back from Cache API), it passes `expectedSize = 639446688` and also verifies the full-file SHA-256 cryptographic digest ([lesson 34.4](/lessons/34-a-model-in-your-browser/34.4-streaming-and-verifying-weights/)). When a user clicks **Use a local GGUF file**, `loadCpu()` calls `validateGguf(message.file)` with `expectedSize = null` and skips the official SHA-256 digest on purpose. That way a visitor can import another compatible Qwen3-0.6B quantization offline—such as a smaller 4-bit GGUF—while still getting the UI size/extension filter (`1,024` bytes to `1,500 × 1,024 × 1,024` bytes—**1 KiB to 1,500 MiB**—and `.gguf`), the 4-byte `"GGUF"` magic check, and the post-load `validateCpuIdentity()` check. The honest boundary is that a local import is checked for format and model identity, never for the official Q8_0 SHA-256 hash.

## Why you cannot base64-embed 639 MB in HTML

In [lesson 34.1](/lessons/34-a-model-in-your-browser/34.1-what-runs-where/), we saw that Qwen Local Lab embeds 11.66 MB of WebAssembly and JavaScript runtimes inside `dist/index.html` using **base64** encoding. Why not go one step further and embed `Qwen3-0.6B-Q8_0.gguf` too so the HTML file needs zero separate downloads?

Base64 encodes every 3 raw bytes (24 bits) as 4 printable ASCII characters (6 bits each), inflating every binary payload by an exact ratio of $4/3$ (+33.3%):

$$
S_{\text{base64}} = 639{,}446{,}688 \times \frac{4}{3} = 852{,}595{,}584\ \text{bytes} \approx 852.60\ \text{MB}
$$

Adding the 15.66 MB of embedded runtimes and interface code would produce a single HTML document of roughly **868 MB**. That breaks browsers in three ways at once:

- **HTML parsing stalls**: the browser must read and tokenize the entire text document before scripts can execute.
- **Peak memory spikes**: decoding an 852.60 MB base64 string with `atob()` forces JavaScript to hold the text string, the decoded binary copy, and the resulting `Blob` in memory at the same time—over 1.5 GB before the model allocates a single tensor or KV cache.
- **No selective backend download**: every GPU visitor would still transfer 852.60 MB of CPU weights they never use.

Keeping the weights in a standalone binary GGUF file respects how browsers actually move large data: as raw streams outside the HTML parser.
