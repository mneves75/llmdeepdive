Downloading a 639.45 MB model into a browser tab sits near the memory ceiling of everyday laptops and phones. If you skip integrity verification, a truncated proxy response or a corrupted browser cache can feed broken weights into WebAssembly. Yet checking a 639 MB file the obvious way—using the browser's built-in **WebCrypto** `crypto.subtle.digest()` function—can crash the tab with an out-of-memory error before the model ever starts.

## Why one-shot WebCrypto `digest()` is risky at 639 MB

A **cryptographic hash** such as **SHA-256** computes a fixed 256-bit fingerprint of a file: flip even one bit anywhere inside 639,446,688 bytes, and the 64-character hexadecimal digest changes completely. Browsers ship SHA-256 natively in `crypto.subtle.digest()`, so why does Qwen Local Lab embed `hash-wasm` 4.13.0 (216,120 raw bytes) instead?

The reason is API shape. `crypto.subtle.digest('SHA-256', buffer)` is a **one-shot** function: it requires holding the entire 639.45 MB input in one contiguous **ArrayBuffer** (a single flat block of RAM). Calling `await blob.arrayBuffer()` on a 639.45 MB download materializes that entire 639.45 MB contiguous buffer in memory alongside the download `Blob`—before `wllama` even allocates its WebAssembly heap and context cache.

**Streaming** solves this by processing small chunks of bytes as they arrive from the network rather than waiting for the entire file to land in RAM. Qwen Local Lab pipes `response.body` through a **TransformStream** (a browser pipeline stage that inspects each chunk and passes it along unchanged) backed by `hash-wasm`'s incremental `createSHA256()`.

Before reading the code below, notice the four safeguards running inside `hashingStream()` and `assertModelDigest()`. Every chunk checks whether the user clicked Cancel (`assertActive`), enforces a hard byte ceiling so a misbehaving server cannot stream past `CPU_MODEL_SIZE` (639,446,688 bytes), updates the incremental SHA-256 state in tiny constant memory, and throttles progress events to roughly once every 120 ms before forwarding the chunk to `new Response(body).blob()` so the browser collects the `Blob` outside the JavaScript heap.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
// Hash the model chunk by chunk as it streams, so verification never holds a second model-sized buffer.
function hashingStream(op, hasher, onProgress) {
  let loaded = 0;
  let lastUpdate = 0;
  return new TransformStream({
    transform(chunk, controller) {
      assertActive(op);
      loaded += chunk.byteLength;
      if (loaded > CPU_MODEL_SIZE) {
        throw new AppError("The model download has an unexpected size. Please retry.", "INVALID_MODEL");
      }
      hasher.update(chunk);
      const now = performance.now();
      if (now - lastUpdate > 120 || loaded === CPU_MODEL_SIZE) {
        lastUpdate = now;
        onProgress(loaded);
      }
      controller.enqueue(chunk);
    },
  });
}

function assertModelDigest(hasher) {
  if (hasher.digest("hex") !== CPU_MODEL_SHA256) {
    throw new AppError("The model file does not match the official SHA-256 checksum, so it was not used. Download it again.", "INVALID_MODEL");
  }
}
```

The network fetch itself pins the exact Hugging Face commit URL (`23749fef...`) and sets `credentials: "omit"`, `cache: "no-store"`, and `referrerPolicy: "no-referrer"` so cookies, stale HTTP caches, and referrer headers never interfere with the download. Only after `validateGguf()` confirms 639,446,688 bytes and `"GGUF"` magic bytes **and** `assertModelDigest()` confirms `9465e63a...` does `obtainCpuModel()` call `cache.put()`. A corrupted download is refused and never written to the browser's Cache API.

## Re-hashing cached weights before every reuse

Even after a verified file reaches Cache API, disk storage and browser caches can suffer corruption or partial eviction. Rather than trusting a cached entry blindly, `obtainCpuModel()` streams every cache hit back through the exact same `hashingStream()` into a discard `WritableStream`. If size, magic bytes, or SHA-256 fail, the worker deletes the damaged entry (`cache.delete(CPU_MODEL_URL)`) and falls through to a clean network download—while preserving user cancellation via `assertActive(op)`.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
    if (globalThis.caches) {
      cache = await caches.open(MODEL_CACHE_NAME);
      const saved = await cache.match(CPU_MODEL_URL);
      if (saved) {
        progress(op, 0.15, "Reading Qwen3 from this browser's model cache…");
        const blob = await saved.blob();
        const hasher = await sha256Hasher(assets);
        assertActive(op);
        try {
          await validateGguf(blob, CPU_MODEL_SIZE);
          await blob.stream().pipeThrough(hashingStream(op, hasher, loaded => progress(op, 0.15 + 0.6 * loaded / CPU_MODEL_SIZE,
            `Verifying the cached model's SHA-256 · ${(loaded / 1000000).toFixed(1)} / 639.4 MB`))).pipeTo(new WritableStream());
          assertModelDigest(hasher);
          modelCacheStatus = 'hit';
          modelCacheWarning = '';
          progress(op, 0.8, "Cached model verified. Preparing the CPU runtime…");
          return blob;
        } catch {
          assertActive(op);
          await cache.delete(CPU_MODEL_URL);
        }
      }
```

Re-hashing 639.45 MB sounds expensive, yet WebAssembly SHA-256 runs close to local storage speed. In the Apple M5 Pro verification run (`VERIFICATION.md`, 2026-11-26), a cold CPU load (network download, streaming SHA-256, Cache API write, and 4-thread initialization) took **40.93 s**, whereas a warm reload (Cache API read, full 639.45 MB SHA-256 re-verification, and 4-thread initialization with zero HTTP requests) took **1.89 s**.

## Budgeting first-load download time

Because a cold load must move hundreds of megabytes across the visitor's internet link, network bandwidth dominates the very first wait. Convert file size $S$ in bytes to bits ($S \times 8$) and divide by effective download speed $B$ in bits per second to get the idealized transfer time:

$$
t = \frac{S \times 8}{B}
$$

On a 50 Mbps connection ($B = 50 \times 10^6\ \text{bit/s}$), compare the 639.45 MB CPU GGUF against the ~346.79 MB GPU MLC bundle (~335.37 MB weights plus ~11.42 MB tokenizer, configuration, and compiled library):

$$
t_{\text{CPU}} = \frac{639{,}446{,}688 \times 8}{50 \times 10^6} \approx 102.3\ \text{s}
$$

$$
t_{\text{GPU}} = \frac{346{,}790{,}000 \times 8}{50 \times 10^6} \approx 55.5\ \text{s}
$$

At 100 Mbps those idealized times halve to roughly 51.2 s (CPU) and 27.7 s (GPU); at 10 Mbps the CPU file alone takes 511.6 s (over 8.5 minutes). Real loads add protocol overhead, disk caching, and engine initialization on top—which is why Qwen Local Lab never starts a model download automatically on page open and always requires an explicit click on **Load model**.

## The honest integrity boundary

Precise engineering documents what a system verifies **and** where its checks stop. Across the three ways weights enter Qwen Local Lab, the verification boundary differs by path:

- **Official CPU Q8_0 GGUF (639.45 MB)**: verified by exact byte count (639,446,688 B), `"GGUF"` magic bytes, full-file SHA-256 (`9465e63a...`) on both download and every Cache API hit, plus post-load Qwen3-0.6B architecture, layer, and hidden-size checks.
- **GPU WebLLM path (~346.79 MB total)**: the 6,561,594-byte compiled `model_lib` WASM is pinned to commit `5b7251f3...`, SHA-256 verified (`b277797f...`) on download and cache hit, and handed to WebLLM via a `blob:` URL. The GPU weight shards (~335.37 MB), tokenizer, and config are pinned to Hugging Face revision `8c14ce481d4c692769976ad52afea453a102df19` over HTTPS and cached by WebLLM's own loader; our wrapper worker does **not** re-hash those shards.
- **Local GGUF import**: user-selected files skip the official Q8_0 SHA-256 and exact byte count so compatible alternate quantizations work offline; they receive only the UI filter, `"GGUF"` magic bytes, and post-load Qwen3-0.6B identity checks.

Naming those boundaries plainly lets reviewers and users know exactly what each route guarantees—and what it relies on HTTPS, commit pinning, or local disk trust to cover.
