Traditional web **SaaS** (Software as a Service — subscription software accessed online) enjoys 80–90% **gross margins** (the share of revenue left after direct delivery costs) because serving one extra request has near-zero **marginal cost**. AI systems break that assumption: every user turn streams billions of weights across Graphics Processing Unit (GPU) memory, runs **embeddings** (numeric meaning vectors) and **rerankers** (models that reorder search hits), and triggers multi-step retries. In [lesson 9.10](/lessons/9-hardware-and-infrastructure/9.10-cost-per-token/), we derived the raw cost per token of a single model call. Here we assemble the full **unit economics** of a production AI feature—what one completed user task actually costs across the entire stack—and stress-test what breaks when traffic scales $10\times$ or $100\times$.

## Computing true cost per completed task

Token list prices understate real spend because one user action rarely equals one bare LLM call. Write out the full cost of a single user turn $C_{\text{turn}}$ by summing every variable component and multiplying by the **amplification factor** $\alpha$ (average LLM calls per user turn, including agent loops, rerankers, guardrail judges, and retries):

$$
C_{\text{turn}} = (1 - h) \cdot \left[ c_{\text{ret}} + \alpha \cdot \left( \frac{N_{\text{in,miss}} p_{\text{in}} + N_{\text{in,hit}} p_{\text{cache}} + N_{\text{out}} p_{\text{out}}}{10^6} \right) \right],
$$

where $h$ is the response cache hit rate from [lesson 31.2](/lessons/31-ai-system-design-and-caching/31.2-multi-layer-caching-and-semantic-risk/), $c_{\text{ret}}$ is embedding + vector search + rerank cost per uncached query, $N_{\text{in,miss}}$ and $N_{\text{in,hit}}$ are uncached and prefix-cached input tokens, $N_{\text{out}}$ is output tokens, and $p_{\text{in}}$, $p_{\text{cache}}$, $p_{\text{out}}$ are per-million token prices.

Plug in concrete numbers for a realistic customer-facing RAG copilot before optimization ($h = 0$, no prefix caching, $\alpha = 1.3$ due to query rewriting + retries):

- $N_{\text{in,miss}} = 4{,}000$ tokens at $p_{\text{in}} = \text{USD } 3.00 / 1\text{M} \rightarrow \text{USD } 0.0120$.
- $N_{\text{out}} = 500$ tokens at $p_{\text{out}} = \text{USD } 15.00 / 1\text{M} \rightarrow \text{USD } 0.0075$.
- Retrieval + rerank $c_{\text{ret}} = \text{USD } 0.0005$.
- Total per turn: $0.0005 + 1.3 \times (0.0120 + 0.0075) = \text{USD } 0.02585$ (USD 25.85 per 1,000 turns).

Now apply three levers from earlier lessons: exact/semantic caching ($h = 0.25$), stable-prefix caching on 3,000 static tokens ($p_{\text{cache}} = \text{USD } 0.30 / 1\text{M}$), and routing 75% of uncached traffic to a small model costing $1/10$th as much ([lesson 31.3](/lessons/31-ai-system-design-and-caching/31.3-model-routing-cascades-and-gateways/)). Blended cost per turn drops from USD 0.02585 to roughly **USD 0.0046**—an $82\%$ reduction without degrading hard-query quality.

## Quadratic context growth and power-user skew

Two silent multipliers blow up AI budgets after launch even when single-turn spreadsheets look healthy:

- **Quadratic multi-turn history:** In a chat interface that appends every user message, assistant reply, and retrieved chunk without compaction, if each turn adds $d = 1{,}000$ tokens, turn $t$ sends $t \cdot d$ input tokens. Across a $T = 20$-turn session, cumulative input tokens equal:

$$
\text{Total Input Tokens} = d \cdot \frac{T(T + 1)}{2} = 1{,}000 \times \frac{20 \times 21}{2} = 210{,}000\ \text{tokens}.
$$

<Figure id="31-4-quadratic-chat-tokens" />

As the curve above shows, that $10.5\times$ jump happens purely from re-sending earlier turns. Fix it by dropping raw retrieved chunks from historical turns (keeping only the grounded answer and source IDs), summarizing old turns past a **sliding window** (retaining only the newest few turns verbatim), and keeping the static prefix cache-aligned.

- **Power-user distribution skew:** Suppose you sell a flat USD 20/month seat. Median users run 250 turns/month (at USD 0.02/turn = USD 5.00 **COGS** — Cost of Goods Sold, the direct variable cost to deliver the service — giving 75% gross margin). The top 5% power users run 4,000 turns/month (USD 80.00 COGS against USD 20.00 revenue, losing USD 60.00 per user every month). Always compute gross margin by **usage decile** (dividing users into ten equal 10% bands from lightest to heaviest), never just on the mean user. When variance is extreme, align pricing with cost drivers—tiered monthly credits, soft throttling into smaller models after a quota, or per-task pricing for heavy agent workflows.

## Running a 100x traffic stress test before launch

Never assume a system that runs smoothly at 10,000 requests/day will survive 1,000,000 requests/day ($100\times$). Walk every subsystem through a quantitative **100x stress test** using peak traffic, not daily averages (enterprise workloads often concentrate 50% of daily traffic inside 3 peak hours, creating a $4\times$ peak-to-average ratio):

- **Peak token throughput (TPM, tokens per minute):** At 1,000,000 requests/day ($\approx 11.6$ req/s average, $46$ req/s peak) with 4,500 total tokens per uncached request (65% miss rate $\rightarrow 30$ uncached req/s), peak throughput reaches $30 \times 60 \times 4{,}500 = 8.1\text{ million TPM}$. A single standard API tier capped at 2 million TPM will reject 75% of peak traffic with **HTTP 429** (too-many-requests rate-limit) errors.
- **Retry storms:** If clients retry 429s aggressively without **exponential backoff** (waiting progressively longer, such as 1 s, 2 s, 4 s, between tries), **jitter** (adding a small random delay so thousands of clients do not retry at the same instant), and a global retry budget (at most 10% extra traffic), a transient dip triples load and locks the service into permanent overload.
- **Vector index & reranker saturation:** At 46 peak queries/second, a **cross-encoder** reranker running on a general-purpose Central Processing Unit (**CPU**) taking 50 ms per query across 4 cores maxes out at 80 queries/second—leaving almost no headroom for **index compaction** (background index maintenance) or a 2x marketing spike.
- **Monthly spend jump:** At USD 4.50 per 1,000 uncached calls (from [lesson 31.1](/lessons/31-ai-system-design-and-caching/31.1-end-to-end-latency-budgets/)), scaling $100\times$ from 100k to 10M monthly requests takes cached pay-as-you-go (PAYG) spend from USD 292/month to USD 29,250/month—deep into territory where provisioned throughput, multi-region pools, or self-hosted serving (Kwon et al., 2023) must be evaluated.

:::caveat
Do not wait for a viral launch day to discover your provider's default TPM quota or your reranker's CPU saturation point. Run a synthetic load test at $3\times$ expected peak concurrency in **staging** (a pre-production copy of your live environment) with mock or shadow model endpoints, and verify that rate limits degrade gracefully (routing overflow to a secondary region or fast fallback model) rather than cascading into **HTTP 500** server errors.
:::

Healthy AI unit economics comes from treating tokens, retries, and peak TPM as first-class architectural constraints alongside latency and accuracy—measuring cost per completed task every week in production just like error rate.
