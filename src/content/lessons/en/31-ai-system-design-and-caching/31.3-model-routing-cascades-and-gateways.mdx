Sending every user query—from "summarize this three-line receipt" to "reconcile a multi-jurisdiction tax clause"—to your most expensive **frontier model** (a large, top-tier model with the highest capability and price) wastes 60% to 85% of your **inference budget** (the money spent running models to answer requests) and inflates latency across routine traffic. In [lesson 24.4](/lessons/24-agent-resilience-and-fallbacks/24.4-model-cascades-and-budgets/), you built a budget-capped sequential cascade for an invoice agent. In full-scale production systems, teams combine two complementary dispatch patterns—**upfront model routing** and **sequential cascades**—behind a centralized **AI gateway**.

## Upfront routing vs. sequential cascades

Both techniques pair a fast, inexpensive model ($c_{\text{small}}$, latency $T_{\text{small}}$) with a capable, expensive frontier model ($c_{\text{large}}$, latency $T_{\text{large}}$), but they decide *when* to escalate at different moments:

- **Upfront routing (RouteLLM — Ong et al., 2024):** A small classifier or **matrix-factorization router** (a compact statistical model that scores query–model fit using learned numeric factors) inspects the prompt *before* any LLM runs, sends fraction $p$ straight to the small model, and sends $(1 - p)$ straight to the frontier model. Trained on human preference datasets (such as Chatbot Arena), these routers cut cost by over $2\times$ on standard test **benchmarks** (MT-Bench and MMLU) while keeping over 95% of frontier quality.
- **Sequential cascade (FrugalGPT — Chen et al., 2023):** Every request goes to the cheap model first. A **verifier**—such as a deterministic rule check on format or arithmetic, a **groundedness score** (whether source documents support the reply), or a trained reliability scorer—inspects the answer, and only the failing fraction $(1 - p)$ escalates to the frontier model.

Compare the exact cost and latency math using small, concrete numbers. Let $c_{\text{small}} = \text{USD } 0.60$ per 1,000 requests, $c_{\text{large}} = \text{USD } 9.00$ per 1,000 requests, $T_{\text{small}} = 900\text{ ms}$, $T_{\text{large}} = 4{,}500\text{ ms}$, router latency $T_{\text{route}} = 20\text{ ms}$, and suppose $p = 0.75$ of queries are handled well by the small model. Step through the three dispatch paths below:

<Figure id="31-3-routing-vs-cascade" />

- **Frontier only:** Cost = $\text{USD } 9.00 / 1\text{k}$; hard-query latency = $4{,}500\text{ ms}$.
- **Upfront router ($p = 0.75$):**

$$
C_{\text{route}} = p \cdot c_{\text{small}} + (1 - p) \cdot c_{\text{large}} = 0.75 \times 0.60 + 0.25 \times 9.00 = \text{USD } 2.70 / 1\text{k}.
$$

Hard queries pay $T_{\text{route}} + T_{\text{large}} = 4{,}520\text{ ms}$.

- **Sequential cascade ($p = 0.75$):**

$$
C_{\text{cascade}} = c_{\text{small}} + (1 - p) \cdot c_{\text{large}} = 0.60 + 0.25 \times 9.00 = \text{USD } 2.85 / 1\text{k}.
$$

Hard queries pay $T_{\text{small}} + T_{\text{large}} = 5{,}400\text{ ms}$ unless the verifier rejects early while tokens are still **streaming** (arriving one by one).

Routing protects tail latency on hard queries from [lesson 31.1](/lessons/31-ai-system-design-and-caching/31.1-end-to-end-latency-budgets/) whenever difficulty is predictable from the prompt alone—such as intent classification, query length, or clues of **multi-hop reasoning** (combining facts across several steps). Cascades win whenever you have a **cheap, trusted verifier** of the output—structured JSON schema validation, automated software unit tests, database SQL syntax and row checks, or citation grounding—because the verifier catches mistakes no upfront router can foresee.

## Calibration: choosing the routing threshold without blind spots

A router outputs a probability score $s(x) \in [0, 1]$ estimating the chance that the frontier model outperforms the small model on prompt $x$, and routes to the frontier model when $s(x) \ge \theta$. Sweeping $\theta$ traces a **cost-quality Pareto curve** (the boundary of best possible trade-offs where raising quality requires spending more and cutting spend lowers quality):

- Lowering $\theta$ sends more traffic to the frontier model (higher quality, higher spend).
- Raising $\theta$ sends more traffic to the small model (lower spend, steeper quality drop once difficult prompts leak onto the small tier).

Never calibrate $\theta$ on generic public leaderboards alone. A router trained on general chat preferences can score poorly on domain-specific legal citations or internal SQL database queries because **distribution shift** (real production inputs differing from training examples) changes which queries are hard. Collect 500–1,000 real production queries, grade both models with your domain **eval rubric** (explicit scoring criteria), and pick the highest $\theta$ that stays inside your acceptable quality margin (for example, within 1 percentage point of frontier-only pass rate). Re-calibrate whenever either model updates.

## What an AI gateway actually owns in production

Once an application talks to multiple models, caches, and providers, scattering vendor client libraries (**SDKs**, software development kits) and retry loops across separate backend **microservices** creates ungovernable spend and inconsistent outages. A centralized **AI gateway** (an internal **proxy service** sitting between your application servers and external model providers) consolidates six cross-cutting responsibilities:

- **Unified routing and fallback:** Maps logical model aliases (`support-fast`, `reasoning-high`) to concrete provider **endpoints** (API network addresses), failing over across regions or secondary providers on **HTTP 429/5xx** bursts (rate-limit rejections or server failures) or TTFT **circuit-breaker** trips (an automatic switch that stops sending traffic to a slow provider until it recovers).
- **Per-tenant rate limiting and token quotas:** Enforces requests-per-minute (RPM), tokens-per-minute (TPM), and daily dollar caps per tenant so one runaway script cannot exhaust shared provider quotas.
- **Virtual keys and secret isolation:** Issues scoped internal tokens to application services while keeping real provider API keys locked inside the gateway.
- **Semantic/exact caching and PII redaction:** Runs caching and masks **personally identifiable information (PII)** (names, emails, card numbers) once at the edge instead of duplicating **middleware** (shared request-processing layers) in every service.
- **Normalized telemetry and cost attribution:** Tags every request in operational **telemetry** (automated logs and metrics) with `tenant_id`, `feature`, `prompt_version`, `route_decision`, cached vs uncached input tokens, output tokens, and exact USD cost.
- **Shadow traffic and canary splits:** Mirrors a small percentage of live requests to a candidate smaller model or updated router threshold so teams compare real quality before shifting production traffic.

:::caveat
An AI gateway is itself on the critical path of every single LLM call. Keep the gateway lightweight (under 5–10 ms added proxy latency), deploy it redundantly across **availability zones** (physically separate datacenter buildings in the same cloud region), and verify every fallback model against your full eval suite—a blind failover to a weaker model that breaks structured JSON or ignores safety rules causes a silent outage worse than a clean retry.
:::

Combine all three pieces—a stable-prefix cache for repeated context, an upfront router for predictable difficulty splits, and a verified cascade where deterministic checks exist—behind one observed AI gateway, and you turn model selection from a hardcoded constant into an adjustable engineering dial.
