This track is about the step between "a model that predicts text" and "a model you can ask for things". The first question is why that step is needed at all, and the answer is worth getting right, because the wrong answer sends teams to fix the wrong problem.

Send the sentence "Write three reasons to test backups" to the Qwen3.8-27B checkpoint (a saved set of trained weights) that the Qwen Team published on 14 August 2026 under Apache 2.0. You get three reasons. By default they are preceded by a separate thinking segment, because thinking mode is this model's default behaviour. Now send the same sentence to a pretrained checkpoint that has never been post-trained. To that model the sentence is just text to continue. The likeliest continuation might be a fourth bullet from somebody else's blog post, a rewritten headline, a snarky "and two reasons not to", or a paragraph explaining why the question matters.

Both checkpoints have the same arithmetic, the same 64 layers, the same 5120-dimensional residual stream (the vector each token carries through the layers) and the same vocabulary of 248,320 tokens. They are still radically different products.

## What a base model does with an instruction

The difference is not knowledge. It is which of many plausible continuations the model picks. Take the prompt above and list four continuations a strong base model might rank highly:

1. The three reasons themselves. This is what the user wants.
2. A fifth line reading "Write three reasons to test restores, too", because prompts of this shape appear in lists of prompts.
3. A critique: "This question assumes backups are already running."
4. A document header, because imperative sentences often sit under one.

Now ask what in the training objective prefers the first over the other three. Nothing does. All four are things that follow such a sentence somewhere in written text, and the model was scored only on how well it predicted the text that actually followed. The user's expectation is "treat the imperative as an instruction directed at you, and carry it out". That expectation lives entirely outside next-token prediction. This gap has a name, **behavioural underspecification**: the capability is present, but the rule for choosing which behaviour to show is not.

## What the training objective rewards

A base language model is trained on an objective that is easy to state: given the preceding tokens, assign high probability to the token that actually came next in its training text. Apply that one token at a time and multiply the probabilities, and you get the probability of a whole response $y$ given a prompt $x$:

$$
p_\theta(y\mid x)=\prod_{t=1}^{|y|}p_\theta\left(y_t\mid x,y_{<t}\right),
$$

where $\theta$ stands for the model's weights and $y_{<t}$ for the response tokens before position $t$. The trouble is that many different sequences $y$ can carry comparable probability mass (a similar share of the total probability) under the same prompt $x$. The four continuations above are such sequences. The training corpus contains answers, questions, arguments, fiction, source code, spam, unsafe instructions, corrections, and unfinished fragments. Predicting that mixture well is a different job from behaving like a reliable assistant.

## Why the base model already knows the answer

Here is the classic wrong turn. Many people conclude that the base model does not know how to write three reasons, and that post-training teaches it. Test that claim and it collapses. Prefix the same base model with two worked examples in the same format, and it produces a competent third. The knowledge and the format were both already there; the context drew them out instead of the weights.

What post-training changed was not competence but the default: which behaviour wins when the context contains no demonstration at all. Getting this backwards leads teams to throw capability data at a behaviour problem. They are then surprised when a bigger supervised fine-tuning (SFT) set makes the model no more obedient.

## What post-training adds

Post-training narrows the range of behaviour the model produces. It comes in a few families, each covered later in this track:

- **Supervised fine-tuning** shows the model prompts paired with desirable responses ([lesson 6.2](/lessons/6-post-training-and-alignment/6.2-supervised-fine-tuning-and-instruction-data/)).
- **Preference optimization** learns from preference feedback, most often a comparison between two responses, and raises the relative probability of the better one ([lessons 6.4](/lessons/6-post-training-and-alignment/6.4-reward-models-and-human-preference-data/) through [6.7](/lessons/6-post-training-and-alignment/6.7-orpo-kto-simpo-and-the-alignment-zoo/)).
- **Reinforcement learning against checkable outcomes** rewards solutions that actually work ([lesson 6.8](/lessons/6-post-training-and-alignment/6.8-grpo-and-rl-on-verifiable-rewards/)).

The result is usually called an **instruct** or **assistant** model. Internally it is still predicting tokens. Its weights now make assistant-shaped continuations far more likely inside the conversational format used during training. No new mechanism is added: the attention projections from [lesson 4.2](/lessons/4-transformer/4.2-self-attention/) are the same matrices with different values.

Qwen3.8-27B makes this layering unusually easy to see, because the vendor ships two operating modes in one set of weights. Thinking mode is the default. The model card recommends different sampling settings for each mode (settings that control how random the choice of the next token is). Among those full recommended settings, thinking mode uses temperature 1.0, top_p 0.95, and top_k 20; instruct mode uses 0.7, 0.80, and 20. Min-p, presence penalty, and repetition penalty complete both configurations, as [lesson 7.4](/lessons/7-inference-and-efficiency/7.4-sampling/) details. A caller who wants the direct answer without the reasoning segment sets enable_thinking to False on the request. None of that is a property of the transformer architecture. All of it is post-training plus a serving convention.

Formatting matters as much. Chat models receive structured roles (system, user, assistant), encoded through a **chat template**: a fixed text layout with special marker tokens around each turn. Those markers are ordinary tokens, not privileged permissions. The model has to learn three things from training: system content outranks user content, user text may contain quoted or hostile instructions, and the assistant turn is where the answer belongs. Feed a post-trained checkpoint a template different from the one it was trained under, and its behaviour degrades even when the prose looks identical.

## What post-training cannot do

:::caveat
Post-training cannot reliably manufacture knowledge the model and its context do not contain. It improves how knowledge is drawn out, the format, calibration (how well confidence matches correctness), and tool use. A confident, well-formatted answer is evidence about the post-training, not about the fact.
:::

One honest limit is specific to this course's model: Qwen3.8-27B has no accompanying technical report. We can observe and cite what the model card documents: the modes, the presets, the switch, the reported benchmark scores. We can also measure the checkpoint ourselves. We cannot say what data or procedure produced the behaviour, and this course will not pretend otherwise.

Alignment is not obedience, either. A useful assistant balances following instructions against truthfulness, safety, privacy, and honest uncertainty, and those goals collide. A request can be clear but unsafe. A factual answer can be unknown. A concise reply can be dangerously incomplete. No single number called "helpfulness" resolves every case.

Nor is the result permanent. Behaviour still shifts with phrasing, long contexts, inputs unlike the training data, decoding settings, and conflicting instructions. Alignment is an engineering process spanning training, evaluation, system design, access control, and monitoring, not a certificate stapled to a checkpoint.

The central distinction is one question becoming two. Pretraining asks: what text is likely here? Assistant post-training adds: among the plausible continuations, which behaviour should this system choose for the person in front of it right now?
