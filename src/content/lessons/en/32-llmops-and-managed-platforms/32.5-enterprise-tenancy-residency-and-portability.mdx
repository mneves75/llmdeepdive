A single-team prototype cares mostly about latency and accuracy. An enterprise deployment cares just as much about four legal and operational boundaries: keeping Customer A's data unreachable from Customer B, proving which country processed each prompt, keeping traffic off the public internet, and staying able to swap models when pricing or quality shifts six months later.

## Multi-tenancy: pooled versus siloed isolation

**Multi-tenancy** means serving multiple independent customer organizations (**tenants**) from one software product. In an AI system, tenant boundaries exist in four places, not just the relational database (the standard table-and-row database): document storage, vector indexes, caches, and telemetry logs.

Teams choose between two isolation models—or mix them by customer tier:

- **Pooled tenancy (logical isolation)**: all tenants share one vector cluster, one cache cluster, and one inference endpoint. Every query injects a mandatory server-side `tenant_id` pre-filter (filtering rows before searching) ahead of Approximate Nearest Neighbor (ANN, fast vector similarity) lookup and prefixes every cache key with `tenant_id` plus the caller's role hash. It minimizes idle cost for hundreds of small customers, but a single missing filter bug creates a cross-tenant leak.
- **Siloed tenancy (physical or namespace isolation)**: each regulated enterprise tenant gets its own dedicated vector collection (an isolated namespace or storage partition), encryption key, and optional dedicated provisioned endpoint. Isolation is enforced by separate infrastructure credentials and keys rather than a single database `WHERE` filter clause, at the cost of higher baseline spend and more operational objects to manage.

Notice how a single shared cache breaks pooled isolation. Suppose a Software as a Service (SaaS) assistant serves 200 tenants and enables a global semantic cache (a cache that matches similar questions by embedding vector similarity). Tenant A asks, "What is our Q4 acquisition budget?" and gets a grounded answer from Tenant A's private board memo. Ten minutes later, Tenant B asks the same question. Without `tenant_id` and Access Control List (ACL, the rules stating which users may read which documents) scopes inside the cache key, the semantic cache returns Tenant A's confidential figure to Tenant B at 0.99 cosine similarity. Every layer that stores derived state—embeddings, rerank results, exact caches, semantic caches, and fine-tuned adapters—must carry the tenant boundary explicitly.

## Data residency, private networking, and encryption keys

Enterprise security reviews—aligned with the National Institute of Standards and Technology (NIST) AI 600-1 profile and the European Union (EU) AI Act—ask three concrete questions about where bytes travel and rest:

- **Regional inference pinning**: many managed cloud platforms offer "global" or "cross-region" inference profiles that route overflow bursts to GPUs in other continents. That boosts availability, but it silently violates contracts promising that EU or Brazilian customer data never leaves the region. Pin single-region or explicit geography-locked endpoints (such as `eu-central-1` or an EU-only cross-region profile) and verify the active endpoint in your Continuous Integration (CI) deployment checks.
- **Private networking**: instead of sending prompts over the public internet to `api.vendor.com`, route calls through Virtual Private Cloud (VPC) private endpoints (AWS PrivateLink, Google Private Service Connect, or Azure Private Link). Traffic stays on the cloud backbone (the provider's private internal network) with Identity and Access Management (IAM) policies and zero public egress (outbound public-internet transfer).
- **CMEK and ZDR**: **Customer-Managed Encryption Keys** (CMEK) let the enterprise hold the root encryption key in its own Key Management Service (KMS) and revoke access to stored indexes, fine-tuned weights, and audit logs if required. **Zero Data Retention** (ZDR) ensures the model provider holds prompt and completion payloads only in volatile memory (short-lived RAM that clears after inference) and never writes them to disk or training sets.

Verify whether ZDR conflicts with provider-side abuse monitoring or prompt caching. Some providers require an enterprise addendum to disable 30-day abuse logging, and prefix caches hold key-value (KV) tensors in accelerator memory for a short Time To Live (TTL, a few minutes) rather than writing text to disk; document that distinction explicitly in your data-flow diagram.

## Measuring the cost of vendor lock-in

Switching models every year is now normal in production AI—a newer model cuts cost by 40% or fixes a reasoning weakness. Yet teams routinely trap themselves inside one provider without realizing it. Notice the difference between a **stateless** API (each call is self-contained and the vendor stores nothing afterward) and a **stateful** API (the vendor stores your chat history, files, and tool state on its own servers):

| Layer | Easy to swap (low lock-in) | Hard to swap (high lock-in) |
| --- | --- | --- |
| Inference call | Stateless chat/messages API behind an internal adapter | Proprietary stateful threads / Assistants storage |
| Retrieval | Self-managed or portable vector DB + chunk pipeline | Vendor-hosted black-box file search with no chunk export |
| Guardrails & evals | Manifest-pinned prompts + OpenTelemetry + own eval suite | Vendor-only dashboard prompts and proprietary eval logs |
| Tool orchestration | Application-owned state machine and tool schemas | Vendor-hosted server-side tool loops tied to one SDK |

Run a concrete portability test before adopting any managed convenience feature: *If we had to move 100% of traffic to a second model family in 14 days, which data or state could we not export?*

If your conversation history, chunked documents, tool definitions, and offline eval corpus live in your own infrastructure, migration is mostly a prompt re-tuning and eval-suite run: you build a new coupled manifest targeting Provider B, run the offline benchmark from track 29, shadow-test it, and shift traffic. If your customer history and document chunks live exclusively inside Provider A's proprietary stateful API, migration turns into a multi-quarter rewrite.

:::warning
Portability does not mean writing a lowest-common-denominator wrapper that forbids useful model features like prompt caching or structured outputs. Keep your internal **model gateway** thin: normalize authentication, retries, timeouts, token accounting, and OpenTelemetry `gen_ai.*` spans across providers, while passing model-specific parameters cleanly from the release manifest.
:::

## Designing a two-provider escape hatch

High-availability enterprise systems often maintain a tested **secondary provider** (for example a frontier model on a managed cloud primary plus a second model family on a standby endpoint) both for outage resilience and commercial leverage. Keeping that escape hatch real requires two habits:

- **Run your offline eval suite on the secondary model monthly**: a backup model whose prompt has never been evaluated against your current schema will fail the day you actually fail over to it.
- **Keep prompt templates modular**: separate stable business rules and JSON schemas from provider-specific formatting tags so updating the secondary manifest takes hours instead of weeks.

:::caveat
Multi-provider abstraction has a real cost. Supporting two models in production doubles prompt-tuning work, evaluation runs, and behavioral edge cases because every model family responds slightly differently to the same wording. Use a thin gateway from day one so migration stays cheap, but actively maintain a hot failover (a standby provider kept ready to take live traffic immediately) only when uptime Service Level Agreements (SLAs, contractual uptime guarantees) or regulatory continuity justify the ongoing evaluation load.
:::
