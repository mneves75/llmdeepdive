In conventional web software, a release is usually one container image tagged with a Git commit SHA. If an endpoint starts returning errors after a deploy, rolling back that single image restores the previous behavior. Production AI systems break that assumption. Even if your application code does not change by a single line, an edit to a prompt template in a dashboard, a silent model alias update by a vendor, or a re-indexed embedding table can drop answer quality overnight while every server still returns HTTP 200.

This lesson explains why an AI release is a **coupled artifact** (a bundle of interdependent files and versions that only work as a verified set), how to pin every component in one immutable manifest, and how to make rollbacks atomic.

## Why independent deploys create silent drift

Picture a customer-support RAG assistant serving 10,000 queries per day. Five separate artifacts determine what the user sees on every request:

- **Prompt template and system instructions**: the exact wording, few-shot examples, and formatting rules from [lesson 26.5](/lessons/26-llm-apis-and-structured-outputs/26.5-prompt-engineering-hierarchy-and-caching/).
- **Output schema and parser**: the JSON Schema enforcing structured fields and tool signatures.
- **Model snapshot and decoding parameters**: the pinned checkpoint ID (for example `model-2026-08-15`, not a floating alias), temperature, and max-token cap.
- **Embedding model and retrieval index revision**: the exact encoder and chunked snapshot used to search documents.
- **Guardrail and router configuration**: classifier thresholds, allowlists, and fallback routes.

Now trace what happens when a team manages those five pieces independently. Suppose each component changes once per week on its own schedule. On Monday, an engineer edits a prompt in a web UI to add a `refund_tier` field. On Tuesday, the data pipeline upgrades the document encoder from `embed-v2` to `embed-v3` (both producing 1,536-dimensional vectors, so the database accepts the writes without complaint), while the online API keeps encoding user queries with `embed-v2`. On Wednesday, the model provider quietly shifts the `fast-latest` alias to a new checkpoint.

By Thursday, groundedness on support tickets has fallen from 91% to 74%. No crash alert fired. No CI job failed because the prompt edit bypassed Git, the index update bypassed the API repo, and the model swap happened outside your cluster. When an engineer tries to roll back Monday's prompt edit, the quality stays broken because the query encoder and document index are still living in two incompatible vector spaces.

## Counting the coupling surface

A small calculation shows why ad-hoc tracking collapses as soon as a product grows. If $k$ components each have $v$ independently toggled versions in production, the number of distinct runtime combinations is:

$$
N_{\text{configs}} = v^{k}
$$

With $k = 5$ components and just $v = 3$ active versions each (say previous, current, and canary), there are $3^{5} = 243$ possible runtime states. Your offline evaluation suite from [lesson 29.5](/lessons/29-llm-and-rag-evaluations/29.5-offline-to-online-eval-flywheels/) tested at most one or two of those 243 combinations. The other 241 states are untested production software.

Pinning all five references into a single **release manifest** (an immutable JSON or YAML document identified by a cryptographic digest) collapses $v^{k}$ loose combinations down to one named bundle per release. You never deploy "prompt v18" or "index rev 42" in isolation. You deploy manifest `rel-042`, whose digest proves the exact prompt, schema, model snapshot, embedding model, index revision, and guardrail policy that passed CI together.

```json
{
  "release_id": "rel-2026-11-20-a4f2",
  "prompt_sha256": "9c31b8e0...7d4a",
  "schema_version": "support-reply.v4",
  "model_snapshot": "claude-sonnet-4-5-20250929",
  "decoding": { "temperature": 0.0, "max_output_tokens": 800 },
  "embedding_model": "text-embed-v3-2026-04",
  "index_revision": "kb-chunks-20261119-02",
  "guardrail_policy": "policy-v9"
}
```

Google's release engineering guidance makes hermetic, reproducible builds the bedrock of safe operations: if you cannot reconstruct the exact inputs that produced a binary, you cannot debug or roll it back reliably. For AI systems, the prompt, schema, model snapshot, and index revision *are* part of the binary.

## Handling index migrations and blue-green snapshots

Code and prompts are cheap to version in Git because they are kilobytes of text. A vector index containing 2,000,000 document chunks is gigabytes of state, so you cannot copy it on every commit. Teams avoid version skew between embeddings and indexes with **blue-green index revisions** (keeping the previous index revision readable alongside the newly built one until the rollout succeeds).

Suppose manifest `rel-041` points at `embedding_model: embed-v2` and `index_revision: kb-rev-41`. To upgrade to `embed-v3`:

1. An offline batch job embeds the corpus with `embed-v3` and writes a brand-new immutable collection `kb-rev-42`. Production traffic still hits `kb-rev-41`.
2. A pull request creates manifest `rel-042`, changing `embedding_model` and `index_revision` together in one commit.
3. CI runs the full offline evaluation suite against `rel-042` pointing at `kb-rev-42`, checking Recall@k, schema validity, and groundedness before merge.
4. Production rolls out `rel-042` via shadow and canary traffic while `kb-rev-41` remains warm and untouched.
5. Only after `rel-042` holds steady at 100% traffic for the retention window (say 72 hours) does a cleanup job retire `kb-rev-41`.

Because `kb-rev-41` stays intact throughout the rollout, rolling back from `rel-042` to `rel-041` takes one atomic pointer flip and zero re-indexing wait time.

:::warning
Prompt-management dashboards that edit live production prompts directly—outside Git, code review, and offline evaluation—violate coupled versioning. Use a prompt registry to browse traces or draft experiments, never as an unreviewed backdoor into live traffic. Every change that reaches users must compile into a new immutable manifest and pass the same CI gate.
:::

## Tagging every trace with the manifest ID

A manifest only pays off during an incident if you can see which bundle produced each answer. Every request handler should attach `release_id` as a mandatory field on every log line, metric label, and distributed trace span.

When a user reports a hallucinated refund policy at 14:32 UTC, the on-call engineer reads `release_id: rel-2026-11-20-a4f2` from the trace, checks out that exact manifest from Git, replays the user's input against the identical model snapshot and index revision, and confirms whether the failure is a regression introduced by `rel-042` or an existing gap in the knowledge base. Without coupled versioning, debugging turns into archaeology across four separate dashboards.

:::caveat
Pinning a vendor's dated snapshot protects you from silent mid-week weight swaps, not from eventual vendor deprecation. Providers retire dated snapshots on a 6-to-18-month cycle. Track snapshot sunset dates inside the manifest metadata and run an automated reminder 60 days ahead so migrations happen through your normal CI evaluation pipeline rather than during an emergency cutoff.
:::
