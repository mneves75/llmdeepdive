When a traditional web endpoint slows down, an application performance monitor points to a slow database query or a busy pool of worker threads (parallel execution slots on a server). When an AI endpoint slows down or starts returning bad answers, standard Hypertext Transfer Protocol (HTTP) metrics only tell you that `POST /ask` returned status 200 (success) in 1.4 seconds. They hide whether the time went into vector search, a reranker (a second model that re-scores retrieved passages), an automatic retry after a rate limit (a provider's speed cap), or a model that suddenly started generating three times as many tokens.

This lesson shows how to instrument an AI pipeline with **OpenTelemetry** (an open-source observability standard for traces, metrics, and logs) using its **GenAI Semantic Conventions** (the shared field names for Large Language Model calls, tokens, tools, and agents) so every millisecond of latency, dollar spent, and quality failure maps back to the exact `release_id` from [lesson 32.1](/lessons/32-llmops-and-managed-platforms/32.1-coupled-versioning-and-release-artifacts/).

## Reading a concrete RAG trace

A **distributed trace** records one end-to-end user request as a tree of timed steps called **spans**. Each span carries a start time, a duration, a parent ID, and structured key-value **attributes** (named fields describing what ran).

Look at one support question passing through a Retrieval-Augmented Generation (RAG) pipeline under root span `rag.request` (`release_id = "rel-2026-11-20-a4f2"`). Its four sequential child spans—vector search (`retrieval.search`), cross-encoder reranking (`retrieval.rerank`), input policy check (`guardrail.input`), and model inference (`chat claude-sonnet-4-5`)—add up to 700 ms:

$$
T_{\text{total}} = 45 + 35 + 20 + 600 = 700\ \text{ms}
$$

Switch between the two frames below to see the full 700 ms breakdown—splitting the 600 ms model call into 220 ms Time To First Token (TTFT, the prefill wait before the first word appears) and 380 ms decoding the remaining output tokens—versus what happens if your team spends two weeks cutting vector search in half.

Looking at the span proportions answers a practical engineering question in ten seconds: halving the 45 ms `retrieval.search` span saves only 22.5 ms (3.2%), because the 600 ms model span accounts for 85.7% of wall-clock time. Without child spans, teams routinely optimize the 6% slice they know how to tune while missing the 86% slice where the wait actually lives.

## OpenTelemetry GenAI semantic conventions

Early AI teams wrote custom logging wrappers or tied their code to one monitoring vendor's proprietary Software Development Kit (SDK, a vendor-specific code library). Switching backends (the storage and dashboard service receiving telemetry) later meant rewriting instrumentation across every service and agent loop.

The **OpenTelemetry GenAI Semantic Conventions** (published by the OpenTelemetry project in 2025) solve that portability problem by standardizing span names, attributes, and metrics across providers and frameworks. Your application emits **OpenTelemetry Protocol (OTLP)** data once, and any compliant collector (a forwarding service) can route it to Prometheus, Grafana Tempo, Jaeger, Honeycomb, Datadog, or an internal data warehouse (an analytical database).

The core attributes worth requiring on every LLM span are small and concrete:

| Attribute | Example value | What it diagnoses |
| --- | --- | --- |
| `gen_ai.operation.name` | `chat`, `embeddings`, `execute_tool` | Separates generation from retrieval and tool execution |
| `gen_ai.system` | `anthropic`, `openai`, `aws.bedrock` | Attributes outages or rate limits to the exact provider |
| `gen_ai.request.model` / `gen_ai.response.model` | `model-2026-08-15` | Proves which snapshot actually served the request |
| `gen_ai.usage.input_tokens` / `output_tokens` | `1850` / `240` | Drives per-feature cost attribution and verbosity alerts |
| `gen_ai.response.finish_reasons` | `["stop"]` or `["length"]` | Catches silent truncation and refusal spikes |
| `gen_ai.server.time_to_first_token` | `0.22` (seconds) | Splits prefill/queue delay from decode speed |

Pair those standard fields with two custom application attributes—`app.release_id` (from lesson 32.1) and `app.cache_hit` (`none`, `exact`, `prefix`, `semantic`)—and your dashboards can immediately slice cost, TTFT, and `max_output_tokens` truncation rates by release version. Notice that streaming responses delivered over Server-Sent Events (SSE, a live token-by-token web stream) still emit these exact summary attributes when the stream finishes.

## Metrics, traces, and logs: what belongs where

Recording every token of every request forever is expensive and unnecessary. Observability works best as three complementary layers with different retention budgets:

- **Metrics (100% of requests, low cardinality)**: aggregated counters and histograms (bucketed timing summaries) for latency (`gen_ai.client.operation.duration`), token totals (`gen_ai.client.token.usage`), error rates, and cache hit rates grouped by `release_id` and route. Never put `user_id` or `request_id` as a metric label, or cardinality (the number of distinct label combinations) explodes your time-series database bill.
- **Structural traces (sampled or tail-sampled)**: full span trees with timings, token counts, finish reasons, and retrieved chunk IDs. **Tail-based sampling** waits until a request finishes, then keeps 100% of slow traces (for example p95+, the slowest 5% of requests), 100% of errors or `length` truncations, 100% of user thumbs-down feedback, and a small random sample (say 5%) of healthy traffic.
- **Content audit logs (opt-in, tightly governed)**: raw prompts, retrieved chunk texts, and completions, stored only where privacy policy permits and kept separate from general engineering telemetry.

Check the sampling arithmetic on a service handling 1,000,000 requests per month. Suppose 2% are errors or slow outliers and you keep 5% of the remaining 98% healthy requests. Total stored traces are:

$$
N_{\text{traces}} = 1{,}000{,}000 \times (0.02 + 0.98 \times 0.05) = 69{,}000\ \text{traces/month}
$$

You retain every single failure and tail-latency outlier while cutting trace storage volume by 93.1% compared with logging everything.

:::warning
The OpenTelemetry GenAI specification explicitly marks prompt and completion bodies as opt-in because they frequently carry customer Personally Identifiable Information (PII, such as names, emails, or account numbers), credentials, or confidential documents. Never enable raw `gen_ai.content.prompt` or `gen_ai.content.completion` capture to a third-party Software as a Service (SaaS) telemetry vendor without redaction and legal sign-off. Default to structural metadata in OpenTelemetry spans, and keep sensitive text inside a redacted, encrypted store with an explicit Time To Live (TTL, an automatic deletion timer).
:::

## Closing the loop to quality alerts

Latency and token counts catch operational bugs, but an AI system can still fail silently with fast spans and status 200. Attach asynchronous (background, non-blocking) quality signals back onto the same `trace_id`:

- **Explicit user signals**: thumbs-up/down clicks, regeneration clicks, copy-to-clipboard events, or support escalations attached as span events on the original `trace_id`.
- **Online sample evaluators**: a background worker reads a 2% sample of traces (joined with redacted text inside your secure boundary), runs calibrated graders, and emits `eval.groundedness` and `eval.schema_valid` metrics labeled by `release_id`.

:::caveat
Do not run LLM-as-a-judge evaluators (a second language model grading the first model's reply) synchronously inside the user-facing request path. A synchronous judge adds 300–900 ms of wait time and doubles token spend on every user turn. Emit the trace asynchronously, evaluate sampled traces out of band (on a separate background queue), and feed regressions into your alerting and rollout controller.
:::

With coupled release manifests in place and OpenTelemetry GenAI traces lighting up every span, you now have the telemetry required to roll changes out safely. Lesson 32.3 uses these exact trace signals to drive shadow deployments, canary traffic shifts, and automated rollbacks.
