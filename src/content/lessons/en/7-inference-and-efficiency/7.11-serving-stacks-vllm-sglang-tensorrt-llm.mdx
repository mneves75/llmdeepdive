You have chosen Qwen3.8-27B; now something has to serve it. A **serving engine** is the program that loads the weights onto accelerators, accepts requests from many users, schedules them, and streams tokens back. The model card names vLLM, SGLang, and Transformers as supported paths. SGLang maintains an official cookbook page for this exact model. TensorRT-LLM is NVIDIA's own engine, the option that ties you most closely to NVIDIA hardware and tooling.

This lesson is deliberately a decision map, not a manual. Each stack gets its own lesson in Track 8, where the flags, configs, and failure modes live. Here you learn only which door to walk through.

## First gate: does the model fit on your hardware?

The first gate is arithmetic, not software. The weights cost 54 GB in bf16 (bfloat16, two bytes per number). [Lesson 9.3](/lessons/9-hardware-and-infrastructure/9.3-kv-cache-sizing-and-memory-budgets/) owns what is left over on an 80 GB card: **23.3 GiB** of KV pool, the memory set aside for the KV cache of [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/), once the framework's own reservation is subtracted. At lesson 7.2's 64 KiB per token, that pool is roughly 381,700 tokens, or about ten 32K sessions once the 144 MiB per-sequence DeltaNet state from lesson 7.8 is included (the KV-only count of eleven overstates capacity).

Do not reach for the obvious $80 - 54$ here: that subtraction is the worked mistake 9.3 opens with. It inflates the pool only slightly. But dividing it by context alone, as though a sequence cost nothing but its cache, overstates how many conversations fit by a fifth.

If your hardware budget is a 24 or 48 GB card, this whole lesson is premature. A data-center GPU or **sharding** (splitting the weights across several GPUs) is the price of entry here. Below that, you are on the quantized-artifact path through [lesson 7.12](/lessons/7-inference-and-efficiency/7.12-running-models-locally/) and the local runners of Track 8, not choosing among data-center engines.

## Which engine fits your workload?

With capacity settled, match the engine to the shape of your traffic.

**vLLM** is the default for a high-concurrency API (many users at once) over conversations of varying length, on GPUs you control. It grew around exactly the PagedAttention and continuous-batching machinery of [lesson 7.8](/lessons/7-inference-and-efficiency/7.8-pagedattention-and-continuous-batching/): the KV cache stored in small fixed-size pages, and a running batch that finished requests leave and new ones join at every step. It serves an OpenAI-style API and covers the broadest range of open models. Details in [lesson 8.4](/lessons/8-building-and-serving-stacks/8.4-vllm/).

**SGLang** fits when your traffic is not isolated prompts but structured programs: agent pipelines making many related calls, long prompt beginnings (prefixes) shared across calls, and JSON output constrained to a schema. Its RadixAttention keeps the KV cache of shared prefixes so later calls can reuse it, and its scheduler orders requests so that ones sharing a prefix run close together, which pays off when many calls come from the same program. Its official Qwen3.8-27B cookbook means this model is directly supported there. Details in [lesson 8.5](/lessons/8-building-and-serving-stacks/8.5-sglang/).

**TensorRT-LLM** fits a fleet already committed to NVIDIA that is chasing the last percent of latency. It gets there by compiling the model into an optimized engine, for example using FP8 (8-bit floating-point numbers). The cost is operational: an ops team must own compilation, version pinning, and rebuilds when shapes change. Details in [lesson 8.6](/lessons/8-building-and-serving-stacks/8.6-tensorrt-llm/).

Plain **Transformers**, the Hugging Face library, remains right for one researcher on one GPU checking that outputs are correct, not maximizing throughput. Details in [lesson 8.2](/lessons/8-building-and-serving-stacks/8.2-huggingface-transformers-ecosystem/).

No GPUs at all? A managed endpoint such as Workers AI serves this model per token: USD 0.45 per million input tokens and USD 3.20 per million output as of Aug 2026. [Lesson 8.11](/lessons/8-building-and-serving-stacks/8.11-serving-in-the-cloud/) does that cost math.

## Before any benchmark: support, then correctness

The classic wrong turn is picking by headline throughput. A vendor benchmark at one batch size, one prompt length, and one quantization tells you almost nothing about your **goodput**: the rate of requests completed within your latency target, as opposed to raw tokens per second.

The corrected order has three steps:

1. Confirm the engine version supports your exact model.
2. Verify correctness: the tokenizer and **chat template** (the format that wraps messages into one prompt) match the reference, thinking mode is handled, generation stops where it should, and structured output is valid.
3. Only then benchmark pinned versions on your hardware, with your own prompt and output lengths, identical decoding settings, and production-like concurrency.

Measure time to first token (how long until the first token arrives), inter-token latency (the gap between later tokens), and goodput against your latency objective, not a single peak number.

:::caveat
For this model, the support question decides everything else. Qwen3.8-27B's hybrid layout, 48 Gated DeltaNet layers beside 16 attention layers, is new enough that an engine release either implements its state management or cannot run the model at all. Architecture support outranks every other row of this map; check it before reading any benchmark.
:::

:::warning
An OpenAI-compatible API is a transport shape, not semantic equivalence. Defaults for chat templates, thinking-mode toggles, stop tokens, log-probabilities, seeds, and tool calls differ across engines. The same request can produce different answers on stacks that both call themselves compatible.
:::

## What decides a tie between engines?

Operations often decide ties: metrics and traces, health checks, rolling upgrades, cleanup when a request is cancelled, admission control (deciding which requests to accept under load), multi-tenancy, container size, and cold-start time. A marginal kernel gain rarely justifies an engine your team cannot diagnose at 3 a.m.

Mixing stacks is legitimate, for example throughput-oriented batch generation on one and interactive serving on another. But every extra runtime multiplies conformance testing.

Hold the map, not the manuals. Hardware gate first. Then workload shape: concurrency to vLLM, program structure to SGLang, last-percent latency on NVIDIA to TensorRT-LLM, simplicity to Transformers, no hardware to a managed endpoint. Then correctness, then your own benchmark.
