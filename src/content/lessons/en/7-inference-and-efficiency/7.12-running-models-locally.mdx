Can your machine run Qwen3.8-27B? The honest answer is a ladder, not a yes or no. The rung you land on is set by the quantization level you accept, using exactly the arithmetic of [lesson 7.9](/lessons/7-inference-and-efficiency/7.9-quantization-i-int8-int4-the-basics/) and [lesson 7.10](/lessons/7-inference-and-efficiency/7.10-quantization-ii-gptq-awq-gguf-qat/).

## The ladder of file sizes

At the top, **bf16** weighs about 54 GB; int8 is approximately 27 GB before format overhead. At the pinned community revision, near-4-bit text-model files span 15.7–17.9 GB (14.6–16.7 GiB), with Q4_K_M at 17.1 GB (15.93 GiB). Lesson 7.10 owns those exact artifact figures.

The model card does not state a 24 GB VRAM minimum (VRAM is the GPU's own memory). So this lesson treats 24 GB as a concrete course scenario whose complete resident budget, everything the running process actually holds in memory, must be measured.

## Sizing the 24 GB scenario

The classic mistake is to multiply the rounded 27B label by half a byte and conclude that a 16 GB card works. The exact pinned Q4_K_M text file is already 15.93 GiB, and that is before adding any of these:

- the separate multimodal projector (the piece that connects the vision tower to the text model);
- the KV cache, which, unless it is quantized too, accrues in bf16 regardless of weight precision;
- the DeltaNet state;
- runtime workspace;
- whatever the display uses.

File size is an input to capacity planning, not the resident-memory answer.

Size the 24 GB scenario step by step:

1. Q4_K_M text weights occupy 15.93 GiB on disk.
2. At 8,192 tokens, KV costs 512 MiB ([lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/)'s 64 KiB per token).
3. The reference float32 DeltaNet matrix state adds 144 MiB per sequence.
4. Runtime workspace, compute buffers (scratch memory for intermediate results), allocator behavior, the optional separate projector, and display use remain backend-dependent.

Because step 4 depends on the backend, load the exact stack and inspect realized memory rather than claiming a universal total. Context length moves the total most: at 65,536 tokens the KV term alone reaches 4 GiB, and at the native 262,144-token window it reaches 16 GiB. Configure the context you will actually support.

## Speed is set by memory bandwidth

Capacity decides whether the model loads; **bandwidth** (how many bytes per second memory can deliver) decides whether it is pleasant to use. Each decoded token moves a large fraction of the resident weight bytes through memory. So local generation speed tracks memory bandwidth far more than compute specs. That is one reason unified-memory machines, where the CPU and GPU share one large pool of fast memory, punch above their apparent class; [lesson 9.1](/lessons/9-hardware-and-infrastructure/9.1-memory-bandwidth-vs-flops/)'s roofline treatment gives the exact mathematics.

Remember too that this is a multimodal model. The vision tower is part of the checkpoint, and image inputs add encoder computation and buffers on top of text-only sizing.

## Which runtimes can run it

Where does it actually run? The community quantization ecosystem for this model spans llama.cpp and its GGUF format, the runners that wrap it such as Ollama and LM Studio, and MLX, Apple's machine-learning framework, on Apple silicon.

One check outranks every download: the runtime must implement Qwen3.8-27B's hybrid architecture, Gated DeltaNet layers beside full attention, in its kernels. Support for brand-new layer types arrives in specific releases, not automatically, so verify it before pulling 17.1 GB.

From here the course goes hands-on. [Lesson 8.7](/lessons/8-building-and-serving-stacks/8.7-llama-cpp-and-gguf/) works through llama.cpp and GGUF properly, [lesson 8.9](/lessons/8-building-and-serving-stacks/8.9-mlx/) runs the model through MLX, and [lesson 9.6](/lessons/9-hardware-and-infrastructure/9.6-apple-silicon-unified-memory/) explains why Apple's unified memory changes the local calculation.

:::warning
Local does not automatically mean private or safe. Applications may send telemetry (usage data sent back to the vendor), plugins may read files, prompts can land in logs or in swap (memory written out to disk), and community model files are third-party artifacts that can be tampered with. Verify sources and hashes, prefer non-executable tensor containers, and audit what your runner actually transmits.
:::

:::note
Benchmark your intended task, not a screenshot. Record runtime and model versions, backend, thread count, context length, and thermal state (how hot the machine is running). Measure load time, time to first token, tokens per second, and peak memory. A laptop that briefly bursts to a nice number may sustain something very different ten minutes into a session.
:::

Plan in this order:

1. Pick the quantization rung your memory affords.
2. Add cache at the context you will really use, plus state and workspace.
3. Confirm the runtime supports the architecture and consumes the packed format natively.
4. Then measure the bandwidth-bound reality.

Local inference is rewarding precisely because every layer is visible. That also makes you the serving operator, and this lesson's arithmetic is your capacity plan.

## Case study: Kimi K3 in C and storage-backed inference

Keeping all weights resident is not the only execution strategy. [Kimi K3 in C](https://github.com/FareedKhan-dev/kimi-k3-in-c) implements CPU inference in C99. It loads selected MoE experts (in a mixture-of-experts model, each token uses only a few of many expert sub-networks) in native MXFP4, a 4-bit floating-point format, and it streams the dense trunk layers within a configurable memory budget. The [architecture](https://github.com/FareedKhan-dev/kimi-k3-in-c/blob/ac1584a70205c3a00d5346f736834818f4cc11b4/docs/ARCHITECTURE.md) makes the tradeoff visible: fewer resident weights can mean more storage reads per token. This is a separate model and runtime from the course's Qwen example.

Read the [measurement data and its limits](https://github.com/FareedKhan-dev/kimi-k3-in-c/blob/ac1584a70205c3a00d5346f736834818f4cc11b4/docs/data/README.md) alongside the headline. Peak RSS (resident set size) measures the process's resident RAM; the checkpoint and packed trunk still require terabytes of disk space. The published memory ladder varies budgets on a server, rather than benchmarking a collection of laptops. Keep its hardware, prompt, threads, storage and cache conditions attached to any timing claim. These are engine measurements, not task-quality scores.

For a code-reading exercise, follow `src/io/k3_trunk.c` and `src/cache/k3_cache.c`, then inspect the [tests that need no model weights](https://github.com/FareedKhan-dev/kimi-k3-in-c/blob/ac1584a70205c3a00d5346f736834818f4cc11b4/docs/TESTING.md). Fixture correctness (passing tests on small built-in inputs) and practical full-model performance are separate checks; the former is a useful starting point before a large download.
