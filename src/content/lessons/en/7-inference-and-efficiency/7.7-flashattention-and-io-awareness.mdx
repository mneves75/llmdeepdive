Qwen3.8-27B accepts a native context of 262,144 tokens, and 16 of its 64 layers run full softmax attention over that entire span. Feed the model a maximal prompt and each of those layers must, in principle, compare every query with every key. The attention formula is one line. The question this lesson answers is whether the intermediate objects it implies can physically exist, and what to do when they cannot.

## Why the naive score matrix cannot exist

The object in question is the score matrix $QK^\top$: one entry for every pair of a query and a key, holding how strongly that query matches that key. Run the arithmetic. With $N = 262{,}144 = 2^{18}$, the score matrix $QK^\top$ has $2^{18} \times 2^{18} = 2^{36} \approx 6.9 \times 10^{10}$ entries per head. At two bytes each in bf16, that is $2^{37}$ bytes, or **128 GiB, for one head of one layer**.

Qwen3.8-27B has 24 query heads per full-attention layer, so materializing one layer's scores (writing them all out to memory) would take about 3 TiB, and its 16 full-attention layers together roughly 48 TiB. A naive implementation would write that to high-bandwidth memory (HBM, the GPU's main memory), read it back for softmax, write it again as probabilities, and read it once more to multiply $V$. An 80 GB-class accelerator cannot hold even a single head's matrix. Naive attention at this context length is not slow; it is impossible without changing the memory plan.

## Working in tiles that fit on chip

Accelerators have a memory hierarchy. A small pool of on-chip SRAM, measured in tens of megabytes, sits right beside the arithmetic units and is very fast. HBM is orders of magnitude larger but far slower to reach. The arithmetic units idle while tensors travel between the two. **IO-awareness** means designing the algorithm around the bytes moved through this hierarchy, rather than only counting floating-point operations.

FlashAttention's observation is that attention can be computed in tiles, small blocks of the matrices, that fit in SRAM, so the score matrix never needs to exist as a whole. Split the queries into row blocks and the keys and values into column blocks, and size the tiles to the head dimension. Qwen's full-attention heads use head dimension 256, so a 128-row key tile occupies $128 \times 256 \times 2 = 65{,}536$ bytes, 64 KiB, and its value twin another 64 KiB.

That is twice the footprint of the 128-dimensional heads many early kernels (the GPU routines that implement attention) were tuned for. Within the same SRAM budget it forces smaller row blocks or more passes. It also means kernel support for $d = 256$ must be verified for the exact library version, not assumed from an API flag.

## The softmax obstacle, and the online fix

The obstacle to tiling is softmax: normalizing a row of scores appears to require seeing the whole row at once, because every weight is divided by the sum over the entire row.

The obvious shortcut is to softmax each tile locally and concatenate the results. Try it on one query row whose scores arrive as a block $[1.0,\ 3.0]$ followed by a block $[5.0]$. A local softmax of the first block gives the score 3.0 a weight of $e^{3}/(e^{1}+e^{3}) \approx 0.881$. But the true weight, once the dominant 5.0 arrives, is only about 0.117. Local normalization bakes in a denominator that later tiles invalidate.

Online softmax corrects this by carrying two running statistics per row: the maximum $m$ seen so far and the exponential sum $\ell$. Each score is exponentiated after subtracting the current maximum, the standard trick that keeps the exponentials from overflowing without changing the result ([lesson 4.3](/lessons/4-transformer/4.3-scaled-dot-product-attention/)). Follow the same row:

1. After the first block, $m_1 = 3$ and $\ell_1 = e^{1-3} + e^{3-3} = 0.135 + 1 = 1.135$.
2. The second block raises the maximum to $m_{new} = 5$, so the old sum was measured against the wrong maximum. Rescale it by $e^{m_1 - m_{new}} = e^{-2}$: $\ell \leftarrow 1.135 \times 0.135 = 0.154$.
3. The new term adds $e^{5-5} = 1$, giving $\ell = 1.154$.

Computing directly, $e^{-4} + e^{-2} + e^{0} = 0.018 + 0.135 + 1 = 1.154$: identical. The partial output accumulators are rescaled by the same factor, so after the last tile the division by $\ell$ yields exact attention. The order of operations changes, so the last floating-point bits may differ, but nothing is approximated, sparsified, or truncated.

Recomputation extends the same logic to training. The backward pass, the step that computes gradients, can recompute local scores inside tiles instead of reading a stored $N^2$ matrix. It spends cheap arithmetic to avoid expensive HBM traffic.

:::caveat
FlashAttention fixes the memory of stored intermediates, not the dependency structure. Exact dense attention still performs pairwise work that grows quadratically with sequence length, so a 262,144-token prefill remains a large computation. It just becomes one that fits. The paper's bounds keep the two costs apart. Extra memory grows linearly with sequence length $N$. Traffic to HBM is $\Theta(N^2d^2/M)$ for head dimension $d$ and SRAM size $M$, still quadratic in $N$, and many times below standard attention's only when $d^2$ is much smaller than $M$, a margin that shrinks at $d = 256$.
:::

## Where the speedup applies

The benefit depends on the phase. Prefill processes many query rows at once, which is exactly the workload the tiling targets. Single-token decode has one query row. As [lesson 7.3](/lessons/7-inference-and-efficiency/7.3-prefill-vs-decode-two-different-machines/) established, decode is dominated by reading the weights and the KV cache ([lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/) derives Qwen's per-token cache cost). Specialized decode kernels borrow the same ideas, but they do not get the same headline speedup.

:::insight
Only 16 of Qwen3.8-27B's 64 layers ever face the quadratic object at all. The other 48 use Gated DeltaNet, whose fixed-size state sidesteps the score matrix entirely: the architectural complement to FlashAttention's algorithmic fix. IO-awareness and hybrid layouts are two answers to the same enemy, bytes moved per token.
:::

The idea outlives any one kernel. When arithmetic is cheap and memory movement is not, algorithm design must count bytes through the hierarchy. FlashAttention is exact attention rearranged around that physical reality, and it is the reason a quarter-million-token context is a product feature rather than a thought experiment.
