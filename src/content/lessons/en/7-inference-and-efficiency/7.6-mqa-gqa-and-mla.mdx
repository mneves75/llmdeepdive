Open Qwen3.8-27B's config (the configuration file listing the model's dimensions) and an asymmetry jumps out: 24 query heads, but only 4 key/value heads. Why would a design team give a layer six times more questions than answers? Because of what each one costs during serving. A query is computed fresh at each step and is then thrown away, so it costs only weights. Every key and value, though, must be *stored for every past token* in the KV cache of [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/). KV heads are the expensive ones, and this lesson is about the family of designs that economize on them: MQA, GQA, and MLA.

## What a KV head costs

Set up the accounting. In standard multi-head attention, a layer runs several heads side by side, each with its own query, key and value projections (matrix multiplications that reshape a token's vector). With $H_q$ query heads and $H_{kv}$ KV heads, cache size per token per layer is proportional to $H_{kv}$ (times head dimension, times two for K and V, times bytes per element). Classic multi-head attention (MHA) sets $H_{kv} = H_q$: every query head owns a private key/value view.

Here is a mistake worth staging deliberately, because you will see it in the wild. Someone reads "24 heads, head dimension 256, bf16" and computes Qwen's cache as $24 \times 256 \times 2 \times 2\ \text{B} = 24\ \text{KiB}$ per token per layer. That is the *MHA* number. It ignores grouped-query attention, and it overestimates by exactly the factor the designers engineered away.

The real figure, derived once in lesson 7.2 and only referenced here, uses the 4 KV heads: 4 KiB per token per caching layer, 64 KiB per token across the 16 full-attention layers, 16 GiB per sequence at the native 262,144-token context. Run the hypothetical MHA variant through the same pipeline and the comparison is stark:

$$
\underbrace{24 \times 256 \times 2 \times 2\ \text{B}}_{\text{same-geometry MHA}} = 24\ \text{KiB}
\quad\text{vs}\quad
\underbrace{4 \times 256 \times 2 \times 2\ \text{B}}_{\text{Qwen's GQA}} = 4\ \text{KiB per token per layer},
$$

a **6× shrink**. Per token that is 384 KiB versus 64 KiB, and at full context a hypothetical 96 GiB per sequence versus the actual 16 GiB. The MHA variant could not hold even a single full-length sequence next to the 54 GB of bf16 weights on an 80 GB accelerator; the GQA design can. The same factor governs decode bandwidth, since every caching layer must *read* the cache at each step.

## MQA: one shared key/value head

**Multi-query attention** (MQA) pushes sharing to the limit: $H_{kv} = 1$. For Qwen's geometry that would mean $1 \times 256 \times 2 \times 2\ \text{B} = 1\ \text{KiB}$ per token per layer. That is 16 KiB per token, about 4 GiB at full context, a 24× shrink from MHA.

The price is in what the model can represent. All 24 query heads must read from one shared key/value subspace, a single way of describing every past token. Query heads can still ask different questions, but they all consult the same index and the same payload. Whether quality survives depends on the model, the scale, and the training recipe; it cannot be read off the architecture diagram.

## GQA: sharing within groups

**Grouped-query attention** (GQA) sits between those two extremes, and Qwen3.8-27B's choice is squarely on it: 24 query heads in 4 groups of 6, each group sharing one K/V head. The groups keep some variety of key/value subspaces while dividing cache and bandwidth by six.

The GQA paper (Ainslie et al.) showed the design can also be *converted into*. Pool an MHA checkpoint's K/V heads group by group, then continue training briefly. The mapping is structural, so two pieces of software must agree on it:

- kernels, the GPU routines that compute attention, must know which query heads read which K/V head;
- checkpoints encode the projection shapes. Recall from [lesson 4.2](/lessons/4-transformer/4.2-self-attention/) that Qwen's K and V projections output 1024 dimensions, 4 heads × 256, against 12288 for Q: 6144 of queries interleaved per head with 6144 of gate (an extra learned signal that scales each head's output).

## MLA: caching a compressed summary

**Multi-head latent attention** (MLA), introduced with DeepSeek-V2, leaves the $H_{kv}$ axis entirely. Instead of caching per-head keys and values, it caches a learned low-dimensional *latent* vector per token, a compact summary from which keys and values can be rebuilt. Attention components are then reconstructed through projections, with decoupled (kept separate rather than compressed together) handling of the RoPE positional part (RoPE, from [lesson 4.7](/lessons/4-transformer/4.7-rope/), encodes position by rotating query and key vectors). Its cache size is set by the latent dimension, not a head count. Its algebra differs too, so the quality-versus-size point it reaches is not on the MHA-GQA-MQA line at all.

Read down the last column and two of this lesson's axes show at once: how many KV heads a layer keeps, and how many layers keep a cache at all. A few readings of the configs need saying. GPT-2 XL and Phi-4 state no head dimension; it is the hidden size divided by the heads (1,600 ÷ 25 = 64 and 5,120 ÷ 40 = 128). DeepSeek-V3's row counts what the DeepSeek-V2 paper says MLA must cache, the latent plus the separate RoPE key. DeepSeek-V3 and GLM-4.5 also declare one multi-token-prediction layer (an extra layer trained to predict a token further ahead), which the table leaves out. The hybrids' other layers keep a fixed-size state instead of a cache: Gated DeltaNet in the two Qwen models, as lesson 7.2 showed for Qwen3.8-27B, and Mamba-2, a state-space layer, in Nemotron; [lesson 4.16](/lessons/4-transformer/4.16-hybrid-layouts/) places both in the family of hybrid layouts. Nemotron's config also counts each of its 23 expert feed-forward blocks ([lesson 4.18](/lessons/4-transformer/4.18-mixture-of-experts/)) as a layer of its own.

:::caveat
Two things this comparison is not. MLA is not "GQA with more compression": its cache contents and reconstruction math are different, and summarizing it as a group count misdescribes the design. And a config file is not an optimization interface. Editing the KV-head count without an actual weight conversion and adaptation procedure does not produce a smaller model; it produces a broken one.
:::

:::insight
These designs move information from per-token memory into shared structure or computation. They do not make information free; they choose where capacity lives and what must be reconstructed on demand.
:::

## Choosing between them in practice

Deployment is the final filter. A smaller cache pays off only when kernels, quantization (storing numbers in fewer bits), and parallel layouts implement the exact variant efficiently; falling back to generic attention code can erase the gain. Compare candidates on cache bytes per token, decode bandwidth, throughput at realistic concurrency (the number of requests served at once), and quality on long contexts. A small-cache design often wins at the *system* level by admitting more concurrent sequences, a gain that single-request benchmarks never see.

Each design trades repeated state for a stronger structural constraint. Qwen3.8-27B's designers took two savings at once: GQA's 6× head-sharing shrink alongside the hybrid layout that limits caching to 16 layers in the first place. The lab after the analogy combines all four axes at once: KV heads, how many layers run attention, cache precision and context.
