Serve Qwen3.8-27B and watch the timings: an 8,192-token prompt is absorbed in about the time it takes to read this clause, then the answer trickles out token by token. Same weights, same GPU, yet the two phases run at speeds separated by orders of magnitude. They are effectively two different machines. **Prefill** processes the prompt and creates state; **decode** consumes that state one token at a time. Knowing which machine is slow tells you which fix can possibly help.

## Prefill: the whole prompt at once

During prefill, every prompt position moves through the network together. The linear layers, which multiply a weight matrix by the input vectors, now multiply it by a whole matrix of activations (the intermediate vectors flowing through the network) with one row per token, so thousands of rows at a time. The 16 attention layers compute interactions among prompt positions and write keys and values, while the 48 Gated DeltaNet layers fold the prompt into their recurrent states.

Accelerators love this shape: plenty of independent work across tokens, heads, and batch entries, all running in parallel. Long prompts can approach the hardware's arithmetic ceiling. Prefill's output is the first token's logits (the scores for every possible next token) plus the populated state. That is why prompt length and kernel efficiency (how well the GPU routines use the hardware) dominate **time to first token**.

## Decode: one token, all the weights

Decode presents the opposite shape: one new position per active sequence per step, through every layer.

When decode feels slow, most people reach for the wrong fix. They assume the GPU has run out of arithmetic and buy more FLOPs (floating-point operations per second). Run the numbers instead, starting with one weight matrix and two cases:

- **Prefill, 8,192 tokens.** Each weight is fetched from memory once and then used for all 8,192 prompt positions.
- **Decode, one token.** Each weight is fetched once and used for exactly one position.

In general, for a weight matrix of $P$ parameters in bf16 (2 bytes each), processing $n$ tokens costs about $2nP$ operations (one multiply and one add per weight per token) against at least $2P$ bytes of weight traffic. The ratio of the two is the **arithmetic intensity**, the useful work done per byte fetched:

$$
I \approx \frac{2\,n\,P}{2\,P} = n\ \text{operations per weight byte}.
$$

Prefill with $n = 8{,}192$ prompt positions performs roughly 8,192 useful operations for every weight byte it fetches. Batch-1 decode, serving a single sequence, has $n = 1$: about one operation per byte. And the bytes are substantial. Qwen3.8-27B's bf16 checkpoint is about 54 GB, and a text decode step streams most of it from memory: every layer's weights, though not the vision tower, and only one row of the input embedding table. So 54 GB is a planning approximation of the bytes per step, not a measurement; actual traffic has to be measured.

One operation per byte is far below what any modern accelerator needs to keep its arithmetic units busy. So the decode step is limited by memory bandwidth (how many bytes per second memory can deliver), not by compute, and adding FLOPs would change nothing. The roofline model (Williams et al.) makes this precise. [Lesson 9.1](/lessons/9-hardware-and-infrastructure/9.1-memory-bandwidth-vs-flops/) divides H100-class memory bandwidth by the 54 GB checkpoint size to get an order-of-magnitude tokens-per-second heuristic, and explains why an exact roofline needs measured active bytes.

The corrected picture explains why every decode remedy is about bytes:

- quantized weights, which store each weight in fewer bytes;
- batching, which reuses each weight read across several sequences;
- speculative decoding, which verifies several tokens per weight read.

## The second stream: cache and state

The second stream of decode traffic is state, and here Qwen3.8-27B's hybrid layout changes the classic picture. In a uniform attention model, every layer reads a KV history (the cached keys and values of all earlier tokens) that grows with context, so decode gets progressively more expensive per token.

In this model only the 16 full-attention layers do that, reading a cache that grows at the 64 KiB per token derived in [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/). Illustratively, at 100,000 cached tokens those layers stream about 6 GiB of K/V per step. The 48 DeltaNet layers instead read and update fixed-size matrix states totaling 144 MiB in the reference float32 path, the same at token ten and token 200,000.

Three-quarters of the depth therefore contributes constant decode traffic. Cost still grows with context, but far more slowly than the layer count alone would suggest, and that flattening is precisely what the architecture bought.

## Batching, and two phases sharing one GPU

Batching changes the arithmetic for both phases. Independent sequences decoded together share each weight read, multiplying useful work per byte. That is why $n$ in the intensity formula is really the number of tokens in flight, not just prompt length.

But batches have costs. Waiting to form one raises queue latency, and sequences finish at different times. Continuous batching ([lesson 7.8](/lessons/7-inference-and-efficiency/7.8-pagedattention-and-continuous-batching/)) replaces a fixed rectangle of requests with a shifting set of token steps, which the scheduler must keep fair.

The phases also interfere. A large prefill monopolizes compute and bandwidth exactly while decode requests need their steady cadence. Two remedies exist. Chunked prefill cuts a long prompt into pieces and interleaves them between decode steps. Some deployments disaggregate the phases, running prefill and decode on separate workers and paying to transfer the KV cache between them to avoid the contention.

:::caveat
"Compute-bound prefill, bandwidth-bound decode" is a first-order model, not a law. Tiny prompts, very large decode batches, quantized kernels, and extreme context lengths (where the 16 attention layers' cache reads rival the weight reads) can all move the bottleneck. Measure per phase before optimizing.
:::

## Measuring each phase on its own

Metrics should respect the split. Record queue time, prefill duration, and prompt throughput separately from decode step time and output throughput. Report them as percentiles (for example the 99th, the latency that 99 of every 100 requests stay at or below), broken down by prompt length and concurrency. A single average can hide a scheduler that feeds bulk jobs while starving interactive users.

Put the two halves together: a parallel prompt processor hands state to a latency-sensitive token engine that mostly moves memory. Everything in the rest of this track (IO-aware attention, paged caches, quantization, speculative decoding) attacks one side or the other of that boundary.
