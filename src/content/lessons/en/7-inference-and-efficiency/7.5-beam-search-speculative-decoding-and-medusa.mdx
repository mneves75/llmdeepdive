[Lesson 7.3](/lessons/7-inference-and-efficiency/7.3-prefill-vs-decode-two-different-machines/) left decode in an uncomfortable place: at batch 1, Qwen3.8-27B streams most of its weights from memory for every token it emits, roughly 54 GB by checkpoint size (a planning approximation, as that lesson explains). The chain is serial, since token $t+1$ cannot be finalized before token $t$, and that seems to force the price on every token.

This lesson covers methods that spend extra parallel work around that chain, and they optimize two very different things. **Beam search** buys output *quality*. **Speculative decoding** and **Medusa** buy *speed*, by getting more than one token out of each expensive weight read. Qwen3.8-27B arrives with its own native version of that speed trick.

## Beam search: several candidates, one better sequence

Beam search comes first, briefly, because it is the odd one out. Instead of one partial sequence it keeps $b$ candidates, called beams. At each step it extends each beam with plausible next tokens, scores every extension by cumulative log-probability (the sum of the logarithms of each token's probability, which is the logarithm of the whole sequence's probability), and prunes back to the best $b$. The scores need length normalization, or short outputs win by default, because every added token can only lower the total.

Beam search shines when sequence-level likelihood matters: constrained transduction (turning one sequence into another under fixed rules, such as translation) and some structured tasks. It disappoints in open-ended dialogue, where the beams collapse into near-duplicate, blandly probable text. Its width multiplies compute and KV-cache use; beams share their common prefixes through copy-on-write block tables, which copy a cache block only when one beam changes it ([lesson 7.8](/lessons/7-inference-and-efficiency/7.8-pagedattention-and-continuous-batching/) covers block tables). It is a search algorithm, not an acceleration.

## Speculative decoding: guess cheaply, check in one pass

Speculative decoding attacks latency directly. It pairs two models:

1. A cheap **draft model** proposes a block of $k$ future tokens, one after another, as any model would.
2. The expensive **target model**, the one whose output you want, evaluates all $k$ positions in a single pass. That pass has the same parallel shape as a short prefill, so one weight read is amortized over $k$ candidates.
3. An acceptance rule compares the draft's probability with the target's probability, token by token. Accepted tokens commit. At the first rejection, the suffix that depended on it is discarded, and a corrected token is sampled from an adjusted distribution.

Done properly (Leviathan et al.), the output is distributed *exactly* as if the target had decoded alone under the same sampler. That guarantee is stronger than merely checking that both models agree on the argmax, their single top token.

## How many tokens per pass?

An illustrative back-of-envelope estimate shows the size of the gain. It makes one simplifying assumption, as the speculative-decoding paper does: each drafted token is accepted independently, with the same probability. Real acceptances are correlated, so treat the result as a rough guide. Suppose each drafted token is accepted with probability 0.8 and the draft proposes 4 tokens at a time. In general, with per-token acceptance probability $\alpha$ and block length $k$, the expected number of tokens committed per target pass is

$$
\mathbb{E} = \frac{1-\alpha^{k+1}}{1-\alpha},
$$

counting the bonus token the target itself supplies. At $\alpha = 0.8$ and $k = 4$: $0.8^{5} = 0.32768$, so $\mathbb{E} = (1 - 0.32768)/0.2 \approx 3.36$ tokens per pass. Each weight read, roughly 54 GB by checkpoint size, now yields three-plus tokens instead of one.

The figures are illustrative, not Qwen benchmarks. Real acceptance rates depend on prompts, sampler settings, and how well the draft mimics the target.

## Why more computation makes decode faster

A natural guess is that speculative decoding saves computation. It does the opposite: it *increases* total FLOPs. The draft runs on every token, the target re-scores every proposal, and every rejected suffix is pure waste. If decode were compute-bound, speculation would make it slower.

It wins because lesson 7.3 showed that decode is bandwidth-bound. The arithmetic units sit idle while the weights stream in, so the extra verification math costs almost nothing in time. Meanwhile the scarce resource, bytes moved per committed token, drops by the acceptance factor.

Getting this right tells you when to reach for the technique: latency-sensitive serving with small batches. At high batch sizes the weight read is already amortized across many sequences, and speculation's appeal fades.

## Medusa and Qwen's built-in drafter

The draft model is a balancing act. Too weak, and its proposals get rejected. Too large, and proposing costs what verifying saves. And a separate model must be hosted, scheduled, and kept compatible with the target.

**Medusa** (Cai et al.) removes the separate model by bolting lightweight decoding heads onto the target itself. Each head predicts the token at a different future offset. Together the heads propose a small tree of continuations, which one verification pass prunes to an accepted path. The heads must be trained against the exact base checkpoint: change the base, and you retrain the heads.

Qwen3.8-27B offers a related option: the model card states it was trained with **multi-token prediction** (MTP) over multiple steps, so the checkpoint itself can propose several future tokens. At inference this works as a native draft source, with no second model to deploy. Serving stacks that support it (the model card lists vLLM and SGLang among its runtimes) can verify MTP proposals exactly as they would a draft model's.

## Measuring a speedup behind a correctness gate

A public RTX 5090 campaign shows why this must be measured behind a correctness gate. Its canaries are fixed test prompts whose correct behavior is known in advance. In that report, a stock accelerated stack with TurboQuant 4-bit KV (a KV cache stored at 4 bits per number) and MTP3 launched but failed the exact-output, JSON, tools, coding, and multi-turn canaries. So the speed result was held rather than published as a win.

After patch #40914, the same frozen canaries passed. The matched C1 run then reported 151.27 tok/s true decode, TTFT (time to first token) 0.920 s, E2E (end-to-end time) 7.69 s, and 830 of 834 MTP proposals accepted (99.52 percent). That is a useful case study for this one stack, not a universal Qwen number. The lesson is correctness before speed, and then acceptance statistics and workload shape reported beside the throughput figure.

:::caveat
Any acceleration claim must state the target model, draft or head configuration, hardware, batch size and concurrency, prompt and output lengths, sampler settings, and acceptance statistics. A single low-load latency demo predicts nothing about production throughput.
:::

The bookkeeping is the hard part that nobody sees. Tree-structured candidates share a prefix and diverge later. Attention masks must keep branches from reading each other. Accepted states commit in order, while rejected branches release their cache blocks. A bug here produces plausible but wrong tokens, so compare the distribution of outputs against baseline decoding. Streaming clients must also tolerate bursts: when four tokens are accepted at once, they arrive at once.

What separates the three methods is purpose. Beam search pays for multiple hypotheses to *choose* a better sequence. Speculation pays a proposer to expose parallel work, while the target stays authoritative over the distribution. Medusa moves the proposer into the architecture, and Qwen3.8-27B's MTP training ships a proposer inside the checkpoint, turning a serving trick into a property of the model itself.
