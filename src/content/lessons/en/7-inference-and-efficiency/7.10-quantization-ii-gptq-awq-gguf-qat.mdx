Search a model hub for quantized builds of Qwen3.8-27B and you meet a wall of suffixes. Community quantizations of this model circulate across the llama.cpp/GGUF, Ollama, LM Studio, and MLX ecosystems, maintained by those communities rather than by the model's authors. The names on those artifacts mix three different layers:

- an **algorithm** that chooses the approximate values;
- a **format** that stores the tensors and metadata in a file;
- a **runtime** whose kernels (GPU or CPU routines) consume the result.

GPTQ, AWQ, GGUF, and QAT each live at a different layer, and choosing well begins by separating their jobs. [Lesson 7.9](/lessons/7-inference-and-efficiency/7.9-quantization-i-int8-int4-the-basics/) covered the basic mechanics of scales, rounding, and groups; this lesson is about the methods built on top of them.

## Choosing the values after training: GPTQ, AWQ and imatrix

**GPTQ** is a post-training weight-quantization method. It starts from the trained bf16 checkpoint and a set of calibration inputs, sample prompts run through the model to see how it behaves. It then quantizes the weights column by column. Along the way it uses approximate second-order information, an estimate of how errors in different weights interact, to compensate reconstruction error: the gap between the layer's outputs before and after quantization. Later weights adjust to absorb damage done by earlier rounding. That preserves layer outputs far better than rounding each weight independently to its nearest value. Implementations expose bit width, group size, and ordering choices.

**AWQ**, activation-aware weight quantization, observes activations on calibration data. It looks for the small fraction of weight channels that matter most to the observed outputs, then protects them via scaling before the low-bit conversion. The activation data informs how weights are treated; the shipped artifact is still weight-only and low-bit.

Both GPTQ and AWQ are **post-training quantization** (PTQ): there is no retraining, so quality depends heavily on calibration coverage. A set of short English prompts may not preserve behavior on code, other languages, or Qwen's very long contexts.

A third member of the same family is the one you will actually see named on the Hub. An **importance matrix**, `imatrix`, is produced by running calibration data through the model and accumulating, per tensor column, the sum of squared activations passing through it. The quantizer then weights its error by that statistic, spending scarce precision on the columns the corpus exercised hardest. It measures activations rather than per-weight sensitivity. And it is a measurement rather than a format, so it can be applied underneath several of them. [Lesson 7.13](/lessons/7-inference-and-efficiency/7.13-choosing-and-judging-a-community-quant/) works through the artifacts it produces and the distinction it is most often confused with.

## QAT: training with the rounding in the loop

**QAT**, quantization-aware training, moves the effort earlier. Fake-quantization ops round and clip inside the training forward pass, so the model sees the rounded values while it learns. Meanwhile higher-precision master weights receive approximate gradients, so the optimizer steers values away from fragile rounding boundaries. QAT costs training compute and needs a recipe matched to the deployment format. In return, it can recover quality where one-shot PTQ struggles at aggressive bit widths.

## GGUF: a container, not an algorithm

**GGUF** is not an algorithm at all. It is the container ecosystem of llama.cpp-family runtimes: one file carrying model metadata, tokenizer information, and tensors in any of a ladder of quantized types, from 8-bit down past 4-bit. Saying "a GGUF of Qwen3.8-27B" says nothing about quality until you name the tensor type, the tool that produced it, and the source checkpoint.

The file sizes themselves show the layering. Pure 4-bit codes for a rounded 27 billion parameters would occupy $27\text{e}9 \times 4 / 8 = 13.5$ GB. At the pinned community revision, the Q4_K_M **text-model** file is exactly 17,106,773,984 bytes: 17.1 GB, or 15.93 GiB. Group metadata and tensors retained at higher precision account for the gap.

Do not reverse that file size through the marketed 27B count and call the result exact bpw (bits per weight). The marketed count is rounded and includes the vision tower, while the GGUF is the text model. The multimodal projector, the piece that connects the vision tower to the text model, is a separate roughly 0.93 GB file.

## Conversion only loses information

It is also easy to assume that conversion is free. Repackaging bf16 weights into a 4-bit format hands the algorithm the best available source. Requantizing an already 4-bit artifact into another format starts from values that were rounded and clipped once. The discarded precision is gone, and errors compound. A container can change; information cannot return. Keep provenance (a record of where each file came from) and hashes for the original checkpoint and every derived artifact.

## What quality to expect

How much quality do the rungs cost on this model? Be honest about the uncertainty. No dedicated technical report exists for Qwen3.8-27B, and community quantizations ship without standardized evaluations, so treat any specific perplexity or benchmark delta you find as unverified. The qualitative shape is stable across models:

- 8-bit weight-only is usually hard to distinguish from bf16;
- mainstream 4-bit recipes give up measurable but often acceptable quality;
- below 4 bits, degradation grows quickly and unevenly.

The damage hits low-margin decisions first, where the right token only narrowly beat the wrong one: rare tokens, structured output, long-context retrieval. It shows there before the averages move. Evaluate the artifact on your tasks and languages before trusting it.

:::warning
Model formats are a supply-chain boundary. Community quantizations are third-party derived artifacts, not vendor releases. Prefer non-executable tensor containers, verify hashes and licenses, reject inconsistent shapes or metadata, and bound allocations before loading untrusted files.
:::

:::caveat
The runtime layer has the final word. A server can load a GPTQ or AWQ file yet fall back, without telling you, to dequantized floating-point matrix multiplications, keeping the small download and losing the speed. And for a brand-new hybrid architecture like this one, kernel support for each format arrives unevenly. Measure resident memory, selected kernels, and tokens per second on your hardware rather than trusting the label.
:::

In one line each: GPTQ reconstructs with error awareness, AWQ protects what activations prove salient, QAT lets training adapt to deployment error, and GGUF packages the result for compatible runtimes. Algorithms create approximations, formats transport them, and kernels turn them into speed.
