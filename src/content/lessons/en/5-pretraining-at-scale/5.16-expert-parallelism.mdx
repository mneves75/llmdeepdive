## The bytes, counted

[Lesson 4.18](/lessons/4-transformer/4.18-mixture-of-experts/) split the feed-forward block into experts and noted the bill: every MoE layer sends each token to the GPUs holding its experts and brings the results back. This lesson prices that exchange.

Start with one token, one layer, top-8, hidden width 5,120, bf16. Each copy of the token is 5,120 values of 2 bytes, 10,240 bytes, and the token sends one copy per selected expert:

$$
8 \times 5{,}120 \times 2 = 81{,}920 \text{ bytes} = 80 \text{ KiB}.
$$

Across 64 layers that is 5 MiB per token, and a 2,048-token micro-batch sends 10 GiB per forward — one way, before the combine sends anything back.

<Figure id="moe-all-to-all-bytes" />

Two facts make that number matter. Inside a node the copies travel on NVLink, at hundreds of gigabytes per second. Between nodes they cross the cluster fabric, where the handbook's measured all-to-all bus bandwidth ran 77.14 GB/s on two nodes, 39.25 on four and 30.91 on eight. The same bytes cost very different time depending on where the experts sit.

On one node, the handbook traced a single step of a 7B-A1B MoE and found half of it spent in all-to-all that nothing overlapped — with the router still sending uneven loads. Forcing an even distribution in an otherwise identical run cut that iteration's time by 40%. So before treating the network as the problem, check the load — [lesson 5.14](/lessons/5-pretraining-at-scale/5.14-keeping-experts-busy/) is the cheaper fix.

## Expert parallel size

**Expert parallelism** (EP) spreads the experts of a layer across ranks. Megatron forms each EP group from consecutive ranks by default, so an EP size that divides a node's GPU count keeps every exchange inside the node. Our nodes hold eight GPUs, so EP8 stays on NVLink and EP16 spans two nodes.

The difference is not small. In the handbook's comparison, EP16 across two nodes ran 59% below EP8 within one node — though those runs also used different nodes and a different number of micro-batches per step, which is why the book presents it as an indication rather than a controlled result.

The practical sequence is: fit the experts inside a node, add data-parallel replicas as you add nodes, and time both placements at your target node count before committing. A larger EP reduces the weights each GPU holds but widens the group every token may have to reach.

:::warning
Check the transport before blaming the fabric. NCCL can fall back to TCP sockets while the job asks for the fabric: the handbook reports two runs that set the EFA variables and still logged "Using network Socket", running about 25 times slower than its EP16 run (1.7 against 42.0 TFLOP/s). `NCCL_DEBUG=INFO` prints the chosen transport on a "Using network" line; Libfabric or IB is the fabric, Socket is the fallback.
:::

## Overlapping the exchange

The exchange is on the critical path because it sits between two computations: the router reads attention's output, so dispatch cannot start earlier, and the next layer reads the MoE's output, so nothing starts until combine ends. Three ways break that dependency.

- **A parallel block** hands attention and the MoE one shared input, so the exchange can start while attention is still working. Combine has less room: only work remaining in the same layer can cover it.
- **A shortcut-connected MoE** also hides combine, behind the dense compute that runs beside it. A LLaMA2-style model wired this way trained 1.14 times faster than a standard top-2 MoE on one node of eight GPUs, and a GPT-2-sized one gained 1.12, and LongCat-Flash reports its exposed communication falling from 25.3% to 8.4%.
- **Interleaving micro-batches** needs no architecture change: one micro-batch's forward runs beside another's backward, so one's all-to-all hides behind the other's compute. The handbook measured up to 35% more throughput on two nodes, at a cost of 5 to 10 GB more reserved memory per rank.

:::caveat
The overlap and activation recomputation compete for the same memory and, in Megatron, full recomputation must be off for the overlap to run. If the run only fits with full recompute, the overlap is not available without a finer grained memory plan — selective recompute plus offloading the large inputs — which is a different trade than "turn on the flag".
:::

## Capping where tokens go

A token's top-k experts can sit anywhere. **Group-limited routing** restricts where it may look first: DeepSeek-V3 scores each node by summing the token's top-2 expert scores there, keeps 4 of 8 nodes, and then picks the top-k among the experts on them, so no token reaches more than four nodes.

What that saves depends entirely on the dispatcher. Megatron's `alltoall` dispatcher sends one copy per selected expert, so capping nodes only moves the copies onto fewer nodes: if a token still reaches experts outside its own node, the same number of copies crosses the fabric. With the DeepEP dispatcher, a token sends one copy per destination node and that node forwards it internally, so capping nodes caps bytes. Recent models mostly dropped the cap — DeepSeek-V4 removed V3's limit — while Ling and Ring keep it.

:::insight
The cap changes which experts a token may choose, so it changes what the model learns, for a small quality cost. That is a different kind of change from a faster kernel: try every recommendation that leaves training unchanged before you spend quality on the network.
:::

## Dropping or replicating

The rank holding a hot expert finishes last. There are two answers.

**Drop.** A **capacity factor** caps how many tokens each expert accepts, keeping the highest-probability ones; the rest skip that expert. It bounds the memory and the busiest rank's work, and it costs loss: Pangu compared a 20B MoE at capacity factor 1.5 against a run that dropped nothing: the dropless run's loss stayed lower throughout, and the distance widened as experts were added. At factor 1.5 that team saw about 6% of tokens dropped in a 20B model and about 8% in a 718B one.

**Replicate.** Copy the hot expert to a quieter rank. Each copy costs weights in the forward pass and a gradient reduction back in the backward, so a planner makes as few as possible. The handbook reports UltraEP, replanning per micro-batch and layer, taking the busiest rank of three training runs from 1.30–2.86 times the mean down to 1.01–1.03. Serving does the same with longer-lived copies.

Keep dropless as the default. A capacity factor is for a run short of memory whose imbalance cannot be fixed more cheaply, and fine-tuning returns to dropless because dropped tokens fall inside instruction-response pairs.

## Precision

The Megatron Core team puts the end-to-end gain for large MoE training between about 10 and 25%.

The split matters. The linear layers' forward and both backward multiplications run in FP8; outside them, the norms, attention's core, the embedding and output head, and the router keep higher precision. The router is not negotiable: quantization noise there changes which experts a token reaches. DeepSeek trained 16B and 230B MoEs in FP8 for about a trillion tokens each and stayed within 0.25% relative error of bf16; The handbook reports Ling-1T holding the same bound over 900B tokens with about 15% more MFU.

Four bits is the next step, and the first large MoEs have been pretrained there. Nemotron 3 Super ran 25T tokens in NVFP4 for most linear layers, holding bf16 for the final 15% of layers, the attention projections, the embeddings and the MTP blocks. The handbook notes the cost signal: under NVFP4, exactly-zero expert weight-gradient elements grew to 7% of parameters by the end, and switching an ablation back to bf16 restored the count.

## What this does not establish

- The bandwidth, speedup and percentage figures are measurements on named hardware and shapes. A different node count has a different baseline, which is why the handbook's own policy is to compare each allocation with a baseline at the *same* node count.
- The fixes do not add up. Each comes from its own setup; test them one at a time.
- FP8's loss bound is a measurement on three runs, not a guarantee for another model or recipe.
- Nothing here says which combination is right for a given cluster. It says how each choice spends traffic, precision or tokens, and what it costs in return.
