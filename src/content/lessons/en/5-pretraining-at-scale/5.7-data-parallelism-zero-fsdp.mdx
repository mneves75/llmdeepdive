Training a 27-billion-parameter model needs far more memory than running it. Under the illustrative recipe this lesson uses, the persistent training state alone is several times what one 80 GB GPU holds. This lesson shows how a training job spreads that memory across many GPUs, and what the spreading costs.

## How much memory does training need?

Qwen3.8-27B ships as safetensors files (the weight-file format on the model page) stored in bf16, totalling about 54 GB. That is a fact about checkpoint storage. It is not a training-memory recipe, and not proof that the full serving stack fits a nominal 80 GB device: the KV cache, activations (the intermediate values each layer produces), runtime workspaces, and fragmentation also consume memory. Training adds further persistent and temporary categories, and their dtypes (number formats) must be stated rather than inferred from the released checkpoint.

[Lesson 9.3](/lessons/9-hardware-and-infrastructure/9.3-kv-cache-sizing-and-memory-budgets/) owns the course-wide derivation of this model’s memory budget. This lesson imports one explicit scenario from it:

- bf16 parameters and bf16 gradients (the per-weight corrections from backpropagation),
- fp32 master weights, a 32-bit copy of the weights that the optimizer updates,
- two fp32 AdamW moments, the running averages the AdamW optimizer ([lesson 2.7](/lessons/2-neural-network-fundamentals/2.7-optimizers/)) keeps for every weight.

Together that is about 432 GB of persistent state for 27 billion parameters, before activations and workspaces. It is a common conservative recipe, not a claim about Qwen’s undisclosed training run and not a universal requirement; pure-bf16 and alternative optimizer-state policies exist. The ZeRO arithmetic below is conditional on that scenario, so the sharding stages can be compared consistently.

## What does data parallelism do?

**Data parallelism** is the starting point, and it does nothing about this memory. Give several workers, called ranks, identical replicas of the model and different examples. If rank $r$ computes gradient $g_r$, a collective reduction (an all-reduce, in which every rank ends up with the same combined result) forms the mean that every replica uses. Starting from equal weights and applying equal updates keeps the replicas synchronized.

The batch the optimizer sees grows with the number of ranks. Take a toy setup: 8 ranks, each processing a local microbatch of 4 sequences of 2,048 tokens, with 2 accumulation steps (forward and backward passes whose gradients are summed before one update). One update then covers 8 × 4 × 2 × 2,048 = 131,072 tokens. In general, with $P$ ranks, local microbatch $b$, sequence length $T$, and $a$ accumulation steps, the global batch holds $PbaT$ tokens. So adding workers changes the optimization, not merely the speed. And under ordinary replication, every rank still holds the full assumed persistent state.

## How do ZeRO's three stages cut memory?

**ZeRO** removes that redundancy in three stages. Each stage shards (splits into equal slices, one per rank) one more category of state. Compute the effect on a concrete cluster: 64 ranks and the illustrative 432 GB budget imported from lesson 9.3.

Stage 1 shards optimizer state only. Each rank keeps full bf16 parameters and gradients but $1/64$ of the optimizer: $324/64 = 5.06$ GB. Per-rank persistent state becomes $54+54+5.06 \approx 113$ GB. That still cannot fit on 80 GB cards.

Stage 2 also shards gradients: $54/64 = 0.84$ GB. Now $54+0.84+5.06 \approx 59.9$ GB. This fits, barely. About 20 GB remains for activations, temporaries, fragmentation, and communication buffers, on a model with hidden size 5120 and long sequences. [Lesson 5.10](/lessons/5-pretraining-at-scale/5.10-gradient-checkpointing/) will show that this is not much.

Stage 3 shards the parameters as well, so persistent state is the whole budget divided by the world size (the total number of ranks): $432/64 = 6.75$ GB per rank. The full parameters of a module exist only temporarily, materialized just before they are needed.

:::warning
The misconception this lesson exists to kill is that serving memory predicts training memory. It does not: under the stated illustrative recipe, the ratio of persistent state is about eight to one. Worse, the intuition fails in the reassuring direction. The model loads fine, a short forward pass runs fine, and the out-of-memory failure arrives at the first optimizer step, after the job has already consumed cluster time. Compute the full budget (parameters, gradients, master weights, both moments, activations, temporaries) before requesting nodes.
:::

## How does FSDP gather parameters just in time?

**Fully Sharded Data Parallel** (FSDP) is that stage-3 pattern implemented around the model's modules. Before a module's forward pass, the ranks run an all-gather: each sends its shard of that module's parameters, so every rank reconstructs the full parameters locally. After use, they can be dropped back to shards. During the backward pass, communication reconstructs parameters again as needed, and a reduce-scatter (sum the gradients, then hand each rank only its own slice) sends gradient shards to their owners. Where ordering and the network permit, that communication overlaps with computation.

The wrapping policy, meaning how the model is cut into sharded units, decides how well stage 3 actually performs. If a unit is too large, the all-gather needs a lot of peak memory and leaves little room for overlap. If it is too small, collectives become numerous and their latency dominates. Transformer-block boundaries are the usual choice because they place substantial compute between communications.

This model offers an unusually natural alternative unit. Its 64 layers are organized as 16 repeating super-blocks of three Gated DeltaNet layers followed by one full-attention layer. Wrapping the decoder per super-block gives 16 coarse units with identical layer composition; the embeddings, the output head and the vision tower sit outside them and need their own wrapping and memory accounting. Wrapping per layer gives 64 finer units of two distinct shapes. Either is defensible, and only measurement decides.

:::caveat
Sharding lowers persistent memory but does nothing for activations. Long sequences, an FFN intermediate of 17,408, attention intermediates, temporary all-gather buffers, fragmentation, and communication workspaces can still cause out-of-memory failures on a job whose persistent budget looks comfortable. Lesson 5.10 attacks that category directly.
:::

## What changes for checkpoints and failures?

Checkpointing becomes distributed. Gathering the full state dict (every named tensor of the model and optimizer) onto one machine may exceed host memory, so each rank writes the tensors it owns, alongside metadata that reconstructs global names and shapes. Resuming at a different world size requires a format and loader that support resharding. Saving the weights alone is not enough for exact continuation: optimizer moments, scheduler position, loss scaler, random-number state, and data-loader cursor all matter. Under the illustrative recipe, the optimizer state is the largest category in the checkpoint.

Failures must also be handled collectively. If one rank hits bad data while the others enter an all-reduce, the job hangs instead of raising a clean exception. Timeouts, coordinated error propagation, rank-aware logs, and reproducible batch identifiers are necessities, not niceties.

Network topology shapes the design too. Fast links inside a node and slower links between nodes favour hierarchical collectives, and a stage-3 job whose all-gathers cross a slow network can spend more time moving parameters than using them.

The stable picture is replicated computation over different data, with increasingly sharded state behind it. Data parallelism buys throughput. ZeRO and FSDP remove redundant memory. Neither creates capacity without a cost: the price is communication volume, scheduling complexity, and much more demanding checkpoint and failure handling.
