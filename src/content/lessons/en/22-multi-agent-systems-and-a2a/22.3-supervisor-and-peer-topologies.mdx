Four children run at once for one purchasing run. The first reserves invoice number INV-0001. The second finds that PO-1003's record is missing and raises an error. The third is still waiting on a slow supplier portal for PO-1004. What state is the run in now, who decides it, and what happens to INV-0001?

Without an owner the answer is "whatever happened last". This lesson gives each question a defined answer, in code that the tests run deterministically: no sleeps, no real threads racing, and every interleaving written out step by step.

## Who owns the run?

A *topology* is the shape of who talks to whom. In a *supervisor* topology one coordinator hands out the work, collects the results and decides the run's final state. The orchestrator-workers design of [lesson 22.1](/lessons/22-multi-agent-systems-and-a2a/22.1-decide-whether-to-divide-work/) is one. In a *peer* topology agents work side by side, reading and writing shared state or waiting on each other's output, and no single agent decides for all.

Neither is safer by default. A supervisor is one place for cancellation and cleanup, and also one place that can stall: Anthropic's research system runs its subagents synchronously, which "simplifies coordination, but creates bottlenecks." Peers avoid that bottleneck but must guard shared state and waits themselves. The rest of the lesson takes the peer problems first, then the supervisor's.

## Peers sharing state lose updates

Two workers each add an evidence reference to the same `RunState`. Each reads the run, adds its reference and writes the run back. If both read before either writes, the second write replaces the first, and the first worker's evidence is gone with no error. Berenson and colleagues name this the *lost update*, which "occurs when transaction T1 reads a data item and then T2 updates the data item (possibly based on a previous read), then T1 (based on its earlier read value) updates the data item and commits." The test `test_a_plain_shared_dict_loses_an_update` shows it on an ordinary dictionary.

The fix is the compare-and-swap save of [lesson 14.3](/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/): a write names the version it read, and the store refuses it with `StaleWrite` if someone committed since. Refusing is half the answer. The worker must then read again and retry, a bounded number of times:

```python
# file: examples/agent-engineering/src/agentlab/multiagent/topology.py
def add_evidence(store: CheckpointStore, run_id: str, ref: EvidenceRef, *, attempts: int = 3, between: Callable[[], None] = lambda: None) -> RunState:
    """Append ``ref`` to the run's evidence without losing a concurrent append.

    ``between`` runs after the read and before the write; tests use it to
    place another peer's commit exactly there.
    """
    for _ in range(attempts):
        current = store.load(run_id)
        if current is None:
            raise KeyError(run_id)
        between()
        changed = RunState.model_validate({**current.model_dump(), "evidence": (*current.evidence, ref)})
        try:
            return store.save(changed, expected_version=current.version)
        except StaleWrite:
            continue  # someone committed after our read: read again, never overwrite
    raise Contention(f"{run_id}: lost the write race {attempts} times")
```

`between` is a hook that runs after the read and before the write, so a test can place another peer's commit exactly there. With it, `test_add_evidence_rereads_after_a_conflict_and_keeps_both` ends with both references in the run. If another writer wins every time, the loop gives up with `Contention` after its attempts instead of spinning forever, and the caller decides what to do.

## Peers waiting on each other

Suppose the researcher waits for the reviewer to say which report format it wants, the reviewer waits for the coder's report and the coder waits for the researcher's findings. Each is waiting for another, so none ever starts. That is a *deadlock*.

Draw an arrow from each peer to every peer it waits on, and you have a *wait-for graph*. A deadlock is a cycle in that graph. `plan_peers` walks the graph before anyone starts. If the walk returns to a peer still on its current path, it raises `DeadlockRefused` with the cycle, here researcher, reviewer, coder. Otherwise it returns an order in which every peer starts after the peers it waits on. A peer waiting on someone nobody starts is an error too.

This is a narrower rule than "no loops". [Lesson 14.2](/lessons/14-agent-architecture-and-state/14.2-states-dags-branches-and-loops/) showed that a run's own state machine may loop, bounded by a step budget. What must stay acyclic is the set of waits between peers, because a cycle there blocks every peer in it, and a step budget would only end the run after wasting it.

## A supervisor's fan-out and fan-in

*Fan-out* is starting several children at once; *fan-in* is collecting their results into one outcome. The supervisor marks each child as required or optional and gives it an optional `undo`, a *compensation*: an action that reverses what the child did, such as releasing a reserved invoice number.

```python
# file: examples/agent-engineering/src/agentlab/multiagent/topology.py
async def supervise(children: list[Child], *, cleanup_attempts: int = 2) -> FanIn:
    """Run children concurrently; a required failure stops the rest and undoes what finished.

    shortcut: a child that swallows cancellation and keeps running would make
    this wait for it; production code puts a deadline on the cancel too.
    """
    by_task = {asyncio.create_task(child.run(), name=child.name): child for child in children}
    pending = set(by_task)
    results: dict[str, object] = {}
    failed: dict[str, str] = {}
    cancelled: list[str] = []
    while pending:
        done, pending = await asyncio.wait(pending, return_when=asyncio.FIRST_COMPLETED)
        for task in sorted(done, key=lambda t: children.index(by_task[t])):
            child = by_task[task]
            if task.exception() is None:
                results[child.name] = task.result()
            else:
                failed[child.name] = repr(task.exception())[:200]
        if any(by_task[t].required for t in done if t.exception() is not None):
            for task in pending:
                task.cancel()
            await asyncio.gather(*pending, return_exceptions=True)  # let each child run its cleanup
            cancelled = [child.name for task, child in by_task.items() if task in pending]
            pending = set()
```

The run ends in one of three defined states. *Completed*: every child succeeded. *Partial*: only optional children failed; their errors are recorded and the other results are kept. *Failed*: a required child failed. Then the supervisor cancels the children still running and waits for them to finish their cleanup. Python's documentation describes what cancelling does: "asyncio.CancelledError will be raised in the task at the next opportunity," and it recommends that coroutines "use try/finally blocks to robustly perform clean-up logic." In the opening case, the PO-1004 child is cancelled inside its wait, and its `finally` block releases its lock.

## Cleanup has a bound too

After a required failure, every finished child with an `undo` is compensated: INV-0001 is released. The run's history still records that the reservation happened, because hiding it would make the audit lie. A compensation can fail too, for example when the numbering service is down. It gets a fixed number of attempts (`cleanup_attempts`, two by default). A child whose undo kept failing goes to `cleanup_pending` instead of being retried forever. That list is work for a person or a reconciler, the job [lesson 14.4](/lessons/14-agent-architecture-and-state/14.4-replay-and-side-effects/) gave to reconciliation of unknown outcomes.

:::caveat
Cancellation in asyncio is cooperative. A child that catches `CancelledError` and keeps running would make `supervise` wait for it, as the function's docstring says; production code puts a deadline on the cancel as well. Undo also only reverses what can be reversed: an email that was sent stays sent.
:::
