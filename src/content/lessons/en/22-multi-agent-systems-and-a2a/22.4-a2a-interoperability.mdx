The purchase-records lookup now belongs to another team. It runs as their agent, in its own process, started on its own schedule. The purchasing assistant cannot import its code; it can only send it requests. To get the total of PO-1001 the two sides must agree on how to find each other, how to ask, how an answer looks and which edition of the rules they follow. And when they disagree, both sides must notice before anything happens.

That agreement is the job of A2A, the *Agent2Agent protocol*. This lesson pins A2A specification v1.0.1, released on 2026-05-28, and builds a small part of it. Everything below is a deliberately bounded subset for learning, not a compliant implementation.

## A2A and MCP do different jobs

A2A's own comparison page puts the line here. MCP "defines how an AI agent interacts with and utilizes individual tools and resources, such as a database or an API." A2A "focuses on enabling different agents to collaborate with one another to achieve a common goal." In track 15 the MCP server offered tools to one agent, which decided when to call them. Here the remote side is an agent that receives a task and decides for itself how to do it.

A few terms come from the specification. The *A2A client* sends requests; the *A2A server* is the remote agent. An *Agent Card* is a JSON document in which the server describes itself. A *Message* is one turn, made of *Parts*: text, structured data or a file. A *Task* is the unit of work, with an id the server generates and a state such as `TASK_STATE_COMPLETED`. An *Artifact* is a task's output. The specification separates the last two on purpose: "Messages SHOULD NOT be used to deliver task outputs. Results SHOULD BE returned using Artifacts associated with a Task."

Both protocols carry their version on every request, and neither keeps a session in which a version was agreed once. MCP revision 2026-07-28 puts it in each request's `_meta`, as [lesson 15.2](/lessons/15-tool-contracts-and-mcp/15.2-json-rpc-and-protocol-lifecycle/) showed. A2A puts it in an `A2A-Version` header.

## Discovery: the Agent Card

A client finds a server's card at `/.well-known/agent-card.json`. The card from the fixture names the agent, describes it, lists one skill, `lookup-purchase-order`, and declares its capabilities: no streaming, no push notifications, no extended card. It also declares a bearer-token security scheme and one interface: the URL, the binding `JSONRPC` and the protocol version `1.0`. The proto file at the tag is the normative data model (section 1.4), so the card carries every field the proto marks as required, with the camelCase names that section 5.5 asks for.

The specification's rule for the client is to pick the first interface it supports. This client adds one rule of its own:

```python
# file: examples/agent-engineering/src/agentlab/multiagent/a2a.py
def choose_interface(card: dict, *, origin: str) -> dict:
    """The first JSON-RPC interface at protocol 1.0, and only on the origin the card came from."""
    offered = card.get("supportedInterfaces") or []
    for interface in offered:
        if interface.get("protocolBinding") == "JSONRPC" and negotiated(interface.get("protocolVersion")) == PROTOCOL_VERSION:
            if _origin(interface.get("url", "")) != _origin(origin):
                # A card can name any URL; following it blindly would hand the bearer token to that host.
                raise IncompatibleAgent(f"the card points its interface at {_origin(interface.get('url', ''))[1]!r}")
            return interface
    raise IncompatibleAgent(f"no JSONRPC interface at {PROTOCOL_VERSION}; offered {[(i.get('protocolBinding'), i.get('protocolVersion')) for i in offered]}")
```

A card that offers only protocol 0.3 is refused before any request is sent. So is a card whose interface points to a different host, because the client would attach its token to every request it sends there.

## A version on every request

The server reads the header on every call. The specification identifies a version by "the `Major.Minor` elements" and says patch numbers "MUST not be considered when clients and servers negotiate protocol versions". It also says "Agents MUST interpret empty value as 0.3 version":

```python
# file: examples/agent-engineering/src/agentlab/multiagent/a2a.py
def negotiated(header: str | None) -> str:
    """The Major.Minor a request asks for; an empty or absent header means 0.3 (section 3.6.2)."""
    requested = (header or "").strip() or "0.3"
    return ".".join(requested.split(".")[:2])
```

```python
# file: examples/agent-engineering/src/agentlab/multiagent/a2a.py
def _run(name: str, params: dict, version: str | None, operations: dict) -> dict:
    # Checked on every request: there is no session in which a version was agreed once.
    if negotiated(version) != PROTOCOL_VERSION:
        details = error_info("VERSION_NOT_SUPPORTED", requested=negotiated(version)[:16], supported=PROTOCOL_VERSION)
        raise RpcError(VERSION_NOT_SUPPORTED, "Version not supported", details)
    if name in REFUSED:
        raise RpcError(*REFUSED[name])
    return operations[name](params)
```

A request with no header, or with `0.5` or `2.0`, gets JSON-RPC error `-32009`, the code section 5.4 assigns to `VersionNotSupportedError`, and nothing runs. `1.0.1` is served as 1.0. The agent reuses the JSON-RPC dispatcher from track 15, which turns the raised `RpcError` into an error response; its details follow section 9.5, an array of objects that each carry an `@type`.

## One exchange, pinned

The server runs as its own process, `python -m agentlab.multiagent.a2a`, on 127.0.0.1; the test is the client. The JSON-RPC binding sends `application/json` bodies to the URL in the card (section 9.1). The pinned fixture holds the exact first exchange, and the test requires the parsed response to equal it exactly. The client's message, with an id the client chose and one data part:


Other answers are pinned in the tests. Each one uses the code section 5.4 assigns:

| Situation | Answer |
|---|---|
| `GetTask` for a task that does not exist, or that another tenant created | `-32001` TaskNotFound |
| `CancelTask` on a finished task | `-32002` TaskNotCancelable |
| A push-notification method, when the card declares none | `-32003` PushNotificationNotSupported |
| `SendStreamingMessage`, when the card declares no streaming | `-32004` UnsupportedOperation |
| A message with no parts | `-32602` Invalid params |

Asking for another tenant's order, PO-2001, is not a protocol error: the request is valid. The work is refused, so the task ends in `TASK_STATE_REJECTED` with a status message and no artifact.

## Tolerant on the wire, strict inside

Section 5.7 says "Implementations SHOULD ignore unrecognized fields in messages, allowing for forward compatibility as the protocol evolves." The wire models here ignore unknown fields, so a server that adds a field in a later minor version does not break this client. That is the opposite of the handoffs in [lesson 22.2](/lessons/22-multi-agent-systems-and-a2a/22.2-typed-handoffs/), which forbid unknown fields. The difference is who owns the format. A2A is shared between parties who upgrade at different times. Your own handoffs change only when you change them, and there an unknown field means a bug or an attack. The skill's own input, `{"poId": "PO-1001"}`, is strict again: it is this agent's contract, not the protocol's.

## Who is asking

The card declares a bearer scheme, and section 7.4 says the server "MUST authenticate every incoming request". A missing or wrong token gets HTTP 401 with a `WWW-Authenticate: Bearer` challenge. The server maps the token to a `Principal` and scopes every task to it. Like the token checks in [lesson 15.5](/lessons/15-tool-contracts-and-mcp/15.5-transport-and-authorization-boundaries/), identity comes from the credential, never from anything the message says. Another tenant asking for a task id gets the same `TaskNotFound` as for an id that never existed, because servers "MUST NOT reveal the existence of resources the client is not authorized to access."

:::caveat
This subset runs plain HTTP on localhost. Section 7.1 requires encrypted transport in production. The tokens in the tests are synthetic strings, not secrets, and nothing leaves the machine.
:::

## What the subset leaves out

Implemented: the card, `SendMessage` in blocking mode, `GetTask` and `CancelTask` over the JSON-RPC binding, the version check and bearer authentication. Refused with the specification's error: streaming, `SubscribeToTask`, push notifications, `ListTasks` (a core operation that a compliant server must support), and the extended card. Not implemented at all: multi-turn input, task history and `historyLength`, file parts, extensions, card signatures, caching headers, tenants, the gRPC and HTTP+JSON bindings, the `A2A-Version` request-parameter form that section 3.6.1 allows (only the header is read) and TLS. A client-supplied `contextId` is accepted and kept. Every task here finishes inside `SendMessage`, so a cancel always meets a finished task. The module's docstring keeps this list next to the code.
