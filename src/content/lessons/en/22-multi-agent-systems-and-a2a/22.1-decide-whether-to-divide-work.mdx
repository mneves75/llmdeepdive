The purchasing assistant has four supplier invoices to check against their purchase orders. A colleague proposes a team instead of one agent: a *planner* that splits the work, one *worker* per invoice and a *synthesizer* that merges the workers' answers into one report. It sounds faster. Is it?

Here is what the course's fixture (fixed synthetic invoices and scripted model replies) measured when both designs read the same invoices and reported the same totals:

| Task | Design | Model calls | Input tokens | Output tokens | Critical path | Correct |
|---|---|---|---|---|---|---|
| one invoice | single agent | 1 | 102 | 4 | 1 | yes |
| one invoice | team | 3 | 144 | 16 | 3 | yes |
| four invoices | single agent | 4 | 748 | 16 | 4 | yes |
| four invoices | team | 6 | 422 | 40 | 3 | yes |

On one invoice the team is slower and dearer. On four it is shorter and, surprisingly, cheaper. The rest of this lesson explains each column and the rule that turns the table into a decision.

## What does dividing the work add?

A *multi-agent system* is several model-driven loops, each with its own instructions and its own conversation, passing results between them. The design above is the pattern Anthropic's guide to building agents lists among its workflows as *orchestrator-workers*: "a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results." The same guide opens with the advice that governs this lesson: find "the simplest solution possible, and only increasing complexity when needed."

Dividing work adds three costs before it saves anything. Every extra agent is an extra model call. Every handoff copies some context into the next agent. And someone must merge the parts, which can drop or distort one of them. What it can save is waiting: workers that do not depend on each other can run at the same time.

## Measure both designs on the same tasks

The *baseline* is the simplest design that does the job: one agent with one conversation, reading the messages one after another. The candidate is the team. Both run on `ScriptedModel` from the project, so the replies are fixed and every run gives the same numbers.

Tokens here are *estimated* tokens, about four characters each, with the same `approx_tokens` estimate that [lesson 19.3](/lessons/19-agent-memory-and-context/19.3-token-budgets-and-compression/) uses; a real tokenizer gives other counts. Cost uses illustrative prices of USD 0.50 per million input tokens and USD 2.00 per million output tokens, not any provider's list price. [Lesson 9.10](/lessons/9-hardware-and-infrastructure/9.10-cost-per-token/) explains where real per-token prices come from.

The *critical path* is the longest chain of calls that must happen one after another. It is the lower bound on how long a run takes, however many calls run in parallel. Each call records which earlier calls it had to wait for, and the path is computed like this:

```python
# file: examples/agent-engineering/src/agentlab/multiagent/baseline.py
def critical_path(calls: tuple[Call, ...]) -> int:
    """The longest chain of calls that must run one after another.

    shortcut: every call counts as one unit of latency; weight calls by
    their output tokens if replies differ a lot in length.
    """
    depth: list[int] = []
    for index, call in enumerate(calls):
        if any(parent >= index for parent in call.after):
            raise ValueError(f"call {index} waits for a call that comes after it")
        depth.append(1 + max((depth[parent] for parent in call.after), default=0))
    return max(depth, default=0)
```

The single agent's calls form a chain, so four invoices give a path of 4. The team's workers all wait only for the planner, and the synthesizer waits for all of them, so its path is 3 however many invoices there are. The function refuses a call that waits for a later one, because such a trace could hide a cycle and report a path that is too short.

## Why did the team read fewer tokens?

The single agent keeps its conversation. Its fourth call re-reads the instructions, all four messages and its three earlier replies, so its input grows with every invoice: 748 estimated tokens in total. Each worker reads only the plan and one message. The team makes two more calls, yet reads 422 tokens.

Be careful about what that shows. The saving comes from giving each call a short, separate context, not from having several agents. A single agent that started a fresh conversation for every message would get much the same saving without a planner or a synthesizer. The course did not measure that variant, and the teach-back asks you to reason about it. If your provider prices repeated prompt prefixes differently, rerun the comparison with its real prices before trusting this column.

Published numbers can point the other way. Anthropic reports that in its data "multi-agent systems use about 15× more tokens than chats," and that its research system beat a single agent by 90.2% on its internal evaluation. Those are measurements of Anthropic's system on research questions, the kind of breadth-first query the post says these systems suit best, and the same post warns that "most coding tasks involve fewer truly parallelizable tasks than research." The authors of a study that annotated more than 1,600 traces from seven multi-agent frameworks start from the observation that such systems' "performance gains on popular benchmarks are often minimal." None of these numbers replaces measuring your own tasks.

## A win needs every number at once

`compare` turns two lists of measurements into a verdict. It refuses to compare results from different tasks, and it adopts the candidate only if three things hold together:

```python
# file: examples/agent-engineering/src/agentlab/multiagent/baseline.py
def compare(baseline: list[Metrics], candidate: list[Metrics], *, max_cost_ratio: Decimal) -> Verdict:
    """Adopt the candidate only if it keeps every success, shortens the critical path and stays within the cost limit."""
    if sorted(m.task_id for m in baseline) != sorted(m.task_id for m in candidate):
        raise ValueError("the two designs were measured on different tasks")
    base = {m.task_id: m for m in baseline}
    reasons = [f"the candidate failed {m.task_id}, which the baseline passed" for m in candidate if base[m.task_id].success and not m.success]
    base_path, cand_path = sum(m.critical_path for m in baseline), sum(m.critical_path for m in candidate)
    if cand_path >= base_path:
        reasons.append(f"no shorter critical path: {cand_path} calls against {base_path}")
    base_cost = sum(m.cost_usd for m in baseline)
    if base_cost == 0:
        raise ValueError("the baseline cost nothing, so no cost ratio exists")
    ratio = sum(m.cost_usd for m in candidate) / base_cost
    if ratio > max_cost_ratio:
        reasons.append(f"costs {ratio:.2f} times the baseline, over the limit of {max_cost_ratio}")
    return Verdict(not reasons, tuple(reasons))
```

On the four-invoice task alone, the team passes, is shorter (3 calls against 4) and costs about 0.72 times as much, so it is adopted. On a mix of both tasks it costs about 0.85 times as much, but its summed path is 6 calls against 5, so it is refused. The verdict depends on the mix you measured. If most real requests carry one invoice, the team makes most of them slower, and only a mix that looks like real traffic can tell you that.

:::warning
The cost limit and the speed goal are decided before the run, not after looking at the table. Choosing the limit once the numbers are in turns the comparison into a story that fits them.
:::

## Success comes from the records, not from the agents

A faster team that gets an answer wrong has not won. `measure` reads the report line by line and checks each total with `invoice_matches_purchase`, the success check from [lesson 14.1](/lessons/14-agent-architecture-and-state/14.1-when-a-workflow-needs-an-agent/), against the purchase records of the run's tenant. A requested order missing from the answer is a failure too. If the synthesizer drops one worker's line, the team is still shorter and cheaper, and it is still refused, because it lost a task the single agent passed. This is the same habit [lesson 21.5](/lessons/21-bounded-agent-self-correction/21.5-evaluate-a-correction/) applied to repairs: judge the outcome against something the system under test cannot write.

:::caveat
Every number in this lesson is fixture-tested evidence: scripted replies, estimated tokens and illustrative prices. It shows that the measurement and the decision rule work. It says nothing about how a real model splits or merges invoices, which needs live trials (track 23).
:::
