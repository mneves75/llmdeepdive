The team has to pick where the report generator runs. Five names keep coming up in the discussion: E2B, gVisor, WebContainers, "just a container" and Docker-in-Docker. Each is offered as "a sandbox", as if they were interchangeable. They are not. Each puts the boundary somewhere else, protects someone else, and needs a different machine. This lesson compares them against the five exposures from [lesson 17.1](/lessons/17-sandboxed-agent-execution/17.1-what-isolation-protects/), then does two things no comparison table can do: it measures the backend you actually configured, and it cleans up after it.

## Six options, six different boundaries

The table adds the course's Firecracker reference to the five candidates. "Network" lists only what the cited documentation states.

| Option | Where the guest's code runs | What stands between it and your host | Network |
|---|---|---|---|
| E2B | the provider's cloud | the provider's sandbox; your controller calls its API | outbound open by default |
| gVisor (`runsc`) | your Linux host | an application kernel in user space | set by the container runtime |
| WebContainers | the visitor's browser tab | the browser | the browser's rules |
| Unprivileged container | your Linux host | namespaces, cgroups, seccomp; shared kernel | set by the runtime |
| Docker-in-Docker | your Linux host | usually nothing: it runs `--privileged` | set by the runtime |
| Firecracker reference | your Linux host with KVM | a guest kernel and a jailed VMM | none: no network device |

Read across a row and the differences show. **E2B** moves the guest off your machines, which also makes the provider part of your control plane: your controller needs network access to it, and the learner's own account and consent. **gVisor** keeps the guest on your host, answering its system calls with the Sentry rather than the host kernel. It is not a VM. **WebContainers** run Node.js "entirely inside your browser tab", so they protect a visitor's machine from a coding demo and do nothing for Python next to your data. An **unprivileged container** shares the host kernel, and Docker notes that user namespaces are "available but not enabled by default". **Docker-in-Docker** is the use case the `docker run` reference gives for `--privileged`.

## Configurations that remove the boundary

A boundary is a configuration, and three common ones undo it:

- **`--privileged`.** The `docker run` reference says it enables all capabilities, grants access to all host devices, disables the default seccomp and AppArmor profiles, and "is not a securely sandboxed process".
- **A mounted Docker socket.** The Docker daemon "requires `root` privileges unless you opt-in to Rootless mode". Docker's page on protecting the daemon says anyone with the keys "can give any instructions to your Docker daemon", which means root on its host. A guest that can reach the socket can start a container with the host's `/` mounted, which Docker's security page says "can alter your host filesystem without any restriction".
- **Defaults left on.** E2B's documentation, read on 2026-10-18, says "Every sandbox has outbound access to the internet by default". Allow rules "always take precedence" over deny rules, and domain filtering covers only HTTP on port 80 and TLS on port 443. An unexamined default is a decision too.

None of the options is free of vulnerabilities, and none claims to be. gVisor's documentation even lists where it "does not help": attacks before the sandbox starts, Spectre-style side channels, and exploits inside the workload, where "the attacker will still have access to whatever the sandbox is configured to have access to".

## Measure, do not describe

A vendor page describes a product. Your configuration of it is what runs. So the project measures a backend with small probes, each a guest script whose output the controller compares with the marker that means "the guest could do this":

```python
# file: examples/agent-engineering/src/agentlab/sandbox/boundary.py
def probe_boundary(backend: Backend) -> dict[str, bool]:
    with tempfile.TemporaryDirectory(prefix="agentlab-probe-") as host:
        # A file the guest was never given, outside any workspace.
        secret = Path(host) / "host-secret.txt"
        secret.write_text("host-only data", encoding="utf-8")
        probes = {
            "reads_host_file": (f"print(open({str(secret)!r}).read())", "host-only data\n"),
            "inherits_environment": ("import os\nprint('PATH' in os.environ or 'HOME' in os.environ)", "True\n"),
            "starts_processes": (FORK, "started\n"),
        }
        report = {name: _stdout(backend, name, code) == marker for name, (code, marker) in probes.items()}
    report["output_bounded"] = len(_stdout(backend, "output", f"import sys\nsys.stdout.write('x' * {FLOOD})")) < FLOOD
    return report
```

For the subprocess backend, run as an ordinary user, the measured report is `reads_host_file=True`, `inherits_environment=False`, `starts_processes=False` and `output_bounded=True`. Three controls hold and one boundary is absent, which is exactly what lessons 17.1 and 17.2 predicted. A positive control runs the same probes against a looser configuration and gets different answers, so the probes really can tell configurations apart. Network probes are left out on purpose: they need a destination you control and a firewall to test against, and E2B's warning that blocked connections can look open applies to them.

## Clean up exactly what the run owns

Every run creates resources: a workspace, a process group, and on the microVM path a jail directory and a cgroup. Cleanup removes those, named by what the run recorded when it created them. It never removes "everything that looks like ours". `rm -rf /tmp/agentlab-sandbox-*` would delete another run's workspace in the middle of its work. A `pkill python` would hit processes that belong to someone else.

The project follows that rule at each layer. The workspace is the exact path `TemporaryDirectory` returned. The kill targets the process group the child leads. On the microVM path, the jailer's id names both the chroot `/srv/jailer/firecracker/<id>` and the cgroup, and the jailer documentation leaves that cleanup to you. The cleanup must also run on failure: after a timeout, and after the guest locks its own files with `chmod 0`.

## Write the decision down

An *architecture decision record* (ADR) is a short document that states one decision, its context and the alternatives rejected, so the next person knows why. For a sandbox, it must hold measured values, not adjectives. The template below is an illustration for you to fill in. The course's CI does not check it, because only you know your threat model and your machines:

```markdown
# ADR: Execution boundary for the report generator

Status: proposed
Context: model-written Python over one tenant's purchase CSV; the script is untrusted.
Threat model: what the guest must never reach (files, credentials, network, other tenants).
Decision: the backend chosen, and its exact configuration.
Measured limits: probe_boundary output, with date, commit and host.
Unsupported platforms: where this cannot run, and what learners there do instead.
Failure cleanup: which resources a run creates, and how each is removed by its id.
Rejected alternatives: each option considered, and the exposure that ruled it out.
```

## Run the exercise

The module is `src/agentlab/sandbox/boundary.py`; the tests are in `tests/test_sandbox_boundary.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_sandbox_boundary -v`. Expect `Ran 5 tests` and `OK`. Run as root, the measured-report test skips, because `RLIMIT_NPROC` does not bind root.

The cleanup tests place a neighbouring directory named `agentlab-sandbox-neighbour` beside the workspaces. After a normal run, a timeout and a guest that locked its files, only the neighbour remains. To see them catch a leak, add `delete=False` to the `TemporaryDirectory(...)` call in `SubprocessBackend.run`. All three cleanup tests fail, listing the workspace left behind. The probe runs, which use the system temporary directory, leave eight workspaces there as well. Restore the line, then remove exactly those eight directories by the names the failure output and your temporary directory show.
