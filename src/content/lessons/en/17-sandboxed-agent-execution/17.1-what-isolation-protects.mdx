The purchasing assistant can produce a small report. The model writes a Python script that totals tenant-a's purchases by supplier, and the controller runs it. On the way, the model read the supplier message, and in [lesson 16.2](/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) that message carried instructions for it. So the script is *untrusted code*: nobody reviewed it, and an attacker may have shaped it. This track answers one question in five parts. When that script runs, what can it reach, and what stops it?

## What can a script you did not write reach?

Run it the way the simplest controller would: `subprocess.run(["python", "report.py"])` from the worker process. The child process starts with everything its parent has, minus the parent's memory:

- **Files.** It runs as the same operating-system user, so it can open every file that user can read: the checkpoint database from [lesson 14.3](/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/), a private key in the home directory, the other tenant's records.
- **Credentials.** A child inherits its parent's *environment variables* by default. If the worker holds `MODEL_API_KEY`, so does the script.
- **Network.** It can open a connection to any address the host can reach. On a cloud machine, that includes the metadata service at `169.254.169.254`, which can hand out the machine's own credentials ([lesson 17.3](/lessons/17-sandboxed-agent-execution/17.3-network-egress-and-secrets/)).
- **Resources.** It can spin the CPU, allocate memory, fill the disk and start processes until the machine struggles.
- **The kernel.** The *kernel* is the core of the operating system: every file open, socket and new process is a *system call*, a request the program makes to the kernel. The script's system calls go to the same kernel that runs everything else on the host, so a bug in that kernel is a way out.

Those are five separate exposures. A sandbox is only as good as its answer to each of them, and different sandboxes answer different subsets.

## Who is trusted: the control plane and the guest

Two roles appear in every design in this track. The *control plane* is the trusted code around the sandbox: it decides what runs, holds credentials, sets limits, receives and validates results, and destroys the sandbox afterwards. The *guest workload* is the untrusted code inside. Firecracker's design document takes the strictest view of the guest: all its virtual CPU threads "are considered to be running malicious code as soon as they have been started".

Keeping the roles apart prevents a common confusion. The controller may need the network, to call the model or a sandbox provider's API, while the guest needs none. "No network" is a property of the guest, not of the whole system. The same holds for secrets: the controller holds the API key, and the guest must never receive it.

## Four boundaries, four different answers

A *boundary* is the mechanism that stands between the guest and what it must not reach. Four kinds are common, and the figure below stacks each one between the script and the host.

<Figure id="isolation-layers" />

A **process with resource limits** bounds how much the script uses. Lesson 17.2 builds one. It changes nothing about what the script can reach: same user, same files, same network, same kernel.

A **container** adds *namespaces*, which give the process its own view of files, processes and network interfaces. It also adds *cgroups*, which set quotas on CPU, memory and process count. The system calls still go to the shared host kernel. Docker's security documentation warns that the default capabilities and mounts "may provide incomplete isolation", alone or "in combination with kernel vulnerabilities".

A **userspace kernel** puts a program between the guest and the host kernel. gVisor's documentation calls it "an application kernel, not a virtual machine hypervisor or a system call filter". Its Sentry component reimplements Linux in Go and runs in user space, and "gVisor never passes through any system call to the host". It is not a microVM.

A **virtual machine** gives the guest a kernel of its own, running on emulated hardware. A *microVM* is a virtual machine with a deliberately small set of emulated devices, so it starts fast and exposes less code to the guest. Firecracker builds microVMs on KVM, the Linux kernel's virtualization module.

| Boundary | The guest's system calls reach | Still needs separate controls for |
|---|---|---|
| Process with limits | the host kernel | files, network, secrets, the kernel |
| Container | the host kernel, filtered | network policy, secrets, kernel bugs |
| gVisor | the Sentry | network policy, secrets |
| MicroVM | its own guest kernel | egress filtering on the host, cleanup |

The last column never empties. Even a microVM leaves network filtering to the host: Firecracker's design document says it "does not perform any network traffic filtering". That is the laboratory point from the analogy. A strong wall does not filter the air.

:::warning
A configuration can remove a boundary entirely. The `docker run` reference says a container started with `--privileged` "is not a securely sandboxed process" and that such containers "can get a root shell on the host". Lesson 17.5 covers this and a mounted Docker socket, which has the same effect.
:::

## A browser runtime is a different place, not a smaller VM

WebContainers, from StackBlitz, run Node.js applications "entirely inside your browser tab". The code runs on the visitor's machine, inside their browser, and never on your server. That is useful for an interactive coding page, but it answers a different question. It does not run a CPython interpreter next to your controller and your data, so it is not a substitute for a Python microVM. Lesson 17.5 compares it with the others.

## Run the exercise: limits are not isolation

The module is `src/agentlab/sandbox/process.py`, which [lesson 17.2](/lessons/17-sandboxed-agent-execution/17.2-resource-and-filesystem-limits/) explains line by line. Here you only use it. The test creates a file outside the script's working directory and never passes it in:

```python
# file: examples/agent-engineering/tests/test_sandbox_isolation.py
    def test_the_same_process_reads_a_host_file_it_was_never_given(self):
        # The file lives outside the working directory; nobody passed it in.
        code = f"print(open({str(self.secret)!r}).read(), end='')"
        result = run_python(code, Path(self.workdir.name))
        self.assertEqual(result.stdout, b"host-only data\n")
```

From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_sandbox_isolation -v`. Expect `Ran 3 tests` and `OK`. The three tests hold together. `test_the_limits_are_applied` shows that a busy loop is killed by the CPU limit, not by the wall clock. The host-file test shows that the same process still reads a file it was never given. The positive control shows that a missing path really fails, so the read above found the real file.

To see the first test catch a regression, delete the line that sets `RLIMIT_CPU` in the bootstrap inside `process.py`. The loop then runs until the wall-clock timeout, `result.timed_out` becomes true, and the test fails. Restore the line. The host-file test has no fix inside this module: closing that exposure needs a different boundary, which lessons 17.4 and 17.5 build and measure.
