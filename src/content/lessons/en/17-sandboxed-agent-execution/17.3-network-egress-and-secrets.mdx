The report script totals a CSV and writes a JSON file. It needs no network at all. Now suppose the supplier message steered the model, and the script adds two lines. One sends the whole CSV to a server the attacker runs. The other asks `http://169.254.169.254/latest/meta-data/` for the machine's cloud credentials. Both are *egress*, traffic leaving the sandbox, and both succeed in the subprocess from [lesson 17.2](/lessons/17-sandboxed-agent-execution/17.2-resource-and-filesystem-limits/), which shares the host's network. This lesson decides which connections a guest may make, explains why the decision must be about addresses rather than names, and keeps the controller's secrets out of the guest's reach.

## Where can the guest's packets go?

The safe default is *default deny*: no destination is allowed unless a rule names it. For the report script, the rule list is empty. A guest that needs one supplier API gets exactly one `(host, port)` pair.

Three details decide whether "deny" really denies:

- **DNS is egress.** Resolving a name sends a query to a resolver, and the name itself can carry data out (`<stolen-data>.attacker.example`). A guest with no network should not resolve names either.
- **IPv4 and IPv6 are separate paths.** A firewall rule written only for IPv4 leaves IPv6 open on a host that has both.
- **Metadata endpoints are local.** Cloud machines expose a metadata service on a *link-local* address, one that only works on the local network segment. AWS documents `169.254.169.254` and, for IPv6, `[fd00:ec2::254]` (AWS calls it link-local; it is a unique local address). The same service can return credentials for the machine's role, so a guest that reaches it can act as the host.

## Deciding on a name is not deciding on an address

An allowlist lists names, because names are what people approve. The connection, though, goes to an address, and the name-to-address mapping belongs to whoever runs the DNS. *DNS rebinding* exploits that gap: the first lookup returns a public address and passes the check, and a later lookup returns `169.254.169.254` for the actual connection.

The project's decision function closes the gap. It resolves once, rejects the run if *any* answer is not public, and returns the one address the caller must connect to:

```python
# file: examples/agent-engineering/src/agentlab/sandbox/egress.py
def check_egress(host: str, port: int, policy: EgressPolicy, resolve: Resolver) -> Decision:
    name = host.lower().rstrip(".")
    if (name, port) not in policy.allowed:
        return Decision(False, f"{name}:{port} is not on the allowlist")
    answers = [ipaddress.ip_address(a) for a in resolve(name)]  # resolved once, then pinned
    if not answers:
        return Decision(False, f"{name} has no addresses")
    for address in answers:
        if not is_public(address):
            return Decision(False, f"{name} resolved to non-public {address}")
    return Decision(True, "allowed", str(answers[0]))
```

The name is normalized first, so `API.Supplier-Alpha.example.` with a trailing dot matches its lowercase entry. An address typed as a host, such as `169.254.169.254` or its decimal spelling, is just another name that is not on the list, and it is denied without being resolved. The resolver is a parameter, so the tests pass a fake one and nothing touches the network.

## Addresses that hide another address

"Public" means globally reachable, and Python's `ipaddress` module answers that with `is_global`, using IANA's special-purpose registries. Some IPv6 forms carry an IPv4 address inside them. Python 3.13 judges an IPv4-mapped address such as `::ffff:169.254.169.254` by its IPv4 part, and the 6to4 range `2002::/16` is not global. One form slips through. RFC 6052 defines the well-known NAT64 prefix `64:ff9b::/96`, which a NAT64 gateway translates to the IPv4 address in its last 32 bits. IANA lists that prefix as globally reachable, so `is_global` says `64:ff9b::a9fe:a9fe` is public, yet the gateway turns it into the metadata address. The project unwraps it:

```python
# file: examples/agent-engineering/src/agentlab/sandbox/egress.py
def is_public(address: Address) -> bool:
    """Globally reachable, judging an IPv4 address carried inside IPv6 by the IPv4 part."""
    if isinstance(address, ipaddress.IPv6Address) and address in NAT64:
        return ipaddress.IPv4Address(int(address) & 0xFFFFFFFF).is_global
    # Python 3.13 judges ::ffff:a.b.c.d by its IPv4 part; 6to4 (2002::/16) is not global.
    return address.is_global
```

## A decision is not enforcement

`check_egress` binds only code that calls it. Untrusted code can open its own socket, so the real blocking must happen where every packet passes and the guest cannot reach: a host firewall, or a network namespace with no route out. Firecracker's production guide says plainly that, as its threat model states, Firecracker "does not perform any network traffic filtering". The same guide shows a host rule that drops guest traffic to the metadata address. The rule below is quoted from that guide as an illustration. It needs a Linux host with Firecracker's network tables, and the course's CI does not run it:

```bash
sudo nft add rule firecracker filter iifname "tap*" ip daddr 169.254.169.254 counter drop
```

That rule covers IPv4 only, which is the point of the second bullet above. The simplest enforcement for the report script is to give its microVM no network device at all ([lesson 17.4](/lessons/17-sandboxed-agent-execution/17.4-a-python-interpreter-in-a-microvm/)).

Managed sandboxes need the same scrutiny. E2B's documentation, read on 2026-10-18, says "Every sandbox has outbound access to the internet by default", and `allow_internet_access=False` turns it off. It also warns that "blocked connections may appear successful from inside the sandbox". So a probe must check for a real application response, not just a connected socket.

## Secrets the guest never sees

The cheapest secret to protect is one the guest never receives. `run_python` starts the child with `env={}`, so an API key in the worker's environment does not cross over. Firecracker's jailer does the same for its own process: one of its documented steps is to "Cleanup all environment variables received from the parent process". Files are the other carrier: never place a credential file in the workspace, and mount nothing from the host that holds one.

Dependencies belong to the image, not the run. A guest that installs packages at run time needs a route to a package index. That route is an outbound channel, and the installed package runs its own code inside the guest. Build the image ahead of time, from pinned versions, and the guest needs no network.

## Run the exercise

The module is `src/agentlab/sandbox/egress.py`; the tests are in `tests/test_sandbox_egress.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_sandbox_egress -v`. Expect `Ran 8 tests` and `OK`.

The decision tests pair each denial with an allowed case. An allowlisted name with public IPv4 and IPv6 answers passes, while the same name answering with any of eleven non-public forms is denied, one bad address mixed into good ones included. A rebinding resolver that changes its answer on the second call is asked only once. The environment test sets a canary variable, `AGENTLAB_CANARY_TOKEN`, in the test process and checks that the sandboxed child cannot see it. The only names it may see are `LC_CTYPE`, which CPython's locale coercion sets, and `__CF_USER_TEXT_ENCODING`, which macOS adds. Neither is inherited. A positive control starts a normal child and confirms it does see the canary, so the empty environment is a property of the sandbox, not of the test.

To see the canary test catch a leak, change `env={}` to `env=dict(os.environ)` in `run_python`. `test_the_sandbox_starts_with_an_empty_environment` fails at once, naming the canary. Restore the line. These tests prove the policy and the environment. They do not prove that any packet is blocked, which needs a firewall or a VM with no network device and a probe that checks for a real reply.
