[Lesson 8.7](/lessons/8-building-and-serving-stacks/8.7-llama-cpp-and-gguf/) left you with a file and the command `llama-server -m model.gguf -ngl 99`. On a machine with both a CPU and a GPU, that command decides which processor computes each piece of the model. Get the placement wrong and you either run out of GPU memory or leave the GPU idle. This lesson asks what the command does to each tensor, and how to check it.

The answer sits in the **load log**, the lines llama.cpp prints while it loads a model, if you know how to read it. All logs below come from llama.cpp tag `b11380` on an Apple M5 Pro with 64 GB. Homebrew's build 11146 printed the same buffers for the `--n-cpu-moe 20` run.

## What llama.cpp builds before it computes

ggml is the tensor library under llama.cpp. A tensor here is a multi-dimensional array of numbers. A ggml tensor carries four things:

- its shape and its byte strides (how many bytes to step to reach the next element along each dimension);
- the operation that produces it;
- pointers to its source tensors;
- the **buffer** that holds its data, a block of memory that belongs to one device.

The header says that defining a function "does not involve any actual computation". You build a graph, and a separate call runs it. A Makefile works the same way: it describes targets and what each depends on, and only `make` runs anything. The comparison stops at that idea: a ggml graph holds tensor operations, not files.

llama.cpp builds such a graph for each **batch**, the group of tokens it processes in one call. When the shape repeats, it reuses the graph, and the log line `graphs reused` counts that.

## Who runs each node: backends and the scheduler

A **backend** is a way to run graph nodes on one kind of hardware: CPU, Metal (Apple's GPU interface), CUDA (NVIDIA's), Vulkan (a GPU interface across vendors), RPC (which sends work to another machine, as [lesson 13.5](/lessons/13-llama-cpp-in-depth/13.5-speculative-decoding-and-rpc-in-llama-cpp/) shows) and others. A **scheduler** decides which backend runs which node.

The comment in `ggml-backend.h` names two rules:

1. The backend must support the operation.
2. An operation "will be assigned preferably to run on the same backend as the buffer" that holds its weights.

The scheduler then cuts the graph into **splits**, one per run of consecutive nodes on the same backend, and copies tensors across each seam between splits. Take a made-up graph of six nodes whose weights sit on GPU, GPU, CPU, CPU, GPU, GPU. That gives three splits and two seams, and each seam copies the tensor that crosses it. So weights decide placement, and every seam costs a copy.

## Which layers `-ngl` puts on the GPU

`-ngl` sets how many layers get their weights on the GPU. At b11380 it defaults to `auto`, and `--fit` is on, so the server first estimates memory and adjusts the values you left unset. On the 35B file further down, the log says `projected to use 26808 MiB of device memory vs. 53020 MiB of free device memory`, so nothing changed. The `-ngl 99` of lesson 8.7 is a manual override of that default.

Try a number. The Qwen3-1.7B Q8_0 file has 28 layers, and `-ngl 10` printed `offloaded 10/29 layers to GPU`. The 29th "layer" is the output projection, which the loader counts last. The loader finds the first GPU layer as the total layer count plus one minus `-ngl`: 28 + 1 − 10 = 19. The debug log agreed. It put layers 0 to 18 on the CPU and 19 to 28 on `MTL0`, the first Metal device. So the **last** layers go to the GPU, not the first. The KV cache (the stored keys and values of past tokens, from [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/)) follows its layer: 152 MiB on the CPU, 72 MiB on Metal.

The loading mode follows the same logic. According to the README, `-lm auto` maps the file with mmap (the operating system maps the file into virtual memory, and its pages are loaded on demand or prefetched) unless a device cannot. The `Mapped` in `MTL0_Mapped` marks a buffer backed by that mapping. `--load-mode none` reads the weights into allocated memory instead. The loader warning shown further down recommends it when you override tensors to the CPU. Neither mode was timed.

After any change, compare three things in the log: the `offloaded` line, the buffer sizes and the split count.

## Experts: `--n-cpu-moe` and `-ot`

A mixture-of-experts (MoE) model replaces some or all of its dense feed-forward blocks with a router and several expert blocks, and runs only a few experts per token ([lesson 4.9](/lessons/4-transformer/4.9-feed-forward-block/)). Such a model keeps most of its bytes in the expert matrices, named `blk.N.ffn_up_exps.weight`, `ffn_gate_exps` and `ffn_down_exps`. `llama-gguf` confirmed those names in the Qwen3.6-35B-A3B Q4_K_XL file. Qwen3.8-27B is dense, so this model only serves as a public MoE example. The `common.h` pattern that selects those names is `\.ffn_(up|down|gate|gate_up)_(ch|)exps`.

```
llama-completion -m MODEL.gguf -c 4096 -n 2 -p "Hello" -no-cnv --no-warmup -v \
  --n-cpu-moe 20
```

Three flags write that override. `--n-cpu-moe N` adds it for the first N layers, `-cmoe` does it for all layers, and `-ot "ffn_.*_exps=CPU"` is the hand-written form. This is what the log showed:

| Run (Qwen3.6-35B-A3B Q4_K_XL) | Experts on CPU | New CPU buffer | Graph splits |
|---|---|---|---|
| default (the model's 262,144-token context) | none | none | 2 |
| `--n-cpu-moe 20` | 20 layers | 9,378 MiB | 42 |
| `-ot "ffn_.*_exps=CPU"` | 40 layers | 18,760 MiB | 82 |

Splits grow by two per overridden layer: 2 + 2 × 20 = 42, and 2 + 2 × 40 = 82. That fits one seam into the CPU and one back out for each layer. The 9,378 MiB buffer is named `CPU_REPACK`, because llama.cpp copies the weights into a layout the CPU kernels (the CPU's compute routines) prefer. With `--no-repack` the buffer became `CPU_Mapped`, and the prompt graph had 62 splits against 42 for decode.

## Why `--n-cpu-moe` frees nothing on a Mac

Flags like these exist for a discrete GPU, a graphics card with its own memory (VRAM) separate from system RAM, when that VRAM is smaller than the model. The reflex is to copy the recipe to a Mac "to save memory". But a Mac has unified memory: the CPU and GPU share one pool ([lesson 9.6](/lessons/9-hardware-and-infrastructure/9.6-apple-silicon-unified-memory/)). There is no separate VRAM on a Mac to save.

The measurements show it from both sides:

- Under the default mmap, the footprint rose from 0.36 GB to 10.2 GB peak, because the repacked copy sits next to the 21,314 MiB mapping.
- With `--load-mode none`, the total stays at 21,314 MiB and the Metal buffer shrinks to 11,421 MiB.

Either way nothing is freed. The experts only change which processor computes them. The Mac's GPU budget is the wired limit, the cap on memory the GPU may keep locked in RAM ([lesson 11.1](/lessons/11-mac-studio-ultra-and-mlx/11.1-mac-studio-ultra-as-an-inference-machine/)). The same reasoning applies to a unified pool such as the DGX Spark's ([lesson 12.1](/lessons/12-dgx-and-cuda/12.1-dgx-spark-grace-blackwell-on-a-desk/)), but it was not run there. [Lesson 12.2](/lessons/12-dgx-and-cuda/12.2-dgx-station-hbm-beside-a-big-pool/) covers the case where placement does matter, a Station with fast and slow pools.

:::warning
With `-ot` or `--n-cpu-moe` and mmap on, `llama_model_loader` prints `tensor overrides to CPU are used with mmap enabled - consider using --load-mode none for better performance`. Read the warnings in this log. They come from the loader, which knows your placement.
:::

## Why the prompt still reaches the GPU at `-ngl 0`

At `-ngl 0` you would expect one split, all on the CPU. The prompt graph had 281 splits, and the decode graph had 1.

The scheduler code explains part of this. When a weight sits in host memory (the CPU's RAM) and a faster backend reports `offload_op`, the operation moves there. Metal and CUDA accept when the batch has at least 32 rows (`GGML_OP_OFFLOAD_MIN_BATCH`, default 32), one row per token. A prompt arrives as many rows at once. A decode step has one row, so it stays on the CPU.

`--no-op-offload` turns this off. It lowered the count to 201, not to 1, and the rest was not traced.

:::caveat
Split counts, buffer sizes and the `pp bs=512, tg bs=1` log format belong to one build and one machine. Build 11146 printed a single split number. Treat a log as evidence about your own run, not as a constant.
:::

To sum up: a ggml graph does not know where it will run. The placement of the weights decides where each node runs and how many seams it crosses. Read `offloaded`, the buffer lines and the split count before you tune anything.
