A server is a scheduler with an HTTP face: it accepts requests from many users and decides whose tokens the model computes next. [Lesson 7.8](/lessons/7-inference-and-efficiency/7.8-pagedattention-and-continuous-batching/) explained continuous batching in the abstract. Here you meet the flags that control it in `llama-server`, plus the ones that protect and observe a running server.

Every flag below comes from the `tools/server/README.md` at `b11380`. The slot, batching, cache-type, prompt-reuse, API-key and metrics settings were run against a server on 127.0.0.1, with Qwen3-1.7B Q8_0 as a stand-in model. The caveat at the end lists the flags that were read but not run. Paths and keys are placeholders.

```
llama-server -m MODEL.gguf -c 16384 -np 4 -fa on -ctk q8_0 -ctv q8_0 \
  --metrics --api-key-file KEYS.txt --host 127.0.0.1 --port 8080
```

## How `-c` is shared across slots

A **slot** is one independent conversation with its own position in the KV cache (the stored keys and values of past tokens, from [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/)). `-c` sets the context, the number of tokens of KV cache the server allocates. `-np` sets how many slots there are, and the README default is `-1`, meaning auto. In `server.cpp` auto means four slots and a **unified** KV pool, one pool that every slot draws from. An explicit `-np` turns that default off.

The common assumption is that `-c` is divided among the slots. That is only half true, and the log shows both halves:

| Command | Log line |
|---|---|
| `-c 8192` | `n_slots = 4, n_ctx_slot = 8192, kv_unified = 'true'` |
| `-c 8192 -np 4` | `n_slots = 4, n_ctx_slot = 2048, kv_unified = 'false'` |

`GET /slots` returned the same `n_ctx` per slot, and Homebrew's build 11146 printed the same two lines.

The two rows behave differently:

- **Unified** (first row). Each slot may grow to the whole pool, but the four of them together still fit in 8192 tokens. If one conversation holds 6,000 tokens, the other three share the remaining 2,192.
- **Divided** (second row). The code divides `-c` by the slot count and pads to a multiple of 256, so no slot can exceed 2048.

The first is better when requests differ in length. The second gives a hard ceiling per user. Adding `-kvu` turns the unified pool back on: `-c 8192 -np 4 -kvu` logged `n_ctx_slot = 8192` and `kv_unified = 'true'`. `--kv-unified-per-slot N` sizes the pool as slots times N when you leave `-c` out. [Lesson 9.3](/lessons/9-hardware-and-infrastructure/9.3-kv-cache-sizing-and-memory-budgets/) owns the memory budget for the context you choose.

## Serving several users at once: batching and cache types

Continuous batching is on by default (`-cb`). Requests join and leave the running batch at every decode step, so one step carries tokens from every busy slot. Two 200-token generations sent at once gave `llamacpp:n_busy_slots_per_decode` 1.957. Almost every decode call carried tokens from both slots, which is the point of the feature.

`-ctk` and `-ctv` set the types of the K and V caches, the two halves of the KV cache. The README allows `f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1`, default `f16`. A smaller type fits more tokens into the same memory, so you can afford more slots. The quality cost is yours to measure with the tools of [lesson 13.2](/lessons/13-llama-cpp-in-depth/13.2-making-your-own-gguf-convert-imatrix-quantize/).

The V cache has a rule. A quantized V cache needs flash attention, the fused attention kernel from [lesson 7.7](/lessons/7-inference-and-efficiency/7.7-flashattention-and-io-awareness/). `-ctv q8_0 -fa off` exited with status 1 and `quantized V cache requires flash_attn to be enabled`, on both builds. With `-fa` at its default of `auto`, `-ctk q8_0 -ctv q8_0` started.

## Reusing a prompt the server has already seen

`--cache-prompt` is on by default. When a new request begins with the same tokens a slot already holds, the server keeps that prefix in the KV cache and evaluates only the new tokens.

The test sent a 547-token chat prompt, then the same system text with a different last message. The second reply reported `cache_n` 536 (tokens reused from the cache) and `prompt_n` 11 (tokens evaluated). With `cache_prompt` set to `false` it evaluated 547 again. For reuse to work, put what changes at the end of the prompt.

Three related controls exist:

- `--cache-reuse N` tries to reuse chunks by shifting the KV cache (default 0, off).
- `--cache-ram` caps the prompt cache in host memory (default 8192 MiB).
- `--slot-save-path` enables `POST /slots/{id}?action=save` and `restore` for explicit snapshots.

## When a conversation outgrows its slot

`--context-shift` decides whether the server may discard old tokens to keep generating, and the README lists it as disabled by default. The overflow path was not tested, so check it with your own client before launch: send a prompt longer than `n_ctx_slot` and see whether you get an error, a truncation or a shift.

Two more flags matter for long jobs. `-to` sets the read and write timeout in seconds (default 3600). `--sleep-idle-seconds` lets an idle server unload its model and KV cache (default off). `GET /slots` shows each slot's `n_ctx` and whether it is processing. `?fail_on_no_slot=1` returns 503 when no slot is free, which suits the health probe a load balancer sends to decide where to route traffic.

## What the server exposes

`--jinja` is enabled by default, so the server renders the model's own chat template (the format that wraps messages into one prompt). `POST /apply-template` returns the rendered prompt, which is the quickest way to see what the model actually receives. Qwen3 templates read `enable_thinking`, which the tests set per request with `chat_template_kwargs`; `--chat-template-kwargs` sets it for the whole server.

The endpoints are the OpenAI routes (`/v1/chat/completions`, `/v1/responses`, `/v1/embeddings`), the Anthropic route (`/v1/messages`), and the native `/completion`, `/tokenize`, `/props`, `/slots` and `/metrics`.

If you constrain a reply to a JSON schema, as [lesson 8.5](/lessons/8-building-and-serving-stacks/8.5-sglang/) describes, a schema-valid object is still only a request. Before anything acts on it, check that generation ended normally rather than at a length limit, validate what the arguments mean, and check that this caller is allowed to do what they ask. [Lesson 15.1](/lessons/15-tool-contracts-and-mcp/15.1-from-model-output-to-a-tool-request/) builds that check.

## Locking it down and watching it

`--host` defaults to `127.0.0.1`, so only the same machine can connect. Without a key the log warns `no API key is set and CORS allows all origins`; CORS is the browser rule for which other websites may call the server. With `--api-key` or `--api-key-file` (one key per line, `#` for comments), the measured statuses were:

| Request | Status |
|---|---|
| `/health`, no key | 200 |
| `/v1/models`, no key | 401 |
| `/metrics`, no key | 401 |
| `/metrics`, `Authorization: Bearer KEY` | 200 |
| `/v1/models`, `X-Api-Key: KEY` | 200 |

Only `/health` and `/v1/health` are public, plus the web UI assets.

`/metrics` is off unless you pass `--metrics`, and your scraper then needs the key. It exports metrics in the format of Prometheus, a common monitoring system that polls ("scrapes") such endpoints. There are two kinds:

- **counters**, cumulative totals that only increase between resets such as a server restart, such as `llamacpp:prompt_tokens_total` and `llamacpp:tokens_predicted_total`;
- **gauges**, which report a current value, such as `llamacpp:requests_processing` and `llamacpp:n_busy_slots_per_decode`.

The exporter also printed `llamacpp:prompt_tokens_cached_total`, which the README table does not list.

:::warning
An API key on the command line is visible in the process list, so prefer `--api-key-file`. For a public deployment, the README advises an API key and a reverse proxy (a front server, such as nginx, that receives public traffic and forwards it). `--tools` is marked experimental, and `--agent` carries the README's warning not to enable it in untrusted environments. They expose file access and a shell tool, so leave them off on a shared server.
:::

:::caveat
These flags come from the README only and were not run: `--cache-reuse`, `--cache-ram`, `--slot-save-path`, `--context-shift`, `-to`, `--sleep-idle-seconds`, `--kv-unified-per-slot`, `--chat-template-kwargs`, `--tools` and `--agent`. TLS (`--ssl-key-file`, `--ssl-cert-file`), router mode (`--models-dir`) and the multi-key list were not tested either.
:::

To sum up, a server has three budgets, the context pool, the slots that share it and the cache types that shrink it. Choose them from your traffic, then read the startup log to confirm what you got.
