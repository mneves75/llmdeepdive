A benchmark is a measurement with a protocol: fixed conditions, repeated runs and a reported spread. `llama-bench` supplies a good stopwatch and a bad temptation, which is to paste one number into a table. This lesson reads the tool at tag `b11380`, then uses it to ask when a Mac Ultra and a DGX Spark can be compared fairly.

Every command was run on an Apple M5 Pro with Qwen3-1.7B Q8_0 as a stand-in. No throughput from that run is published. It only showed that the flags work.

## What pp and tg measure

```
llama-bench -m MODEL.gguf -p 512 -n 128 -r 3 -fa 0,1
llama-bench -m MODEL.gguf -p 512 -n 0 -d 0,2048 -pg 256,64 -r 2 -ngl 99 -o json
```

The two default tests time the two phases of generation from [lesson 7.3](/lessons/7-inference-and-efficiency/7.3-prefill-vs-decode-two-different-machines/). Both report tokens per second (t/s).

- `-p 512` is **pp512**: process a 512-token prompt in batches. This is prefill. Each read of the weights serves many tokens, so compute dominates.
- `-n 128` is **tg128**: generate 128 tokens one by one. This is decode. Each token reads the weights again, so memory bandwidth dominates ([lesson 9.1](/lessons/9-hardware-and-infrastructure/9.1-memory-bandwidth-vs-flops/)).

Two more flags shape the test. `-pg 256,64` runs a prompt then a generation. `-d 2048` fills the KV cache with 2,048 tokens first, so you measure decode at depth rather than on an empty cache. The README adds that the measurements "do not include the times for tokenization and for sampling".

Every parameter takes comma-separated lists and runs the full grid of combinations. `-fa` (flash attention) defaults to `auto` at b11380, which the JSON reports as `-1`. Set `-fa 0` or `-fa 1` when you compare machines, so both use the same flash-attention setting.

## Reading the spread, and a Mac trap

`-r` repeats each test (default 5), and the table prints the mean and the standard deviation, a measure of how much the repeats differ. `-o json` also keeps every sample in `samples_ts`, plus `build_commit` and `build_number`, so a result carries its own provenance. The JSON from this run said commit `eec18f5` and number 1, because the binary was built from a shallow clone of the tag (a clone without the history that numbers the build).

Use `--delay` between tests, and `--prio` if the machine is shared. A laptop ten minutes into a session is a different machine, as [lesson 7.13](/lessons/7-inference-and-efficiency/7.13-choosing-and-judging-a-community-quant/) warned.

On a Mac there is a trap. In Homebrew's build 11146, `-ngl 0,99` printed a table with **no `ngl` column**, so the two pairs of rows look identical. The code in `llama-bench.cpp` adds `n_gpu_layers` only when the backend label does not contain `CPU` or `BLAS`. On this Mac the label contains `BLAS` (`MTL,BLAS` at b11380, `BLAS,MTL` at 11146), because Apple's Accelerate library is registered as a BLAS backend, a library of linear-algebra routines. Use `-o json` or `-o csv`, which always carry the field.

## A fair Mac versus Spark pair

The llama.cpp repository keeps two files of its maintainers' runs. Both use `llama-bench` on **gpt-oss-120b MXFP4** (59.02 GiB), with `n_ubatch` 2048 and flash attention on. One is a Mac Studio M2 Ultra at build 7948. The other is a DGX Spark (GB10) at build 7941 with `ngl` 99. These are gpt-oss numbers, not Qwen numbers.

Two details limit the match. The Mac file does not name the chip, so "M2 Ultra" comes from its directory name. The Spark ran with mmap off and direct I/O on, and the Mac with defaults; that should not change the steady-state t/s, the rate once loading is over.

| gpt-oss-120b MXFP4 | pp2048 (t/s) | tg32 (t/s) |
|---|---|---|
| Mac Studio M2 Ultra | 1648.69 ± 1.80 | 85.60 ± 0.52 |
| DGX Spark | 2443.91 ± 7.47 | 58.72 ± 0.20 |

The Spark prefills about 1.48 times faster and decodes about 1.46 times slower. That is the prefill and decode split from lesson 7.3, measured by someone else.

Can bandwidth alone predict the decode gap? The bandwidths are 800 GB/s for the M2 Ultra (Apple, 2023) and 273 GB/s for the Spark ([lesson 12.1](/lessons/12-dgx-and-cuda/12.1-dgx-spark-grace-blackwell-on-a-desk/)), a ratio of 2.9. The measured decode gap is only 1.46, so the bandwidth quotient overstates it. The model is the same on both machines, so both read the same bytes per token. Possible explanations for the smaller gap include:

- the two chips reach different fractions of their peak bandwidth;
- costs that do not scale with bandwidth take a larger share of each token's time.

The 7B example below illustrates the first possibility. A bandwidth quotient is a planning heuristic ([lesson 9.6](/lessons/9-hardware-and-infrastructure/9.6-apple-silicon-unified-memory/)), not a prediction.

## A looser pair: M5 Ultra against Spark on 7B

The pair above is an M2 Ultra, not an M5 Ultra. [Lesson 11.1](/lessons/11-mac-studio-ultra-and-mlx/11.1-mac-studio-ultra-as-an-inference-machine/) owns the M5 Ultra figures. For an M5 Ultra, the only llama.cpp numbers found are in discussion 4167, and they are weaker evidence. As read on 2026-10-03:

- **Mac.** A user comment (commit `c1d0e7a00`, macOS 27.0.1, 80 GPU cores, 256 GB) gives `llama 7B Q4_0`, 3.53 GiB: pp512 4944.66, tg128 179.10.
- **Spark.** Discussion 15013 has a row from a maintainer (commit `5acd455`) for `llama 7B Q4_0` (the thread intro says Llama 2 7B), 3.56 GiB: pp512 3062.31 without flash attention and 3661.37 with it, tg128 57.21 and 56.74.

Those rows differ in submitter, commit and file size. The thread intros name the model LLaMA 7B and Llama 2 7B while the rows carry the same label, and the flash-attention mode of the Mac row is not stated. Treat the pair as a hypothesis.

It still teaches one thing. For a dense model like this 7B, each decoded token reads roughly the whole file, so decode rate times file size gives an *implied* bandwidth. With made-up numbers: a 2 GB file decoded at 50 t/s implies about 100 GB/s. Now the real rows:

- Mac: 179.10 x 3.53 GiB is about 679 GB/s, 57 % of Apple's 1.2 TB/s.
- Spark: 57.21 x 3.56 GiB is about 219 GB/s, 80 % of 273 GB/s.

A small model does not saturate the bigger chip, so the 3.1 times decode ratio is not a bandwidth ratio. Both figures are derived here from the threads' own numbers.

## Why one tokens-per-second figure misleads

The usual mistake is quoting one "tokens per second" figure, or quoting a 7B number as if it described the 27B model. A rate belongs to one model, one file and one machine. Report pp and tg separately, with the model, file size, build, flags and spread.

:::warning
`llama-bench` is not `llama-server`. It has no HTTP layer, no tokenizer time, no sampling and no concurrent users, so it cannot predict latency under load. Use it to compare configurations, then measure the server with its own `/metrics`.
:::

:::caveat
Discussion tables are user-submitted and cannot be pinned to a tag. They were read once, on 2026-10-03. Rows can change, and nobody audits them. The repository's `benches/` files are pinned at b11380, but they hold only the maintainers' machines.
:::

So a fair comparison fixes the file, the build, the flags and the depth, and reports pp, tg and spread separately. Next, [lesson 13.5](/lessons/13-llama-cpp-in-depth/13.5-speculative-decoding-and-rpc-in-llama-cpp/) asks what speculative decoding and a second machine do to those two numbers.
