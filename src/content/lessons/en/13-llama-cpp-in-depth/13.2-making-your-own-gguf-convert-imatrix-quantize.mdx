[Lesson 7.13](/lessons/7-inference-and-efficiency/7.13-choosing-and-judging-a-community-quant/) taught you to judge a quant somebody else made. This lesson makes one, in four steps, with a check after each. Making your own is how you get a quant for a model nobody has quantized yet, or one tuned to your own text.

Every command below was run at llama.cpp tag `b11380` on a small stand-in model, Qwen3-0.6B, because a recipe you cannot rerun in minutes teaches nothing. The recipe was not run on Qwen3.8-27B. Paths are placeholders.

## Write down how it fails first

Five things go wrong, so the commands guard against each:

1. The converter does not know the architecture. Run `python convert_hf_to_gguf.py --print-supported-models` before you download anything.
2. You quantize an already quantized file. `llama-quantize` refuses: `requantizing from type q4_K is disabled`. The flag `--allow-requantize` exists, and the README warns it "can severely reduce quality".
3. You ask for a very low-bit type with no matrix. `IQ2_XXS` exits with `this quantization requires an imatrix!`.
4. You calibrate and score on the same text.
5. You trust one number from one run.

## The four steps

```
python convert_hf_to_gguf.py MODEL_DIR --outtype bf16 --outfile model-bf16.gguf
llama-imatrix -m model-bf16.gguf -f calib.txt -o imatrix.gguf -ngl 99
llama-quantize --imatrix imatrix.gguf model-bf16.gguf model-Q4_K_M.gguf Q4_K_M
llama-perplexity -m model-bf16.gguf -f wiki.test.raw --kl-divergence-base base.kld --chunks 20 -ngl 99
llama-perplexity -m model-Q4_K_M.gguf -f wiki.test.raw --kl-divergence-base base.kld --kl-divergence --chunks 20 -ngl 99
```

**Convert.** A Hugging Face checkpoint is a folder of weight files plus the model's configuration and tokenizer. The converter turns it into one GGUF file. Always write the highest-fidelity file first: `bf16` (bfloat16, two bytes per weight), or `auto` for the highest-fidelity 16-bit type. Conversion is lossless only when the source checkpoint is already bf16; converting from fp32 or fp16 to bf16 rounds values that are not exactly representable, for example 1.0009765625 is exact in fp16 but rounds to 1.0 in bf16. Call the bf16 file 'lossless' only relative to a bf16 source. Every later step reads this file. The Qwen3-0.6B conversion wrote 311 tensors and a 1.5 GB file.

**Collect.** The importance matrix (imatrix) records which input columns of each weight matrix the calibration text exercised most strongly. As lesson 7.13 explained, it is the sum of squared activations per tensor column. An activation is a value a layer produces while the model reads text. The **calibration text** is the text you run through the model to collect those values.

At b11380 the output defaults to `imatrix.gguf`. Only `--output-format dat` writes the legacy format; a `.dat` file name alone still writes GGUF and logs a warning. The calibration text here was the llama.cpp documentation and tool READMEs, 523,956 bytes, which gave 305 chunks of 512 tokens. For your own model, use text that looks like your traffic, in the chat format you serve (`--parse-special` reads special tokens in the text).

To look inside the matrix, the README shows `llama-imatrix --in-file imatrix.gguf --show-statistics`. Both b11380 and Homebrew's build 11146 answered `error: --model is required`. Add `-m model-bf16.gguf` and it works; the table goes to stderr. It shows the sum of squared activations per tensor, and on this model it spans orders of magnitude: 15.68 for `attn_k` in layer 1 against 192,029.52 in layer 26.

**Quantize.** Overrides let you give named tensors a different type from the rest. They are regular expressions on tensor names. The run added `--tensor-type attn_v=q6_k --token-embedding-type q8_0`, and the log confirmed `applying manual override: q4_K -> q6_K` for each layer.

The README lists more knobs:

- `--pure` turns off the k-quant mixtures (the per-tensor choice of types inside a k-quant recipe) and uses one type everywhere.
- `--leave-output-tensor` keeps `output.weight` unquantized.
- `--include-weights` or `--exclude-weights` limits the matrix to named tensors. You cannot mix the two.

`llama-imatrix` skips `output.weight` by default, because the README says it is usually better not to apply the matrix there; `--process-output` changes that.

**Measure.** The question now is how far the quantized model drifted from the bf16 original. Two scores answer different versions of it:

- **Perplexity** measures how well a model predicts a text; lower is better ([lesson 1.7](/lessons/1-text-to-tensors/1.7-entropy-perplexity/)).
- **KL divergence** (Kullback–Leibler divergence, also from lesson 1.7) measures how far one probability distribution sits from another. Here it compares, token by token, the quantized model's next-token probabilities with the bf16 model's. Zero means identical.

The first `llama-perplexity` run records the bf16 logits (the raw scores a model gives every vocabulary token before they become probabilities) once. The second run compares each candidate against them.

Provenance is cheap, so keep it. For the file made with a matrix, `llama-gguf` listed the metadata keys `quantize.imatrix.file`, `quantize.imatrix.dataset`, `quantize.imatrix.entries_count` and `quantize.imatrix.chunks_count`, and the plain file had none of them. Keep the bf16 file, because every new recipe starts from it. Write the exact command, the build and the calibration corpus next to any file you share, so a reader can repeat it.

## What the run showed

| Qwen3-0.6B, 20 chunks of Wikitext-2 test | Quantized tensor size | Mean KL divergence | Same top token |
|---|---|---|---|
| Q4_K_M, no matrix | 456.11 MiB | 0.1036 ± 0.0022 | 83.3 % |
| Q4_K_M, imatrix | 456.11 MiB | 0.0689 ± 0.0016 | 85.8 % |
| imatrix, `attn_v` at Q6_K, embeddings at Q8_0 | 533.91 MiB | 0.0616 ± 0.0014 | 86.3 % |

"Same top token" is the share of positions where the quantized model and bf16 rank the same token first. Read the table row by row:

- The matrix cost no bytes and removed about a third of the KL divergence.
- The overrides bought a smaller gain for 78 MiB, mostly the embedding table, which is large in a 0.6B model. Whether that trade is worth it is a decision for your model and your memory.

Two details keep the numbers honest. The bf16 reference printed perplexity 23.6783 ± 1.12824 in the run that recorded its logits, and the KL reports print `Mean PPL(base)` 23.405638 ± 1.096843 on the same 20 chunks. The sizes in the table are the quantizer's own `quant size`; on disk the files were 461.8 and 539.6 MiB.

Why KL divergence and not perplexity alone? The perplexity README separates the two. Perplexity asks how well the model predicts a text. KL divergence, and statistics such as the share of tokens where both models pick the same top token, ask how far the quantized distribution moved from the original one. The README also warns that llama.cpp perplexity values are "not directly comparable" to other projects, and not comparable across models with different tokenizers.

A last check costs one command. Load the quantized file in `llama-completion` or `llama-server` and read the first answers by eye before you trust any number. A file can score well and still fail on your template or your language. Use the chat template you will serve, because a calibration made on plain text says little about special tokens.

## Why calibration and scoring need different text

The easy mistake is to calibrate and score on the same file. The matrix then looks better than it is, because it was fitted to what you grade it on. It is the same reason you keep a test set apart from training data. Keep the sets disjoint: docs for calibration, Wikitext-2 test for scoring.

The logits file needs planning too. It grows with vocabulary size times scored tokens, and the file here reached 1.55 GB for 20 short chunks on a 151,936-row vocabulary. A full test set on a large vocabulary needs real disk, so plan the volume before you start.

:::warning
Do not publish a quant on one run. The ± values above are the sampling error of 20 chunks on one small model. Rerun on text from your own work before you trust a ranking of recipes, including this table.
:::

:::caveat
The README's scoreboard uses Llama 3 8B on a CUDA GPU. Do not carry its numbers over to Qwen3.8-27B, and do not carry these. A recipe is a procedure; the table is a result about one 0.6B model.
:::

In short: conversion preserves, calibration steers, quantization spends, and held-out measurement judges. Each step has a refusal or a number you can read, so you never have to guess. Next, [lesson 13.3](/lessons/13-llama-cpp-in-depth/13.3-llama-server-in-production/) serves the file you built.
