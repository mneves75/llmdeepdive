When a language model gets a company-specific question wrong, teams reach for one of three tools: stuff every reference file into a long context window (the prompt limit the model reads at once), build a retrieval-augmented generation (RAG) pipeline (a chain of automated steps that searches external files before answering), or fine-tune the model's weights (the learned numbers stored inside the model). Picking the wrong tool wastes months. Teams fine-tune on manuals that change every Friday, or send 200,000 tokens into every prompt and watch latency (the wait time before an answer arrives) spike while the monthly invoice explodes. This lesson gives you a concrete arithmetic and systems framework to choose the right mechanism—or the right pair—before writing pipeline code.

## A worked cost and freshness comparison

Start with numbers from a realistic internal product: a 400-page operations handbook totaling 200,000 tokens, queried 10,000 times per month, with policy edits arriving every week. Suppose input tokens cost USD 2.00 per million uncached and USD 0.20 per million on a prefix-cache hit (reusing stored calculations for identical opening text at a 90% discount).

If you stuff the entire handbook into every request without caching, each query pays for 200,000 input tokens:

$$
\text{Uncached long-context cost} = \frac{200{,}000}{1{,}000{,}000} \times 2.00 = 0.40\ \text{USD per query}.
$$

Now compare baseline RAG using the hybrid search stack from [lesson 27.5](/lessons/27-retrieval-and-hybrid-search/27.5-bm25-hybrid-search-and-rrf/). Instead of sending all 400 pages, the retriever pulls the 6 most relevant chunks (short passages cut from longer documents) of 500 tokens each, totaling 3,000 context tokens per query:

$$
\text{RAG context cost} = \frac{3{,}000}{1{,}000{,}000} \times 2.00 = 0.006\ \text{USD per query}.
$$

The stepped plot tracks how those per-query rates separate across 10,000 monthly requests before counting any generated output tokens. Even at a 90% warm prefix-cache hit rate (USD 0.04 per cached query, USD 0.40 per miss), weekly handbook edits repeatedly wipe the cached prefix. More importantly, when the corpus (the full document collection) grows from 400 pages to 40,000 support tickets totaling 20,000,000 tokens, long-context stuffing stops fitting in the window at all, while RAG still sends the same 3,000 tokens per request.

## What each mechanism actually changes

Each approach modifies a different part of the system, so they do not compete on the same axis. Lewis et al. (2020) introduced RAG to separate *parametric memory* (knowledge baked into neural network weights) from *non-parametric memory* (an external index updated independently of training).

- **Long context** places raw source text directly into the prompt's KV cache (short-term memory holding per-token attention keys and values for one request), giving attention direct access to every token without an indexing step.
- **RAG** keeps knowledge in an external search index and injects only a small retrieved subset at query time, decoupling corpus size, freshness, and per-user access control from the model weights.
- **Fine-tuning**, including low-rank adaptation (LoRA) from [lesson 6.3](/lessons/6-post-training-and-alignment/6.3-lora-qlora-and-peft/), updates weights so the model shifts *how* it behaves: format adherence, domain terminology, tool-calling habits, or concise reasoning style.
- **Hybrid systems** combine mechanisms when a product needs both: RAG supplies fresh, permission-filtered facts while a lightweight adapter (a small add-on set of trained weights) shapes output format and refusal tone.

Trying to store volatile facts in weights via fine-tuning hits three structural walls. First, updating or revoking one customer's outdated policy requires curating data, retraining, evaluating, and redeploying weights rather than deleting a row in an index. Second, weights cannot enforce row-level access control (restricting each user to only the records they are permitted to see): once a confidential contract is trained into parameters, every user shares those same weights. Third, fine-tuned weights carry no native source pointer, making auditable citations impossible without external retrieval.

## Where long context wins and where it stalls

Long context is the cleanest architecture for a specific class of problems. Suppose a lawyer uploads one 35,000-token merger agreement and asks 25 analytical questions during a single review session, including global questions like "list every clause that conflicts with Section 14's indemnity cap."

Splitting that contract into 500-token chunks risks missing an indirect cross-reference buried in an appendix. Putting all 35,000 tokens into the prompt once, backed by prefix caching across the 25 turns, keeps total session cost low (one uncached write plus 24 cached reads) while letting attention compare any two clauses directly.

Long context stalls as soon as four boundaries appear: corpus size exceeds a few hundred thousand tokens, documents differ per user or change every minute, time-to-first-token (TTFT, the wait before the first generated word appears) must stay under a few hundred milliseconds, or irrelevant text fills most of the window. Liu et al. (2023) demonstrated that even when a model accepts long inputs, accuracy drops when key facts sit buried in the middle of many distracting passages—a failure mode we unpack and fix in the next lesson.

:::note
A model advertising a 1,000,000-token context window does not promise flat cost, flat latency, or uniform recall across all 1,000,000 tokens. Prefill compute (the initial pass reading the prompt), memory bandwidth (how fast data moves from chip memory to processors), and distractor interference all rise with prompt length.
:::

## When fine-tuning belongs beside RAG

A reliable production rule is to treat RAG as the *knowledge* layer and fine-tuning as the *behavior* layer. Start with a strong off-the-shelf model, clear prompt instructions, structured outputs (forcing replies into a fixed data template such as JSON), and solid hybrid retrieval. Measure where errors actually happen.

Fine-tuning earns its maintenance cost only when retrieval already puts the right evidence in the prompt yet the model still fails consistently in style, domain dialect, or specialized reasoning—or when a smaller fine-tuned model can replace an expensive frontier model at high volume to cut latency and unit cost. Until you have hundreds of verified input-output examples proving that prompting plus retrieval hits a ceiling, adding training pipelines only slows down iteration.
