So far one agent read the supplier's message and drafted the invoice. Split that job in three. A *mail reader* reads supplier messages and reports which order and total a message is about. An *invoice drafter* drafts invoices. A *records clerk* updates an order's status when goods arrive. The mail reader reads attacker-written text all day, so it is the role most likely to be steered. Suppose it is steered completely and emits a perfectly shaped request. The next block is an illustration of that request's fields, not code the course's CI runs; the test below builds the same request in Python:

```json
{"tool": "write_purchase_record", "arguments": {"po_id": "PO-1003", "status": "received"}}
```

PO-1003 is a real open order of the run's own tenant. Marking it received would hide a delivery that never came. Should the gate allow it?

## Least privilege, one grant per role

Saltzer and Schroeder's principle of *least privilege* says every program "should operate using the least set of privileges necessary to complete the job", and that this "limits the damage that can result from an accident or error". OWASP's prompt-injection entry gives the same advice for models: "restrict the model's access privileges to the minimum necessary for its intended operations." For the three roles that means three grants:

```python
# file: examples/agent-engineering/src/agentlab/security/privilege.py
ROLE_GRANTS: dict[str, frozenset[str]] = {
    "mail_reader": frozenset({"lookup_po"}),
    "invoice_drafter": frozenset({"lookup_po", "create_invoice_draft"}),
    "records_clerk": frozenset({"lookup_po", "write_purchase_record"}),
}
```

The gate from [lesson 16.2](/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) checks the grant before anything else, so the mail reader's perfect request is refused with "write_purchase_record is not granted to this agent". The shape never mattered. The same request from the records clerk is allowed: that is the positive control, and without it a gate that refused everything would also pass the test.

It helps to list what a fully fooled mail reader can still do with this grant. It can read its own tenant's orders, which it needs for its job, and it can report a wrong order or total. It cannot read another tenant's orders, because the tenant check still runs, and it cannot write anything. That short list is the point of least privilege: the damage from a successful attack is bounded by the grant, not by how convincing the attack was.

This is the difference between *validation* and *authorization*. Validation asks whether a request is well formed; the project's core tests already show a perfectly shaped request for another tenant's invoice validating. Authorization asks whether this caller may do this thing to this object. A model that has read the tool's schema can always produce a valid request, so validity can never be the permission.

## Typed fields between roles

How does the drafter learn which invoice to draft? Not from the mail reader's free text, which could carry the attacker's sentences onward. The mail reader's only output is a record with two fields:

```python
# file: examples/agent-engineering/src/agentlab/security/privilege.py
class ExtractedInvoice(Record):
    """What the mail reader may report about a message: two fields, nothing else."""

    po_id: str = Field(pattern=r"^PO-\d{4}$")
    total: Decimal = Field(gt=0, max_digits=12, decimal_places=2)
```

The record is strict and forbids unknown fields, so a reply that adds `"payee": "Supplier Omega"` or `"approved": true` fails to parse. The attacker's favourite fields have nowhere to land. This is *typed extraction*. It has a limit worth stating plainly: a type validates structure, not meaning. The mail reader can still report the wrong total, so the drafter's gate still compares the total with the purchase record. Types narrow what can be passed on; checks against trusted sources decide whether it is true.

## Secrets the agent never sees

The back office needs a key. The tempting design puts it where the agent can use it: in the prompt, in an environment variable a tool can read, or as a tool argument. Then a steered agent can print it or send it elsewhere. A *credential broker* holds the secret and attaches it itself, only for calls on its list:

```python
# file: examples/agent-engineering/src/agentlab/security/privilege.py
@dataclass
class CredentialBroker:
    """Holds one secret and the only destinations it may be sent to."""

    routes: dict[str, str]  # tool name -> fixed URL; the model cannot choose the destination
    secret: str = field(repr=False)
    transport: Transport = field(repr=False)

    def call(self, tool: str, arguments: dict) -> JsonValue:
        url = self.routes.get(tool)
        if url is None:
            raise PermissionError(f"no credential route for {tool}")
        reply = self.transport(url, {"Authorization": f"Bearer {self.secret}"}, arguments)
        text = json.dumps(reply)
        # A service that echoes the header (in a debug field or an error) must not leak it onward.
        return json.loads(text.replace(self.secret, "[redacted]")) if self.secret in text else reply
```

Three properties matter. The agent never holds the key, so no prompt can extract it. The destination is fixed per tool, so the model cannot choose where the key goes. And a reply that echoes the key, in a debug field or an error, is redacted before it reaches the model. The `repr=False` fields keep the secret out of logs and test failure messages, the same choice `OpenAICompatibleModel` makes for its API key.

:::note
The MCP security guide forbids the related anti-pattern *token passthrough*: a server forwarding a client's token to a downstream API. Its rule is that MCP servers "MUST NOT accept any tokens that were not explicitly issued for the MCP server." It also recommends minimal, incrementally raised scopes instead of one broad token. [Lesson 15.5](/lessons/15-tool-contracts-and-mcp/15.5-transport-and-authorization-boundaries/) covers those authorization boundaries.
:::

## Show outside text as inert text

The last asset in lesson 16.1's table is the reviewer's screen. The assistant's reply often repeats parts of the supplier's message, so it is outside text too. If the reviewer's screen renders HTML or Markdown, the reply can carry markup that runs, or an image whose address carries data to the attacker's server the moment the page loads. `render_untrusted` removes every link and image target, then escapes the rest:

```python
# file: examples/agent-engineering/src/agentlab/security/privilege.py
def render_untrusted(text: str) -> str:
    """Return HTML-safe text with every link and image target removed.

    Escaping stops markup; removing targets stops a reviewer's browser from
    fetching an attacker's URL, which could carry data in its query string.
    """
    text = MARKDOWN_LINK.sub(lambda match: f"{match.group(1)} [link removed]", text)
    return html.escape(BARE_URL.sub("[link removed]", text))
```

A label survives as text ("status [link removed]") so the reviewer still sees that something was there. Escaping alone would not be enough: Markdown image syntax contains no character that HTML escaping changes.
