NVIDIA's DGX Station page says "748 GB of coherent memory". Read fast, that sounds like one huge pool at the speed of the fastest part. Count what the page lists. The GB300 Grace Blackwell Ultra Desktop Superchip has one Blackwell Ultra GPU and a 72-core Grace CPU. The GPU side has 252 GB of HBM3e at 7.1 TB/s. The CPU side has 496 GB of LPDDR5X at 396 GB/s. NVLink-C2C joins them at 900 GB/s. And 252 plus 496 is 748. Two pools, two speeds, one address space.

Coherent is a statement about correctness. The CUDA Programming Guide describes hardware-coherent systems such as Grace Hopper: a logically combined page table for CPUs and GPUs, and coherence at cache-line granularity. The Unified Memory guide names DGX Station among hardware-coherent systems, and the attribute query below confirms it on your machine. Any processor can read any byte and see the latest value. The guide does not promise that every byte arrives at the same rate. Speed follows the physical home of the bytes.

Apply the method of lesson 9.6 to each pool separately. These are planning heuristics from vendor figures, with the same artifact sizes as lesson 12.1.

$$
\frac{7100\ \text{GB/s}}{17.1\ \text{GB}} \approx 415\ \text{tok/s}, \qquad \frac{7100\ \text{GB/s}}{54\ \text{GB}} \approx 131\ \text{tok/s}.
$$

$$
\frac{396\ \text{GB/s}}{17.1\ \text{GB}} \approx 23.2\ \text{tok/s}, \qquad \frac{396\ \text{GB/s}}{54\ \text{GB}} \approx 7.3\ \text{tok/s}.
$$

The first line is the Station with every byte in HBM. The second is the Station with every byte in LPDDR5X. HBM is about 26 times the Spark's 273 GB/s. The slow pool alone is about 1.45 times the Spark's only pool. On the same 54 GB artifact, the Station's worst case of 7.3 tok/s beats the Spark's 5.1, and its best case is another world.

Now the blend. Put a share of the 54 GB in HBM and the rest in LPDDR5X. Suppose the layers are read one after another with no overlap, so the times add. Time per token is the bytes in each pool divided by that pool's bandwidth.

| Share of the 54 GB in HBM | Time per token | Planning rate |
|---|---|---|
| 100 percent | 7.6 ms | 131 tok/s |
| 90 percent | 20.5 ms | 49 tok/s |
| 50 percent | 72.0 ms | 13.9 tok/s |
| 0 percent | 136.4 ms | 7.3 tok/s |

Look at the second row. Only 10 percent of the bytes sit in the slow pool, and the rate falls from 131 to 49 tok/s. If a runtime prefetches the next layer while the current one computes, the sum becomes a maximum. The slow pool still sets the pace once it holds more than 396 / (7100 + 396), about 5.3 percent, of the bytes. This is the classic wrong turn: dividing by 7,100 GB/s because the page says 748 GB. Averaging the two rates fails the same way. Times add. Rates do not average.

Why would anyone put weights in the slow pool? Because some models do not fit in 252 GB. The share that spills sets the pace. NVIDIA's own vLLM playbook shows the other side. For the Spark it picks a 27B model. For the Station it picks a larger mixture-of-experts model, one that uses the extra memory. A 54 GB checkpoint does not need the Station's capacity. What the Station sells that model is bandwidth.

You steer placement with tools the Programming Guide documents. A hardware-coherent system keeps access counters and may migrate pages toward the processor that touches them most. You override that with hints.

```cpp
// 1 = every allocation is unified memory; hostTables 1 = coherence in hardware.
int pageable = -1, hostTables = -1;
cudaDeviceGetAttribute(&pageable, cudaDevAttrPageableMemoryAccess, 0);
cudaDeviceGetAttribute(&hostTables, cudaDevAttrPageableMemoryAccessUsesHostPageTables, 0);

float *hot, *cold;
cudaMallocManaged(&hot, hotBytes);
cudaMallocManaged(&cold, coldBytes);
// device 0 is assumed to be the GB300; check with nvidia-smi -L
cudaMemLocation gpu = {.type = cudaMemLocationTypeDevice, .id = 0};
cudaMemLocation cpu = {.type = cudaMemLocationTypeHost};
cudaMemAdvise(hot,  hotBytes,  cudaMemAdviseSetPreferredLocation, gpu);  // keep in HBM
cudaMemAdvise(cold, coldBytes, cudaMemAdviseSetPreferredLocation, cpu);  // keep in LPDDR5X
cudaMemAdvise(cold, coldBytes, cudaMemAdviseSetAccessedBy,        gpu);  // map it for GPU reads
cudaMemPrefetchAsync(hot, hotBytes, gpu, 0, stream);                     // move it now
```

Where the platform exposes device memory as a NUMA domain, the guide also describes `numa_alloc_on_node` and `mbind`. Memory pinned that way does not migrate. Check with `numactl --hardware` which nodes your machine shows. Runtimes expose the same idea as flags. Lesson 13.1 shows llama.cpp's tensor-placement options.

:::warning
Hints are not guarantees. The guide says a preferred location "does not guarantee" residence, and a later prefetch may override it. Do not assume your weights stayed in HBM. Measure it. Nsight Compute has a `C2CLink` section that reports NVLink-C2C utilization, so a model that streams weights over the link shows up as link traffic. Lesson 12.4 covers profiling.
:::

Compute capability is the other trap. NVIDIA's list puts the GB300 in the DGX Station at 10.3 and the GB10 in the DGX Spark at 12.1. The family name is the same. The build targets are not, and a binary built only for one does not run on the other. Lesson 12.3 shows how to build for both. Beyond the box, a ConnectX-8 SuperNIC gives up to 800 Gb/s, which is 100 GB/s. That is about 1.4 percent of the HBM figure, so the network stays far slower than local memory (lesson 9.9).

:::caveat
All figures are NVIDIA's claims, read from its product page on 3 October 2026. The page's FP4 row carries sparsity footnotes that this lesson does not try to resolve, so it quotes no Station FP4 number. The blend table assumes a sequential read with no overlap. A real runtime will land somewhere between the sum and the maximum.
:::

The durable idea is that coherence gives you an address space and placement gives you a speed. Before you read a spec sheet's total capacity, ask which bytes live where. Lesson 12.3 turns to the programming model that decides how a kernel touches them.
