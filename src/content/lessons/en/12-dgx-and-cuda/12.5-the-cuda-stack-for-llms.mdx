Your Spark arrives with a working stack. Then you pip-install a framework, pull a container or build a server, and something slips. A model loads and produces tokens at a third of the speed you expected. Or an import fails on a missing library. The cause is almost never the model. It is one layer of the CUDA stack that disagrees with its neighbours about the chip. This lesson names the layers, so you can test them one at a time.

Start at the bottom. The driver talks to the hardware. The toolkit is what you compile with: `nvcc`, headers, the runtime and libraries such as cuBLAS for matrix multiplies. Other libraries sit beside them: cuDNN for neural-network primitives and NCCL for collective communication between GPUs and machines. NVIDIA's Spark release notes show how tightly these are bound. The current Founders Edition stack is DGX OS 7.5.0 with driver 580.159.03 and CUDA Toolkit 13.0.2. CUTLASS 4.8 requires CUDA 13.0 or newer for this chip, and the stock toolkit 13.0.2 meets that.

The compatibility rules decide how far above the stock versions you may go. NVIDIA's release notes pair each toolkit with a driver branch: 13.0 with 580 and 13.4 with 615. The same notes add that existing CUDA 13.x applications run on any driver from 580 under minor-version compatibility, which the compatibility guide describes as allowing some feature limits. Then the sharp part: CUDA 13.4's new features and newly enabled platforms need 615 or later. A container built for 13.4 may therefore start on a stock Spark, and then fail on the one feature you needed. The rule is simple. The driver sets the ceiling, and the toolkit and every library inside your container must fit under it. NVIDIA's known-issues page adds that the latest features and performance improvements are available through NGC containers.

Next the framework. The PyTorch index at `download.pytorch.org/whl/cu130` carries aarch64 wheels, built for CUDA 13.0. Name the flavour explicitly, then verify. Do not assume.

```bash
nvidia-smi --query-gpu=name,driver_version,compute_cap --format=csv
nvcc --version
python3 -m venv ~/venvs/torch && . ~/venvs/torch/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cu130
python3 -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.get_device_capability(), torch.cuda.get_arch_list())"
```

Read the last line against the first. The capability should be (12, 1). The arch list shows what the wheel was compiled for. If it has no entry that can serve 12.1, do not expect optimized kernels, even though `torch.cuda.is_available()` says True. Run a real matrix multiply and time it.

Containers move the whole problem to NVIDIA's registry. The Spark's NGC page says the box needs the ARM64 build of the NGC command-line tool, and it advises pinning container tags. Take the current tag from the catalog, not from a blog post. Tags age quickly.

Now the numeric format that Blackwell added. NVFP4 stores E2M1 values, 1 sign, 2 exponent and 1 mantissa bit, in blocks of 16. Each block has an FP8 E4M3 scale, and a second FP32 scale covers the tensor. NVIDIA counts 4.5 bits per value. It claims about 3.5 times less memory than FP16 and 1.8 times less than FP8. Its contrast is MXFP4, with blocks of 32 and a power-of-two scale. Those ratios apply to the tensors the recipe covers. NVIDIA's own checkpoint for the course model, `nvidia/Qwen3.8-27B-NVFP4`, is mixed: NVFP4 on the MLP layers and `lm_head`, FP8 on the self-attention and linear-attention layers. It was produced with Model Optimizer, and the card lists vLLM and SGLang as its runtimes. This is the point lesson 9.4 made: a validated recipe for this hybrid model comes first, then the format.

Now three servers, in the order they are easiest to start. For vLLM, lesson 8.4 owns the flags. NVIDIA's DGX Spark playbook, updated on 14 September 2026, pulls a prebuilt container and the NVFP4 checkpoint, then tests the OpenAI-compatible endpoint. Copy the tag from the live page.

```bash
# on the Spark
hf download nvidia/Qwen3.8-27B-NVFP4 --cache-dir "$HOME/.cache/huggingface/hub"
# on your laptop, through NVIDIA Sync's port forward
curl -i http://localhost:8000/health
curl -sS http://localhost:8000/v1/models
```

Run the launch script that the playbook gives. Then wait for the line "Application startup complete" before you send a request. GPU activity in a monitor only shows that something is loading.

For TensorRT-LLM, lesson 8.6 owns the concepts. On the Spark you start from a container, as the known-issues page advises: `nvcr.io/nvidia/tensorrt-llm/release`, NVIDIA's own registry rather than Docker Hub. The tag comes from NVIDIA's TensorRT-LLM playbook for the Spark, which pins a release candidate, so copy it from the live page. The playbook serves with `trtllm-serve` and a Hugging Face token. It has no engine-build step, which matches the PyTorch-only backend of lesson 8.6. One caveat: its model matrix does not list Qwen3.8-27B, so check the hybrid layers before you plan around it.

For llama.cpp, build from source on the box. The pinned build guide gives two lines, and a native build sees the Spark's GPU.

```bash
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release
```

The pinned CMake file at b11380 does the target work for you. It rewrites a plain `120` or `121` architecture into `120a` or `121a`, because, in the file's own words, the Blackwell FP4 tensor core instructions are not forward compatible. For builds that are not native, it lists `120a-real` from toolkit 12.8 and `121a-real` from 12.9. To build on a machine without a GPU, set `-DCMAKE_CUDA_ARCHITECTURES="121a-real"`.

The classic wrong turn is to check only the last layer. The server answers `/health`, so the stack must be fine. Health proves a process is alive. It does not prove the kernels are the fast ones. Walk the stack from the bottom. Check the driver and capability, then the toolkit, then the wheel's arch list, then one real completion with a timer.

:::warning
A passing import is not a passing stack. A wheel built for an older architecture can load, run and quietly fall back to slower kernels. A benchmark taken on that stack measures the fallback. Record driver, toolkit, wheel or container tag, and the arch list next to every number you publish.
:::

:::caveat
The commands here are copied from NVIDIA's pages, the PyTorch index and the pinned llama.cpp sources, but the authors have not run them on a Spark. The stock versions above come from release notes dated 2026 and apply to the Founders Edition. A partner GB10 system may differ.
:::

The durable idea is a ladder of five checks: driver, toolkit, libraries, framework, server. Each rung can fail alone and each has one command that proves it. Track 13 climbs into the last rung and shows what llama.cpp does with the device once it is found.
