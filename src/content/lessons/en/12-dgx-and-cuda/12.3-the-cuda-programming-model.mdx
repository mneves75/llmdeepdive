You own a Spark and open a kernel somebody else wrote. It has no loop over the data. It has an index built from three odd names, and a launch line with triple angle brackets. The CUDA model behind it is small. This lesson builds it up from the vector add in NVIDIA's Programming Guide and ends with the compiler flag that decides whether your binary runs on your machine.

## From a loop to a kernel

On a CPU you add two arrays with a loop: `for (int i = 0; i < n; ++i) C[i] = A[i] + B[i];`. One core walks through every `i` in turn. A CUDA kernel is that loop's body, written for one value of `i`. A function marked `__global__` is a kernel: the CPU launches it, thousands of GPU threads run it at once, and each thread works out which element is its own.

The comparison stops at ordering. A loop runs its iterations one after another, so iteration 7 can count on iteration 6 being done. Threads run in no guaranteed order, so a kernel must not assume another thread has finished unless it waits for it explicitly. [Lesson 12.4](/lessons/12-dgx-and-cuda/12.4-writing-a-fast-kernel-tiling-and-tensor-cores/) shows one such wait, a barrier that holds every thread of a block until all of them arrive.

## Threads, blocks, grids and warps

Threads are organised in levels, and each level maps onto the hardware:

- A **thread** runs the kernel once, usually for one element.
- A **block** is a group of at most 1,024 threads. A block lives on one streaming multiprocessor (SM), one of the many independent processing units a GPU is built from. Threads of one block share fast on-chip memory and can synchronize, which means wait for each other.
- The **grid** is the set of blocks in one launch.
- A **warp** is 32 threads of one block that the hardware schedules together. NVIDIA calls the model SIMT, single instruction, multiple threads: the warp issues one instruction at a time, but each thread keeps its own control flow, so do not rely on lockstep.

Warps have two practical consequences. Threads in a warp that take different branches of an `if` are masked off in turn: the warp runs one branch while the other threads wait, then the other. So keep branches uniform within a warp. And a block size that is not a multiple of 32 leaves part of its last warp empty, so keep block sizes a multiple of 32.

## A first kernel: adding two vectors

```cpp
__global__ void vecAdd(const float* A, const float* B, float* C, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // my element
    if (i < n) C[i] = A[i] + B[i];                   // guard: the grid is rounded up
}

float *A, *B, *C;                                    // unified memory, no copies
cudaMallocManaged(&A, n * sizeof(float));
cudaMallocManaged(&B, n * sizeof(float));
cudaMallocManaged(&C, n * sizeof(float));
// ... fill A and B on the host ...
int threads = 256;
int blocks  = (n + threads - 1) / threads;           // ceiling division
vecAdd<<<blocks, threads>>>(A, B, C, n);
cudaDeviceSynchronize();                             // launches are asynchronous
```

The three odd names give each thread its position. `blockIdx.x` is the block's number in the grid, `blockDim.x` is the number of threads per block, and `threadIdx.x` is the thread's number inside its block. With 256 threads per block, thread 5 of block 2 gets `i` = 2 × 256 + 5 = 517. The triple angle brackets set the launch shape: how many blocks, and how many threads in each. `cudaMallocManaged` gives memory that the CPU and the GPU can both use ([lesson 12.2](/lessons/12-dgx-and-cuda/12.2-dgx-station-hbm-beside-a-big-pool/)), and `cudaDeviceSynchronize` makes the CPU wait, because a launch returns before the kernel finishes.

The rounded-up grid creates `blocks * threads` threads, usually more than `n`. With `n` = 1,000, four blocks of 256 make 1,024 threads, and the last 24 have no element. Without the guard, the extra threads write past the arrays. That is the commonest first bug.

## How memory is organised, and how a warp should read it

Now memory, because the roofline of [lesson 9.2](/lessons/9-hardware-and-infrastructure/9.2-the-roofline-model/) is drawn against it (the roofline caps a kernel's speed by either arithmetic or memory bandwidth). From fastest and smallest to slowest and largest:

1. Registers belong to one thread.
2. Shared memory belongs to one block and sits on the SM, on the same physical resource as the L1 cache.
3. The L2 cache serves the whole chip.
4. Global memory is the DRAM.

For compute capability 12.x, the Programming Guide lists 64 K registers per SM, 100 KiB of shared memory per SM with 99 KiB usable by one block, 1,536 resident threads (48 warps) per SM and 24 resident blocks. Those are the limits that the GB10 inherits.

Access pattern comes first. A CPU never fetches a single byte from RAM: it fetches a whole cache line. A GPU does something similar at warp scale. Global memory moves in 32-byte transactions, and the hardware merges the reads of one warp into as few transactions as it can, which is called **coalescing**.

- If consecutive threads of a warp read consecutive 4-byte words, the warp's request is 128 bytes, served by four transactions, with full use.
- If neighbouring threads are 32 bytes or more apart, the warp needs 32 transactions, 1,024 bytes of traffic for 128 bytes used. That is 12.5 percent efficiency.

The rule is to let `threadIdx.x`, the fastest-moving index, step along the contiguous dimension.

## A naive matrix multiply, and why it is slow

A matrix multiply computes each output `C[row][col]` as the sum over `k` of `A[row][k]` times `B[k][col]`. The simplest kernel gives each output element its own thread. Here is one that follows the access rule. Column `col` comes from `threadIdx.x`, so reads of `B` and writes of `C` are coalesced, and the threads of one row share each `A` load. `dim3 block(16, 16)` asks for a 16 by 16 block of threads.

```cpp
__global__ void matmulNaive(const float* A, const float* B, float* C, int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < M && col < N) {
        float acc = 0.0f;
        for (int k = 0; k < K; ++k) acc += A[row * K + k] * B[k * N + col];
        C[row * N + col] = acc;
    }
}

dim3 block(16, 16);
dim3 grid((N + 15) / 16, (M + 15) / 16);             // x covers columns, y covers rows
matmulNaive<<<grid, block>>>(A, B, C, M, N, K);
```

It is correct and slow. Each step of the `k` loop loads two 4-byte values and does one multiply-add, which counts as 2 FLOP (floating-point operations). Arithmetic intensity, from lesson 9.2, is the number of operations per byte moved. If no load hit a cache, it would be

$$
\frac{2\ \text{FLOP}}{2\times 4\ \text{B}} = 0.25\ \text{FLOP/B}, \qquad 273\ \text{GB/s}\times 0.25\ \text{FLOP/B} \approx 68\ \text{GFLOP/s}.
$$

The second figure uses the Spark's vendor bandwidth and is a pessimistic planning number, because L1 and L2 do catch some reuse. The distance between it and the chip's arithmetic peak is the room that lesson 12.4 fills.

Occupancy is the other number a profiler shows. The Best Practices Guide defines it as active warps per SM over the maximum. It matters because a warp waiting on memory stalls, and the SM can then issue instructions from another resident warp, so more resident warps give it more work to switch to. The guide also warns that more is not always faster. With 256-thread blocks on compute capability 12.x, six blocks give 1,536 threads, which is 48 warps and full occupancy. That holds only if each thread uses at most about 42 registers, since 65,536 / 1,536 is 42.7, and before allocation rounding. Shared memory limits it as well. `nvcc -res-usage` prints registers per thread.

## Building for the right GPU

Now the target. Compute capability is NVIDIA's version number for a GPU's features, and `nvidia-smi --query-gpu=name,compute_cap` prints it. NVIDIA's list gives 12.1 for the GB10 in the Spark and 10.3 for the GB300 in the Station.

A CUDA binary can carry two kinds of GPU code. Machine code runs directly, with no compile step at load time. PTX is a virtual assembly that the driver can compile at load time, just in time (JIT), for the GPU it finds. `nvcc -arch=sm_121` embeds PTX and machine code for that chip. The manual's example for `sm_100` expands to `compute_100` plus `sm_100`, and `sm_121` follows the same rule. With no `-arch` flag, the manual's default is `sm_75`, so the code may still run through PTX recompilation but does not use what the chip added since.

```bash
nvcc -O3 -arch=sm_121 -lineinfo matmul.cu -o matmul-spark       # GB10, compute capability 12.1
nvcc -O3 -arch=sm_103 -lineinfo matmul.cu -o matmul-station     # GB300, compute capability 10.3
nvcc -O3 -gencode arch=compute_121,code=sm_121 \
        -gencode arch=compute_103,code=sm_103 matmul.cu -o matmul   # one binary, both machines
```

CUTLASS, NVIDIA's C++ template library for matrix multiplies, lists in its 4.8 hardware table CUDA 13.0 as the minimum toolkit CUTLASS itself requires for both capabilities.

A tempting mistake is to build on one machine and copy the binary to the other. `-arch=native` makes it easy: it detects the visible GPU and emits machine code for it, with no PTX. But the capability is the cause of the failure. Code for 12.1 cannot run on a 10.3 GPU, with or without PTX, so a plain `-arch=sm_121` build fails on the Station too.

The two-target build above gives native machine code on both machines. A build that carries `compute_100` PTX would also start on both through JIT, but without the `a` features described below. The missing PTX is a separate cost: a native binary will not carry forward to a later GPU either.

:::warning
Suffixes narrow the target. An `a` target, such as `sm_121a`, unlocks the architecture-specific features, including the newest Tensor Core instructions, and the guide states that such code runs only on the exact compute capability it was built for. An `f` target covers a family: `compute_120f` runs on 12.0 and 12.1. Use the least specific target that still has the features you need: plain first, then `f`, then `a`.
:::

:::caveat
The listings follow the patterns in NVIDIA's Programming Guide, but this course's authors have not run them on a GPU. Run them under `compute-sanitizer` first. Launches are asynchronous, so an error from a kernel can surface at the next synchronization. Call `cudaGetLastError()` after a launch and check the result of `cudaDeviceSynchronize()`.
:::

A CUDA program, then, is a rule for one thread, a launch shape, and a target. The rule decides correctness, the access pattern decides how many bytes move, and the target decides where the binary runs. Lesson 12.4 rewrites the matrix multiply so that fewer bytes move.
