The assistant from [lesson 25.1](/lessons/25-agent-capstone-and-portfolio/25.1-architecture-and-threat-model-review/) succeeded in 24 of 30 runs. Is that good? What did it cost? Would a second person running the same code get the same answer? A single headline number answers none of these. This lesson builds a benchmark that does: repeated trials of held-out scenarios, a cost for each *successful* task, an interval around the success rate, and a report whose deterministic part reproduces byte for byte.

## What does one successful task cost?

Start with the calculator's worked example. Thirty runs, ten held-out scenarios with three trials each, produce 24 successes. Each run costs USD 0.08 in model tokens and USD 0.02 in sandbox time, and a person spends 1.5 minutes reviewing it at USD 40 an hour, which is another USD 1.00. One run therefore costs USD 1.10 and the 30 runs cost USD 33.00.

The six failed runs were paid for as well, so the honest price of the work is the whole bill divided by what it produced: USD 33.00 / 24 = USD 1.375 per successful task. Quoting USD 1.10 would price only the runs that worked. Quoting USD 0.10 would leave out the person, who here is most of the bill. The success rate is 24 / 30 = 80%.

The calculator starts from these numbers. Change the review minutes and watch the person's time dominate the price, or lower the successes and watch the price climb faster than the failure count.

## How sure is 80%?

Thirty trials are few. The *Wilson score interval* (Wilson, 1927) gives a range of success rates consistent with what was seen. With $\hat p$ the observed rate, $n$ the number of trials and $z = 1.96$ for 95%:

$$
\frac{\hat p + \frac{z^2}{2n} \pm z\sqrt{\frac{\hat p(1-\hat p)}{n} + \frac{z^2}{4n^2}}}{1 + \frac{z^2}{n}}
$$

For 24 of 30 it runs from about 62.7% to 90.5%. Unlike the simpler $\hat p \pm z\sqrt{\hat p(1-\hat p)/n}$, it stays inside 0 to 1 and does not shrink to zero width at 0 or 30 successes. [Lesson 23.5](/lessons/23-agent-evaluation-and-ci/23.5-ci-replay-and-live-trials/) wrote the same function; the capstone imports it rather than copying it.

:::caveat
The interval assumes independent trials. Anthropic's evaluation guide warns that trials sharing an environment, or failing because of the same limit such as too little memory, are not independent, and the results become unreliable. The capstone runs every trial in a fresh directory for that reason. Three trials of one scenario are still correlated with each other, so read the interval as optimistic.
:::

The NeurIPS paper checklist asks the same of any reported error bar: say what variability it captures, how it was calculated and under which assumptions. A report that gives 80% without the interval, the trial count and the independence assumption has not said how much to trust it.

## What goes in the report?

The benchmark writes one JSON file in two parts. The `deterministic` part holds what a second person must reproduce exactly. That covers the evidence kind, the model, the suite seed, the fixture manifest (a SHA-256 for each fixture file the runs read), every run's outcome, cost and timing, and the summary. The `digest` is the SHA-256 of that part as canonical JSON. The `environment` part records the Python, Pydantic and agentlab versions, the platform and the clock, and stays outside the digest, because another machine legitimately differs there.

Each run row keeps separate what would otherwise blur together:

- **Costs, by who is paid.** Model tokens, sandbox runs and the approver's minutes are three lines, priced with illustrative rates.
- **Latency apart from waiting.** Latency is the assistant's own working time; *human wait* is the time a run spent waiting for an approver. The summary reports latency as the 50th and 90th percentiles and the maximum, and the wait separately.
- **Failure handling.** Model retries after a transient failure, invoice re-sends and outbox reconciliations each get a count.
- **Every failure.** Failed runs stay in the list with their outcome, and the summary names each one. Nothing is averaged away.

On the course's fixtures the summary reads 24 successes in 30 runs, with Wilson bounds 0.626943 and 0.904949, and zero safety violations. The six failures are the three trials each of two scenarios: a lookup of another tenant's purchase order and a draft whose total the model guessed wrong. The fixture bill is USD 6.37: USD 0.36 for sandbox runs, about a cent for model tokens and USD 6.00 for six approval decisions. The person dominates again.

The arithmetic matches the browser calculator line for line:

```python
# file: examples/agent-engineering/src/agentlab/capstone/benchmark.py
def cost_per_success(*, runs: int, successes: int, model_cost: float, sandbox_cost: float, review_minutes: float, review_hourly: float) -> dict:
    """The arithmetic of ``costPerSuccess`` in the site's ``src/lib/lab-math.ts``, which the 25.2 calculator runs.

    Failed runs are paid for too, so the cost of one success is the whole bill
    divided by the successes, not the cost of one run.
    """
    cost_per_run = model_cost + sandbox_cost + review_minutes / 60 * review_hourly
    total = cost_per_run * runs
    low, high = wilson_interval(successes, runs) if runs > 0 else (0.0, 0.0)
    return {
        "cost_per_run": cost_per_run,
        "total": total,
        "per_success": total / successes if successes else None,
        "rate": successes / runs if runs else 0.0,
        "low": low,
        "high": high,
    }
```

## Why the same seed gives the same bytes

Two sources of variation would break reproduction: time and randomness. Time comes from an injected clock that starts at a fixed instant and advances by simulated amounts per model call, tool call and sandbox run. The latency and wait figures therefore show the report's shape; they are not measurements of any system. Randomness comes from one generator per run, seeded with the string `seed:case_id:trial`, which picks the simulated latencies and the approver's delay. A string seed gives the same sequence in every process. A seed built with Python's `hash()` would not, because that function is salted per process, and [lesson 25.4](/lessons/25-agent-capstone-and-portfolio/25.4-write-the-teardown/) shows a test catching exactly that.

## What the scripted benchmark cannot tell you

With a scripted model the three trials of a scenario cannot disagree, because the model replays the same replies. The repeated trials here demonstrate the bookkeeping, not variance. The report says so in its `evidence_kind` field: `fixture-tested`, with the model recorded as `scripted`. The benchmark is scripted by construction: `run_benchmark` always replays each scenario's script on the injected clock, so it can only produce this label. `run_case` accepts any model, but its clock stays simulated, so it would report a live model's outcomes without real latency. For live trials the course's harness is lesson 23.5's `run_trials` with its `LiveAdapter`, which labels a report `live-model-tested` only when every trial reached `OpenAICompatibleModel`, and records the model name the server reported; you record the revision yourself. The course's CI runs neither, so every number in this lesson describes the controls, not a model.

## Run the exercise

The module is `src/agentlab/capstone/benchmark.py` and the tests are in `tests/test_capstone_benchmark.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_capstone_benchmark -v`. Expect `Ran 10 tests` and `OK`. To write a report, run `uv run --frozen python -m agentlab.capstone.benchmark report.json`. It prints `24/30 succeeded, 0 safety violations` and the start of the digest.

To watch reproduction break, change `rng = random.Random(tseed)` in `run_case` (in `assistant.py`) to `rng = random.Random()`. The outcomes stay the same, but `test_the_same_seed_reproduces_the_same_digest` fails, because each run now draws its own timings. Restore the line before moving on.
