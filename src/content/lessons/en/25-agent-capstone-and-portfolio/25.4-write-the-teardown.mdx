You have a benchmark report from [lesson 25.2](/lessons/25-agent-capstone-and-portfolio/25.2-a-reproducible-benchmark/) and postmortems from [lesson 25.3](/lessons/25-agent-capstone-and-portfolio/25.3-failure-analysis/). Could someone else, on another machine, take your write-up and get the same numbers? If they cannot, the numbers are a claim about your laptop. This lesson writes the *teardown*, the document that lets a second person rerun and check the work, and tests that a clean process really reproduces it.

## What a second person needs

The NeurIPS paper checklist states what reviewers expect of any experimental result, and its items map onto six sections:

- **Setup.** The checklist asks for the code, the data and instructions with "the exact command and environment needed to run to reproduce the results". Here that is `uv sync --frozen` and the benchmark command, plus the recorded Python, Pydantic and agentlab versions.
- **Methodology.** The scenarios, the trial count, the seed, a fresh environment per trial, the evidence kind, and what counts as success. Here success means the environment ended in the expected state with no safety violation, and the model's words are not graded.
- **Results.** Every number from the report, with the interval, the failures by name and a table per scenario. The checklist asks you to state which results are reproducible if only some are.
- **Limitations.** The checklist asks for a separate section on strong assumptions, such as independence, and how robust the results are when those assumptions fail. It also asks about scope, such as testing with only a few runs.
- **Artifact manifest.** The report's digest, the fixture manifest and a SHA-256 for each input file, so a reader can tell whether they hold the same inputs.
- **Licenses.** The checklist asks you to state the version and license name of each asset you used. The capstone reads both from the installed packages' metadata: agentlab and Pydantic are MIT, and so are three of Pydantic's four dependencies.

NIST's AI Risk Management Framework makes the same point from the side of governance. Its MEASURE function says that test sets, metrics and details about the tools used during testing, evaluation, verification and validation are documented. The framework adds that documentation can enhance transparency, improve human review and bolster accountability. The teardown is that documentation for one small system.

## Render it, do not retype it

A teardown typed by hand drifts from the report it describes: a number gets rounded differently, or a failure gets left out because it was embarrassing. `render_teardown` builds the Markdown from the report itself, so every number in the text is the number in the JSON. The Limitations section is fixed text that states what this evidence cannot show. Every run used a scripted model. With a scripted model three trials cannot disagree. The clock was injected. Ten scenarios with three trials each is a teaching check, not a production reliability estimate.

A limitation is useful when it names an assumption, what breaks it and what that would do to the result. "Results may vary" names nothing. "The interval assumes independent trials; three trials of one scripted scenario are identical, so the interval is narrower than the evidence supports" names all three. The checklist adds a point worth copying. Reviewers are told not to penalize honesty about limitations, and it warns that a worse outcome is a reviewer discovering a limitation the paper did not acknowledge. Write down the limitations you know before someone else finds them.

`review_teardown` then checks what a reader must find. Each of the six sections must exist and hold text. The evidence kind, `fixture-tested`, must be stated. The report digest must appear. A test replaces the evidence kind with the vaguer word "tested" and checks that the review objects.

## Does a clean process reproduce it?

Reproduction is a comparison, not a feeling. The test that settles it starts a new Python process with `-I`, which ignores the `PYTHON*` environment variables and the current directory, in an empty temporary directory. It gives that process a different `PYTHONHASHSEED` and runs the benchmark there. Then it compares the digest with an in-process run. Anthropic's evaluation guide asks for the same isolation per trial: shared state between runs, such as leftover files, can cause correlated failures or inflate scores.

When the digests differ, a bare "the hash is different" tells nobody where to look. `reproduces` names what changed:

```python
# file: examples/agent-engineering/src/agentlab/capstone/teardown.py
def reproduces(expected: dict, actual: dict) -> list[str]:
    """Empty when the deterministic parts match; otherwise the digest and every run that differs."""
    if expected["digest"] == actual["digest"] and expected["deterministic"] == actual["deterministic"]:
        return []
    problems = [f"digest differs: {expected['digest'][:12]} vs {actual['digest'][:12]}"]
    key = lambda run: f"{run['case_id']}.t{run['trial']}"
    theirs = {key(run): run for run in actual["deterministic"]["runs"]}
    for run in expected["deterministic"]["runs"]:
        other = theirs.get(key(run))
        if other != run:
            changed = "missing" if other is None else ", ".join(name for name in run if run[name] != other.get(name))
            problems.append(f"{key(run)}: {changed}")
    if expected["deterministic"]["fixture_manifest"] != actual["deterministic"]["fixture_manifest"]:
        problems.append("fixture manifest differs: the runs read different fixture files")
    return problems
```

A tampered report with one success flipped produces `digest differs` followed by `ordinary-po1001.t1: success`, which is the run and the field to inspect.

The fresh-process test is narrower than a clean machine, and the difference matters. It reuses the installed environment. The full check is yours to run, and the course's CI does not run it. Clone the repository into a new directory, run `uv sync --frozen` and the benchmark from `examples/agent-engineering/`, and compare the new report's digest with the one in your teardown. A second person doing exactly that, on their own machine, is the acceptance test of this lesson.

## Run the exercise

The module is `src/agentlab/capstone/teardown.py` and the tests are in `tests/test_capstone_teardown.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_capstone_teardown -v`. Expect `Ran 7 tests` and `OK`. The tests render the teardown from a fresh report, check all six sections and the two required facts, flag a missing section and an empty one, read the license table from the installed metadata, reproduce the digest in a new process, and name the run in a tampered report.

To watch the fresh-process check earn its place, change `trial_seed` in `assistant.py` to return `hash((seed, case_id, trial))`. Every test in `test_capstone_benchmark.py` still passes, because two runs in one process share the same hash salt. `test_a_fresh_process_in_an_empty_directory_reproduces_the_digest` fails, because the new process salts string hashes differently and draws different timings. Restore the string seed before moving on.
