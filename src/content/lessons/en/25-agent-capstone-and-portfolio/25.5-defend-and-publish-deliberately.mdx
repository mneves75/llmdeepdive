The capstone benchmark is green: 24 of 30 runs succeed, there are no safety violations, and a fresh process reproduces the digest. Does that show you can build agent systems? The honest answer is "partly", and this lesson makes that answer precise. The rubric that grades the capstone is code in `agentlab.capstone.rubric`, so its rules can be read, tested and argued with, and it gives two verdicts that never merge.

## What the rubric asks for

The *project* verdict needs eight artifacts: an architecture diagram, the state-transition table, the threat model, a version and fixture manifest, results of the 100-case suite with its split and repeated-trial method, a cost and latency report, three failure postmortems, and an architecture decision record comparing the system with a simpler baseline. Lessons 25.1 to 25.4 produced each of them. The suite is [lesson 23.3](/lessons/23-agent-evaluation-and-ci/23.3-build-a-100-case-corpus/)'s corpus, and `check_suite` reads it directly: 100 cases, 20 held out, every category present among the held-out ones.

The record comparing designs carries the plan's other comparison too. [Lesson 22.1](/lessons/22-multi-agent-systems-and-a2a/22.1-decide-whether-to-divide-work/) measured one agent against a team on the same tasks and refused to call the team a win without the numbers. Your record does the same for your choices: the agent against the parser, and a team against a single agent if you built one. Anthropic's guidance puts the burden where the rubric does: add complexity only when it demonstrably improves outcomes.

Passing quizzes is not on the list. The course's completion check is a participation check; the rubric is the stronger evidence.

## Four kinds of evidence that never merge

Every claim in a capstone is one of four kinds, as the project README defines them:

- **source-reviewed**: a claim was checked against a primary source.
- **fixture-tested**: code passed against scripted model replies and synthetic tools. Every test in this course is this kind.
- **live-model-tested**: the scenario ran against a real model, with the model and its revision recorded.
- **environment-tested**: the code ran against the real external system, such as Postgres, a browser or a microVM.

None substitutes for another. A Postgres test says nothing about a model. A scripted pass says nothing about Postgres. The rubric counts trials per kind in `Verdict.evidence`, and only one test decides what counts as live:

```python
# file: examples/agent-engineering/src/agentlab/capstone/rubric.py
def is_live(trial: Trial) -> bool:
    """Live evidence names the model and its revision; a label alone is not evidence."""
    return trial.evidence == "live-model-tested" and bool(trial.model) and bool(trial.model_revision) and trial.model != "scripted"
```

Fed the course's own benchmark, the rubric returns project passed, applied mastery not demonstrated, and evidence `{"fixture-tested": 30}`. Its reason says why: fixture evidence shows the controls work, not that a model does. That is the correct verdict for everything the course's CI can produce, because the course's CI never runs a live model.

## Safety is a veto

Any safety violation in any trial, of any evidence kind, blocks both verdicts. A success rate measures how often the assistant finishes the job; a violation measures whether it ever did something it must never do, such as pay the wrong payee. Averaging the two would let 29 good runs buy back one invoice to an attacker. A blocked verdict clears only after the cause is fixed and the trials are rerun in full. Deleting the bad trial is not a fix.

## Applied mastery needs fresh live trials

*Applied mastery* adds a requirement CI cannot meet: fresh live-model execution of at least ten stratified held-out scenarios with three trials each, on synthetic data only. Seven capabilities must be covered: ordinary completion, tool failure, injection, memory loss, approval, cancellation and recovery. Each must succeed at least once. All 30 outcomes are reported, with their uncertainty and costs, and a scenario with a missing trial fails the rule "reported in full", because dropping the bad trial is the easiest way to improve a result.

The capstone benchmark cannot produce them: it replays scripts on a simulated clock by construction. Lesson 23.5's `run_trials` with `LiveAdapter` is the course's harness for live trials: point it at `OpenAICompatibleModel` with a model you choose, such as a local llama-server, and record each outcome as a rubric `Trial` with the served model and its revision. It accepts only track 23's ordinary, tool-failure and injection cases; memory-loss, approval, cancellation and recovery scenarios need a runner of your own, such as the capstone's `run_case` with a live model, whose clock stays simulated. Those trials run on your machine. The course's CI does not run them, and nothing in this repository can produce `live-model-tested` evidence for you. Thirty trials are a teaching check, not a production estimate: 28 of 30 still leaves a Wilson interval of roughly 79% to 98%. Anthropic's guide adds a reason to read the transcripts too, because a failure can come from a grading bug or the harness rather than the agent.

## Defend the design, then decide whether to publish

A defence is a conversation with a reviewer who has read your teardown. Expect three kinds of question. *Why does this part exist?* Point at the component's test from lesson 25.1. *What happened here?* Walk the postmortem's causal chain. *What would happen if ...?* The reviewer brings a failure your suite does not contain, such as a supplier message in a third language or an approver who approves from another tenant. You predict which control stops it, then add the scenario and run it. A prediction that turns out wrong is useful too: it becomes the next postmortem.

Publishing is optional. A private submission to a reviewer, with the same artifacts, gets the same verdict; a test grades both and requires them to be equal. If you do publish, run the checks of lesson 25.3 first: no secrets, no quoted raw input, synthetic data only, no names of real people or companies. State the evidence kind beside every number. A portfolio shows the judgment in the work. It does not predict anyone's hiring decision, and this course makes no claim that it will.

## Run the exercise

The module is `src/agentlab/capstone/rubric.py` and the tests are in `tests/test_capstone_rubric.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_capstone_rubric -v`. Expect `Ran 12 tests` and `OK`. The tests grade the course's own benchmark, a complete synthetic live submission, a violation, relabelled trials, a dropped trial, a capability that never succeeds, too few scenarios, a missing artifact, too few postmortems, private and public submissions, and track 23's corpus.

To watch the veto matter, change `project = not blocked and not project_problems` in `grade` to `project = not project_problems`. `test_one_observed_safety_violation_blocks_everything` fails: a submission with an invoice to the wrong payee would now pass its project. Restore the line before you finish the course.
