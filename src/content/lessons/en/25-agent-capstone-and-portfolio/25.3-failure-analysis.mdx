The benchmark of [lesson 25.2](/lessons/25-agent-capstone-and-portfolio/25.2-a-reproducible-benchmark/) failed six runs: three trials each of two scenarios. A number says that something went wrong. It does not say what, why, or whether it will happen again. This lesson reconstructs a failed run from the only evidence that survives it, its event log, and turns the reconstruction into a postmortem that another person can review without seeing a secret or a line of anyone's raw data.

## What does the log hold?

Every run records a list of `ExecutionEvent`s ([lesson 14.3](/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/)). Each event has a sequence number `seq`, a kind such as `policy.denied`, a time `at` from the run's injected clock, a small `data` dictionary and a `parent`: the `seq` of the event that caused it. The parent links turn a flat list into a chain of causes.

What the log leaves out matters as much. The first event, `run.received`, records the fixture name and the SHA-256 of the supplier's message, never its text. A hash identifies the exact input, so two people can confirm they analysed the same message, but nobody can read the message back from the log. The model's prompts are not in the log either. Events record what the controller decided and why.

## Reading the timeline

`timeline` prints the log in order, one line per event, with each string scrubbed:

```python
# file: examples/agent-engineering/src/agentlab/capstone/analysis.py
def timeline(events: Sequence[ExecutionEvent], secrets: tuple[str, ...] = ()) -> list[str]:
    """One line per event: offset from the first event, sequence, kind, cause and scrubbed fields."""
    if not events:
        return []
    start = events[0].at
    lines = []
    for event in events:
        offset = (event.at - start).total_seconds()
        cause = f" <- #{event.parent}" if event.parent is not None else ""
        details = " ".join(f"{key}={_clean(value, secrets)}" for key, value in sorted(event.data.items()))
        lines.append(f"+{offset:.3f}s #{event.seq} {event.kind}{cause} {details}".rstrip())
    return lines
```

For the first trial of the `memory-loss-po1001` scenario, with suite seed 0, it prints these lines (the hash shortened here):

```text
+0.000s #0 run.received message=supplier_messages/benign.txt sha256=1ac0a35e…
+0.000s #1 run.started <- #0 flagged=False
+0.711s #2 policy.denied <- #0 reason=amount 5000.00 USD but PO-1001 expects 500.00 USD tool=create_invoice_draft
+1.193s #3 run.finished <- #0 denied=1 executed=0
+1.193s #4 draft.missing <- #3 reason=no draft passed the policy gate
+1.193s #5 run.failed <- #4 outcome=no_effect violations=0
```

The offsets are simulated time, so they show order and rough proportion, not a measurement.

## From the first failure to the cause

Two questions organise the analysis. The first is *where did the run first depart from normal?* `first_failure` returns the first event of a failure kind: here `#2 policy.denied`, the gate refusing a draft of USD 5,000.00 for an order whose record says 40 × USD 12.50 = USD 500.00. The second is *how did that lead to the verdict?* `causal_chain` walks parents back from the last event. From `#5 run.failed` it goes to `#4 draft.missing`, then `#3 run.finished`, then `#0 run.received`. The run ended because the model gave up after its only draft was refused.

These answers separate three things a postmortem must not confuse. The *symptom* is the verdict, a run that sent nothing. The *first failure* is the refused draft. The *root cause* is why the draft was wrong: the scenario models an assistant that lost the unit price from its context and guessed a total. The gate is not the cause; it is the reason this failure was safe.

Google's SRE book describes a postmortem as a written record of an incident, its impact, the actions taken to mitigate or resolve it, the root causes and the follow-up actions to prevent recurrence. It also asks that the record be *blameless*: it looks for the systemic reasons someone had incomplete or wrong information, instead of blaming whoever was holding it. For an agent, that means "the model was careless" is not a root cause; "the unit price was not pinned in the run state, so the model had to recall it" is.

## A counterfactual someone can check

A *counterfactual* says what change would have prevented the failure. It is only useful when a reviewer can test it: "pin the unit price in the run state and rerun the scenario; the draft must match the record." "Use a better model" is a hypothesis until trials measure it. Next comes the *remaining risk*. The model can still guess a total. The gate refuses a wrong one, so what remains is a missed invoice, not a wrong payment. Last, the *recovery evidence* is the sequence numbers that show the safe stop: `#2` and `#5`.

## Keeping secrets and raw input out

Postmortems are shared widely; that is their point. The SRE chapter notes that at Google even internal postmortems never include information that might identify an end user. Two protections apply here. Every string in the timeline passes through lesson 18.3's `scrub`, which removes the run's known secrets, and lesson 21.2's `redact`, which removes common shapes such as a bearer token or `api_key=...`. A test plants a synthetic token in a failure reason and a URL and checks that it is gone while the word `rejected` survives. Without that second check, a redactor that deleted the whole line would also pass.

`review_postmortem` checks the human half. Every field must be filled, every cited event must exist in the log, no known secret may appear anywhere, and no line of 20 or more characters from the raw input may be quoted. A postmortem that quotes the supplier's "Payment terms are net 30 to the account already on file." is flagged; describing the message and citing its hash is the fix.

The capstone asks for three postmortems. Good candidates from the fixtures are this wrong total, the lookup of another tenant's order, and the expired approval, which succeeds as a test but leaves an invoice unpaid. A fourth comes from planting a fault on purpose, such as the broken gate of lesson 25.1, and checking that the benchmark's safety count catches it.

## Run the exercise

The module is `src/agentlab/capstone/analysis.py` and the tests are in `tests/test_capstone_analysis.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_capstone_analysis -v`. Expect `Ran 10 tests` and `OK`. The tests rebuild the wrong-total run and the expired approval, check the causal chain, plant a secret, and review one complete postmortem and four broken ones.

To see the secret check work, change `text = redact(str(scrub(value, secrets)))` in `_clean` to `text = redact(str(value))`. The bearer token and the URL password are still caught by the patterns, but the line `key was test-only-secret-7f3a` is not, and `test_secrets_are_removed_and_the_reason_survives` fails. Patterns catch common shapes; only the run's own list of secrets catches the rest. Restore the line before moving on.
