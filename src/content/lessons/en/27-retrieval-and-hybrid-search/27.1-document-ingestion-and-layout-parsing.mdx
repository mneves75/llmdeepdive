Most Retrieval-Augmented Generation (RAG, answering questions by first searching a document collection and then passing the retrieved passages to a model) projects blame the embedding model or the large language model (LLM) when answers quote the wrong number from a report. Open the raw text stored in the search index (the searchable catalog built from your documents), and half the time the answer was already destroyed before a single vector (a list of numbers representing a passage's meaning) was computed: two columns got glued together, a financial table dissolved into naked digits, or five scanned pages disappeared without raising an error. Ingestion is where retrieval quality is won or lost.

## Why PDF is hostile to text extraction

Web pages (HTML), Markdown (plain text with simple formatting marks), and Word files (DOCX) store a logical document tree—headings, paragraphs, lists, and explicit `<table>` rows. **Portable Document Format (PDF)**, standardized in ISO 32000-2, was built for a different job: guaranteeing that a page prints identically on every printer. Internally, a PDF page is mostly a stream of drawing instructions saying "paint glyph (the drawn shape of one character) `R` at coordinate `(72, 710)` in 11 pt Helvetica." Tagged PDFs can carry structure trees (hidden labels marking headings and tables), yet most real-world business PDFs omit or break them.

Picture a concrete two-column quarterly report. On horizontal line `y = 640`, column A reads `"Revenue rose 14% year over year"` and column B reads `"excluding the Q4 European write-off."` A naive extractor sorting glyphs by `y` then `x` stitches them into `"Revenue rose 14% year over year excluding the Q4 European write-off."` Worse, a 4-column balance sheet loses its column headers and turns into `"2024 41.2 2025 38.9"`—once split into tokens (word pieces, as in [Tokenization I](/lessons/1-text-to-tensors/1.2-tokenization-i/)), neither vector search nor an LLM can tell which figure belongs to which metric.

Running page headers and footers compound the damage. If a `40`-page PDF carries a `30`-word header and footer (`"Acme Corp Confidential — FY2025 Audit — Page 12 of 40"`) on every page, naive extraction splices `40 × 30 = 1,200` words of identical boilerplate right through the middle of sentences that cross page breaks.

## A four-stage layout-aware ingestion pipeline

Building on the ingestion loop introduced in [Ingestion and Retrieval](/lessons/19-agent-memory-and-context/19.2-ingestion-and-retrieval/), a production pipeline treats parsing (reading raw files into structured text) as data engineering rather than a one-line `pdftotext` command (a basic terminal tool that dumps PDF characters in raw order):

- **Format triage and OCR routing.** Inspect each file's MIME type (the short format label that identifies whether a file is PDF, HTML, or DOCX) and per-page character density. Parse HTML, Markdown, and DOCX directly from their native trees. For PDFs, detect scanned or image-heavy pages—raster images (flat pixel grids like photographs, such as embedded JPEGs, that hold no character codes) with a low text-to-area ratio—and route them to **Optical Character Recognition (OCR)** or a vision-language parser (a model that reads page images directly) instead of indexing zero tokens with no warning.
- **Layout analysis and reading-order reconstruction.** Segment each page into typed blocks—title, heading, paragraph, list, table, figure caption, header/footer—using a layout detector. Drop repeating headers, footers, and page numbers; reconstruct multi-column reading order; and serialize (convert into plain structured text) tables into Markdown or compact HTML so every cell stays bound to its row and column header.
- **Canonical text normalization.** Repair broken soft hyphens at line wraps (`"retriev-\nal"` → `"retrieval"`), normalize Unicode ligatures (two letters fused into a single printed glyph, such as `ﬁ` → `fi`), and preserve code blocks intact without stripping indentation.
- **Provenance and access-control attachment.** Attach structured metadata (descriptive tags stored beside the text) to every extracted block before chunking: provenance (where the text came from) fields like `doc_id`, `source_uri`, `page`, and `section_path` (such as `"4. Pricing > 4.2 Enterprise"`), plus access-control fields like `tenant_id` (the customer organization that owns the file), `acl_groups` (the Access Control List of user groups permitted to read it), `content_hash`, and `updated_at`.

:::insight
Serialize every table with its headers intact and prepend its nearby title or caption. If a long table spans three pages, repeat the column header row on every split chunk so no fragment becomes an orphan wall of numbers.
:::

## Incremental sync, deduplication, and tombstones

Document corpora (full collections of searchable documents) are not static zip archives; policies get amended, contracts expire, and wiki pages get deleted. Re-embedding a 100,000-document repository from scratch every night wastes money and leaves stale answers in production.

Compute a deterministic `content_hash`—a short digital fingerprint computed from the canonical parsed text plus security metadata so identical input always yields the exact same fingerprint. On each sync run:

- If `doc_id` exists with the same `content_hash`, skip chunking and embedding altogether.
- If `content_hash` changed, insert the new version's chunks atomically (in one indivisible swap so live queries never see a half-updated document) and delete the old version's chunks using the prior `version_id` so two conflicting editions of the same policy never coexist in search results.
- If a document disappeared from the source system (or lost permissions), write a **tombstone** (an explicit deletion marker) and purge its indexed chunks immediately.

:::warning
Always inspect 20 randomly sampled parsed documents visually—side by side with the original PDFs—before tuning embeddings or prompts. A 30-minute parser audit routinely recovers more retrieval recall (the share of relevant passages the search engine finds) than weeks of model swapping.
:::

## When text extraction is still not enough

Some enterprise documents—engineering blueprints, dense slide decks with callout arrows, scanned handwritten forms, or multi-axis financial charts—encode key meaning visually rather than in prose. Converting those pages to text alone discards spatial relationships. Later in Part 3, you will see how visual document RAG indexes page images directly alongside text parsing; for every text-centric corpus, clean layout-aware parsing remains the foundation that sets your retrieval ceiling.
