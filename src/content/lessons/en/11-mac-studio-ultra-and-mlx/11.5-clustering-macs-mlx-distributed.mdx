Apple's newsroom post describes clustering several Mac Studios with Thunderbolt 5 and RDMA, and says a cluster of four delivers up to 3x faster AI inference than a single system. The Mac Studio page's footnote names the test: completion time of a 32K-token LLM summarization on a 72-billion-parameter dense model with mlx-lm, single system against a 4-node full-mesh Thunderbolt 5 and RDMA cluster. That is a long-prefill job, not single-stream decode, and it is Apple's test, not a plan. This lesson gives you a plan: what a cluster adds, what the link costs, and how to test a launch before you trust it. Lesson 5.8 owns the theory of tensor and pipeline parallelism, and lesson 9.9 owns the per-token communication model.

## The link against the memory

Apple quotes Thunderbolt 5 at up to 120 Gb/s, and an M5 Ultra has up to six ports. Intel's launch release for the standard gives 80 Gb/s of bi-directional bandwidth and describes 120 Gb/s as Bandwidth Boost, aimed at video-intensive use. Collectives move data both ways, so read 80 Gb/s as the planning bound and Apple's figure as a best case. A model's weights are read from local memory at 1.2 TB/s. The link is far narrower:

$$
\frac{80\ \text{Gb/s}}{8} = 10\ \text{GB/s}, \qquad \frac{1{,}200\ \text{GB/s}}{10\ \text{GB/s}} = 120.
$$

At Apple's 15 GB/s the gap is 80 times. Either way, weights stay where they are, and only activations cross. Lesson 9.9's model of tensor parallelism sends 128 all-reduces per token with 1.25 MiB of payload. At 10 GB/s that payload is about 0.13 ms of wire time per token (0.09 ms at 15), which is small. What costs is the 128 waits, one per collective. Decode is latency-bound. A 4,096-token prefill carries about 5 GiB of the same traffic, roughly 0.54 s at 10 GB/s (0.36 s at 15), so prefill is bandwidth-bound. Both figures are planning heuristics from peak rates that ignore protocol overhead and overlap.

## The backends

| Backend | What it is |
|---|---|
| ring | All-reduce and all-gather over TCP sockets. Always available. Works over Ethernet or a Thunderbolt ring. |
| MPI | A mature library you install; `mlx.launch --backend mpi` wraps `mpirun`. |
| JACCL | RDMA over Thunderbolt, from macOS 26.2. The docs give it communication latency "an order of magnitude lower" than ring and call it needed for tensor parallelism at usable latency. |
| NCCL | The CUDA backend. |

`mx.distributed.init(backend=...)` accepts `any`, `ring`, `jaccl`, `mpi` and `nccl`. JACCL asks for a fully connected mesh: a cable between every pair of Macs, as the distributed docs require. v0.32.3 also ships a `jaccl-ring` launcher mode that checks only neighbour links; this lesson did not test it. Four Macs need six cables and three Thunderbolt ports each, which an M5 Ultra has. RDMA is off by default. The docs say you enable it with `rdma_ctl enable` in macOS Recovery, that this cannot be done remotely even with sudo, and that `ibv_devices` should then list the `rdma_en` devices. `mlx.distributed_config` discovers the cabling, checks the mesh and writes the hostfile for `mlx.launch`:

```bash
mlx.distributed_config --verbose --hosts host1,host2 --over thunderbolt --backend jaccl --auto-setup --output-hostfile hosts.json
mlx.launch --backend jaccl --hostfile hosts.json --python /path/to/python sharded_generate.py --model MODEL --prompt "Hello"
```

Not run here: that needs two Macs, recovery-mode RDMA, and password-less sudo for `--auto-setup`. Its network changes are real: the script disables the Thunderbolt bridge and sets up a private subnet per cable.

## Test the launch on one Mac first

`mlx.launch -n 2` starts two ranks on localhost with the ring backend, so you can check the script, the launch line and the model's sharding before cabling anything. Two ranks share one GPU here, so this proves correctness, not speed. Save the docs example and run it:

```python
import mlx.core as mx

world = mx.distributed.init()
x = mx.distributed.all_sum(mx.ones(10))
mx.eval(x)
print(world.rank(), world.size(), x)
```

```bash
mlx.launch -n 2 --python "$(mlx.launch --print-python)" dist_sum.py
```

Both ranks print their rank, the size 2 and an array of 2s. Then try the mlx-lm example with each sharding mode. Fetch `sharded_generate.py` from the pinned tag. The ids below are MLX builds on the Hub that stand in for the course model, one dense `qwen3` and one hybrid `qwen3_5`:

```bash
PY="$(mlx.launch --print-python)"
mlx.launch -n 2 --python "$PY" sharded_generate.py --model mlx-community/Qwen3.5-9B-4bit --prompt "Name one planet." --max-tokens 12
mlx.launch -n 2 --python "$PY" sharded_generate.py --pipeline --model mlx-community/Qwen3.5-9B-4bit --prompt "Name one planet." --max-tokens 12
mlx.launch -n 2 --python "$PY" sharded_generate.py --pipeline --model mlx-community/Qwen3-4B-Instruct-2507-4bit --prompt "Name one planet." --max-tokens 12
```

The first runs tensor parallelism, the default. The second runs pipeline parallelism. The third stops with `ValueError: The model does not support pipelining but a pipeline_group was provided`, and `mlx.launch` still exits 0. In mlx-lm 0.32.0, `sharded_load` needs the model class to define `shard` for tensor parallelism and `pipeline` for pipelining. The dense `qwen3` has the first only, and `qwen3_5` has both. `mlx_lm.chat` and `mlx_lm.server` take the same `--pipeline` flag. In distributed mode, `mlx_lm.chat` rejects adapters, and `mlx_lm.server` rejects adapters and draft models. For Qwen3.8-27B, lesson 9.9 caps clean tensor parallelism at the 4 KV heads, which is also the size of Apple's cluster. This lesson loaded no 27B.

## The classic wrong turn

The wrong turn is to cluster a model that fits one machine and expect it to go faster. The pinned 17.1 GB artifact fits a single Mac Studio with room to spare, so splitting it adds 128 waits per token and removes nothing it needed. A cluster pays off when the model does not fit one machine's GPU-usable pool, the number you read in lesson 11.1, or when the job is a long prefill, the case Apple's 32K-token test measures. The 128 per-token waits belong to tensor parallelism in decode. To predict decode on a real cluster, put your own measured per-collective latency into lesson 9.9's model; the MLX docs give none.

:::warning
Do not trust the launcher's exit status. When both ranks exited with code 3, `mlx.launch` printed a warning for each and still returned 0 at v0.32.3. Read each rank's output before you believe a run.
:::

:::caveat
The MLX docs advise leaving `MLX_METAL_FAST_SYNCH` unset, because it can deadlock and leave the GPU wedged (issue 3142), while the docstring of the mlx-lm example sets it to 1. Follow the docs. Also, do not read `mx.distributed.is_available("jaccl")` as proof that RDMA works: on the Mac used to check this lesson, `rdma_ctl status` printed `disabled` and `ibv_devices` listed no devices, yet the call returned true. Apple's 3x and every JACCL claim in this lesson come from vendor or project documents, not from a cluster run for this lesson.
:::

The durable idea is that a cluster moves the bottleneck from capacity to the wire. Local memory is 80 to 120 times faster than the link, so the design that works keeps weights home and spends the link on small, rare messages.
