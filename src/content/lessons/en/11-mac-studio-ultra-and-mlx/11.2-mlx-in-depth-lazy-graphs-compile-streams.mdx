[Lesson 8.9](/lessons/8-building-and-serving-stacks/8.9-mlx/) introduced two ideas. MLX is **lazy**: a line such as `y = a @ a` does not multiply anything yet; it only records the operation in a **graph**, a list of operations and the arrays each one depends on. And MLX arrays live in unified memory, one pool that the CPU and GPU share. This lesson turns those ideas into controls. Every MLX job raises four questions: when does the graph run, how is it fused, which queue runs it, and how much memory may it take. The answers explain most of the odd timings and out-of-memory surprises you will meet on a Mac Studio.

## When the graph runs

Each operation adds a node to the graph, and nothing is computed until you ask. `mx.eval(x)` runs the part of the graph that `x` needs and waits for it to finish. `mx.async_eval(x)` starts the same work and returns at once, while the GPU keeps going. Its docstring calls it experimental, but mlx-lm depends on it.

Here is how mlx-lm uses it to keep the GPU busy. In `generate_step`, the loop builds the graph for the next token from the sampled token, which is itself still an uncomputed node. It calls `async_eval` on that graph, and only then calls `.item()` to read the previous token's value. So the CPU prepares step n+1 while the GPU runs step n. Without laziness there would be nothing to overlap.

Some actions force evaluation without an explicit call. The docs name these implicit triggers: printing an array, converting it to NumPy, `.item()`, saving it, and using a scalar array in Python control flow (an `if` or a `while`). They also give a sizing rule: from a few tens to many thousands of operations per evaluation is fine. Evaluating after every operation pays a fixed cost each time. The natural place to evaluate is once per step of the outer loop.

## How the graph is fused

A **kernel** is a small program that runs on the GPU, and launching each one costs time. `mx.compile` cuts that cost. It **traces** a function once: it runs your Python code with placeholder inputs and records which operations it performs. It then merges common work, fuses chains of element-wise steps (steps that treat each number on its own) into fewer kernels, and caches the result. The docs list what forces a new compile: a changed shape (the size of each dimension), rank (the number of dimensions), dtype (the number type, such as float32 or float16) or input count. A probe counter makes this visible, because Python runs the body only while tracing. Run it:

```python
import math
import mlx.core as mx

traces = 0

def gelu(x):
    global traces
    traces += 1  # a probe: Python runs this body only while MLX traces it
    return x * (1 + mx.erf(x / math.sqrt(2))) / 2

fast = mx.compile(gelu)
x = mx.random.uniform(shape=(8, 16))
mx.eval(fast(x)); mx.eval(fast(x))
print("same shape twice:", traces)
mx.eval(fast(mx.random.uniform(shape=(8, 32))))
print("new shape:", traces)
mx.eval(fast(mx.random.uniform(shape=(8, 32)).astype(mx.float16)))
print("new dtype:", traces)

traces = 0
flex = mx.compile(gelu, shapeless=True)
for shape in [(8, 16), (8, 32), (4, 7)]:
    mx.eval(flex(mx.random.uniform(shape=shape)))
print("shapeless, same rank:", traces)
mx.eval(flex(mx.random.uniform(shape=(2, 3, 5))))
print("shapeless, new rank:", traces)
```

On MLX 0.32.3 this prints 1, 2, 3, then 1 and 2. A new shape and a new dtype each trace again. With `shapeless=True`, three shapes of one rank traced once, and a new rank traced again. That is what this build did, so check it on yours.

Compiled functions must be **pure**: their result may depend only on their inputs, and they may not change anything outside themselves. Printing inside one crashes, because during tracing the arrays are placeholders with no values. State you want to carry from call to call must go through the `inputs` and `outputs` arguments. mlx-lm's samplers use exactly that, compiling with `inputs=mx.random.state, outputs=mx.random.state` so the random key advances.

## Which queue runs it

A **stream** is a queue of work for one device, the CPU or the GPU. Every operation accepts `stream=`, which may be a stream or a device. The default is the default stream of the default device. Arrays are not moved between devices, because they live in unified memory. When an operation on one stream needs the output of another, MLX inserts the dependency itself. `mx.synchronize()` waits for a stream, and `with mx.stream(s):` sets it for a block.

## Hand-written kernels

Some operations are common enough that MLX ships them already fused. `mx.fast` holds them, among others `rms_norm`, `layer_norm`, `rope`, `scaled_dot_product_attention` and the kernel builders. When no fused operation fits, you can write your own kernel in Metal, Apple's language for GPU programs. `mx.fast.metal_kernel` takes only the kernel body and builds the signature from your input and output names:

```python
import mlx.core as mx

source = """
    uint elem = thread_position_in_grid.x;
    T tmp = inp[elem];
    out[elem] = metal::exp(tmp);
"""
kernel = mx.fast.metal_kernel(
    name="myexp", input_names=["inp"], output_names=["out"], source=source
)

def exp_elementwise(a):
    return kernel(
        inputs=[a],
        template=[("T", mx.float32)],
        grid=(a.size, 1, 1),
        threadgroup=(256, 1, 1),
        output_shapes=[a.shape],
        output_dtypes=[a.dtype],
    )[0]

a = mx.random.normal(shape=(4, 16)).astype(mx.float16)
print("matches mx.exp:", mx.allclose(exp_elementwise(a), mx.exp(a)).item())
```

Build the kernel once; each build creates a Metal library. The course model uses this for real. Its Gated DeltaNet layers ([lesson 4.15](/lessons/4-transformer/4.15-gated-deltanet/)) update a fixed-size state once per token, a step called the recurrence. In mlx-lm 0.32.0, `gated_delta.py` runs that recurrence as a Metal kernel on the GPU. It falls back to plain operations when the device is not the GPU or the key dimension is not a multiple of 32. Compare the two paths:

```python
import mlx.core as mx
from mlx_lm.models.gated_delta import gated_delta_update, normalize_qk

B, T, Hk, Hv, Dk, Dv = 1, 16, 2, 4, 128, 128
q = mx.random.normal((B, T, Hk, Dk))
k = mx.random.normal((B, T, Hk, Dk))
v = mx.random.normal((B, T, Hv, Dv))
a = mx.random.normal((B, T, Hv))
b = mx.random.normal((B, T, Hv))
A_log = mx.random.normal((Hv,))
dt_bias = mx.random.normal((Hv,))
q, k = normalize_qk(q, k, inv_scale=Dk**-0.5, eps=1e-6)

y_gpu, s_gpu = gated_delta_update(q, k, v, a, b, A_log, dt_bias, use_kernel=True)
y_ref, s_ref = gated_delta_update(q, k, v, a, b, A_log, dt_bias, use_kernel=False)
print("state:", s_gpu.dtype, s_gpu.shape)
print("max output gap:", mx.abs(y_gpu - y_ref).max().item())
```

The outputs agree to within about $10^{-8}$, and the initial state is float32 with shape batch, value heads, value dimension, key dimension. Lesson 8.9 left the runtime's state dtype open. For the initial state, this source answers it: float32, the dtype [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/) assumed for its reference figure.

## How much memory it may take

Four separate limits decide how much memory an MLX job may take. The first two are about **wired** memory, which is locked in RAM so macOS cannot move it out to disk ([lesson 11.1](/lessons/11-mac-studio-ultra-and-mlx/11.1-mac-studio-ultra-as-an-inference-machine/)). The other two are MLX's own budgets: one for the arrays a graph evaluation creates, one for the freed buffers MLX keeps for reuse. The "recommended working set" in the table is the most memory macOS recommends the GPU use at once.

| Control | What it does |
|---|---|
| `iogpu.wired_limit_mb` (system) | The cap macOS puts on wired GPU memory. `mx.device_info()["max_recommended_working_set_size"]` reports it. |
| `mx.set_wired_limit(bytes)` | Keeps that much memory resident. Default 0, useful on macOS 15 or later, and an error above the system limit. |
| `mx.set_memory_limit(bytes)` | A guideline for graph evaluation. Default is the smaller of 1.5 times the recommended working set and 95 percent of installed memory (60.8 GiB on a Mac with 64 GiB installed, where 1.5 times would be 77.8, so the 95 percent bound is the smaller one). The docstring says only 1.5 times. Past it, with no RAM left, allocation raises an exception. |
| `mx.set_cache_limit(bytes)`, `mx.clear_cache()` | Bound and empty the pool of freed buffers MLX keeps for reuse. The cache limit starts equal to the memory limit. |

Read usage with `get_active_memory` (excludes the cache), `get_cache_memory`, and `get_peak_memory` with `reset_peak_memory`.

## Why a stopwatch around one line reads almost nothing

Laziness also breaks naive measurement. If you read a timer or the peak memory before evaluation, you measure the recording of the graph, not the work. Both readings below are wrong:

```python
import time
import mlx.core as mx

a = mx.random.normal((4096, 4096))
mx.eval(a)
mx.reset_peak_memory()

t0 = time.perf_counter()
y = a @ a                                  # recorded, nothing ran yet
build_ms = (time.perf_counter() - t0) * 1e3
peak_before = mx.get_peak_memory()

mx.eval(y)                                 # the work happens here
total_ms = (time.perf_counter() - t0) * 1e3
print("build ms:", round(build_ms, 2), "total ms:", round(total_ms, 2))
print("peak MB before eval:", peak_before // 10**6, "after:", mx.get_peak_memory() // 10**6)
```

The first time is graph building, and the first peak is zero because the product has not been allocated. The fix has three steps: evaluate, warm up with a run you throw away, then read.

:::warning
Do not change the wired limit while an `async_eval` may be running. The mlx-lm source says so, and its `wired_limit` context manager synchronizes the stream before it restores the old value.
:::

:::caveat
Facts here are for MLX 0.32.3 and mlx-lm 0.32.0. The docs mark `async_eval` experimental and describe the advanced environment variables as subject to change. The shapeless result was observed on this build, not promised by the docs.
:::

An MLX program is a graph you steer: you choose when it runs, what is fused, where it runs and how much memory it may take. [Lesson 11.3](/lessons/11-mac-studio-ultra-and-mlx/11.3-mlx-lm-in-practice/) uses these rules inside mlx-lm to convert, tune and cache real models.
