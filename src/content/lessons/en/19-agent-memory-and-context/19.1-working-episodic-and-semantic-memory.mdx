Next week the purchasing assistant handles PO-1002 again, and it "remembers" that Supplier Omega is pre-approved. Nobody at the company said that. The sentence came from a supplier e-mail the assistant read last week, which carried a prompt-injection attempt: text written to make a model follow it as an instruction. Somewhere between last week and now, a quoted claim from outside became something the assistant treats as known. This lesson names the kinds of things an agent keeps, and the two fields every stored item needs so that it cannot come back as something it was not.

## What does "memory" mean for an agent?

The word covers several different things, and mixing them up causes most of the confusion.

- **Model weights.** What a model learned in training. Lewis et al. (2020) call this *parametric* memory and contrast it with *non-parametric* memory, in their case a dense vector index of Wikipedia searched by a retriever. Your agent cannot write to the weights while it runs.
- **The context window.** The input of one model call, measured in tokens. It is capacity, not storage: when the call ends, nothing in it persists unless your program saved it.
- **Inference memory.** The accelerator memory a call uses while it runs, mostly the KV cache that [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/) sizes. It is a cost of serving, not something the agent recalls later.
- **Stored records.** Everything your program writes down and may put into a later context: run state, events, messages, extracted facts. This track is about these.

Six properties that are often blurred deserve separate names. *Capacity* is how many tokens fit. *Relevance* is whether the text helps with the task. *Retrieval error* is fetching the wrong record or missing the right one. *Model quality* is how well the model uses what it sees. *Latency* grows with input length. *Inference memory* grows with it too. A longer window raises capacity only. It is neither unlimited memory nor a guaranteed cause of hallucination. Liu et al. (2023) measured a different effect: on multi-document question answering, accuracy was often highest when the relevant passage sat at the start or end of the input, and it dropped when the passage was in the middle, even for models built for long inputs.

## Three kinds of record, as a sorting tool

A common way to sort stored records borrows three words. Treat them as a sorting tool for design discussions, not as a protocol or the only architecture.

*Working memory* is the state of the run in hand: the `RunState` that [lesson 14.3](/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/) checkpoints, the request being handled, the invoice draft. It lives as long as the run.

*Episodic memory* is dated records of what happened or what was said: execution events, transcript turns, the supplier's e-mail. An episodic record says "on Tuesday, the supplier wrote that the bolts were delivered". It does not say the bolts were delivered.

*Semantic memory* is facts the assistant may rely on in later runs: the purchase database shows PO-1001 as received; the buyer's standing rule says never to order shelving from Supplier Gamma.

Other designs draw different lines. MemGPT (Packer et al., 2023) borrows from operating systems: it describes memory tiers, moves data between a small context and slower external storage the way an operating system pages memory, and uses interrupts to manage control flow. Its authors evaluate it on document analysis and multi-session chat. A retrieval-augmented system in the style of Lewis et al. has no tiers at all, only a model and an index. The three words help you ask "how long should this live, and what may it be used for?". The answer to "is it safe to reuse?" comes from somewhere else.

## Provenance: who said it, and who may read it

*Provenance* is the record of where a piece of data came from. In the project every stored item is a `MemoryRecord`, and two of its fields carry most of the safety:

```python
# file: examples/agent-engineering/src/agentlab/memory/records.py
class MemoryRecord(Record):
    memory_id: str = Field(pattern=r"^[a-z0-9][a-z0-9_.:-]{0,63}$")
    tenant_id: str = Field(min_length=1, max_length=64)
    kind: MemoryKind
    origin: Origin
    text: str = Field(min_length=1, max_length=4000)
    created_at: AwareDatetime
    # Empty means every user of the tenant; otherwise only these user ids.
    readers: frozenset[str] = frozenset()
    # The memory_ids this record was made from, so deleting a source can find it.
    derived_from: tuple[str, ...] = ()
    supersedes: str | None = None
    expires_at: AwareDatetime | None = None
    # Pinned records are never evicted to save space; expiry still applies.
    pinned: bool = False
```

`origin` says who produced the text: `user` (the authenticated person), `system_of_record` (the company's own database), `external` (someone outside, such as a supplier) or `model` (a summary or extraction a model wrote). There is no default, so a record without an origin fails validation. `derived_from` lists the records this one was made from; [lesson 19.4](/lessons/19-agent-memory-and-context/19.4-scoring-eviction-and-forgetting/) uses it to delete a summary when its source is deleted.

The access rule is `tenant_id` plus `readers`. A *tenant* is one customer company whose data must never reach another. `visible(record, principal)` allows a read only when the tenant matches and, if `readers` is not empty, the user is listed. The `Principal` comes from the trusted runtime, as in every earlier track, never from a query or from model output.

## When does a transcript line become a fact?

A transcript faithfully records what was said. That is exactly why it cannot be read back as truth: the supplier's e-mail and the injected note are both faithful transcript. Promotion to a semantic fact is an explicit step with a rule:

```python
# file: examples/agent-engineering/src/agentlab/memory/records.py
    if observation.kind != "episodic":
        raise ValueError("only an episodic observation can be promoted")
    if corroboration is not None and corroboration.tenant_id != observation.tenant_id:
        raise UnverifiedFact("corroboration comes from another tenant")
    if observation.origin not in TRUSTED_ORIGINS and (corroboration is None or corroboration.origin != "system_of_record"):
        raise UnverifiedFact(f"{observation.origin} text needs a system-of-record source before it is a fact")
```

The supplier's "delivered on Tuesday" alone raises `UnverifiedFact`. With the purchase record for PO-1001 as corroboration, it becomes a fact whose `derived_from` names both records. A model's summary alone is refused for the same reason as the supplier's text. A user's own statement may stand as the user's claim, keeping `origin="user"`, which is right for a rule the buyer sets and says nothing about what a supplier did. The fact's readers are the narrowest of its sources' readers, and two sources with no common reader raise instead of producing a tenant-wide fact.

:::warning
Even a verified fact is not authority. A fact that PO-1001 was delivered cannot approve a payment or change a payee. Permissions come from the principal and the approval path, never from text in memory. [Lesson 16.2](/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) treats an instruction found in retrieved text as data; memory must never turn it back into an instruction a later run obeys.
:::
