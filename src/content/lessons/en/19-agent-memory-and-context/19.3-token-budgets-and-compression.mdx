The purchasing assistant runs on a model with a 32,768-token context window. One request carries 1,200 tokens of system instructions, 2,400 tokens of tool schemas, six retrieved chunks of 800 tokens each and a 50-turn conversation history of 21,000 tokens. You want 4,096 tokens kept free for the answer. Does the request fit, and if not, what has to give? This lesson does the arithmetic, then compresses a real 50-turn conversation and measures what the compression lost.

## Where does a context window go?

A *context window* is the number of tokens one model call can hold. It holds the prompt and the tokens the model generates, so a prompt that fills the window leaves no room for an answer. The first step is therefore to reserve the output:

- input limit: 32,768 − 4,096 = 28,672 tokens.

Some parts of the request are fixed for this step: the system instructions, the tool schemas (the descriptions of the tools the model may call) and the retrieved chunks. Together they take 1,200 + 2,400 + 6 × 800 = 8,400 tokens. The conversation history gets the rest. The request as given uses 8,400 + 21,000 = 29,400 tokens, which is 728 over the input limit. The history must shrink to at most 28,672 − 8,400 = 20,272 tokens.

Change the window and the verdict changes. With 131,072 tokens the same request fits with 97,576 to spare. With 8,192 tokens the input limit is 4,096, which cannot hold even the 8,400 fixed tokens, so no amount of history compression helps; you must send fewer schemas or fewer chunks. The calculator below starts from these numbers and lets you move each part.

## Counting tokens, approximately and on purpose

Every number above assumes you counted with the model's own tokenizer. [Lesson 1.4](/lessons/1-text-to-tensors/1.4-sentencepiece-byte-level-token-counts/) showed why: token counts belong to a tokenizer, not to the text, and the same sentence costs different amounts in English and Portuguese. The exercise must run offline with no model, so it uses a deliberate approximation, labelled as one in the code:

```python
# file: examples/agent-engineering/src/agentlab/memory/compression.py
def approx_tokens(text: str) -> int:
    """About four characters per token, rounded up.

    shortcut: an approximation, not any model's tokenizer; real counts differ
    by tokenizer and language (lesson 1.4). Count with the model's own
    tokenizer before trusting a budget that is close to the limit.
    """
    return math.ceil(len(text) / 4)
```

A budget with a wide margin survives an approximate count. A budget 728 tokens over, or 728 under, does not: measure it with the real tokenizer.

## Fitting is not the same as being used

A history that fits is not a history the model will use well. Liu et al. (2023) measured multi-document question answering and key-value retrieval. Accuracy was often highest when the relevant information sat at the beginning or the end of the input and dropped when it sat in the middle, including for models built for long inputs. Input length also costs latency and inference memory; the KV cache that grows with every token is sized in [lesson 7.2](/lessons/7-inference-and-efficiency/7.2-the-kv-cache/). Capacity, position, latency and memory are four different questions, and a bigger window answers only the first.

## Compressing fifty turns, measured by lost facts

The exercise's conversation is small enough to read: 50 alternating turns, 937 approximate tokens, generated by `conversation()` in `compression.py`. Six user turns state the facts that matter; the rest is routine chatter about couriers, tickets and meetings. Three facts are commitments (pay PO-1001 within 30 days, an approval limit of USD 5,000, ask the warehouse lead before accepting a partial delivery) and three are negations (never order shelving from Supplier Gamma, do not combine PO-1002 and PO-1004 on one invoice, do not pay PO-1003 until the gloves arrive). The budget is 500 tokens. The lab's numbers and the exercise's numbers are the same arithmetic at two sizes.

`score` checks each fact against the compressed turns. A fact is *kept* when one turn still holds all its key terms and, for a negation, the negating word. It is *flipped* when the terms survive but the negating word does not, and *lost* otherwise. Three compressors, all within 500 tokens:

| Compressor | Tokens | Turns kept | Kept | Lost | Flipped |
|---|---|---|---|---|---|
| `recent_window` | 497 | 25 | 2 | 4 | 0 |
| `drop_stopwords` | 500 | 35 | 1 | 3 | 2 |
| `pin_ledger` | 490 | 26 | 6 | 0 | 0 |

`recent_window` keeps the newest turns that fit, from turn 25 on, so the four facts stated before it are lost. `drop_stopwords` deletes small words from every turn, using a stopword list that contains *not* and *never*. It packs in more turns and is the worst of the three: "Do not pay PO-1003 until the gloves arrive." becomes "pay PO-1003 gloves arrive.", a prohibition turned into an instruction. A flipped fact is worse than a lost one, because the model now reads the opposite of what the buyer said.

`pin_ledger` keeps every flagged commitment verbatim and fills the rest with recent turns:

```python
# file: examples/agent-engineering/src/agentlab/memory/compression.py
    ledger = [t for t in turns if t.fact]
    remaining = budget - total_tokens(ledger)
    if remaining < 0:
        raise ValueError(f"the commitments alone need {total_tokens(ledger)} tokens; the budget is {budget}")
    recent = recent_window([t for t in turns if not t.fact], remaining)
    return sorted(ledger + recent, key=lambda t: t.index)
```

The six flagged turns cost 85 tokens, and the call fails loudly when they alone exceed the budget instead of cutting one to fit. MemGPT (Packer et al., 2023) is one published design in the same spirit: it moves data between a limited context and external storage rather than trusting the window to hold everything.

:::caveat
The ledger works here because the controller flags a commitment when the user states it. In a real system that flag comes from an extraction step, which can itself miss a commitment, and `score` is how you would find out. A model-written summary is a fourth compressor; scoring it needs a model, so the course's CI does not run one, but you would score it with the same facts.
:::
