In turn 12 of a conversation, the buyer gave the assistant a mobile number, 555-0142, for late-delivery calls. A week later the buyer asks the assistant to forget it. The store holds the turn itself, `turn-12`. It also holds `sum-1`, a summary a model wrote of turns 12 and 13, and `fact-1`, a fact extracted from that summary. The vector index keeps its own copy of all three. Delete only `turn-12` and a search for the number still finds it twice. This lesson separates the reasons a record leaves memory and gives each its own rule.

## Why do records leave memory?

Four different events remove a record, or stop it from being used.

- **Expiry.** A *TTL* (time to live) ends a record's useful life at a fixed instant, `expires_at`. A one-time dock code should not be offered next month. Retrieval ignores an expired record even before anything deletes it.
- **Supersession.** A newer record replaces an older one: "Deliver to dock 5" has `supersedes="addr-1"`, the record that said dock 2. The old record stays as history, but retrieval no longer returns it.
- **Eviction.** The store is full, so something must go to make room.
- **Deletion.** Someone with the right to ask wants the data gone.

The first two are rules about truth over time. The last two are about space and about rights, and they differ in what happens to derived records.

## Scoring what to keep: recency and use

Eviction needs a score that does not depend on a query, because no query is running when space runs out. *Relevance* in the retrieval sense belongs to a query, so this store uses a stand-in: how often a record was retrieved in the past. The score mixes that with *recency*, how recently the record was created:

```python
# file: examples/agent-engineering/src/agentlab/memory/store.py
    def retention_score(self, record: MemoryRecord) -> float:
        """Halves every ``half_life`` of age, times one plus the number of past retrievals."""
        age = self._now() - record.created_at
        return 0.5 ** (age / self._half_life) * (1 + self._hits[record.memory_id])
```

A *half-life* is the time after which the recency part halves. With a seven-day half-life, a ten-day-old record nobody retrieved scores $0.5^{10/7} \approx 0.37$. The same record retrieved three times scores about $4 \times 0.37 \approx 1.49$. A two-day-old record nobody retrieved scores $0.5^{2/7} \approx 0.82$. So the often-used old record outlives the fresh unused one, and without use, recency decides. The clock is injected (`now`), so tests can move time without sleeping.

Two limits come with this choice. A use count rewards whatever was retrieved, including a record retrieved by mistake. And a commitment can be rarely retrieved and still essential, so the store lets you *pin* a record: pinned records are never evicted for space. Expiry still applies to them, because an expired one-time code is wrong whether or not it was pinned.

## Eviction is not deletion

Eviction frees space. If it removes `turn-3` but keeps `sum-1`, the summary of it, that is the point of summarising: the short version stays. Deletion honours a request to forget, so it must also remove every record made from the deleted one, directly or through another derived record:

```python
# file: examples/agent-engineering/src/agentlab/memory/store.py
        doomed = [memory_id]
        changed = True
        while changed:
            changed = False
            for record in self._records.values():
                if record.memory_id not in doomed and any(source in doomed for source in record.derived_from):
                    doomed.append(record.memory_id)
                    changed = True
        for doomed_id in doomed:
            self._remove(doomed_id)
        return doomed
```

The loop repeats until a pass adds nothing, so `fact-1`, made from `sum-1`, goes along with `sum-1`, made from `turn-12`. `turn-13` and a summary of `turn-20` stay: they were not made from the deleted turn. Before deleting anything, `forget` checks `visible(record, principal)`, so another tenant cannot delete this buyer's records.

The rule works only because every derived record lists its sources. That is why [lesson 19.1](/lessons/19-agent-memory-and-context/19.1-working-episodic-and-semantic-memory/) required `derived_from` and [lesson 19.2](/lessons/19-agent-memory-and-context/19.2-ingestion-and-retrieval/)'s chunks name their message. A summary written without its lineage cannot be found by a deletion request later.

## Deletion in a real vector index

The project's store keeps a separate index copy of each record, standing in for a vector database that stores text or metadata beside each vector. `_remove` deletes both, and one test checks that vector search cannot reach a forgotten record. A real index makes this harder, so read the deletion documentation of the one you use. Faiss's wiki, for example, says `remove_ids` scans the whole database, so it is efficient only when many vectors are removed at once. It lists `IndexFlat`, `IndexIVFFlat` and `IDMap` as supporting it. It also says removal from sequential indexes such as `IndexFlat` shifts the ids of the vectors above the removed one, so code that maps memory ids to positions points at the wrong records afterwards.

Weights are harder still. Lewis et al. (2020) describe updating the knowledge stored in a model's parameters as an open problem and present retrieval from an external index as one way around it. A record you can delete is much easier to forget than something trained into weights.

:::caveat
This exercise's retention policy covers the store's records and its index. It does not cover backups, logs, traces, caches or copies sent to a model provider. Each of those needs its own rule and its own test, so never claim deletion beyond what you tested.
:::
