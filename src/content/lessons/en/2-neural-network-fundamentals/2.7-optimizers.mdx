[Lesson 2.6](/lessons/2-neural-network-fundamentals/2.6-gradient-descent-loss-landscape/) left a concrete failure on the table. In a bowl a hundred times steeper along one axis than another, any learning rate small enough to keep the steep direction stable leaves the shallow direction crawling. Any rate fast enough for the shallow direction blows the steep one up. Backpropagation cannot help, because it reported both gradients correctly. The fix has to live in how the update uses them, which is what an **optimizer** is.

## What does plain SGD leave unsolved?

Plain minibatch **SGD** (stochastic gradient descent, one step per noisy minibatch gradient) does the minimum: $\theta_t=\theta_{t-1}-\eta g_t$. It keeps little state and has a clear interpretation, and it has exactly the failure described above.

## How does momentum calm the ravine?

**Momentum** adds a velocity and steps along that instead of the raw gradient. The velocity is usually an **exponential moving average** of gradients: a running average where each new gradient gets a fixed share of the weight and older ones fade geometrically. Components that persist across steps accumulate; components that alternate in sign partly cancel. In the ravine, the wall-to-wall bouncing along the steep axis largely cancels itself, while the steady push along the shallow axis builds up. Different libraries use slightly different equations and Nesterov variants, so hyperparameters do not transfer by name alone.

## How does Adam give each direction its own step size?

**Adam** attacks the scale mismatch directly. Per coordinate it keeps two running averages: a first moment $m_t$, which is a smoothed gradient, and a second raw moment $v_t$, which is a smoothed squared gradient. Both averages start at zero, so early on they are biased toward zero. With the usual decay of 0.9, a first gradient of 2 gives a first average of 0.9 × 0 + 0.1 × 2 = 0.2, ten times too small. A step called bias correction divides by 1 − 0.9 = 0.1 at that first step, giving back 2, and the correction fades as the steps add up. After bias correction the update is roughly

$$
\theta_t=\theta_{t-1}-\eta\,\frac{\hat m_t}{\sqrt{\hat v_t}+\epsilon}.
$$

Here $\epsilon$ is a tiny constant that prevents division by zero. Work out what that update does to the ravine. Along the steep axis the gradients are consistently large, so $\sqrt{\hat v}$ is large and divides the step back down. Along the shallow axis the gradients are consistently tiny, so $\sqrt{\hat v}$ is tiny and divides the step back *up*.

If a coordinate's gradient has a steady magnitude $|g|$, then $\hat m\approx g$ and $\sqrt{\hat v}\approx|g|$. The ratio is approximately $\pm1$, so the parameter moves by about $\eta$, regardless of whether its gradient was $10x$ or $0.1y$. Adam has made the step size roughly scale-free per direction. That is the property lesson 2.6 said one global $\eta$ could not provide.

## Why does AdamW apply weight decay separately?

Now the classic wrong turn, which shipped in real code for years. You want **regularization**, any technique that discourages fitting the training sample at the expense of new data (overfitting, the subject of [lesson 2.9](/lessons/2-neural-network-fundamentals/2.9-overfitting-regularization-bitter-lesson/)). So you add an L2 penalty (a term proportional to the sum of squared weights) to the loss. Its gradient contribution is $\lambda\theta$, and you hand the sum to Adam. Reason about what happens next. That term goes into $m$ and $v$ along with everything else, and then the whole thing is divided by $\sqrt{\hat v}$. A parameter whose gradients happen to be large gets its decay shrunk; a parameter with tiny gradients gets its decay amplified.

The intended behavior was to pull every weight toward zero by the same proportion each step. That is not what occurs, and the strength of the regularizer now depends on unrelated gradient statistics. **AdamW** fixes it by decoupling: the decay term never enters $m$ or $v$. Each step subtracts the adaptive update and a separate shrinkage $\eta\lambda\theta$ together, where $\theta$ is the parameter value from before the step (line 12 of Algorithm 2 in the AdamW paper). Shrinking the already-updated value instead would also scale the adaptive step by $1-\eta\lambda$, a small but different rule. The names are nearly identical but the operations differ, and that difference is why essentially every large model today is trained with AdamW rather than Adam plus L2.

Not every parameter should decay. Biases and normalization scale parameters are commonly placed in a no-decay group. That configuration detail is a frequent source of silent bugs, so log which parameter names entered which group and fail loudly on unexpected omissions.

## What does optimizer state cost in memory?

:::insight
Adam's state is the hidden cost, and this is the first place in the course where it matters. Two extra tensors, $m$ and $v$, exist for every trained parameter. Mixed-precision training (computing in a low-precision number format while keeping some values in a higher one) often keeps them in higher precision, alongside a higher-precision master copy of the weights. Do not compress that into one universal bytes-per-parameter figure. The answer changes with the dtypes (number formats) of parameters and gradients, which copies the implementation retains, and how states are sharded or offloaded. [Lesson 9.3](/lessons/9-hardware-and-infrastructure/9.3-kv-cache-sizing-and-memory-budgets/) owns that full memory arithmetic. The durable conclusion here is narrower: optimizer state adds parameter-sized tensors that inference does not need, so it can outweigh the inference weights before activations enter the budget.
:::

:::warning
The most common misconception is that a model which fits in memory for inference can be fully trained in that same memory. Inference needs weights plus runtime state. Full training also needs gradients, optimizer moments, commonly a master copy, and stored activations for the backward pass. Tracks 5 and 9 explain how sharding (splitting these tensors across many GPUs, as ZeRO and FSDP do) and interconnects divide that bill, and lesson 9.3 derives it without mixing categories. Fine-tuning methods such as LoRA in [lesson 6.3](/lessons/6-post-training-and-alignment/6.3-lora-qlora-and-peft/) attack the same problem from the other side, by shrinking the number of parameters that need optimizer state at all.
:::

## What else must a training run record?

Schedules matter as much as the update rule. **Warmup** keeps early effective steps small while activations and moment estimates settle; **decay** reduces the step later for convergence. A fair experiment reports the optimizer equations or implementation, the learning-rate curve, batch size, clipping threshold (the cap on gradient size), decay groups, total tokens, and seeds (the starting values of the random-number generator). SGD, Momentum, Adam, and AdamW are update rules with different inductive biases, meaning different built-in preferences for which solutions they reach. They are not a chronological ladder on which the newest name wins.

One operational detail that costs people days: optimizer checkpoints must include the step counter and both moment buffers, not only the model weights. Resuming Adam with empty moments silently changes the update rule for hundreds of steps even though the parameters match exactly. Likewise, stepping the schedule once per batch rather than once per accumulation boundary produces a different learning-rate curve entirely. A reproducible run records those boundaries and verifies the first resumed update against an uninterrupted reference.
