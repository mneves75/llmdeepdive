Two workers of the purchasing assistant share one run's budget of USD 1.00. Each needs a model call that may cost up to USD 0.60. Each reads the budget, sees USD 1.00 free, decides there is room and starts its call. Together they spend USD 1.20, and the ledger, which each updated from the total it had read, records only USD 0.60. Nothing crashed, and every check passed when it ran. This lesson builds a ledger where that cannot happen, and a model cascade that spends from it.

## Cheap first, expensive when the check fails

A model cascade asks models in order, from cheapest to most capable, and stops at the first answer good enough to use. The FrugalGPT paper (Chen, Zaharia and Zou, 2023) describes it this way: a cascade "sends a query to a list of LLM APIs sequentially", returns a response once it is judged reliable, and queries the next one "only if the previous APIs' generations are deemed insufficiently reliable". The paper reports that its learned cascade can match the best single model "with up to 98% cost reduction" on the datasets it studied. It also lists its limits: training the cascade needs labelled examples from "the same or similar distribution" as the real queries.

The whole design depends on the check that decides "good enough". FrugalGPT learns a scoring model for it. The course uses something stricter for its one task. `invoice_check` accepts an `extract_invoice` call only if its total equals quantity × unit price in the tenant's purchase record, the success assertion from [lesson 14.1](/lessons/14-agent-architecture-and-state/14.1-when-a-workflow-needs-an-agent/). The model's own confidence never enters it. A check that accepts wrong answers turns the savings into errors, because the cascade then stops at the cheap model exactly when it should have gone on.

Here is a worked example with made-up numbers, because no fixture measures how often a real small model passes. The small tier costs USD 0.002 a call and the large tier USD 0.03, as in the tests. If the small model passed the check on 70% of invoices, the expected cost per invoice would be 0.002 + 0.3 × 0.03 = USD 0.011, against USD 0.03 for the large model alone. Latency moves the other way for the 30% that fall through: they wait for both models. [Lesson 9.10](/lessons/9-hardware-and-infrastructure/9.10-cost-per-token/) shows where per-call prices come from. Measure the pass rate on your own held-out invoices before trusting any such saving.

## Why checking a total is not enough

The opening's overspend is a stale read. A stale read is a decision based on data that changed after it was read. The test file writes the naive ledger out on purpose: `naive_read` reads the committed total, and `naive_write` checks it against the limit and writes the new total. The test interleaves two workers in a fixed order (read, read, write, write), so the race happens every time instead of once in a thousand runs. Both writes succeed, USD 1.20 of calls are approved and the ledger shows USD 0.60.

Locking each step separately does not help, because the gap is between the read and the write. The write itself has to say "only if nothing changed since I read".

## Reservations with compare-and-swap

The ledger is a SQLite table with a `version` column, the same shape as [lesson 14.3](/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/)'s checkpoints. Money is stored as whole micro-dollars (USD 1 is 1,000,000), because SQLite has no decimal type and a float cannot hold USD 0.10 exactly. A worker reserves a call's worst-case price before the call:

```python
# file: examples/agent-engineering/src/agentlab/resilience/budget.py
    def try_reserve(self, seen: Snapshot, reservation_id: str, amount: int) -> bool:
        """Hold ``amount`` if ``seen`` is still current. False: halted or over the limit. ``StaleWrite``: read again."""
        if amount <= 0:
            raise ValueError("a reservation must be positive")
        if seen.halted or seen.committed + amount > seen.limit:
            return False
        with self._transaction():
            cursor = self._db.execute(
                "UPDATE budget SET committed_micros = ?, version = version + 1 WHERE budget_id = ? AND version = ?",
                (seen.committed + amount, seen.budget_id, seen.version),
            )
            if cursor.rowcount != 1:
                raise StaleWrite(f"budget {seen.budget_id} changed since version {seen.version}")
            self._db.execute(
                "INSERT INTO reservation (reservation_id, budget_id, held_micros, status) VALUES (?, ?, ?, 'held')",
                (reservation_id, seen.budget_id, amount),
            )
        return True
```

The `WHERE ... AND version = ?` clause is the compare-and-swap. The update matches a row only if the version is still the one the worker read. Otherwise `StaleWrite` tells the worker to read again, and `reserve` does exactly that in a loop. Each retry means another worker committed something, so the loop always makes progress. In the test both workers open their own connection to the same file, as two processes would. Worker A reserves USD 0.60. Worker B's attempt with its old snapshot raises `StaleWrite`, and its fresh read shows USD 0.40 left, so it is refused. A control test with two USD 0.40 calls shows that both get through: a stale write is retried, not turned into a refusal.

After the call, `settle` replaces the hold with the real cost, and `release` gives the whole hold back when the call never ran. Both work once, because they move the reservation from `held` with a check on its status. A provider can bill more than the hold if the estimate was wrong. `settle` then records the real cost anyway, since that money is gone, and halts the budget until a person looks.

## Deadlines and the kill switch

Money is one limit and time is another. Google's chapter on cascading failures says "it's usually wise to set a deadline", and that "you don't get credit for late assignments with RPCs". Each `Tier` declares the slowest call it may take. Before calling a tier, `run_cascade` checks whether the call could end after the run's deadline and escalates instead of starting it. With a 10-second deadline, the small tier (2 seconds) runs and the large tier (20 seconds) never does.

The kill switch is `halt`. It sets `halted` and also adds one to the version, which matters for the worker that read the budget a moment before the halt. Its snapshot still says the budget is open, but its compare-and-swap fails, and its fresh read sees the halt. The test `test_a_halt_between_read_and_reserve_wins` checks exactly that interleaving. A call already running can still settle after a halt, because its cost has been incurred, and the ledger has to stay true.

`run_cascade` puts the pieces in order: deadline check, reservation, call, settle, then the check. Any refusal escalates with a reason, and the model of a tier that was refused is never called. The tests assert that by counting the scripted model's calls.
