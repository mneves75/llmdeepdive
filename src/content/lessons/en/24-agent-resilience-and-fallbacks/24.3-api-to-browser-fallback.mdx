The supplier's report API used to answer `GET /v1/reports/2026-03` with March's purchase rows. This month it answers 410 Gone, and the API owner announced the retirement months ago. The same report is still on the legacy portal that track 18 drove: sign in, press "Download March 2026 CSV", check the file. Lesson 24.1's classifier already returns a `fallback` candidate for that route. The question in this lesson is what else must be true before a browser may stand in for an API.

The tempting rule is "if the API fails, use the browser". Five mornings show why it is wrong. On one, the API answers 403 and the portal account can still see the report. On another, a live route answers 404 for another tenant's order. On a third, an invoice submission times out. On a fourth, the portal account turns out to be a shared administrator account. On the fifth, the run belongs to a clerk who was never allowed to read reports. A browser fallback in any of those cases would hide a refusal, expose a resource, risk a second invoice, act with someone else's authority or exceed the run's permission.

## When a detour is allowed

A fallback, a second way to do a task after the first way fails, is safe only when it does the same task. For an API-to-browser fallback that means four things stay equal. The **scope** of the task: the same read of the same report. The **identity**: the portal session acts for the same person in the same tenant. The **permissions**: the session has neither more nor less than the run. The **postcondition**, what must be true afterwards: the run holds the same verified rows the API would have returned. A fallback that keeps all four is a detour to the same place. One that changes any of them is a different action, and calling it seamless hides that.

The trigger has to be a known fact. RFC 9110's 410 says access "is no longer available" and that this "is likely to be permanent". RFC 8594 defines a `Sunset` response header which "indicates that a URI is likely to become unresponsive at a specified point in the future", so a client can learn about a retirement before it happens. Either signal is a reason for a person to record the route as retired and review an equivalent. A 404 on a live route is not such a signal: RFC 9110 lets a server send it to hide a resource the caller may not see. A browser that can see more than the API would turn that hidden resource into a leak.

## The same principal, not just the same company

The portal has its own accounts, and the run has a `Principal` built by the controller from authenticated input (`agentlab.domain`). The two must be tied by the runtime, never by text a model wrote, in the same way [lesson 20.4](/lessons/20-human-approval-and-durable-pauses/20.4-slack-and-teams-approval-adapters/) mapped a Slack user to a principal through a directory. Here the runtime keeps a mapping from portal account to principal, and the gate requires that mapping to give back exactly the run's principal: same user, same tenant, same roles.

Equality matters in both directions. A portal account with fewer roles would fail on the portal, which is merely annoying. A portal account with more roles, such as a shared service account that can also approve invoices, would let the run act with authority it never had. The test `test_a_portal_account_with_more_permissions_is_refused` exists for that case.

## The gate in code

<Figure id="fallback-gate" />

```python
# file: examples/agent-engineering/src/agentlab/resilience/fallback.py
def may_fall_back(verdict: Verdict, failure: Failure, *, principal: Principal, portal_account: str,
                  accounts: Mapping[str, Principal]) -> Decision:
    """Every condition must hold; the first one that fails is the reason given."""
    if verdict.action != "fallback":
        return Decision(False, f"24.1 said {verdict.action}: {verdict.reason}")
    equivalent = EQUIVALENTS.get(verdict.equivalent or "")
    if equivalent is None or equivalent.replaces != failure.route or failure.effect != "read":
        return Decision(False, f"no reviewed read equivalent for {failure.route}")
    acting = accounts.get(portal_account)
    if acting is None:
        return Decision(False, f"portal account {portal_account!r} is not mapped to a principal")
    if acting != principal:
        return Decision(False, "the portal session would act as a different principal (user, tenant or roles)")
    if equivalent.required_role not in principal.roles:
        return Decision(False, f"{principal.user_id} lacks {equivalent.required_role}, which the API route required too")
    return Decision(True, f"{equivalent.name} replaces {failure.route}", equivalent)
```

The first check reuses lesson 24.1's verdict, so a 401, a 403, a 404 on a live route and an uncertain write are all refused before identity is even looked at. The reason given is the classifier's own, which keeps the trace honest about why no detour was taken. The last check is the forbidden task. The equivalent records which role the API route required (`reports_reader`), and a principal without it cannot use the portal to do what the API would have refused.

## Equivalent action and the same postcondition

The equivalent fixes the action as well as the permission. `report_target("2026-03")` returns exactly one target, the button named "Download March 2026 CSV", and the model proposes nothing. Track 18 let a model suggest a role and a name because it was exploring an unknown page. A reviewed fallback is not exploration. A person decided that this one button is equivalent to the retired route, and anything else would be an action nobody reviewed.

The postcondition is checked the way [lesson 18.5](/lessons/18-computer-use-and-gui-automation/18.5-recover-and-verify/) checked it: `fetch_report` observes, dismisses a known dialog, presses the one button, and accepts the download only if `validate_report` agrees it is the requested period's report. `read_report` returns rows from the browser only when that outcome is `done`. Otherwise it returns no result, with the reason. In the browser test, June's export is a well-formed file holding March's rows: the gate allows the attempt, the portal serves the file, the check rejects it, and the run ends with nothing rather than with the wrong month. The detour ran and did not reach the destination, so it does not count.

## Why writes never fall back

An uncertain write is classified `reconcile` by lesson 24.1, so it never reaches this gate as a candidate. A retired write route is refused too, even if someone registered an equivalent for it. Two reasons make that rule fixed. First, [lesson 20.2](/lessons/20-human-approval-and-durable-pauses/20.2-bind-approval-to-one-operation/) bound an approval to one operation: its id and the hash of one exact draft. A form submitted through a browser is a different operation, and the approval does not stretch to cover it. Second, a portal form has no idempotency key. If the submission times out, the run cannot ask the portal what it recorded the way lesson 14.4's reconciliation asks the accounts-payable service, so a retry might create a second invoice. A write that must move to a new channel needs a new integration that someone reviews, with its own approval. Until that exists, a person submits it.

:::note
`read_report` does not retry. Retrying the API belongs to lesson 24.2's `call_with_retries`, which runs before a fallback is even considered, because a 503 is a reason to wait, not a reason to take another road.
:::

Break it: in `may_fall_back`, replace `if acting != principal:` with `if acting.tenant_id != principal.tenant_id:` and run the core file. The tests for another user and for extra permissions both fail, because a same-tenant service account can now act for the run. Restore the line.
