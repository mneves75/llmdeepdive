The purchasing assistant has a validated request from [lesson 15.1](/lessons/15-tool-contracts-and-mcp/15.1-from-model-output-to-a-tool-request/): look up PO-1001. The lookup runs in a separate program, the purchasing server, and the two programs talk through one pair of pipes. The assistant may have several questions in the air at once, and the answers come back on the same stream. How does it know which answer belongs to which question? And what if the server expects a different version of the conversation? This lesson builds the message layer that answers both: JSON-RPC 2.0, as the Model Context Protocol uses it.

## Four kinds of message

The *Model Context Protocol* (MCP) is an open protocol that lets an AI application, the *host*, connect to programs that offer tools and data, called *servers*. Inside the host, one *client* per server speaks the protocol. MCP's messages are *JSON-RPC 2.0* messages: JSON objects for calling a named method on another program. There are four shapes:

- A *request* has `"jsonrpc": "2.0"`, an `id`, a `method` and optional `params`. It expects exactly one answer.
- A *result response* carries the same `id` and a `result`.
- An *error response* carries the same `id` and an `error` with an integer `code` and a `message`.
- A *notification* is a request without an `id`. The JSON-RPC specification says: "The Server MUST NOT reply to a Notification."

On the stdio transport, where the client starts the server as a child process, each message is one line of JSON on the server's standard input or output. The trace below is real output from this course's server, given five lines on standard input: discovery (id 1), a request with an unknown version (id 2), a cancellation notification for id 2, a lookup (id 3) and a tool listing (id 4). Four lines came back:

```json
{"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","supportedVersions":["2026-07-28"],"capabilities":{"tools":{"listChanged":true}},"_meta":{"io.modelcontextprotocol/serverInfo":{"name":"agentlab-purchasing","version":"0.1.0"}},"ttlMs":0,"cacheScope":"private"}}
{"jsonrpc":"2.0","id":2,"error":{"code":-32022,"message":"Unsupported protocol version","data":{"supported":["2026-07-28"],"requested":"1900-01-01"}}}
{"jsonrpc":"2.0","id":3,"result":{"resultType":"complete","content":[{"type":"text","text":"{\"po_id\": \"PO-1001\", \"supplier\": \"Supplier Alpha\", \"item\": \"M8 hex bolts, box of 500\", \"quantity\": 40, \"unit_price\": \"12.50\", \"currency\": \"USD\", \"status\": \"received\"}"}],"structuredContent":{"po_id":"PO-1001","supplier":"Supplier Alpha","item":"M8 hex bolts, box of 500","quantity":40,"unit_price":"12.50","currency":"USD","status":"received"},"isError":false}}
```

## Matching answers to questions

The `id` is the only link between an answer and its question. MCP tightens JSON-RPC here: an id is a string or an integer and "MUST NOT be `null`", and it must not repeat the id of any other request the sender has not yet seen answered. The client keeps the waiting ids in a `PendingCalls` object and checks every response against it:

```python
# file: examples/agent-engineering/src/agentlab/tools/jsonrpc.py
    def settle(self, response: dict) -> int | None:
        """Return the id this response answers, None for a cancelled request, or raise."""
        request_id = response.get("id")
        if not is_valid_id(request_id):  # also stops True from matching id 1
            raise ProtocolViolation(f"response without a usable id: {str(request_id)[:64]}")
        if request_id in self._waiting:
            self._waiting.remove(request_id)
            return request_id
        if request_id in self._cancelled:
            self._cancelled.remove(request_id)
            return None
        raise ProtocolViolation(f"response for id {request_id!r}, which is not waiting for one")
```

Three cases. An id that is waiting is settled once and removed, so a second answer to the same request is a violation. An id the client cancelled returns `None`: MCP says a client "SHOULD ignore any response to the cancelled request that arrives afterward". Any other id means the server answered a question nobody asked, and the client stops trusting the stream. The comment about `True` is there because in Python `True == 1`, so a server that sent `"id": true` would otherwise match request 1.

## The receiving side and its error codes

The server's `Dispatcher` takes one line and returns the lines to write back. JSON-RPC fixes five error codes, and MCP adds its own in a reserved range:

| Code | Meaning | When this server sends it |
|---|---|---|
| -32700 | Parse error | the line is not JSON (the id is `null`, since none could be read) |
| -32600 | Invalid Request | wrong `jsonrpc` value, no method, a bad id, or a batch |
| -32601 | Method not found | an unknown method, and the legacy `initialize` |
| -32602 | Invalid params | params are not an object, `_meta` is missing, an unknown tool |
| -32603 | Internal error | the handler crashed |
| -32022 | Unsupported protocol version (MCP) | the request names a version this server does not speak |

MCP divides JSON-RPC's server-error range: codes from -32020 to -32099 belong to the MCP specification, and an implementation must not invent its own there. A *batch*, a JSON array of several requests, is legal JSON-RPC, but MCP's stdio binding says each line is "a single JSON-RPC request, notification, or response", so the dispatcher refuses an array as one invalid request. Here is the heart of `_reply`:

```python
# file: examples/agent-engineering/src/agentlab/tools/jsonrpc.py
        params = message.get("params", {})
        handler = self._methods.get(message["method"])
        try:
            if not isinstance(params, dict):
                raise RpcError(INVALID_PARAMS, "params must be an object")
            if handler is None:
                raise RpcError(METHOD_NOT_FOUND, f"Method not found: {message['method'][:64]}")
            result = handler(params, request_id, emit)
        except RpcError as error:
            return None if notification else error_response(request_id, error.code, error.message, error.data)
        except Exception:
            # Details go to the server's log (stderr), never to the peer.
            log.exception("handler for %s failed", message["method"][:64])
            return None if notification else error_response(request_id, INTERNAL_ERROR, "Internal error")
```

Every exit checks `notification` first, so even a failing notification gets no reply. A crash becomes a bare "Internal error": the details go to standard error, which the stdio binding reserves for logs. One test makes a handler raise an exception whose message contains a fake password and checks that the password never reaches the client.

## A lifecycle without a handshake

If you have read about MCP before, you may expect an `initialize` request that opens a session and fixes the version. The specification now calls those revisions, 2025-11-25 and earlier, *legacy*. In revision 2026-07-28, "There is no negotiation handshake." MCP is stateless: "Servers MUST NOT rely on prior requests over the same connection to establish context". Every request instead carries two required fields in `params._meta`: `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`, the client features this request may rely on. The server checks both, on every request:

```python
# file: examples/agent-engineering/src/agentlab/tools/server.py
def check_request_meta(params: dict) -> None:
    """Every request states its version and capabilities; the server remembers nothing between requests."""
    meta = params.get("_meta")
    if not isinstance(meta, dict) or not isinstance(meta.get(VERSION_KEY), str) or not isinstance(meta.get(CAPABILITIES_KEY), dict):
        raise RpcError(INVALID_PARAMS, "missing required _meta fields", {"required": [VERSION_KEY, CAPABILITIES_KEY]})
    if meta[VERSION_KEY] not in SUPPORTED_VERSIONS:
        raise RpcError(UNSUPPORTED_PROTOCOL_VERSION, "Unsupported protocol version", {"supported": SUPPORTED_VERSIONS, "requested": meta[VERSION_KEY][:64]})
```

What is left of a lifecycle is short. The client launches the server process. It may call `server/discover`, which every server must implement, to learn the supported versions and the server's capabilities, such as `tools`. Then it sends requests. To stop, it closes the server's standard input, waits, and escalates to `SIGTERM` and then `SIGKILL` if the server does not exit; the server should exit as soon as its input closes. If the server dies unexpectedly, the client restarts it and retries. Nothing is lost except the requests in flight, because nothing lived in the connection.

The spec also asks a server that speaks only modern revisions to name its versions in any error it returns to `initialize`, because legacy clients cannot find their way forward otherwise. This server answers `initialize` with -32601 and `"supported": ["2026-07-28"]` in the data.
