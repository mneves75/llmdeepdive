The last two lessons graded one run: its effects in [lesson 23.1](/lessons/23-agent-evaluation-and-ci/23.1-define-success-and-capture-traces/) and its order in [lesson 23.2](/lessons/23-agent-evaluation-and-ci/23.2-evaluate-valid-paths/). One run proves little. Which inputs should the assistant be tested on, how many, and how do you keep the test honest after a month of fixing the code against it? This lesson builds a corpus of 100 cases, writes down everything needed to rerun each one, and keeps a fifth of them sealed.

## How many cases, and which?

Anthropic's 2026 guide to agent evals is modest about the start: "20-50 simple tasks drawn from real failures is a great start", because early changes tend to have large effects, and large effects show up in small samples. The same guide separates two uses of a corpus. A *capability* eval targets what the agent cannot yet do and starts with a low pass rate. A *regression* eval protects what already works and should pass nearly 100% of the time. A corpus at 100% catches regressions but no longer shows improvement; the guide calls that *saturation*.

This course's plan fixes a distribution of 100 cases across six categories. These are coverage choices, made so that each kind of failure the earlier tracks taught has cases. They are not a sample size that proves reliability for any deployment.

| Category | Cases | Held out | Built from | Runs here? |
|---|---|---|---|---|
| Ordinary drafts | 30 | 6 | 6 purchase orders × 5 valid paths | yes |
| Tool, schema and authorization failures | 20 | 4 | 4 orders × 5 kinds of bad call | yes |
| Injection and exfiltration | 15 | 3 | the 9 attacks of lesson 16.5 | yes |
| Crash and idempotency | 15 | 3 | 3 failure points × 1–5 deliveries | yes |
| Approval races and expiry | 10 | 2 | scenarios of track 20 | manifest only |
| Browser and memory degradation | 10 | 2 | scenarios of tracks 18 and 19 | manifest only |

The ordinary cases include valid alternatives on purpose: drafting directly, looking the order up twice, checking another order first, or recovering after a refused draft all leave the same correct draft. A corpus with one path per order would teach the graders to expect a golden path again. The 20 failure cases each end with the reply "Invoice drafted.", a false claim the effect check must ignore. The injection cases take the nine attacks from [lesson 16.5](/lessons/16-agent-security-and-guardrails/16.5-red-team-the-boundary/), obeyed fully, then six of them obeyed only in their first call. The crash cases drive the outbox of [lesson 14.4](/lessons/14-agent-architecture-and-state/14.4-replay-and-side-effects/) with a lost request, a lost reply or no failure, redelivered up to five times.

## What a manifest records

A *manifest* is the corpus written as data: one JSON record per case. Every case in this one carries the same fields:

- `case_id` and `category`, such as `inj-002` in `injection`.
- `split`: `dev` or `held_out`.
- `seed`: a number for any random part of a run. The scripted replay ignores it; it is recorded so that a rerun of something stochastic can ask for the same one.
- `setup`: the runner, the trusted principal, the message (inline text or a fixture path), and the scripted tool calls and reply.
- `oracle`: required effects, the minimum number of refusals, and text the reviewer must never see, such as `collector.invalid`.
- `allowed_effects`: the upper bound from lesson 23.1.
- `provenance`: where the case came from, such as `agentlab.security.redteam base64_note (base64), full obedience`.

Provenance answers the question every failing case raises: is this a real failure pattern, an attack someone wrote, or a scenario invented for coverage? A case nobody can trace back is hard to fix and harder to delete.

## Generating it the same way every time

The corpus is generated by code, not edited by hand, so a reviewer can read the rules instead of 100 records. The split is the delicate part:

```python
# file: examples/agent-engineering/src/agentlab/evals/corpus.py
    total = sum(CATEGORIES.values())
    rng = random.Random(seed)
    cases = []
    for category, count in CATEGORIES.items():
        rows = groups[category]
        if len(rows) != count:
            raise ValueError(f"{category}: {len(rows)} cases, the plan says {count}")
        # Sampling inside each category keeps the held-out set stratified.
        held = set(rng.sample(range(count), count * HELD_OUT // total))
```

*Stratified* means each category gives the same share to the held-out set: 30 × 20 / 100 = 6 ordinary cases, then 4, 3, 3, 2 and 2, which add up to exactly 20. Sampling 20 cases from all 100 at once could, by chance, hold out no attacks at all. `random.Random(seed)` is Python's seeded generator, so the same seed gives byte-identical JSON, and a different seed changes which cases are held out but never how many. Strict validation of each record (the project's `Record` base: wrong types and unknown fields fail) means a typo in a category name is an error when the corpus is built, not a silently skipped case.

## Why hold cases out?

Every time you read a development case's failure and change the code, the code fits that case a little better. After enough rounds the development pass rate measures fit, not ability. The held-out cases are run only for a release candidate, so they still measure something the code was not tuned on. Once someone tunes code against a held-out failure, that case is *exposed*: it moves into development, and new held-out cases are written. The guide's advice to start each trial from a clean environment protects the same thing at the level of one run. Its example is an agent that gained an unfair advantage by reading the git history left by earlier trials. Each case here builds a fresh back office or a fresh in-memory checkpoint store.

## Which cases run here, and which do not?

Eighty cases run against the components of earlier tracks: the assistant and gate of [lesson 16.2](/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) and the outbox of lesson 14.4. The other 20 are manifest-only. The approval scenarios belong to the approval package of track 20, which this track does not import. The browser scenarios need the Playwright portal of track 18. The memory scenarios need a model that reads the assembled context, which [lesson 19.5](/lessons/19-agent-memory-and-context/19.5-evaluate-memory/) deliberately leaves to live trials. `run_case` raises `LookupError` for them rather than returning an empty list of problems, because an empty list means passed.

:::warning
A manifest-only case in a report must be reported as not run. Counting it as passed, or leaving it out of the total silently, makes a corpus of 80 look like a corpus of 100.
:::

## Run the exercise

The module is `src/agentlab/evals/corpus.py`; the tests are in `tests/test_evals_corpus.py`. From `examples/agent-engineering/`, run `uv run --frozen python -m unittest tests.test_evals_corpus`. The output ends with `Ran 12 tests` and `OK`. The tests check the distribution, the 6, 4, 3, 3, 2, 2 held-out split, byte-identical output for one seed, strict round-tripping of the JSON, a fixture path such as `../domain.py` being refused, and all 80 executable cases passing. A negative control replaces the invoice service with one that ignores idempotency keys: 12 of the 15 crash cases fail, and the 3 that pass are the ones in which the service happened to write exactly once. To read the whole manifest, run `uv run --frozen python -m agentlab.evals.corpus`.

To see stratification matter, change the sampling line to `held = set(rng.sample(range(count), 4))`. Two tests fail, `test_twenty_held_out_cases_stratified_by_category` and `test_another_seed_changes_which_cases_are_held_out_but_not_how_many`: the held-out set is now 24 cases, four from every category whatever its size. Restore the line before moving on.
