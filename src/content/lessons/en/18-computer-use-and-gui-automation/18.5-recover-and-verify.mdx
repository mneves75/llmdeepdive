Four mornings with the same task, "download the March 2026 report". On Monday a maintenance notice covers the page and the click on March's button times out. On Tuesday the portal has been redesigned, with the same buttons in a new arrangement. On Wednesday a different redesign has renamed every export button to "Export". On Thursday someone points the run at June by mistake: the click works, a file arrives, the banner says complete, and the file holds March's rows.

A run that treats all four the same way, retrying until something happens, will eventually click the wrong thing. This lesson separates trouble the run can name and recover from, trouble it must hand to a person, and the check that decides when it is finished.

## Expected trouble and unknown trouble

Before every click, Playwright checks that the element is visible, stable, enabled and "Receives Events, as in not obscured by other elements". If the checks do not pass in time, the "action fails with the TimeoutError". Monday's notice is a full-page overlay, so March's button never receives events and the plain click times out. The browser test shows exactly that.

That failure is expected. The notice is a dialog with a button named "Dismiss", and closing it is reversible, harmless and in the run's job. Tuesday's redesign is expected too: [lesson 18.1](/lessons/18-computer-use-and-gui-automation/18.1-observe-before-acting/) chose role-and-name targets so that a new arrangement changes nothing. Wednesday's page is different in kind. The run's target no longer exists, and "Export" matches five buttons. Any choice among them is a guess about a page nobody has told the run about. The rule is to recover only from trouble the code can name and to escalate everything else.

## The recovery loop

`fetch_report` in `browser.py` puts those decisions in order:

```python
# file: examples/agent-engineering/src/agentlab/gui/browser.py
        while True:
            budget.spend("observe")
            state = classify_page(page.url, observe(page), portal_origin)
            trace.record("gui.page", url=page.url, state=state)
            if state != "ready":
                return Outcome(state, f"stopped on {page.url}: {state}")
            dialog = page.get_by_role("dialog")
            if dialog.count():
                dismiss = dialog.get_by_role("button", name="Dismiss", exact=True)
                if dismiss.count() != 1:
                    return Outcome("needs_human", "a dialog without a known way to close it")
                budget.spend("dismiss")
                dismiss.click()
                trace.record("gui.dismiss", target="button:Dismiss")
                continue  # the page changed: observe again before acting
            button = resolve(page, target)
            if button is None:
                return Outcome("needs_human", f"no single {target.role} named {target.name!r}: the layout is not one this run knows")
            budget.spend("click")
            trace.record("gui.click", target=f"{target.role}:{target.name}")
            return download_report(page, lambda: button.click(timeout=timeout_ms), period=period, folder=folder, trace=trace, timeout_ms=timeout_ms)
```

Every pass starts with a fresh observation, because an action changes the page and the old snapshot describes a page that no longer exists. A page that is not ready (an expired session, a challenge, another origin, all from [lesson 18.3](/lessons/18-computer-use-and-gui-automation/18.3-login-and-session-state/)) ends the run with that state. A dialog is closed only by its known button, and a dialog without one escalates. The target must resolve to exactly one element, or the run escalates with a reason that names the layout problem. There is no branch that clicks by coordinates when the semantic target is missing: falling back to a guess is how Wednesday becomes a wrong download.

## A budget on actions

What if dismissing the notice made it come back? The loop would observe, dismiss and observe forever. `ActionBudget` counts every action, and the one past its limit raises `BudgetExhausted`, which `fetch_report` turns into `needs_human`:

```python
# file: examples/agent-engineering/src/agentlab/gui/control.py
    def spend(self, action: str) -> None:
        if len(self.spent) >= self.limit:
            raise BudgetExhausted(f"{self.limit} actions spent ({', '.join(self.spent)}); not taking '{action}'")
        self.spent.append(action)
```

The budget is checked before each action, so the run stops before taking the action it cannot afford. With a limit of 2 and the notice up, the run observes, dismisses, and stops before its second observation, and the portal serves nothing. The spent list doubles as a compact trace of what the run did.

## Verify the outcome, not the click

Thursday's run does everything right mechanically. The click lands, the portal serves `/export?period=2026-06`, the browser saves the file and the banner celebrates. `validate_report` from [lesson 18.4](/lessons/18-computer-use-and-gui-automation/18.4-download-a-csv-from-a-legacy-portal/) then reads the rows and finds `line 2 is for period 2026-03, not 2026-06`, so the outcome is `failed` and the copy is deleted. "Done" is a property of the result in the environment, the right rows in the run's folder, never of the actions that led there. Track 23 builds its evaluations on the same rule, starting in [lesson 23.1](/lessons/23-agent-evaluation-and-ci/23.1-define-success-and-capture-traces/).

## Screenshot comparisons with masks

Visual comparison is a useful extra check: did the page look the same before and after a step that should change nothing? The reports page has a clock that changes every 50 milliseconds, so two raw screenshots never match. Playwright's `screenshot` takes a `mask` list, and masked elements are "overlaid with a pink box `#FF00FF`" that "completely covers its bounding box":

```python
# file: examples/agent-engineering/src/agentlab/gui/browser.py
    image = page.screenshot(mask=[page.get_by_role("timer")], animations="disabled", caret="hide")
    return hashlib.sha256(image).hexdigest()
```

The test controls the page's clock, advances it one second, and checks three things. The raw screenshots differ. The masked digests are equal. A new banner still changes the masked digest. Comparing SHA-256 digests means any changed pixel counts. That works for one browser on one machine, but screenshots from another machine or browser version can differ in font rendering and need a tolerance instead. Screenshots stay the supporting evidence. The semantic checks, the dialog gone and exactly one target resolved, are what the loop acts on.

:::note
A browser route can also stand in for a retired API, but only when it acts with the same identity and permissions and its result is verified this way. [Lesson 24.3](/lessons/24-agent-resilience-and-fallbacks/24.3-api-to-browser-fallback/) works through when that fallback is allowed.
:::
