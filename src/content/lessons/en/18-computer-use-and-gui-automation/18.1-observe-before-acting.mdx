The purchasing assistant needs last month's purchase report from a supplier portal. The portal is old and has no API; a person signs in, opens *Monthly reports* and presses a button. A first script did the same with a CSS selector, a path through the page's structure: `#report-table tbody tr:nth-child(1) button`, "the button in the first row of the report table". It worked for months. Then the portal was redesigned. The table became a column of cards, newest first, and the script failed. A second script, written to be "less fragile", clicked the first export button on the page. It did not fail. It downloaded July instead of March, and nothing complained.

Before the agent acts on a page, it has to decide what to look at. This lesson is about that choice.

## Three observations of one page

A browser offers an agent three different views of the same page.

The *DOM* (Document Object Model) is the tree of elements the browser builds from the HTML: a `table` holding rows holding cells holding a `button`. It is complete and exact, and it describes structure, which is the part a redesign changes.

The *accessibility tree* is what the browser gives to assistive technology such as a screen reader. Each element appears with a *role*, which WAI-ARIA calls the "main indicator of type" (button, link, textbox), and an *accessible name*, the text a screen reader announces for it. The name usually comes from the visible text, but an `aria-label` attribute or a `<label>` element can set it. The tree describes what the page offers a person, and it changes only when what the page offers changes.

A *screenshot* is pixels. It is the only view that exists for a remote desktop or a canvas, and it is what a vision model reads. [Lesson 18.2](/lessons/18-computer-use-and-gui-automation/18.2-pixels-coordinates-and-set-of-mark/) covers acting on it.

Playwright, the browser-automation library the exercises use, prints the accessibility tree as an *aria snapshot*. On both of the exercise portal's layouts, the line that matters has the same role and name. On the original layout it reads as follows; the block is an excerpt of real snapshot output, shown for reading, and the test below produces it:

```text
- button "Download March 2026 CSV" [ref=e16] [box=161,191,225,40]
```

The `ref` is a short reference for this snapshot only, and the `box` is the element's position and size in CSS pixels. On the redesigned page the button shows just "CSV", but its `aria-label` keeps the accessible name, so the role and name read the same; only the reference and the box differ.

## Why a role and a name survive a redesign

Playwright's documentation says it directly: "We recommend prioritizing role locators to locate elements", because they reflect "how users and assistive technology perceive the page". It also says why the alternatives are weaker: "CSS and XPath are not recommended as the DOM can often change leading to non resilient tests." Puppeteer, another browser-automation library, offers the same idea as ARIA selectors, which "find elements using the computed accessible name and role" from "the browsers internal representation of the accessibility tree". Both libraries ask the same browser for the same tree; they differ in API, not in what they can observe.

The portal shows the two failure modes side by side. The CSS path matches nothing on the new layout, which is a visible failure. The positional choice, "first export button", still matches something: July. That is the worse failure, because the run goes on with the wrong report. A semantic target names what the person wants, and the page has to offer exactly that.

## What the model proposes and what the controller resolves

The model never writes a selector. It reads the snapshot and proposes a target, a record with two fields:

```python
# file: examples/agent-engineering/src/agentlab/gui/control.py
class Target(Record):
    role: Literal["button", "link", "textbox", "checkbox", "radio", "combobox", "tab"]
    name: str = Field(min_length=1, max_length=200)
```

The record is strict, so a reply that adds a `css` field or `x` and `y` coordinates fails validation and `propose_target` returns no target at all. The snapshot reaches the model wrapped by `as_untrusted` from [lesson 16.2](/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/): every label on the page was written by whoever controls the portal, so it is outside text that can carry instructions, like a supplier's e-mail. The wrapper only marks it. The limits come from the record's shape and from the controller.

The controller turns the target into an element, and accepts exactly one:

```python
# file: examples/agent-engineering/src/agentlab/gui/browser.py
def resolve(page: Page, target: Target) -> Locator | None:
    """The one element with exactly this role and accessible name, or None when there are zero or several."""
    locator = page.get_by_role(target.role, name=target.name, exact=True)
    return locator if locator.count() == 1 else None
```

`exact=True` makes the name match whole and case-sensitive, so "Download March 2026 CSV" does not also match a longer name that contains it. Playwright's locators are strict anyway: an action on a locator that matches more than one element "will throw an exception". `resolve` counts first, so ambiguity becomes a decision the controller makes instead of an exception in the middle of a click.

:::note
The browser should also run in its own boundary. [Lesson 17.1](/lessons/17-sandboxed-agent-execution/17.1-what-isolation-protects/) separates what isolation protects from what it does not. In the exercises every test opens a fresh browser context, so no cookies or storage from another run are visible.
:::

## Where observing stops being enough

Layout c renames every export button to "Export". The model's target for March now matches nothing, and the generic name "Export" matches five buttons. Either way `resolve` returns `None`. That is the right answer: the run has met a page it does not understand, and [lesson 18.5](/lessons/18-computer-use-and-gui-automation/18.5-recover-and-verify/) turns `None` into an escalation to a person instead of a guess. The accessibility tree is also only as good as the page's authors made it. A button drawn as a bare `div` with no role or name is invisible to these locators, and a screenshot may be the only way to see it.

## Run the exercise

The portal is a small standard-library server in `src/agentlab/gui/portal.py`, started on 127.0.0.1 with a free port by each test and stopped by the same test. Its pages are in `src/agentlab/fixtures/gui/`. The browser tests need the project's `browser` dependency group and Chromium, installed as the project README describes.

From `examples/agent-engineering/`, run `uv run --frozen python -m unittest discover -s tests_browser -p "test_gui_observe.py"`. The output ends with `Ran 6 tests` and `OK`. `test_the_models_target_resolves_to_march_on_both_layouts` lets a scripted model propose March's role and name on layouts a and b, resolves it and checks that the downloaded file is `report-2026-03.csv`. `test_a_css_path_breaks_on_the_redesign` and `test_the_first_button_is_a_different_report_after_the_redesign` show the two structural failures. The core suite's `tests/test_gui_control.py` (6 tests, no browser) checks that a CSS selector or coordinates are never accepted as a target.

To see the safety net work, change the last line of `resolve` to `return locator.first if locator.count() else None`. `test_a_name_that_matches_several_elements_resolves_nothing` goes red, because the run would now click the first of five "Export" buttons. Restore the line.
