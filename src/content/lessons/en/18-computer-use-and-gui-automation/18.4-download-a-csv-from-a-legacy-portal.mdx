The run presses "Download April 2026 CSV". At once a banner appears: "Export complete. Your download has started." A run that trusts the page reports success and moves on. No file ever arrived. The portal's server answered with an error, and the banner had been written by the page's own script the moment the button was clicked, before the server said anything.

This lesson turns "the download worked" into checks a program can run.

## What "the download worked" has to mean

For the purchasing assistant, a finished download means all of these hold:

1. A download actually started within a deadline.
2. It came from the portal's own origin.
3. It was saved inside the run's own folder, under a name the controller accepted.
4. The file is CSV text, not an HTML page wearing a `.csv` name.
5. Its columns are exactly the report's columns.
6. Every row belongs to the requested period and has sane values.

The exercise portal fails each of these on purpose. March is the only good export. April fails on the server, May sends an HTML error page as `report-2026-05.csv`, June sends a well-formed file holding March's rows, and July names its file `../../report-2026-07.csv`. Every export also arrives 400 milliseconds after the banner claims it has started.

## Waiting for the file, not the banner

Playwright reports a download as an event. `page.expect_download()` waits for it while the click runs, and gives up with a timeout error after a deadline. Its documentation adds two facts that shape the code: "All these attachments are downloaded into a temporary folder", and "Downloaded files are deleted when the browser context that produced them is closed." So the controller must copy the file somewhere it owns before the run ends. `Download.failure()` "returns download error if any" and waits for the download to finish first.

```python
# file: examples/agent-engineering/src/agentlab/gui/browser.py
    try:
        with page.expect_download(timeout=timeout_ms) as started:
            press()
    except PlaywrightTimeout:
        banner = page.get_by_role("status").first.inner_text()
        trace.record("gui.download", ok=False, banner=banner)
        return Outcome("failed", f"no download started within {timeout_ms:.0f} ms, although the page says {banner!r}")
```

`press` is whatever starts the export: a semantic click, or a click by coordinates. When nothing arrives, the outcome quotes the banner, so the trace keeps the contradiction for whoever reads it later. The 400-millisecond delay is why the code waits on the event: a run that checked the folder right after the click would find it empty even for March.

Why not wait a fixed time instead? A pause long enough for the slowest export wastes that time on every fast one, and a pause tuned to today's speed fails on the day the server is slow. Waiting on the event ends as soon as the file starts, and the deadline states how long the run is willing to wait before it reports a failure. The tests use 3,000 ms for exports that should work and 1,500 ms for April's, which never will.

## The name comes from the server

The file name arrives in the response's `Content-Disposition` header, written by the server. RFC 6266 tells recipients to treat it "as advisory only" and says that "Recipients MUST NOT be able to write into any location other than one to which they are specifically entitled." One strategy it mentions is keeping only the last path segment. The exercise is stricter and refuses the name, because a portal that sends `../../report-2026-07.csv` is misbehaving:

```python
# file: examples/agent-engineering/src/agentlab/gui/report.py
def safe_destination(folder: Path, suggested_name: str) -> Path:
    """Where to save a download. The name comes from the server's header, so it is untrusted input."""
    if not CSV_NAME.match(suggested_name):
        raise ReportRejected(f"refusing file name {suggested_name!r}")
    target = (folder / suggested_name).resolve()
    if target.parent != folder.resolve():
        raise ReportRejected(f"{suggested_name!r} would land outside {folder}")
    if target.exists():
        raise ReportRejected(f"{target.name} already exists; a download never overwrites a file")
    return target
```

`CSV_NAME` allows letters, digits, dots, hyphens and underscores, ending in `.csv`, so slashes never reach the path check. The `resolve()` comparison is a second, independent guard. A download also never overwrites an earlier file, which could be a report someone already checked.

## Checking what the file holds

Only now does the controller look inside. `validate_report` reads the bytes and refuses, with a reason, anything that is not the requested report:

```python
# file: examples/agent-engineering/src/agentlab/gui/report.py
    if raw.lstrip()[:1] == b"<":
        raise ReportRejected("the file is HTML, not CSV (an error or login page saved under a .csv name)")
    try:
        text = raw.decode("utf-8")
    except UnicodeDecodeError as error:
        raise ReportRejected("the file is not UTF-8 text") from error
    reader = csv.DictReader(io.StringIO(text, newline=""))
    if tuple(reader.fieldnames or ()) != REPORT_COLUMNS:
        raise ReportRejected(f"unexpected columns {reader.fieldnames}")
```

After the columns, each row must carry the requested period, a purchase-order id of the form `PO-` plus four digits, a positive quantity and a positive unit price. If any check fails, `download_report` deletes the saved copy, so a rejected file can never be mistaken for a result later. For March, the accepted rows are exactly the four tenant-a purchase records in the project's fixtures, which a test compares.

:::insight
`failure()` and these checks answer different questions. `failure()` says whether bytes arrived. The checks say whether the bytes are the report. May's error page arrives completely, so `failure()` returns `None`, and only reading the file shows it is HTML.
:::

## Run the exercise

From `examples/agent-engineering/`, run the core checks with `uv run --frozen python -m unittest discover -s tests -p "test_gui_report.py"`; the output ends with `Ran 12 tests` and `OK`. The browser tests run with `uv run --frozen python -m unittest discover -s tests_browser -p "test_gui_download.py"` and end with `Ran 5 tests` and `OK`. Each test downloads into a fresh temporary folder that is removed afterwards.

`test_the_delayed_march_export_matches_the_fixture` waits through the delay and compares the rows with the fixture. `test_a_failed_export_is_caught_although_the_banner_says_complete` asserts both the failed outcome and the banner's text. `test_an_html_page_named_csv_is_refused_and_removed` and `test_a_file_name_that_climbs_out_of_the_folder_is_refused` check that nothing stays in the folder or lands above it. `test_screenshot_only_the_same_checks_apply` downloads March by coordinates.

To see two checks overlap, delete the HTML check in `validate_report`. `test_an_html_page_saved_as_csv_is_refused` goes red, yet the file is still refused, now by the column check with a less useful reason. The test pins which check names the problem. Restore the line.
