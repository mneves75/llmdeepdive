Some interfaces have no accessibility tree worth reading: a remote desktop, a canvas, a legacy page built from images. There the agent sees only a screenshot, and a vision model answers in pixels: "click at (547, 422)". The exercise browser runs at *device scale factor* 2, the ratio of physical screen pixels to CSS pixels on a high-density display. The viewport is 800 by 600 CSS pixels, so the screenshot is 1600 by 1200. March's export button is centred at (273.5, 211) in the viewport, which is (547, 422) on the screenshot. Pass the model's numbers straight to the mouse and the click lands at (547, 422) in the viewport, to the right of every button, on nothing.

Nothing was wrong with the model's answer. The controller mixed up two coordinate spaces.

## Three coordinate spaces

Three spaces meet in one click.

- *Image pixels*: positions in the picture the model saw, with (0, 0) at its top-left corner.
- *Device pixels*: the screen's physical pixels. Playwright's screenshot defaults to `scale="device"`, which its API describes as "a single pixel per each device pixel, so screenshots of high-dpi devices will be twice as large or even larger."
- *CSS pixels relative to the viewport*: the units a web page lays itself out in, measured from the top-left of the visible area. Playwright's `Mouse` class "operates in main-frame CSS pixels relative to the top-left corner of the viewport", and the boxes in an aria snapshot use the same units.

A model provider can add one more step. Anthropic's documentation for its vision models, read on 2026-10-18, says that the coordinates its model returns "are pixel positions in the image Claude sees", after the service has shrunk an oversized image. Its example shrinks a 1920 by 1080 screenshot to 1456 by 819. That page describes one provider's service; the course's tests do not call it, and other providers resize differently or not at all.

The way out is to record the size of the image the model actually received. Then one ratio per axis, the viewport width divided by the image width, covers the device scale factor and any shrinking together. With $r$ that ratio, $s^{\text{capture}}$ the scroll offset when the screenshot was taken and $s^{\text{now}}$ the scroll offset at click time:

$$
x_{\text{view}} = s_x^{\text{capture}} + r\,x_{\text{img}} - s_x^{\text{now}}
$$

and the same for $y$. For the opening case, $r = 800 / 1600 = 0.5$ and nothing scrolled, so (547, 422) becomes (273.5, 211).

## Scroll and stale frames

A *frame* here is one observation: the screenshot plus the geometry needed to act on it later. Between the screenshot and the click the page can move. In the exercise the viewport is 320 pixels high, the model points at March's button, and then the page scrolls 60 pixels. Clicking the converted point without the scroll correction lands on April's button, one row lower. That is a valid click on the wrong report. The transform keeps the capture scroll in the frame and subtracts the current one:

```python
# file: examples/agent-engineering/src/agentlab/gui/coordinates.py
def image_to_viewport(x: float, y: float, frame: Frame, *, scroll_x: float | None = None, scroll_y: float | None = None) -> tuple[float, float]:
    """Map an image pixel to viewport CSS pixels at the page's current scroll position."""
    if not (0 <= x <= frame.image_width and 0 <= y <= frame.image_height):
        raise OffscreenTarget(f"({x}, {y}) is outside the {frame.image_width}x{frame.image_height} image")
    ratio = frame.ratio()
    now_x = frame.scroll_x if scroll_x is None else scroll_x
    now_y = frame.scroll_y if scroll_y is None else scroll_y
    # Page point = where the frame started + offset inside it; the viewport starts at the current scroll.
    view_x = frame.scroll_x + x * ratio - now_x
    view_y = frame.scroll_y + y * ratio - now_y
    if not (0 <= view_x <= frame.viewport_width and 0 <= view_y <= frame.viewport_height):
        raise OffscreenTarget(f"the target is at ({view_x}, {view_y}), outside the viewport after scrolling")
    return (view_x, view_y)
```

`frame.ratio()` raises if the two axes disagree by more than 1%, because then the image was cropped or padded, not resized, and a single ratio would be wrong. A point that has scrolled out of view raises `OffscreenTarget`, which means "take a new screenshot", never "click anyway".

## Set-of-Mark: let the model name a mark

Estimating pixels is the weak step. Set-of-Mark prompting (Yang and colleagues, 2023) moves it out of the model. The paper splits an image into regions with off-the-shelf segmentation models (SEEM and SAM), draws a label on each region (numbers, letters, masks or boxes), and lets GPT-4V answer with a label. The authors report that, zero-shot, this beat the state-of-the-art fully fine-tuned model on one referring-expression benchmark. That result is about the paper's tasks; it is not a measurement of browser agents.

The exercise keeps the idea and changes where the regions come from. In a browser the accessibility tree already knows every interactive element and its box: Playwright's `aria_snapshot(mode="ai", boxes=True)` lists each one with a reference such as `e16` and its viewport box. `parse_marks` keeps the interactive ones, `draw_marks` paints each reference onto the page for the screenshot, and the model can answer "e16". The labels are hidden from the accessibility tree and let clicks through, which a test checks. Playwright itself does not implement Set-of-Mark. Its snapshot is simply a convenient source of regions.

## Check what is under the point before clicking

Whether the model answered with a label or with pixels, the controller confirms the target just before acting:

```python
# file: examples/agent-engineering/src/agentlab/gui/marks.py
def pick_mark(x: float, y: float, marks: list[Mark]) -> Mark | None:
    """The one mark under a point, or None when no mark or several marks contain it.

    None means "observe again", never "click anyway": a point on two targets
    is a guess between them.
    """
    under = [mark for mark in marks if mark.contains(x, y)]
    return under[0] if len(under) == 1 else None
```

`click_point` in `browser.py` converts the point with the current scroll, takes a fresh snapshot, and clicks only if `pick_mark` finds exactly one element there. Otherwise it records a `gui.reobserve` event and returns `None` without touching the mouse. On a remote desktop with no tree, the only check available is another screenshot, which is weaker: it shows what is there, not what it is. That is one more reason [lesson 18.1](/lessons/18-computer-use-and-gui-automation/18.1-observe-before-acting/) prefers the semantic route wherever the page offers it.
