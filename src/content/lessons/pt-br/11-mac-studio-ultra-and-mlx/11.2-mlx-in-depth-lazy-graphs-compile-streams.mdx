A lição 8.9 apresentou duas ideias: o MLX é lazy, e seus arrays vivem em memória unificada. Esta lição as transforma em controles. Todo job de MLX tem quatro perguntas: quando o grafo roda, como ele é fundido, qual fila o executa e quanta memória ele pode ocupar. As respostas explicam a maior parte dos tempos estranhos e das surpresas de falta de memória que você vai encontrar num Mac Studio.

## Quando o grafo roda

As operações registram nós. `mx.eval(x)` executa o grafo de que `x` precisa e espera. `mx.async_eval(x)` o inicia e retorna. A docstring o chama de experimental, mas o mlx-lm depende dele. Em `generate_step`, o laço monta o grafo do próximo token a partir do token amostrado que ainda não foi calculado, chama `async_eval` nele e só então chama `.item()` no token anterior. A CPU prepara o passo n+1 enquanto a GPU executa o passo n. Sem a laziness, não haveria nada para sobrepor.

A documentação nomeia os gatilhos implícitos: imprimir um array, convertê-lo para NumPy, `.item()`, salvá-lo e usar um array escalar no controle de fluxo do Python. Ela também dá uma regra de tamanho: de algumas dezenas até muitos milhares de operações por avaliação é aceitável. Avaliar depois de cada operação paga um custo fixo a cada vez. O lugar natural para avaliar é uma vez por passo do laço externo.

## Como o grafo é fundido

O `mx.compile` traça uma função uma vez com entradas de substituição, junta o trabalho em comum, funde cadeias elemento a elemento em menos kernels e guarda o resultado em cache. A documentação lista o que força uma nova compilação: mudança de shape, rank, dtype ou do número de entradas. Um contador de sonda torna isso visível, porque o Python executa o corpo só durante o trace. Rode:

```python
import math
import mlx.core as mx

traces = 0

def gelu(x):
    global traces
    traces += 1  # a probe: Python runs this body only while MLX traces it
    return x * (1 + mx.erf(x / math.sqrt(2))) / 2

fast = mx.compile(gelu)
x = mx.random.uniform(shape=(8, 16))
mx.eval(fast(x)); mx.eval(fast(x))
print("same shape twice:", traces)
mx.eval(fast(mx.random.uniform(shape=(8, 32))))
print("new shape:", traces)
mx.eval(fast(mx.random.uniform(shape=(8, 32)).astype(mx.float16)))
print("new dtype:", traces)

traces = 0
flex = mx.compile(gelu, shapeless=True)
for shape in [(8, 16), (8, 32), (4, 7)]:
    mx.eval(flex(mx.random.uniform(shape=shape)))
print("shapeless, same rank:", traces)
mx.eval(flex(mx.random.uniform(shape=(2, 3, 5))))
print("shapeless, new rank:", traces)
```

No MLX 0.32.3, isto imprime 1, 2, 3, depois 1 e 2. Um shape novo e um dtype novo traçam de novo cada um. Com `shapeless=True`, três shapes do mesmo rank traçaram uma vez, e um rank novo traçou de novo; foi o que esta versão fez, então confira na sua. Funções compiladas precisam ser puras. Imprimir dentro de uma delas derruba o programa, porque os arrays são substitutos, e o estado que você quer carregar precisa passar pelos argumentos `inputs` e `outputs`. Os samplers do mlx-lm fazem exatamente isso, compilando com `inputs=mx.random.state, outputs=mx.random.state` para que a chave aleatória avance.

## Qual fila executa

Toda operação aceita `stream=`, que pode ser um stream ou um device. O padrão é o stream padrão do device padrão. Os arrays não são movidos, porque vivem em memória unificada. Quando uma operação num stream precisa da saída de outro, o próprio MLX insere a dependência. `mx.synchronize()` espera por um stream, e `with mx.stream(s):` o define para um bloco.

## Kernels escritos à mão

O `mx.fast` reúne operações fundidas, entre outras `rms_norm`, `layer_norm`, `rope`, `scaled_dot_product_attention` e os construtores de kernel. Quando nenhuma operação fundida serve, o `mx.fast.metal_kernel` recebe só o corpo do kernel e monta a assinatura a partir dos nomes de entrada e de saída que você der:

```python
import mlx.core as mx

source = """
    uint elem = thread_position_in_grid.x;
    T tmp = inp[elem];
    out[elem] = metal::exp(tmp);
"""
kernel = mx.fast.metal_kernel(
    name="myexp", input_names=["inp"], output_names=["out"], source=source
)

def exp_elementwise(a):
    return kernel(
        inputs=[a],
        template=[("T", mx.float32)],
        grid=(a.size, 1, 1),
        threadgroup=(256, 1, 1),
        output_shapes=[a.shape],
        output_dtypes=[a.dtype],
    )[0]

a = mx.random.normal(shape=(4, 16)).astype(mx.float16)
print("matches mx.exp:", mx.allclose(exp_elementwise(a), mx.exp(a)).item())
```

Construa o kernel uma vez; cada construção cria uma biblioteca Metal. O modelo do curso usa isso de verdade. No mlx-lm 0.32.0, o `gated_delta.py` executa a recorrência do Gated DeltaNet como um kernel Metal na GPU e recorre a operações comuns quando o device não é a GPU ou quando a dimensão da chave não é múltipla de 32. Compare os dois caminhos:

```python
import mlx.core as mx
from mlx_lm.models.gated_delta import gated_delta_update, normalize_qk

B, T, Hk, Hv, Dk, Dv = 1, 16, 2, 4, 128, 128
q = mx.random.normal((B, T, Hk, Dk))
k = mx.random.normal((B, T, Hk, Dk))
v = mx.random.normal((B, T, Hv, Dv))
a = mx.random.normal((B, T, Hv))
b = mx.random.normal((B, T, Hv))
A_log = mx.random.normal((Hv,))
dt_bias = mx.random.normal((Hv,))
q, k = normalize_qk(q, k, inv_scale=Dk**-0.5, eps=1e-6)

y_gpu, s_gpu = gated_delta_update(q, k, v, a, b, A_log, dt_bias, use_kernel=True)
y_ref, s_ref = gated_delta_update(q, k, v, a, b, A_log, dt_bias, use_kernel=False)
print("state:", s_gpu.dtype, s_gpu.shape)
print("max output gap:", mx.abs(y_gpu - y_ref).max().item())
```

As saídas concordam com precisão de cerca de $10^{-8}$, e o estado inicial é float32 com o shape batch, value heads, dimensão do value, dimensão da chave. A lição 8.9 deixou em aberto o dtype de estado do runtime. Para o estado inicial, esta fonte responde: float32, o dtype que a lição 7.2 supôs para o seu número de referência.

## Quanta memória ele pode ocupar

| Controle | O que faz |
|---|---|
| `iogpu.wired_limit_mb` (sistema) | O teto que o macOS põe na memória wired da GPU. `mx.device_info()["max_recommended_working_set_size"]` o informa. |
| `mx.set_wired_limit(bytes)` | Mantém essa quantidade de memória residente. Padrão 0, útil no macOS 15 ou posterior, e um erro acima do limite do sistema. |
| `mx.set_memory_limit(bytes)` | Uma diretriz para a avaliação do grafo. O padrão é o menor entre 1,5 vez o working set recomendado e 95% da memória instalada (60,8 GiB num Mac de 64 GB, onde 1,5 vez daria 77,8). A docstring diz apenas 1,5 vez. Passando dele, sem RAM sobrando, a alocação levanta uma exceção. |
| `mx.set_cache_limit(bytes)`, `mx.clear_cache()` | Limitam e esvaziam o pool de buffers liberados que o MLX guarda para reutilizar. O limite de cache começa igual ao limite de memória. |

Leia o uso com `get_active_memory` (exclui o cache), `get_cache_memory` e `get_peak_memory` com `reset_peak_memory`.

## A virada errada clássica

A virada errada é medir sem avaliar. As duas leituras abaixo mentem:

```python
import time
import mlx.core as mx

a = mx.random.normal((4096, 4096))
mx.eval(a)
mx.reset_peak_memory()

t0 = time.perf_counter()
y = a @ a                                  # recorded, nothing ran yet
build_ms = (time.perf_counter() - t0) * 1e3
peak_before = mx.get_peak_memory()

mx.eval(y)                                 # the work happens here
total_ms = (time.perf_counter() - t0) * 1e3
print("build ms:", round(build_ms, 2), "total ms:", round(total_ms, 2))
print("peak MB before eval:", peak_before // 10**6, "after:", mx.get_peak_memory() // 10**6)
```

O primeiro tempo é a montagem do grafo, e o primeiro pico é zero porque o produto ainda não foi alocado. Avalie, aqueça e só então leia.

:::warning
Não mude o wired limit enquanto um `async_eval` puder estar rodando. O código-fonte do mlx-lm diz isso, e o gerenciador de contexto `wired_limit` dele sincroniza o stream antes de restaurar o valor antigo.
:::

:::caveat
Os fatos aqui valem para o MLX 0.32.3 e o mlx-lm 0.32.0. A documentação marca o `async_eval` como experimental e descreve as variáveis de ambiente avançadas como sujeitas a mudança. O resultado do shapeless foi observado nesta versão, não prometido pela documentação.
:::

A ideia durável é que um programa MLX é um grafo que você conduz. A lição 11.3 usa essas regras dentro do mlx-lm para converter, ajustar e guardar em cache modelos de verdade.
