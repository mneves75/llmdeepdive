A [aula 8.9](/pt-br/lessons/8-building-and-serving-stacks/8.9-mlx/) apresentou duas ideias. O MLX é **lazy** (preguiçoso): uma linha como `y = a @ a` ainda não multiplica nada; ela só registra a operação num **grafo**, uma lista de operações e dos **arrays** (grades de números, como listas ou matrizes) de que cada uma depende. E os arrays do MLX vivem em memória unificada, um único pool que a CPU (unidade central de processamento) e a GPU (unidade de processamento gráfico) dividem ([aula 11.1](/pt-br/lessons/11-mac-studio-ultra-and-mlx/11.1-mac-studio-ultra-as-an-inference-machine/)). Esta aula transforma essas ideias em controles. Todo job de MLX levanta quatro perguntas: quando o grafo roda, como ele é fundido, qual fila o executa e quanta memória ele pode ocupar. As respostas explicam a maior parte dos tempos estranhos e das surpresas de falta de memória que você vai encontrar num Mac Studio.

## Quando o grafo roda

Cada operação acrescenta um nó ao grafo, e nada é calculado até você pedir. `mx.eval(x)` executa a parte do grafo de que `x` precisa e espera terminar. `mx.async_eval(x)` inicia o mesmo trabalho e retorna na hora, enquanto a GPU continua. A **docstring** dele (o texto curto de documentação embutido na própria função) o chama de experimental, mas o mlx-lm depende dele para sobrepor a montagem do grafo na CPU com a execução na GPU dentro de `generate_step`. Sem a laziness, não haveria nada para sobrepor.

<Figure id="t11-mlx-lazy-overlap" />

Algumas ações forçam a avaliação sem uma chamada explícita. A documentação nomeia esses gatilhos implícitos: imprimir um array, convertê-lo para **NumPy** (uma biblioteca padrão de Python para trabalhar com arrays de números), chamar `.item()` para extrair um único número Python, salvá-lo e usar um array **escalar** (um único número) no controle de fluxo do Python (uma decisão ou um laço, como `if` ou `while`). A documentação também dá uma regra de tamanho: de algumas dezenas até muitos milhares de operações por avaliação é aceitável. Avaliar depois de cada operação paga um custo fixo a cada vez. O lugar natural para avaliar é uma vez por passo do laço externo.

## Como o grafo é fundido

Um **kernel** é um pequeno programa que roda na GPU, e lançar cada um custa tempo. O `mx.compile` reduz esse custo. Ele **traça** a função uma vez: executa o seu código Python com entradas de substituição (*placeholders* que carregam apenas dimensões e tipos numéricos, sem valores reais) e registra quais operações ele faz. Depois junta o trabalho em comum, funde cadeias de passos elemento a elemento (passos que tratam cada número isoladamente) em menos kernels e guarda o resultado compilado num **cache** (um estoque de resultados prontos para reaproveitamento). A documentação lista o que força uma nova compilação: mudança de shape (o tamanho de cada dimensão), de rank (o número de dimensões), de dtype (o tipo numérico, como `float32` de 32 bits ou `float16` de 16 bits) ou do número de entradas.

Como o Python executa o corpo de uma função compilada apenas durante o trace, um pequeno contador de sonda torna a recompilação visível. O script abaixo compila uma função de ativação GELU, chama-a duas vezes com o mesmo shape, depois com um shape novo e um dtype novo, e repete o teste com `shapeless=True` em três shapes do mesmo rank seguidos de um rank novo:

```python
import math
import mlx.core as mx

traces = 0

def gelu(x):
    global traces
    traces += 1  # a probe: Python runs this body only while MLX traces it
    return x * (1 + mx.erf(x / math.sqrt(2))) / 2

fast = mx.compile(gelu)
x = mx.random.uniform(shape=(8, 16))
mx.eval(fast(x)); mx.eval(fast(x))
print("same shape twice:", traces)
mx.eval(fast(mx.random.uniform(shape=(8, 32))))
print("new shape:", traces)
mx.eval(fast(mx.random.uniform(shape=(8, 32)).astype(mx.float16)))
print("new dtype:", traces)

traces = 0
flex = mx.compile(gelu, shapeless=True)
for shape in [(8, 16), (8, 32), (4, 7)]:
    mx.eval(flex(mx.random.uniform(shape=shape)))
print("shapeless, same rank:", traces)
mx.eval(flex(mx.random.uniform(shape=(2, 3, 5))))
print("shapeless, new rank:", traces)
```

No MLX 0.32.3, isto imprime 1, 2, 3, depois 1 e 2. Um shape novo e um dtype novo traçam de novo cada um. Com `shapeless=True`, três shapes do mesmo rank traçaram uma vez, e um rank novo traçou de novo. Foi o que esta versão fez; então confira na sua.

Funções compiladas precisam ser **puras**: o resultado só pode depender das entradas, e elas não podem alterar nada fora de si. Imprimir dentro de uma delas derruba o programa, porque durante o trace os arrays são substitutos sem valores. O estado que você quer levar de uma chamada para a outra precisa passar pelos argumentos `inputs` e `outputs`. Os samplers do mlx-lm usam esse padrão, compilando com `inputs=mx.random.state, outputs=mx.random.state` para que a chave aleatória (o estado interno que guia o gerador de números aleatórios) avance.

## Qual fila executa

Um **stream** é uma fila de trabalho para um device, a CPU ou a GPU. Toda operação aceita `stream=`, que pode ser um stream ou um device. O padrão é o stream padrão do device padrão. Os arrays não são movidos entre devices, porque vivem em memória unificada. Quando uma operação num stream precisa da saída de outro, o próprio MLX insere a dependência. `mx.synchronize()` espera por um stream, e `with mx.stream(s):` o define para um bloco.

## Kernels escritos à mão

Algumas operações são comuns o bastante para o MLX já entregá-las fundidas. O `mx.fast` as reúne, entre outras `rms_norm`, `layer_norm`, `rope`, `scaled_dot_product_attention` e os construtores de kernel. Quando nenhuma operação fundida serve, você pode escrever o seu próprio kernel em Metal, a linguagem da Apple para programas de GPU. O `mx.fast.metal_kernel` recebe só o corpo do kernel e monta a assinatura a partir dos nomes de entrada e de saída que você der. O exemplo abaixo escreve um kernel Metal curto que calcula a exponencial de cada elemento de um array e confere se o resultado bate com o `mx.exp` nativo do MLX:

```python
import mlx.core as mx

source = """
    uint elem = thread_position_in_grid.x;
    T tmp = inp[elem];
    out[elem] = metal::exp(tmp);
"""
kernel = mx.fast.metal_kernel(
    name="myexp", input_names=["inp"], output_names=["out"], source=source
)

def exp_elementwise(a):
    return kernel(
        inputs=[a],
        template=[("T", mx.float32)],
        grid=(a.size, 1, 1),
        threadgroup=(256, 1, 1),
        output_shapes=[a.shape],
        output_dtypes=[a.dtype],
    )[0]

a = mx.random.normal(shape=(4, 16)).astype(mx.float16)
print("matches mx.exp:", mx.allclose(exp_elementwise(a), mx.exp(a)).item())
```

Construa o kernel uma vez; cada construção compila uma **biblioteca** Metal (um pacote de código de GPU pronto para rodar). O modelo do curso usa isso de verdade. As camadas Gated DeltaNet dele ([aula 4.15](/pt-br/lessons/4-transformer/4.15-gated-deltanet/)) atualizam um estado de tamanho fixo uma vez por token, um passo chamado recorrência. No mlx-lm 0.32.0, o `gated_delta.py` executa essa recorrência como um kernel Metal na GPU. Ele recorre a operações comuns quando o device não é a GPU ou quando a dimensão da chave não é múltipla de 32. O script abaixo passa as mesmas entradas aleatórias pelo kernel Metal da GPU (`use_kernel=True`) e pelo caminho alternativo comum (`use_kernel=False`), e imprime o tipo numérico do estado, o shape e a maior diferença numérica:

```python
import mlx.core as mx
from mlx_lm.models.gated_delta import gated_delta_update, normalize_qk

B, T, Hk, Hv, Dk, Dv = 1, 16, 2, 4, 128, 128
q = mx.random.normal((B, T, Hk, Dk))
k = mx.random.normal((B, T, Hk, Dk))
v = mx.random.normal((B, T, Hv, Dv))
a = mx.random.normal((B, T, Hv))
b = mx.random.normal((B, T, Hv))
A_log = mx.random.normal((Hv,))
dt_bias = mx.random.normal((Hv,))
q, k = normalize_qk(q, k, inv_scale=Dk**-0.5, eps=1e-6)

y_gpu, s_gpu = gated_delta_update(q, k, v, a, b, A_log, dt_bias, use_kernel=True)
y_ref, s_ref = gated_delta_update(q, k, v, a, b, A_log, dt_bias, use_kernel=False)
print("state:", s_gpu.dtype, s_gpu.shape)
print("max output gap:", mx.abs(y_gpu - y_ref).max().item())
```

As saídas concordam com precisão de cerca de $10^{-8}$, e o estado inicial é float32 com o shape batch, value heads, dimensão do value, dimensão da chave. A aula 8.9 deixou em aberto o dtype de estado do runtime. Para o estado inicial, esta fonte responde: float32, o dtype que a [aula 7.2](/pt-br/lessons/7-inference-and-efficiency/7.2-the-kv-cache/) supôs para o seu número de referência.

## Quanta memória ele pode ocupar

Quatro limites separados decidem quanta memória um job de MLX pode ocupar. Os dois primeiros tratam de memória **wired**, travada na RAM para que o macOS não possa movê-la para o disco ([aula 11.1](/pt-br/lessons/11-mac-studio-ultra-and-mlx/11.1-mac-studio-ultra-as-an-inference-machine/)). Os outros dois são orçamentos do próprio MLX: um para os arrays que uma avaliação do grafo cria, outro para os **buffers** liberados (blocos de memória alocada) que o MLX guarda para reutilizar. O "working set recomendado" da tabela é o máximo de memória que o macOS recomenda que a GPU use de uma vez.

| Controle | O que faz |
|---|---|
| `iogpu.wired_limit_mb` (sistema) | O teto que o macOS põe na memória wired da GPU. `mx.device_info()["max_recommended_working_set_size"]` o informa. |
| `mx.set_wired_limit(bytes)` | Mantém essa quantidade de memória residente. Padrão 0, útil no macOS 15 ou posterior, e um erro acima do limite do sistema. |
| `mx.set_memory_limit(bytes)` | Uma diretriz para a avaliação do grafo. O padrão é o menor entre 1,5 vez o working set recomendado e 95% da memória instalada (60,8 GiB num Mac com 64 GiB instalados, onde 1,5 vez daria 77,8, então o limite de 95% é o menor). A docstring diz apenas 1,5 vez. Passando dele, sem RAM sobrando, a alocação levanta uma **exceção** (um erro de execução). |
| `mx.set_cache_limit(bytes)`, `mx.clear_cache()` | Limitam e esvaziam o pool de buffers liberados que o MLX guarda para reutilizar. O limite de cache começa igual ao limite de memória. |

Leia o uso com `get_active_memory` (exclui o cache), `get_cache_memory` e `get_peak_memory` com `reset_peak_memory`.

## Por que um cronômetro em volta de uma linha marca quase nada

A laziness também estraga a medição ingênua, como mostrou o passo 1 da figura acima. O script abaixo aloca uma matriz 4.096 × 4.096, registra uma multiplicação de matrizes, lê o tempo decorrido e o pico de memória antes do `mx.eval` e depois roda `mx.eval` para contrastar essas leituras falsas com as reais:

```python
import time
import mlx.core as mx

a = mx.random.normal((4096, 4096))
mx.eval(a)
mx.reset_peak_memory()

t0 = time.perf_counter()
y = a @ a                                  # recorded, nothing ran yet
build_ms = (time.perf_counter() - t0) * 1e3
peak_before = mx.get_peak_memory()

mx.eval(y)                                 # the work happens here
total_ms = (time.perf_counter() - t0) * 1e3
print("build ms:", round(build_ms, 2), "total ms:", round(total_ms, 2))
print("peak MB before eval:", peak_before // 10**6, "after:", mx.get_peak_memory() // 10**6)
```

O primeiro tempo é a montagem do grafo, e o primeiro pico é zero porque o produto ainda não foi alocado. A correção tem três passos: avalie, aqueça com uma execução que você descarta e só então leia.

:::warning
Não mude o wired limit enquanto um `async_eval` puder estar rodando. O código-fonte do mlx-lm diz isso, e o **gerenciador de contexto** `wired_limit` dele (um bloco `with` em Python que prepara um recurso na entrada e o restaura com segurança na saída) sincroniza o stream antes de restaurar o valor antigo.
:::

:::caveat
Os fatos aqui valem para o MLX 0.32.3 e o mlx-lm 0.32.0. A documentação marca o `async_eval` como experimental e descreve as variáveis de ambiente avançadas como sujeitas a mudança. O resultado do shapeless foi observado nesta versão, não prometido pela documentação.
:::

Um programa MLX é um grafo que você conduz: você escolhe quando ele roda, o que é fundido, onde ele roda e quanta memória pode ocupar. A [aula 11.3](/pt-br/lessons/11-mac-studio-ultra-and-mlx/11.3-mlx-lm-in-practice/) usa essas regras dentro do mlx-lm para converter, ajustar e guardar em cache modelos de verdade.
