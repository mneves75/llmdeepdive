Um Mac Studio em cima da mesa é um ótimo servidor de inferência para uma equipe, e dois programas o transformam em um. O `mlx_lm.server` vem com o mlx-lm, do projeto ml-explore da Apple. O `mlx-serve` é um projeto separado de David Dalcu, escrito na linguagem de programação Zig e fixado aqui na v26.10.1. Um projeto sem relação, raspoli/mlx-serve, tem o mesmo nome; então confira o dono antes de baixar. Os dois falam uma API no estilo OpenAI: implementam parte dos endpoints e parâmetros de completion de texto da OpenAI, de modo que um código cliente escrito para eles pode apontar para o seu Mac. Diferem em três pontos: o que agrupam em batch, o que guardam em cache e quem consegue alcançá-los por padrão.

## O mlx_lm.server na 0.32.0

Quem consegue alcançar um servidor depende do endereço de rede em que ele faz o bind, isto é, em que ele escuta. O loopback, 127.0.0.1, só é alcançável a partir do próprio Mac. Inicie o servidor em loopback e depois consulte-o a partir de um segundo terminal:

```bash
mlx_lm.server --model mlx-community/Qwen3-4B-Instruct-2507-4bit --host 127.0.0.1 --port 8080
```

```bash
curl -s http://127.0.0.1:8080/health
curl -s http://127.0.0.1:8080/v1/chat/completions -H 'Content-Type: application/json' -d '{"messages":[{"role":"system","content":"You are a terse assistant for the fictional Harbor service. Retry budget is three attempts. Delay starts at 200 ms and doubles."},{"role":"user","content":"How many attempts?"}],"max_tokens":24,"temperature":0}'
```

Os endpoints são `/v1/chat/completions` (também `/chat/completions`), `/v1/completions`, `/v1/models` e `/health`.

**Reaproveitamento de prompt.** Quando um prompt novo começa com os mesmos tokens de um anterior, o servidor pode reaproveitar o KV cache salvo desse começo (as keys e values guardadas da [aula 7.2](/pt-br/lessons/7-inference-and-efficiency/7.2-the-kv-cache/)) em vez de ler esses tokens de novo. Rode o pedido de chat duas vezes para ver isso. A primeira resposta traz `"cached_tokens": 0` em `usage.prompt_tokens_details`. A segunda repete o prompt e informa 44 dos seus 45 tokens em cache. Esse campo é como você enxerga o reaproveitamento de prompt de fora. Por dentro, o servidor mantém um LRU de caches distintos (*least recently used*: quando enche, descarta o cache que está há mais tempo sem uso). Ele guarda 10 por padrão, com teto em bytes dado por `--prompt-cache-bytes`, e é consultado atrás do prefixo de tokens em cache mais próximo.

**Batching.** Batching é passar vários pedidos pelo modelo no mesmo passo, e o continuous batching ([aula 7.8](/pt-br/lessons/7-inference-and-efficiency/7.8-pagedattention-and-continuous-batching/)) deixa pedidos entrarem e saírem entre os passos. O batching vem ligado por padrão no mlx_lm.server, com `--decode-concurrency 32` e `--prompt-concurrency 8`. Um pedido só entra em batch se as quatro condições abaixo valem:

- o servidor não tem modelo de rascunho (o pequeno modelo auxiliar do speculative decoding, [aula 7.5](/pt-br/lessons/7-inference-and-efficiency/7.5-beam-search-speculative-decoding-and-medusa/));
- todo tipo de cache sabe fazer merge num único cache em batch;
- o pedido não define `seed` (um valor inicial fixo para a amostragem aleatória);
- `--kv-bits` não está definido.

Caso contrário, o servidor esvazia o batch e atende o pedido sozinho. A quantização de KV da [aula 11.3](/pt-br/lessons/11-mac-studio-ultra-and-mlx/11.3-mlx-lm-in-practice/) portanto troca batching por memória: nesta versão, um servidor iniciado com `--kv-bits` trata um pedido por vez.

## O mlx-serve v26.10.1

O mlx-serve é um único binário nativo que serve modelos MLX e, por meio de um llama.cpp embutido, arquivos GGUF (o formato de modelo do llama.cpp, [aula 8.7](/pt-br/lessons/8-building-and-serving-stacks/8.7-llama-cpp-and-gguf/)). Ele fala os formatos OpenAI, Anthropic e Ollama numa só porta. Seu `LICENSE` é MIT para o código próprio, com componentes de terceiros sob termos próprios. Baixe a release, confira o hash contra o digest que o GitHub mostra e inicie em loopback:

```bash
gh release download v26.10.1 --repo ddalcu/mlx-serve --pattern 'mlx-serve-bin-macos-arm64.tar.gz'
shasum -a 256 mlx-serve-bin-macos-arm64.tar.gz
tar -xzf mlx-serve-bin-macos-arm64.tar.gz
./mlx-serve-macos-arm64/mlx-serve --version
./mlx-serve-macos-arm64/mlx-serve --model q4-g64 --serve --host 127.0.0.1 --port 11234 --max-concurrent 4
```

Num segundo terminal, peça uma resposta no estilo Anthropic:

```bash
curl -s http://127.0.0.1:11234/v1/messages -H 'Content-Type: application/json' -H 'anthropic-version: 2023-06-01' -d '{"model":"mlx-serve","max_tokens":16,"messages":[{"role":"user","content":"Name one planet."}]}'
```

A linha de `--version` informa o MLX embutido, 0.32.3 nesta release. O diretório `q4-g64` é o modelo MLX que a aula 11.3 converteu. O continuous batching fica desligado até você passar `--max-concurrent N`, e o prefix cache vem ligado por padrão. As respostas dele acrescentam um objeto `timings`, que é o relógio do próprio servidor.

## Como cronometrar dois servidores no mesmo relógio

O **tempo até o primeiro token** é a espera entre enviar um pedido e receber o primeiro pedaço de texto da resposta. É tentador comparar dois servidores por um número desses vindo de dois relógios diferentes, por exemplo o `timings` do próprio mlx-serve contra um cronômetro no cliente para o outro servidor. Use um só relógio para os dois: o do cliente.

O tempo até o primeiro token também não é o primeiro byte. Uma resposta em streaming chega como SSE (*server-sent events*): o servidor mantém uma resposta HTTP aberta e escreve uma linha para cada pedaço, ou chunk. O `mlx_lm.server` escreve linhas de comentário SSE como `: keepalive 10/11` enquanto processa o prompt, e os dois servidores enviaram bytes antes de qualquer texto. Então pare o relógio no primeiro chunk que traz texto:

```python
import json, sys, time, urllib.request

def measure(base, prompt, max_tokens=64):
    body = json.dumps({
        "messages": [{"role": "user", "content": prompt}],
        "max_tokens": max_tokens, "temperature": 0, "stream": True,
        "stream_options": {"include_usage": True},
    }).encode()
    req = urllib.request.Request(base + "/v1/chat/completions", body,
                                 {"Content-Type": "application/json"})
    t0 = time.perf_counter()
    first_byte = first_text = last_text = usage = None
    with urllib.request.urlopen(req) as resp:
        for raw in resp:
            now = time.perf_counter() - t0
            first_byte = now if first_byte is None else first_byte
            line = raw.decode().strip()
            if not line.startswith("data: ") or line == "data: [DONE]":
                continue
            chunk = json.loads(line[6:])
            usage = chunk.get("usage") or usage
            for choice in chunk.get("choices", []):
                if choice.get("delta", {}).get("content"):
                    first_text = now if first_text is None else first_text
                    last_text = now
    if usage is None or first_text is None or last_text == first_text:
        return {"first_byte_s": first_byte, "ttft_s": first_text,
                "decode_tok_s": None,
                "cached": (usage or {}).get("prompt_tokens_details", {}).get("cached_tokens"),
                "note": "decode rate unavailable: need at least two text chunks and a usage block"}
    n = (usage or {}).get("completion_tokens")
    if not n or n < 2:
        return {"first_byte_s": first_byte, "ttft_s": first_text,
                "decode_tok_s": None,
                "cached": (usage or {}).get("prompt_tokens_details", {}).get("cached_tokens"),
                "note": "decode rate unavailable: need at least two completion tokens"}
    return {"first_byte_s": first_byte, "ttft_s": first_text,
            "decode_tok_s": (n - 1) / (last_text - first_text),
            "cached": (usage or {}).get("prompt_tokens_details", {}).get("cached_tokens")}

print(measure(sys.argv[1], sys.argv[2]))
```

Rode `python ttft.py http://127.0.0.1:8080 "Write two sentences about harbors."` contra cada servidor. A taxa de decode conta os tokens depois do primeiro, a partir do bloco usage, sobre o tempo entre o primeiro e o último texto. Para uma comparação justa:

- Use os mesmos pesos e o mesmo prompt com temperature 0.
- Registre `cached`, para manter separadas as execuções frias (nada em cache) e as quentes.
- Repita e relate a dispersão, não uma execução só.
- Iguale os ajustes que mudam o trabalho. Isso quer dizer `--decode-concurrency` contra `--max-concurrent`, e o speculative decoding do mlx-serve: o Prompt Lookup Decoding dele, que adivinha os próximos tokens a partir de texto que já está no prompt, vem ligado por padrão, e `--no-pld` o desliga.

Não cite números de outro Mac nem de outro modelo.

:::warning
Nenhum dos dois servidores é um serviço de internet endurecido. O `mlx_lm.server` documenta que implementa apenas verificações básicas de segurança. Ele não tem autenticação. O `--allowed-origins`, a lista de sites cujos scripts o navegador deixa ler as respostas do servidor (uma regra de navegador chamada CORS, não autenticação: não barra nada que não seja um navegador), vem como `*` por padrão, o que quer dizer qualquer site. E o campo `model` de um pedido pode nomear outro modelo para o servidor carregar. O mlx-serve usa `0.0.0.0` por padrão, o que quer dizer todas as redes em que o Mac está, no texto de ajuda e no `main.zig`, embora o seu `SECURITY.md` diga que 127.0.0.1 é o padrão. O `--api-key` dele isenta o loopback, a menos que você acrescente `--api-key-strict`, e o `--lan-share` anuncia modelos por Bonjour, a descoberta de rede local da Apple. Passe sempre `--host 127.0.0.1` e ponha um proxy de verdade, com autenticação, na frente de qualquer coisa compartilhada.
:::
