O laço de reparo da [aula 21.3](/pt-br/lessons/21-bounded-agent-self-correction/21.3-repair-with-a-bounded-context/) poderia, em princípio, pedir patches ao modelo para sempre. Cada tentativa custa uma chamada de modelo, uma execução de testes e um pouco de tempo, e um laço preso num bug que não consegue corrigir continua pagando. Quantas tentativas ele deve ter, quanto isso custa em média e no pior caso, e como o limite sobrevive a uma queda do processo no meio do caminho? Esta aula define o orçamento, faz a conta dele e torna os contadores duráveis.

## O que significa "três tentativas"?

O laço começa com uma *execução inicial*: os testes no código original, que medem a falha. Ela não pede nada ao modelo. Depois vêm no máximo três *tentativas de reparo*. Cada tentativa é uma chamada de modelo propondo um patch, a verificação de política e, se o patch for permitido, uma execução de testes. Um patch recusado pela política ainda conta como tentativa, porque a chamada ao modelo foi feita e paga. O laço para na primeira tentativa cujos testes passam, ou depois da terceira.

A orientação da Anthropic sobre construir agentes observa que uma tarefa costuma terminar quando está pronta, mas que também é comum incluir condições de parada, como um número máximo de iterações, para manter o controle. Três é a escolha deste curso, não uma regra de uma fonte; a calculadora abaixo mostra o que ela compra.

## O que a conta diz

Suponha que cada tentativa de reparo passe nos testes com probabilidade 0,4, de forma independente das outras, e custe USD 0,12. As três falham com probabilidade 0,6 × 0,6 × 0,6 = 0,216, então o laço escala em 21,6% das vezes e tem sucesso em 78,4%.

As *tentativas esperadas* contam só tentativas de reparo, incluindo a que dá certo, e nunca a execução inicial. A tentativa 1 sempre roda. A tentativa 2 só roda se a 1 falhou, com probabilidade 0,6. A tentativa 3 só roda se as duas falharam, com probabilidade 0,36. Então o número esperado é 1 + 0,6 + 0,36 = 1,96, e o custo esperado é 1,96 × USD 0,12 = USD 0,2352. O pior caso são as três tentativas, USD 0,36. Orce pelo pior caso: uma média não diz quanto custa uma execução ruim.

A calculadora começa desses números. Mude a chance de sucesso ou o número de tentativas e veja quão rápido as tentativas extras deixam de se pagar.

:::caveat
Todos os números acima supõem tentativas independentes. As reais raramente são. Se o bug está fora dos arquivos permitidos, ou se o próprio teste que falha está errado, toda tentativa falha pelo mesmo motivo e a chance real de sucesso é zero. Huang et al. (2023) viram que modelos revisando o próprio raciocínio sem feedback externo muitas vezes não conseguem corrigi-lo. Um modelo escrevendo o terceiro patch a partir da mesma evidência está numa posição parecida. Falhas correlacionadas tornam a escalada mais provável do que a calculadora diz, e é por isso que o laço também para em falhas repetidas.
:::

## Três limites, verificados antes de cada tentativa

As tentativas são um limite. Tokens e tempo de relógio são os outros dois, porque um prompt enorme ou uma execução de testes travada podem estourar um orçamento sem usar muitas tentativas. O laço verifica os três antes de iniciar uma tentativa:

```python
# file: examples/agent-engineering/src/agentlab/repair/budget.py
    def exhausted(self, spent: Spent) -> str | None:
        """Why no further attempt may start, or None."""
        if spent.attempts >= self.max_attempts:
            return f"budget: {spent.attempts} of {self.max_attempts} repair attempts used"
        if spent.tokens >= self.max_tokens:
            return f"budget: tokens {spent.tokens} of {self.max_tokens}"
        if spent.seconds >= self.max_seconds:
            return f"budget: wall time {spent.seconds:.0f} of {self.max_seconds:.0f} seconds"
        return None
```

Os padrões são 3 tentativas, 20.000 tokens e 600 segundos. Os tokens são contados com a mesma aproximação que a [aula 19.3](/pt-br/lessons/19-agent-memory-and-context/19.3-token-budgets-and-compression/) rotula como tal, cerca de quatro caracteres por token, sobre todo prompt e toda resposta de reparo. No exercício, três patches errados gastam 1.793 tokens aproximados; com um orçamento de 1.000 tokens o laço para depois de duas tentativas, em 1.178. Um limite é verificado entre tentativas, então uma tentativa pode ultrapassá-lo; os limites por execução da [aula 17.2](/pt-br/lessons/17-sandboxed-agent-execution/17.2-resource-and-filesystem-limits/) limitam quanto. O tempo vem de um relógio injetado, então o teste do limite de tempo roda na hora: com um relógio que avança 100 segundos por leitura e um orçamento de 150 segundos, a segunda tentativa é a última.

## Contadores que sobrevivem a um reinício

Um orçamento guardado numa variável zera quando o processo morre, e um laço que cai em toda chamada ao modelo tentaria então para sempre. Por isso os contadores ficam no SQLite, uma linha por execução, gravados com o compare-and-swap da [aula 14.3](/pt-br/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/): uma atualização só casa se ninguém gravou desde que o escritor leu a linha. A ordem das gravações é o ponto:

```python
# file: examples/agent-engineering/src/agentlab/repair/loop.py
    while (reason := budget.exhausted(spent)) is None:
        messages = repair_messages(task, original, spent.history)
        number = spent.attempts + 1
        # Charged before the model call, so a crash from here on still counts this attempt.
        spent = store.charge(run_id, spent, attempts=1, tokens=sum(approx_tokens(m["content"]) for m in messages))
        started = clock()
        reply = model.complete(messages, tools=[PATCH_TOOL])
```

A tentativa e os tokens do prompt são gravados antes da chamada. Se o processo morre dentro da chamada, a tentativa está gasta; o que se perde são só os tokens da resposta e o tempo dessa tentativa, que nunca foram medidos. O exercício derruba uma execução dentro da tentativa 2, abre o banco de novo como um processo novo faria e encontra `attempts` em 2. O laço retomado chama o modelo mais uma vez, para a tentativa 3, e então escala.

A mesma linha guarda o histórico: o número de cada tentativa, a hipótese, o hash do patch, o resultado e a assinatura da falha. O próximo prompt lista as hipóteses anteriores e seus resultados, de modo parecido com o Reflexion (Shinn et al., 2023), que guarda reflexões verbais sobre tentativas anteriores num buffer de memória episódica para as seguintes. Aqui o histórico também alimenta duas regras: um patch idêntico a um anterior é recusado, e uma falha repetida para o laço.

## Pare quando a mesma falha voltar

A *assinatura* de uma falha é o teste que falhou, o tipo de erro e o arquivo e a linha do frame relevante, que continuam iguais quando só os valores mudam. Se dois patches consecutivos que rodaram produzem a mesma assinatura, nenhum dos dois tocou na causa, e um terceiro provavelmente também não vai tocar:

```python
# file: examples/agent-engineering/src/agentlab/repair/loop.py
        if previous is not None and previous.signature == feedback.signature:
            return RepairOutcome("escalated", f"repeated failure: attempts {previous.number} and {number} failed the same way ({feedback.signature})", original, spent)
```

Mudar a taxa de desconto para 0,5 e depois para 0,25 deixa dez unidades sem desconto nas duas vezes, então o laço escala depois de duas tentativas em vez de três. A escalada é a saída projetada, não uma pane: o resultado leva a falha original, a hipótese e o resultado de cada tentativa, e os contadores, que é o que uma pessoa precisa para começar de onde o laço parou.
