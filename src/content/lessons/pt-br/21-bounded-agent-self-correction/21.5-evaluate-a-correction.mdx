Três patches para o bug de preços passam todos nos três testes visíveis. Um troca `>` por `>=`. Um troca `>` por `==`. Um acrescenta um caso especial: se o pedido for exatamente 10 unidades a USD 12,00, retorne USD 114,00. O laço de reparo da [aula 21.4](/pt-br/lessons/21-bounded-agent-self-correction/21.4-budget-the-repair-loop/) aceitaria qualquer um deles, porque não tem mais nada em que se basear. Qual deve ir para produção? Esta aula responde com testes que o laço nunca viu, e mostra um caso em que não colocar reparo nenhum é a escolha mais segura.

## Por que os testes do próprio laço não podem avaliar o laço

Os testes visíveis são aquilo contra o que o laço otimizou. Cada tentativa foi julgada por eles, e o laço parou assim que passaram. Passar neles é, portanto, a condição para o laço parar, e diz pouco sobre qualquer outra coisa. Smith et al. (2015) deram nome ao problema com o vocabulário de aprendizado de máquina: os testes usados para construir um patch são os dados de *treino* dele, e um conjunto independente usado só para julgá-lo são dados *reservados* (*held-out*). Um patch que passa nos testes de treino e falha nos reservados sofre *overfitting*: ele se ajusta aos exemplos em vez de à regra.

Eles estudaram duas ferramentas de reparo guiadas por testes, GenProg e TrpAutoRepair, num benchmark de 998 bugs, e julgaram os patches delas com testes independentes dos testes de reparo. As ferramentas raramente melhoravam a fração de testes independentes aprovados. A qualidade dos patches crescia com a cobertura da suíte de testes de reparo e, para programas que já passavam na maioria dos testes, as ferramentas tinham a mesma chance de quebrar testes e de corrigi-los. Os autores também viram que desenvolvedores iniciantes caem no mesmo overfitting, e que as ferramentas não se saíram pior que eles. Qi et al. (2015) viram que a esmagadora maioria dos patches que sistemas anteriores tinham relatado não estava correta e equivalia a uma única mudança que apaga funcionalidade. Uma suíte de testes que não verifica um comportamento não percebe quando ele some.

## Quatro grupos de testes

O exercício reserva dois testes num arquivo que o laço nunca carrega: doze unidades a USD 10,00 devem custar USD 114,00, e dez unidades a USD 0,99 devem custar USD 9,41 (9,90 menos 5% é 9,405, arredondado pela regra do meio para cima). `evaluate` roda o código original e o código com patch contra os testes visíveis e os reservados juntos, e separa cada teste pelos seus dois resultados:

```python
# file: examples/agent-engineering/src/agentlab/repair/evaluate.py
    groups = {
        "fail_to_pass": (everything - before.passed) & after.passed,
        "pass_to_pass": before.passed & after.passed,
        "pass_to_fail": before.passed - after.passed,
        "fail_to_fail": everything - before.passed - after.passed,
    }
```

Os nomes vêm do SWE-bench (Jimenez et al., 2023). As tarefas dele guardam uma lista de testes *fail-to-pass*, que a correção de referência deixa verdes e que verificam se a issue foi resolvida, e de testes *pass-to-pass*, que já passavam e verificam que o comportamento existente não quebrou. Uma tarefa só conta como resolvida se todo teste das duas listas passar. O exercício acrescenta os dois grupos que o SWE-bench deixa fora da pontuação, porque o veredito de um laço de reparo precisa deles: *pass-to-fail* é uma regressão, e *fail-to-fail* é um teste que o reparo não corrigiu.

Depois vem o veredito, nesta ordem:

```python
# file: examples/agent-engineering/src/agentlab/repair/evaluate.py
    if groups["pass_to_fail"]:
        return Evaluation("keep_original", f"regression: {', '.join(sorted(groups['pass_to_fail']))}", **groups, **counts)
    if groups["fail_to_fail"]:
        return Evaluation("escalate", f"still failing: {', '.join(sorted(groups['fail_to_fail']))}", **groups, **counts)
    return Evaluation("ship", f"{len(after.passed)} of {len(everything)} tests pass and nothing regressed", **groups, **counts)
```

Uma verificação antes dessas recusa uma execução reparada que pulou testes, rodou menos testes que a original ou nunca relatou resultado, pelos motivos que a [aula 21.1](/pt-br/lessons/21-bounded-agent-self-correction/21.1-what-counts-as-corrective-feedback/) deu.

## Três patches, três vereditos

O código original passa em 3 dos 5 testes: nove unidades, a soma da fatura e doze unidades. Eis cada patch:

| Patch | Passa | Corrigidos | Quebrados | Ainda falhando | Veredito |
|---|---|---|---|---|---|
| `>=` | 5 de 5 | dez unidades, arredondamento | nenhum | nenhum | ship |
| `==` | 4 de 5 | dez unidades, arredondamento | doze unidades | nenhum | keep_original |
| caso especial | 4 de 5 | dez unidades | nenhum | arredondamento | escalate |

Os dois patches com overfitting marcam 4 de 5, e esse número sozinho esconde a diferença entre eles. O caso especial não quebrou nada; ele corrigiu exatamente o exemplo que viu e nada além, então uma pessoa deve olhar. O patch com `==` corrigiu dez unidades e tirou o desconto de todo pedido acima de dez. Isso é uma regressão, e aqui o original é mais seguro que o reparo. O original cobra a mais em pedidos de exatamente dez unidades, um bug conhecido com um teste que falha apontando para ele. O código com patch cobraria a mais em todo pedido maior, e os testes visíveis o relatariam como corrigido. Ficar com o original e escalar deixa o sistema não pior do que estava. Colocar o patch em produção o deixa pior de um jeito que ninguém está observando.

## Evidência independente

Testes reservados só são independentes se o laço nunca os vê. O exercício verifica isso de ponta a ponta: roda o laço com um modelo que propõe o patch com `==`, confirma que o laço o aceita, que nenhum prompt contém o nome do arquivo reservado nem os nomes dos testes dele, e que `evaluate` então retorna `keep_original`. Quem escreve os testes reservados não deve ser o autor do patch, seja esse autor um modelo ou uma pessoa.

:::caveat
Dois testes reservados formam um exemplo didático, não uma estimativa de confiabilidade. Todo resultado desta trilha é *fixture-tested* (testado com dados fixos): um modelo roteirizado propôs patches e testes reais os julgaram. Isso prova a lógica de controle do laço, não com que frequência um modelo real repara bugs reais. Medir isso exige um corpus de cenários reservados, tentativas repetidas e um modelo ao vivo, que a [aula 23.3](/pt-br/lessons/23-agent-evaluation-and-ci/23.3-build-a-100-case-corpus/) constrói.
:::

## Rode o exercício

O módulo é `src/agentlab/repair/evaluate.py`; os testes reservados estão em `src/agentlab/fixtures/repair/held_out/`, e os testes do exercício em `tests/test_repair_evaluate.py`. A partir de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest tests.test_repair_evaluate -v`. Espere `Ran 5 tests` e `OK`. Os casos são os três patches da tabela, um patch que sai na importação e nunca vai para produção, e a verificação de ponta a ponta de que os testes reservados continuam reservados.

Para ver a regra de regressão fazer diferença, apague as duas linhas que retornam `keep_original` para `pass_to_fail`. `test_a_patch_that_breaks_a_passing_test_is_worse_than_no_repair` falha com `ship` no lugar de `keep_original`, e `test_the_loop_never_sees_the_held_out_tests` também: o patch com `==` não tem teste que continue falhando, então nada mais o segura. Restaure as linhas antes de seguir.
