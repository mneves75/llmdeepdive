Um benchmark é uma medição com protocolo: condições fixas, execuções repetidas e uma dispersão informada. O `llama-bench` oferece um bom cronômetro e uma má tentação: colar um número numa tabela. Esta aula lê a ferramenta na tag `b11380` e depois a usa para perguntar quando um Mac Ultra e um DGX Spark podem ser comparados de forma justa.

Todos os comandos foram executados num Apple M5 Pro, com o Qwen3-1.7B Q8_0 como substituto. Nenhuma vazão dessa execução é publicada. Ela serviu apenas para mostrar que as flags funcionam.

## O que pp e tg medem

```
llama-bench -m MODEL.gguf -p 512 -n 128 -r 3 -fa 0,1
llama-bench -m MODEL.gguf -p 512 -n 0 -d 0,2048 -pg 256,64 -r 2 -ngl 99 -o json
```

Os dois testes padrão cronometram as duas fases da geração vistas na [aula 7.3](/pt-br/lessons/7-inference-and-efficiency/7.3-prefill-vs-decode-two-different-machines/). Os dois informam tokens por segundo (t/s).

- O `-p 512` é o **pp512**: processar um prompt de 512 tokens em batches. Isso é o prefill. Cada leitura dos pesos serve a muitos tokens, então o compute domina.
- O `-n 128` é o **tg128**: gerar 128 tokens um a um. Isso é o decode. Cada token lê os pesos de novo, então a bandwidth de memória domina ([aula 9.1](/pt-br/lessons/9-hardware-and-infrastructure/9.1-memory-bandwidth-vs-flops/)).

Mais duas flags moldam o teste. O `-pg 256,64` roda um prompt e depois uma geração. O `-d 2048` enche o KV cache com 2.048 tokens antes, de modo que você mede o decode em profundidade, e não num cache vazio. O README acrescenta que as medições "não incluem os tempos de tokenização e de amostragem" (tradução nossa).

Todo parâmetro aceita listas separadas por vírgula e executa a grade completa de combinações. O `-fa` (flash attention) tem padrão `auto` no b11380, que o JSON informa como `-1`. Defina `-fa 0` ou `-fa 1` quando comparar máquinas, para que as duas usem a mesma configuração de flash attention.

## Lendo a dispersão, e uma armadilha no Mac

O `-r` repete cada teste (padrão 5), e a tabela imprime a média e o desvio-padrão, uma medida de quanto as repetições diferem entre si. O `-o json` também guarda todas as amostras em `samples_ts`, além de `build_commit` e `build_number`, de modo que um resultado carrega a própria proveniência. O JSON desta execução disse commit `eec18f5` e número 1, porque o binário foi compilado a partir de um clone raso da tag (um clone sem o histórico que numera o build).

Use `--delay` entre testes, e `--prio` se a máquina for compartilhada. Um laptop dez minutos depois do início da sessão é outra máquina, como a [aula 7.13](/pt-br/lessons/7-inference-and-efficiency/7.13-choosing-and-judging-a-community-quant/) avisou.

Num Mac há uma armadilha. No build 11146 do Homebrew, `-ngl 0,99` imprimiu uma tabela **sem a coluna `ngl`**, então os dois pares de linhas parecem idênticos. O código do `llama-bench.cpp` só acrescenta `n_gpu_layers` quando o rótulo do backend não contém `CPU` nem `BLAS`. Neste Mac o rótulo contém `BLAS` (`MTL,BLAS` no b11380, `BLAS,MTL` no 11146), porque a biblioteca Accelerate da Apple está registrada como backend BLAS, uma biblioteca de rotinas de álgebra linear. Use `-o json` ou `-o csv`, que sempre trazem o campo.

## Um par justo entre Mac e Spark

O repositório do llama.cpp guarda dois arquivos com execuções dos seus mantenedores. Os dois usam o `llama-bench` no **gpt-oss-120b MXFP4** (59,02 GiB), com `n_ubatch` 2048 e flash attention ligada. Um é um Mac Studio M2 Ultra no build 7948. O outro é um DGX Spark (GB10) no build 7941, com `ngl` 99. Esses números são do gpt-oss, não do Qwen.

Dois detalhes limitam a comparação. O arquivo do Mac não nomeia o chip, então "M2 Ultra" vem do nome do diretório. O Spark rodou com mmap desligado e direct I/O ligado, e o Mac com os padrões; isso não deveria mudar o t/s em regime, a taxa depois que o carregamento termina.

| gpt-oss-120b MXFP4 | pp2048 (t/s) | tg32 (t/s) |
|---|---|---|
| Mac Studio M2 Ultra | 1.648,69 ± 1,80 | 85,60 ± 0,52 |
| DGX Spark | 2.443,91 ± 7,47 | 58,72 ± 0,20 |

O Spark faz prefill cerca de 1,48 vez mais rápido e decode cerca de 1,46 vez mais devagar. É a divisão entre prefill e decode da aula 7.3, medida por outra pessoa.

A bandwidth sozinha prevê a diferença no decode? As bandwidths são 800 GB/s para o M2 Ultra (Apple, 2023) e 273 GB/s para o Spark ([aula 12.1](/pt-br/lessons/12-dgx-and-cuda/12.1-dgx-spark-grace-blackwell-on-a-desk/)), uma razão de 2,9. A diferença medida no decode é de apenas 1,46, então o quociente de bandwidth a superestima. O modelo é o mesmo nas duas máquinas, então as duas leem os mesmos bytes por token. Explicações possíveis para a diferença menor incluem:

- os dois chips atingem frações diferentes da sua bandwidth de pico;
- custos que não escalam com a bandwidth ocupam uma fatia maior do tempo de cada token.

O exemplo de 7B logo abaixo ilustra a primeira possibilidade. Um quociente de bandwidth é uma heurística de planejamento ([aula 9.6](/pt-br/lessons/9-hardware-and-infrastructure/9.6-apple-silicon-unified-memory/)), não uma previsão.

## Um par mais solto: M5 Ultra contra Spark em 7B

O par acima é um M2 Ultra, não um M5 Ultra. A [aula 11.1](/pt-br/lessons/11-mac-studio-ultra-and-mlx/11.1-mac-studio-ultra-as-an-inference-machine/) é dona dos números do M5 Ultra. Para um M5 Ultra, os únicos números de llama.cpp encontrados estão na discussão 4167, e são uma evidência mais fraca. Como lido em 2026-10-03:

- **Mac.** Um comentário de usuário (commit `c1d0e7a00`, macOS 27.0.1, 80 núcleos de GPU, 256 GB) traz `llama 7B Q4_0`, 3,53 GiB: pp512 4.944,66, tg128 179,10.
- **Spark.** A discussão 15013 tem uma linha de um mantenedor (commit `5acd455`) para `llama 7B Q4_0` (a introdução da discussão diz Llama 2 7B), 3,56 GiB: pp512 3.062,31 sem flash attention e 3.661,37 com ela, tg128 57,21 e 56,74.

Essas linhas diferem em autor, commit e tamanho do arquivo. As introduções das discussões chamam o modelo de LLaMA 7B e Llama 2 7B, enquanto as linhas trazem o mesmo rótulo, e a configuração de flash attention da linha do Mac não é informada. Trate o par como uma hipótese.

Mesmo assim ele ensina uma coisa. Num modelo denso como este 7B, cada token decodificado lê aproximadamente o arquivo inteiro, então a taxa de decode vezes o tamanho do arquivo dá uma bandwidth *implícita*. Com números inventados: um arquivo de 2 GB decodificado a 50 t/s implica cerca de 100 GB/s. Agora as linhas reais:

- Mac: 179,10 x 3,53 GiB dá cerca de 679 GB/s, 57 % dos 1,2 TB/s da Apple.
- Spark: 57,21 x 3,56 GiB dá cerca de 219 GB/s, 80 % de 273 GB/s.

Um modelo pequeno não satura o chip maior, então a razão de 3,1 vezes no decode não é uma razão de bandwidth. As duas cifras são derivadas aqui a partir dos números das próprias discussões.

## Por que uma única cifra de tokens por segundo engana

O erro comum é citar uma única cifra de "tokens por segundo", ou citar um número de 7B como se descrevesse o modelo de 27B. Uma taxa pertence a um modelo, a um arquivo e a uma máquina. Informe pp e tg separados, com o modelo, o tamanho do arquivo, o build, as flags e a dispersão.

:::warning
O `llama-bench` não é o `llama-server`. Ele não tem camada HTTP, tempo de tokenizer, amostragem nem usuários concorrentes, então não prevê latência sob carga. Use-o para comparar configurações e depois meça o servidor com o seu próprio `/metrics`.
:::

:::caveat
As tabelas das discussões são enviadas por usuários e não podem ser fixadas numa tag. Foram lidas uma vez, em 2026-10-03. As linhas podem mudar, e ninguém as audita. Os arquivos `benches/` do repositório estão fixados no b11380, mas trazem apenas as máquinas dos mantenedores.
:::

Portanto, uma comparação justa fixa o arquivo, o build, as flags e a profundidade, e informa pp, tg e dispersão separadamente. A seguir, a [aula 13.5](/pt-br/lessons/13-llama-cpp-in-depth/13.5-speculative-decoding-and-rpc-in-llama-cpp/) pergunta o que o speculative decoding e uma segunda máquina fazem com esses dois números.
