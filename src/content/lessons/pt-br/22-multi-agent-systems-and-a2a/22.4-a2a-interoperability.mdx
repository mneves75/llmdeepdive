A consulta de registros de compra agora pertence a outra equipe. Ela roda como o agente dessa equipe, no próprio processo, iniciado no próprio ritmo. O assistente de compras não pode importar o código dele; só pode mandar requisições. Para obter o total do PO-1001, os dois lados precisam concordar sobre como se achar, como pedir, como uma resposta se parece e qual edição das regras seguem. E quando discordam, os dois lados precisam perceber antes de qualquer coisa acontecer.

Esse acordo é o trabalho do A2A, o *Agent2Agent protocol* (protocolo de agente para agente). Esta aula fixa a especificação A2A v1.0.1, lançada em 2026-05-28, e constrói uma pequena parte dela. Tudo abaixo é um subconjunto deliberadamente limitado para aprender, não uma implementação conforme.

## A2A e MCP fazem trabalhos diferentes

A página de comparação do próprio A2A traça a linha aqui. O MCP "defines how an AI agent interacts with and utilizes individual tools and resources, such as a database or an API" (define como um agente de IA interage com ferramentas e recursos individuais e os usa, como um banco de dados ou uma API). O A2A "focuses on enabling different agents to collaborate with one another to achieve a common goal" (se concentra em permitir que agentes diferentes colaborem para atingir um objetivo comum). Na trilha 15, o servidor MCP oferecia ferramentas a um agente, que decidia quando chamá-las. Aqui o outro lado é um agente que recebe uma tarefa e decide sozinho como fazê-la.

Alguns termos vêm da especificação. O *cliente A2A* manda requisições; o *servidor A2A* é o agente remoto. Um *Agent Card* é um documento JSON em que o servidor se descreve. Uma *Message* é um turno, feito de *Parts*: texto, dados estruturados ou um arquivo. Uma *Task* (tarefa) é a unidade de trabalho, com um id gerado pelo servidor e um estado como `TASK_STATE_COMPLETED`. Um *Artifact* (artefato) é a saída de uma tarefa. A especificação separa os dois de propósito: "Messages SHOULD NOT be used to deliver task outputs. Results SHOULD BE returned using Artifacts associated with a Task." (mensagens não deveriam entregar saídas de tarefa; resultados deveriam voltar em artefatos associados a uma tarefa).

Os dois protocolos levam a versão em toda requisição, e nenhum mantém uma sessão em que a versão foi combinada uma vez. A revisão 2026-07-28 do MCP a põe no `_meta` de cada requisição, como a [aula 15.2](/pt-br/lessons/15-tool-contracts-and-mcp/15.2-json-rpc-and-protocol-lifecycle/) mostrou. O A2A a põe num cabeçalho `A2A-Version`.

## Descoberta: o Agent Card

Um cliente acha o card de um servidor em `/.well-known/agent-card.json`. O card da fixture dá nome ao agente, o descreve, lista uma skill, `lookup-purchase-order`, e declara as capacidades: sem streaming, sem notificações push, sem card estendido. Ele também declara um esquema de segurança com token bearer e uma interface: a URL, o binding `JSONRPC` e a versão de protocolo `1.0`. O arquivo proto na tag é o modelo de dados normativo (seção 1.4), então o card traz todo campo que o proto marca como obrigatório, com os nomes em camelCase que a seção 5.5 pede.

A regra da especificação para o cliente é escolher a primeira interface que ele suporta. Este cliente acrescenta uma regra própria:

```python
# file: examples/agent-engineering/src/agentlab/multiagent/a2a.py
def choose_interface(card: dict, *, origin: str) -> dict:
    """The first JSON-RPC interface at protocol 1.0, and only on the origin the card came from."""
    offered = card.get("supportedInterfaces") or []
    for interface in offered:
        if interface.get("protocolBinding") == "JSONRPC" and negotiated(interface.get("protocolVersion")) == PROTOCOL_VERSION:
            if _origin(interface.get("url", "")) != _origin(origin):
                # A card can name any URL; following it blindly would hand the bearer token to that host.
                raise IncompatibleAgent(f"the card points its interface at {_origin(interface.get('url', ''))[1]!r}")
            return interface
    raise IncompatibleAgent(f"no JSONRPC interface at {PROTOCOL_VERSION}; offered {[(i.get('protocolBinding'), i.get('protocolVersion')) for i in offered]}")
```

Um card que oferece só o protocolo 0.3 é recusado antes de qualquer requisição sair. Um card cuja interface aponta para outro host também, porque o cliente anexaria o token a toda requisição que mandasse para lá.

## Uma versão em cada requisição

O servidor lê o cabeçalho em toda chamada. A especificação identifica uma versão pelos "`Major.Minor` elements" (os elementos Major.Minor) e diz que números de patch "MUST not be considered when clients and servers negotiate protocol versions" (não devem ser considerados quando clientes e servidores negociam versões). Ela também diz: "Agents MUST interpret empty value as 0.3 version" (agentes devem interpretar valor vazio como versão 0.3):

```python
# file: examples/agent-engineering/src/agentlab/multiagent/a2a.py
def negotiated(header: str | None) -> str:
    """The Major.Minor a request asks for; an empty or absent header means 0.3 (section 3.6.2)."""
    requested = (header or "").strip() or "0.3"
    return ".".join(requested.split(".")[:2])
```

```python
# file: examples/agent-engineering/src/agentlab/multiagent/a2a.py
def _run(name: str, params: dict, version: str | None, operations: dict) -> dict:
    # Checked on every request: there is no session in which a version was agreed once.
    if negotiated(version) != PROTOCOL_VERSION:
        details = error_info("VERSION_NOT_SUPPORTED", requested=negotiated(version)[:16], supported=PROTOCOL_VERSION)
        raise RpcError(VERSION_NOT_SUPPORTED, "Version not supported", details)
    if name in REFUSED:
        raise RpcError(*REFUSED[name])
    return operations[name](params)
```

Uma requisição sem cabeçalho, ou com `0.5` ou `2.0`, recebe o erro JSON-RPC `-32009`, o código que a seção 5.4 dá a `VersionNotSupportedError`, e nada roda. `1.0.1` é atendido como 1.0. O agente reaproveita o dispatcher JSON-RPC da trilha 15, que transforma o `RpcError` lançado numa resposta de erro; os detalhes seguem a seção 9.5, um array de objetos que trazem cada um um `@type`.

Outras respostas estão fixadas nos testes. Cada uma usa o código que a seção 5.4 atribui:

| Situação | Resposta |
|---|---|
| `GetTask` para uma tarefa que não existe, ou que outro tenant criou | `-32001` TaskNotFound |
| `CancelTask` numa tarefa terminada | `-32002` TaskNotCancelable |
| Um método de notificação push, quando o card não declara nenhuma | `-32003` PushNotificationNotSupported |
| `SendStreamingMessage`, quando o card não declara streaming | `-32004` UnsupportedOperation |
| Uma mensagem sem partes | `-32602` Invalid params |

Pedir o pedido de outro tenant, o PO-2001, não é erro de protocolo: a requisição é válida. O trabalho é recusado, então a tarefa termina em `TASK_STATE_REJECTED`, com uma mensagem de status e sem artefato.

## Tolerante no fio, estrito por dentro

A seção 5.7 diz: "Implementations SHOULD ignore unrecognized fields in messages, allowing for forward compatibility as the protocol evolves." (implementações deveriam ignorar campos não reconhecidos, permitindo compatibilidade futura à medida que o protocolo evolui). Os modelos do fio aqui ignoram campos desconhecidos, então um servidor que acrescenta um campo numa versão menor seguinte não quebra este cliente. É o oposto das passagens da [aula 22.2](/pt-br/lessons/22-multi-agent-systems-and-a2a/22.2-typed-handoffs/), que proíbem campos desconhecidos. A diferença é quem é dono do formato. O A2A é compartilhado entre partes que se atualizam em momentos diferentes. As suas passagens só mudam quando você as muda, e ali um campo desconhecido quer dizer bug ou ataque. A entrada da própria skill, `{"poId": "PO-1001"}`, volta a ser estrita: é o contrato deste agente, não o do protocolo.

## Quem está pedindo

O card declara um esquema bearer, e a seção 7.4 diz que o servidor "MUST authenticate every incoming request" (deve autenticar toda requisição recebida). Um token ausente ou errado recebe HTTP 401 com o desafio `WWW-Authenticate: Bearer`. O servidor mapeia o token para um `Principal` e restringe cada tarefa a ele. Como nas verificações de token da [aula 15.5](/pt-br/lessons/15-tool-contracts-and-mcp/15.5-transport-and-authorization-boundaries/), a identidade vem da credencial, nunca de algo que a mensagem diz. Outro tenant que pede o id de uma tarefa recebe o mesmo `TaskNotFound` que receberia para um id que nunca existiu, porque servidores "MUST NOT reveal the existence of resources the client is not authorized to access" (não devem revelar a existência de recursos que o cliente não está autorizado a acessar).

:::caveat
Este subconjunto roda HTTP simples em localhost. A seção 7.1 exige transporte criptografado em produção. Os tokens dos testes são textos sintéticos, não segredos, e nada sai da máquina.
:::

## O que o subconjunto deixa de fora

Implementado: o card, `SendMessage` em modo bloqueante, `GetTask` e `CancelTask` sobre o binding JSON-RPC, a verificação de versão e a autenticação bearer. Recusado com o erro da especificação: streaming, `SubscribeToTask`, notificações push, `ListTasks` (uma operação central que um servidor conforme precisa suportar) e o card estendido. Nem implementado: entrada em vários turnos, histórico de tarefa e `historyLength`, partes de arquivo, extensões, assinaturas de card, cabeçalhos de cache, tenants, os bindings gRPC e HTTP+JSON, a forma de `A2A-Version` como parâmetro de requisição que a seção 3.6.1 permite (só o cabeçalho é lido) e TLS. Um `contextId` enviado pelo cliente é aceito e mantido. Toda tarefa aqui termina dentro de `SendMessage`, então um cancelamento sempre encontra uma tarefa terminada. A docstring do módulo mantém esta lista ao lado do código.

## Rode o exercício

O módulo é `src/agentlab/multiagent/a2a.py` e seus testes estão em `tests/test_multiagent_a2a.py`, dentro de `examples/agent-engineering/`. A partir desse diretório, rode `uv run --frozen python -m unittest discover -s tests -p "test_multiagent_a2a.py"`.

A saída esperada termina com `Ran 14 tests` e `OK`. `test_card_and_first_exchange_match_the_pinned_fixture` inicia um processo de servidor novo e compara o card e a primeira troca com a fixture. `test_incompatible_versions_are_refused_with_version_not_supported` manda nenhum cabeçalho, `0.3`, `0.5` e `2.0`, e `test_a_patch_number_does_not_change_the_negotiated_version` é o controle dele. Em `negotiated`, troque `or "0.3"` por `or "1.0"` e o teste de versão fica vermelho: um cliente que não mandou cabeçalho seria atendido como se falasse 1.0. Restaure.
