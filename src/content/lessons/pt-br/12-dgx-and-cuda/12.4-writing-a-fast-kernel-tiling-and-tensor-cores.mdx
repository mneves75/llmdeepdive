A multiplicação de matrizes ingênua da lição 12.3 está correta e é desperdiçadora. Cada thread lê da memória global uma linha inteira de `A` e uma coluna inteira de `B`, e threads vizinhas buscam os mesmos números de novo. O conserto é o truque mais antigo do manual do roofline da lição 9.2: aumentar a arithmetic intensity reutilizando bytes que você já moveu.

Um bloco coopera. Ele carrega um tile quadrado de `A` e um de `B` para a memória compartilhada, sincroniza, deixa cada thread multiplicar a partir dessa memória rápida, sincroniza de novo e desliza para o tile seguinte.

```cpp
#define TILE 16
__global__ void matmulTiled(const float* A, const float* B, float* C, int M, int N, int K) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];
    int row = blockIdx.y * TILE + threadIdx.y;
    int col = blockIdx.x * TILE + threadIdx.x;
    float acc = 0.0f;
    for (int t = 0; t < (K + TILE - 1) / TILE; ++t) {
        int aCol = t * TILE + threadIdx.x;
        int bRow = t * TILE + threadIdx.y;
        As[threadIdx.y][threadIdx.x] = (row < M && aCol < K) ? A[row * K + aCol] : 0.0f;
        Bs[threadIdx.y][threadIdx.x] = (bRow < K && col < N) ? B[bRow * N + col] : 0.0f;
        __syncthreads();                      // tiles are complete
        for (int k = 0; k < TILE; ++k) acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];
        __syncthreads();                      // everyone is done before the tiles are overwritten
    }
    if (row < M && col < N) C[row * N + col] = acc;
}
// launch: dim3 block(TILE, TILE); dim3 grid((N + TILE - 1) / TILE, (M + TILE - 1) / TILE);
```

Dois detalhes sustentam a correção. Primeiro, `__syncthreads()` precisa ser alcançado por toda thread do bloco. Por isso os elementos fora do intervalo são carregados como zero em vez de pulados com um return antecipado: uma thread que sai cedo deixa as outras esperando. Segundo, a barreira depois da multiplicação impede que uma thread rápida reabasteça os tiles enquanto uma lenta ainda os lê.

Agora o ganho. Cada elemento de um tile é carregado uma vez da memória global e usado por 16 threads. O tráfego global cai pela largura do tile, então a intensidade de 0,25 FLOP/B sobe pelo mesmo fator:

$$
I_{\text{tiled}} = 16\times 0.25\ \text{FLOP/B} = 4\ \text{FLOP/B}, \qquad 273\ \text{GB/s}\times 4\ \text{FLOP/B} \approx 1.1\ \text{TFLOP/s}.
$$

O segundo número usa a bandwidth do fabricante para o Spark. É o teto de bandwidth nessa intensidade, um número de planejamento, não uma medição. Um tile maior reutiliza mais, mas exige mais memória compartilhada. As tabelas do Programming Guide dão 100 KiB por SM na compute capability 12.x e até 228 KiB na 10.3. Um tamanho de tile ajustado no Station pode não caber no Spark. Alocações de memória compartilhada acima de 48 KiB por bloco também exigem alocação dinâmica e uma ativação explícita (opt-in).

Agora os Tensor Cores. Eles multiplicam um pequeno tile por instrução de warp. As warp matrix functions os expõem em C++, e toda thread do warp precisa participar.

```cpp
#include <cuda_fp16.h>
#include <mma.h>
using namespace nvcuda;

__global__ void matmulWmma(const half* A, const half* B, float* C, int M, int N, int K) {
    int tileRow = blockIdx.y * 16, tileCol = blockIdx.x * 16;      // one warp per block
    wmma::fragment<wmma::matrix_a, 16, 16, 16, half, wmma::row_major> a;
    wmma::fragment<wmma::matrix_b, 16, 16, 16, half, wmma::row_major> b;
    wmma::fragment<wmma::accumulator, 16, 16, 16, float> acc;
    wmma::fill_fragment(acc, 0.0f);
    for (int k = 0; k < K; k += 16) {
        wmma::load_matrix_sync(a, A + tileRow * K + k, K);
        wmma::load_matrix_sync(b, B + k * N + tileCol, N);
        wmma::mma_sync(acc, a, b, acc);
    }
    wmma::store_matrix_sync(C + tileRow * N + tileCol, acc, N, wmma::mem_row_major);
}
// launch: matmulWmma<<<dim3(N / 16, M / 16), 32>>>(A, B, C, M, N, K);  M, N, K multiples of 16
```

Este kernel está correto, mas não é rápido. Ele não tem staging em memória compartilhada e usa um warp por bloco. O código rápido com Tensor Cores empilha as mesmas duas ideias: um tile de bloco passado pela memória compartilhada, um tile de warp e então a instrução. É exatamente o loop nest do "Efficient GEMM in CUDA" do CUTLASS, então na prática você chama o CUTLASS ou o cuBLAS. O Programming Guide diz para usar os Tensor Cores por meio de cuDNN, cuBLAS, cuFFT ou CUTLASS. A tabela das warp matrix functions lista FP16, BF16, TF32, FP64, INT8 e tipos inteiros de sub-byte (preview), e nenhum float FP4. As instruções FP4 da Blackwell são específicas de arquitetura (o llama.cpp as compila com um alvo `121a`), e a NVIDIA recomenda fortemente acessá-las pelas bibliotecas. A versão das bibliotecas importa. As notas de versão do CUDA 13.4 Update 1 listam, no cuBLAS 13.2, GEMM em NVFP4 e MXFP8 até 3 vezes mais rápido no DGX Spark para certas dimensões grandes de matriz. É uma alegação do fabricante sobre uma versão de biblioteca.

Por que nenhum desses truques acelera o decode em batch 1? O decode é um produto matriz-vetor, um GEMV. Cada peso é lido uma vez e usado numa multiplicação com soma, que são 2 FLOP. Em bf16, isso dá cerca de 1 FLOP por byte (lição 9.1). Com os 4,5 bits por valor do NVFP4, contando as escalas de bloco, são $2 / (4.5/8) \approx 3.6$ FLOP por byte, ainda muito abaixo de qualquer ridge point. Um único vetor também preenche uma coluna de um tile de 16 de largura, no máximo 1/16 do trabalho. Por isso os kernels de decode leem os pesos em fluxo com cargas largas, acumulam em registradores e reduzem entre as threads do warp. Eles miram uma fração da bandwidth da DRAM, não os FLOPs. Batching e prefill dão aos Tensor Cores um tile cheio.

:::warning
Faça profiling antes de otimizar. Um kernel de decode a 0,3 por cento do pico de FLOPs pode estar a 90 por cento do seu teto de bandwidth, e uma reescrita então não compra nada. Leia primeiro a seção Speed Of Light, depois as seções de roofline: o Nsight Compute tem gráficos de roofline hierárquicos para kernels com Tensor Cores, e manda habilitar o que corresponde ao seu caminho de dados.
:::

```bash
nvcc -O3 -arch=sm_121 -lineinfo matmul.cu -o matmul
ncu --set full -k regex:matmul -c 1 -o matmul-report ./matmul
```

O filtro `-k regex:` escolhe kernels pelo nome, `-c 1` faz profiling só da primeira correspondência e `--set full` coleta todas as seções. Abra `matmul-report.ncu-rep` na interface do Nsight Compute. A linha de comando não imprime nada quando `-o` está definido e `--page` não, então acrescente `--page details` para ler os números no terminal.

:::caveat
As listagens seguem o Programming Guide, e a lógica de índices delas foi conferida contra uma multiplicação de matrizes de referência num modelo em CPU. Os autores não as executaram numa GPU. Compile-as para o seu alvo, rode o `compute-sanitizer` e compare com o cuBLAS antes de confiar num tempo.
:::

A ideia durável é que todo kernel rápido move menos bytes por operação útil, e todo profile pergunta sob qual teto você está. A lição 12.5 dá um passo atrás, dos kernels isolados para a stack que os entrega: drivers, toolkits, bibliotecas e os servidores que os chamam.
