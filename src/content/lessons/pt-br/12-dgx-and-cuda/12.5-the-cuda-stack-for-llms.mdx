Seu Spark chega com uma stack que funciona. Aí você instala um framework com pip, baixa um contêiner ou compila um servidor, e algo dá errado. Um modelo carrega e produz tokens a um terço da velocidade que você esperava. Ou um import falha por falta de uma biblioteca. A causa quase nunca é o modelo. É uma camada da stack CUDA que discorda das vizinhas sobre o chip. Esta lição dá nome às camadas, para você testá-las uma por vez.

Comece por baixo. O driver conversa com o hardware. O toolkit é com o que você compila: `nvcc`, cabeçalhos, o runtime e bibliotecas como o cuBLAS, para multiplicação de matrizes. Outras bibliotecas ficam ao lado: o cuDNN, para primitivas de redes neurais, e o NCCL, para comunicação coletiva entre GPUs e máquinas. As notas de versão do Spark da NVIDIA mostram como essas peças são amarradas. A stack atual da Founders Edition é o DGX OS 7.5.0 com o driver 580.159.03 e o CUDA Toolkit 13.0.2. O CUTLASS 4.8 exige o CUDA 13.0 ou mais novo para este chip, e o toolkit de fábrica 13.0.2 atende a isso.

As regras de compatibilidade decidem quanto acima das versões de fábrica você pode ir. As notas de versão da NVIDIA associam cada toolkit a um ramo de driver: 13.0 com 580 e 13.4 com 615. As mesmas notas acrescentam que aplicações CUDA 13.x existentes rodam em qualquer driver a partir do 580 por minor-version compatibility, que o guia de compatibilidade descreve como permitindo algumas limitações de recursos. Então vem o ponto crítico: os recursos novos do CUDA 13.4 e as plataformas recém-habilitadas exigem 615 ou mais novo. Um contêiner feito para o 13.4 pode, portanto, subir num Spark de fábrica e falhar justo no recurso de que você precisava. A regra é simples. O driver define o teto, e o toolkit e toda biblioteca dentro do seu contêiner precisam caber embaixo dele. A página de problemas conhecidos da NVIDIA acrescenta que os recursos e as melhorias de desempenho mais recentes estão disponíveis por meio de contêineres NGC.

Depois, o framework. O índice do PyTorch em `download.pytorch.org/whl/cu130` traz wheels aarch64 construídas para o CUDA 13.0. Escolha a variante explicitamente e então verifique. Não presuma.

```bash
nvidia-smi --query-gpu=name,driver_version,compute_cap --format=csv
nvcc --version
python3 -m venv ~/venvs/torch && . ~/venvs/torch/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cu130
python3 -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.get_device_capability(), torch.cuda.get_arch_list())"
```

Leia a última linha contra a primeira. A capability deve ser (12, 1). A lista de arquiteturas mostra para o que a wheel foi compilada. Se ela não tiver nenhuma entrada que sirva ao 12.1, não espere kernels otimizados, mesmo que `torch.cuda.is_available()` diga True. Rode uma multiplicação de matrizes real e meça o tempo.

Os contêineres levam o problema todo para o registro da NVIDIA. A página de NGC do Spark diz que a máquina precisa da versão ARM64 da ferramenta de linha de comando do NGC, e recomenda fixar as tags dos contêineres. Pegue a tag atual no catálogo, não num post de blog. As tags envelhecem rápido.

Agora o formato numérico que a Blackwell acrescentou. O NVFP4 guarda valores E2M1, 1 bit de sinal, 2 de expoente e 1 de mantissa, em blocos de 16. Cada bloco tem uma escala FP8 E4M3, e uma segunda escala FP32 cobre o tensor. A NVIDIA conta 4,5 bits por valor. Ela afirma cerca de 3,5 vezes menos memória que o FP16 e 1,8 vez menos que o FP8. O contraste é o MXFP4, com blocos de 32 e uma escala de potência de dois. Essas razões valem para os tensores que a receita cobre. O checkpoint da própria NVIDIA para o nosso modelo, `nvidia/Qwen3.8-27B-NVFP4`, é misto: NVFP4 nas camadas MLP e no `lm_head`, FP8 nas camadas de self-attention e de linear-attention. Ele foi produzido com o Model Optimizer, e o card lista vLLM e SGLang como seus runtimes. É o ponto da lição 9.4: primeiro uma receita validada para este modelo híbrido, depois o formato.

Agora três servidores, na ordem em que são mais fáceis de subir. No vLLM, a lição 8.4 é dona das flags. O playbook do DGX Spark da NVIDIA, atualizado em 14 de setembro de 2026, baixa um contêiner pronto e o checkpoint NVFP4, e então testa o endpoint compatível com OpenAI. Copie a tag da página ao vivo.

```bash
# on the Spark
hf download nvidia/Qwen3.8-27B-NVFP4 --cache-dir "$HOME/.cache/huggingface/hub"
# on your laptop, through NVIDIA Sync's port forward
curl -i http://localhost:8000/health
curl -sS http://localhost:8000/v1/models
```

Rode o script de lançamento que o playbook fornece. Depois espere a linha "Application startup complete" antes de enviar uma requisição. A atividade da GPU num monitor só mostra que algo está carregando.

No TensorRT-LLM, a lição 8.6 é dona do runtime. A página de problemas conhecidos do Spark cita contêineres NGC de PyTorch, vLLM e TensorRT-LLM como o caminho para os recursos mais novos, então comece pelo contêiner, não por uma wheel.

No llama.cpp, compile a partir do código-fonte na própria máquina. O guia de build fixado dá duas linhas, e um build nativo enxerga a GPU do Spark.

```bash
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release
```

O arquivo CMake fixado no b11380 faz o trabalho de alvo por você. Ele reescreve uma arquitetura `120` ou `121` simples para `120a` ou `121a`, porque, nas palavras do próprio arquivo, as instruções FP4 dos tensor cores da Blackwell não são compatíveis com versões futuras. Nos builds que não são nativos, ele lista `120a-real` a partir do toolkit 12.8 e `121a-real` a partir do 12.9. Para compilar numa máquina sem GPU, defina `-DCMAKE_CUDA_ARCHITECTURES="121a-real"`.

O desvio errado clássico é verificar só a última camada. O servidor responde ao `/health`, então a stack deve estar boa. O health prova que um processo está vivo. Não prova que os kernels são os rápidos. Percorra a stack de baixo para cima. Verifique o driver e a capability, depois o toolkit, depois a lista de arquiteturas da wheel, depois uma completion real com um cronômetro.

:::warning
Um import que passa não é uma stack que passa. Uma wheel construída para uma arquitetura mais antiga pode carregar, rodar e cair em silêncio para kernels mais lentos. Um benchmark feito nessa stack mede o fallback. Registre driver, toolkit, tag da wheel ou do contêiner e a lista de arquiteturas ao lado de cada número que você publicar.
:::

:::caveat
Os comandos aqui foram copiados das páginas da NVIDIA, do índice do PyTorch e dos fontes fixados do llama.cpp, mas os autores não os executaram num Spark. As versões de fábrica citadas vêm de notas de versão de 2026 e valem para a Founders Edition. Um sistema GB10 de parceiro pode diferir.
:::

A ideia durável é uma escada de cinco verificações: driver, toolkit, bibliotecas, framework, servidor. Cada degrau pode falhar sozinho e cada um tem um comando que o comprova. A trilha 13 sobe até o último degrau e mostra o que o llama.cpp faz com o dispositivo depois que o encontra.
