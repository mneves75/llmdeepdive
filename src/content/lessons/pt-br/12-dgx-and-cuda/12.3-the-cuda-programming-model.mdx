Você tem um Spark e abre um kernel que outra pessoa escreveu. Não há laço sobre os dados. Há um índice montado com três nomes estranhos e uma linha de lançamento com colchetes angulares triplos. O modelo CUDA por trás disso é pequeno. Esta aula o constrói a partir da soma de vetores do Programming Guide da NVIDIA e termina na flag do compilador que decide se o seu binário roda na sua máquina.

## De um laço a um kernel

Numa CPU você soma dois arrays com um laço: `for (int i = 0; i < n; ++i) C[i] = A[i] + B[i];`. Um núcleo percorre cada `i`, um de cada vez. Um kernel CUDA é o corpo desse laço, escrito para um único valor de `i`. Uma função marcada com `__global__` é um kernel: a CPU o lança, milhares de threads da GPU o executam ao mesmo tempo, e cada thread descobre qual elemento é o seu.

A comparação para na ordem. Um laço executa as iterações uma depois da outra, então a iteração 7 pode contar com a 6 já concluída. As threads rodam sem ordem garantida, então um kernel não pode supor que outra thread terminou, a menos que espere por ela explicitamente. A [aula 12.4](/pt-br/lessons/12-dgx-and-cuda/12.4-writing-a-fast-kernel-tiling-and-tensor-cores/) mostra uma dessas esperas, uma barreira que segura todas as threads de um bloco até que todas cheguem.

## Threads, blocos, grids e warps

As threads se organizam em níveis, e cada nível corresponde a uma parte do hardware:

- Uma **thread** executa o kernel uma vez, normalmente para um elemento.
- Um **bloco** é um grupo de no máximo 1.024 threads. Um bloco vive num streaming multiprocessor (SM), uma das muitas unidades de processamento independentes de que uma GPU é feita. As threads de um bloco compartilham memória rápida do chip e podem sincronizar, ou seja, esperar umas pelas outras.
- O **grid** é o conjunto de blocos de um lançamento.
- Um **warp** são 32 threads de um bloco que o hardware escalona juntas. A NVIDIA chama esse modelo de SIMT, single instruction, multiple threads (uma instrução, várias threads): o warp emite uma instrução por vez, mas cada thread mantém seu próprio fluxo de controle, então não conte com lockstep.

Os warps têm duas consequências práticas. Threads de um warp que tomam ramos diferentes de um `if` são mascaradas em turnos: o warp executa um ramo enquanto as outras threads esperam, depois o outro. Então mantenha os ramos uniformes dentro do warp. E um tamanho de bloco que não seja múltiplo de 32 deixa parte do último warp vazia, então mantenha os tamanhos de bloco múltiplos de 32.

## Um primeiro kernel: somar dois vetores

```cpp
__global__ void vecAdd(const float* A, const float* B, float* C, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // my element
    if (i < n) C[i] = A[i] + B[i];                   // guard: the grid is rounded up
}

float *A, *B, *C;                                    // unified memory, no copies
cudaMallocManaged(&A, n * sizeof(float));
cudaMallocManaged(&B, n * sizeof(float));
cudaMallocManaged(&C, n * sizeof(float));
// ... fill A and B on the host ...
int threads = 256;
int blocks  = (n + threads - 1) / threads;           // ceiling division
vecAdd<<<blocks, threads>>>(A, B, C, n);
cudaDeviceSynchronize();                             // launches are asynchronous
```

Os três nomes estranhos dão a cada thread a sua posição. `blockIdx.x` é o número do bloco no grid, `blockDim.x` é o número de threads por bloco, e `threadIdx.x` é o número da thread dentro do seu bloco. Com 256 threads por bloco, a thread 5 do bloco 2 recebe `i` = 2 × 256 + 5 = 517. Os colchetes angulares triplos definem o formato do lançamento: quantos blocos, e quantas threads em cada um. `cudaMallocManaged` dá memória que a CPU e a GPU podem usar ([aula 12.2](/pt-br/lessons/12-dgx-and-cuda/12.2-dgx-station-hbm-beside-a-big-pool/)), e `cudaDeviceSynchronize` faz a CPU esperar, porque um lançamento retorna antes de o kernel terminar.

O grid arredondado para cima cria `blocks * threads` threads, normalmente mais que `n`. Com `n` = 1.000, quatro blocos de 256 fazem 1.024 threads, e as últimas 24 não têm elemento. Sem a guarda, as threads extras escrevem além dos arrays. É o primeiro bug mais comum.

## Como a memória se organiza, e como um warp deve lê-la

Agora a memória, porque o roofline da [aula 9.2](/pt-br/lessons/9-hardware-and-infrastructure/9.2-the-roofline-model/) é desenhado contra ela (o roofline limita a velocidade de um kernel pela aritmética ou pela bandwidth da memória). Da mais rápida e menor para a mais lenta e maior:

1. Os registradores pertencem a uma thread.
2. A memória compartilhada pertence a um bloco e fica no SM, no mesmo recurso físico do cache L1.
3. O cache L2 atende o chip inteiro.
4. A memória global é a DRAM.

Para a compute capability 12.x, o Programming Guide lista 64 K registradores por SM, 100 KiB de memória compartilhada por SM com 99 KiB utilizáveis por um bloco, 1.536 threads residentes (48 warps) por SM e 24 blocos residentes. Esses são os limites que o GB10 herda.

O padrão de acesso vem primeiro. Uma CPU nunca busca um único byte na RAM: ela busca uma linha de cache inteira. Uma GPU faz algo parecido na escala do warp. A memória global se move em transações de 32 bytes, e o hardware junta as leituras de um warp no menor número de transações que consegue, o que se chama **coalescing** (coalescência).

- Se threads consecutivas de um warp leem palavras consecutivas de 4 bytes, o pedido do warp é de 128 bytes, atendido por quatro transações, com uso total.
- Se threads vizinhas estão 32 bytes ou mais afastadas, o warp precisa de 32 transações, 1.024 bytes de tráfego para 128 bytes usados. É uma eficiência de 12,5 por cento.

A regra é deixar `threadIdx.x`, o índice que muda mais depressa, andar pela dimensão contígua.

## Uma multiplicação de matrizes ingênua, e por que ela é lenta

Uma multiplicação de matrizes calcula cada saída `C[row][col]` como a soma, sobre `k`, de `A[row][k]` vezes `B[k][col]`. O kernel mais simples dá a cada elemento de saída a sua própria thread. Eis um que segue a regra de acesso. A coluna `col` vem de `threadIdx.x`, então as leituras de `B` e as escritas em `C` são coalescidas, e as threads de uma linha compartilham cada leitura de `A`. `dim3 block(16, 16)` pede um bloco de 16 por 16 threads.

```cpp
__global__ void matmulNaive(const float* A, const float* B, float* C, int M, int N, int K) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < M && col < N) {
        float acc = 0.0f;
        for (int k = 0; k < K; ++k) acc += A[row * K + k] * B[k * N + col];
        C[row * N + col] = acc;
    }
}

dim3 block(16, 16);
dim3 grid((N + 15) / 16, (M + 15) / 16);             // x covers columns, y covers rows
matmulNaive<<<grid, block>>>(A, B, C, M, N, K);
```

Está correto e lento. Cada passo do laço `k` carrega dois valores de 4 bytes e faz uma multiplicação com soma, que conta como 2 FLOP (operações de ponto flutuante). A arithmetic intensity, da aula 9.2, é o número de operações por byte movido. Se nenhuma leitura acertasse um cache, ela seria

$$
\frac{2\ \text{FLOP}}{2\times 4\ \text{B}} = 0.25\ \text{FLOP/B}, \qquad 273\ \text{GB/s}\times 0.25\ \text{FLOP/B} \approx 68\ \text{GFLOP/s}.
$$

O segundo número usa a bandwidth do fabricante para o Spark e é um número de planejamento pessimista, porque L1 e L2 capturam parte da reutilização. A distância entre ele e o pico aritmético do chip é o espaço que a aula 12.4 preenche.

A occupancy é o outro número que um profiler mostra. O Best Practices Guide a define como warps ativos por SM sobre o máximo. Ela importa porque um warp que espera a memória fica parado, e o SM pode então emitir instruções de outro warp residente; mais warps residentes lhe dão mais trabalho para alternar. O guia também avisa que mais nem sempre é mais rápido. Com blocos de 256 threads na compute capability 12.x, seis blocos dão 1.536 threads, ou seja, 48 warps e occupancy total. Isso vale só se cada thread usar no máximo cerca de 42 registradores, já que 65.536 / 1.536 é 42,7, e antes do arredondamento de alocação. A memória compartilhada também limita. `nvcc -res-usage` imprime os registradores por thread.

## Compilar para a GPU certa

Agora o alvo. Compute capability é o número de versão da NVIDIA para os recursos de uma GPU, e `nvidia-smi --query-gpu=name,compute_cap` imprime esse número. A lista da NVIDIA dá 12.1 ao GB10 do Spark e 10.3 ao GB300 do Station.

Um binário CUDA pode levar dois tipos de código de GPU. O código de máquina roda diretamente, sem etapa de compilação no carregamento. O PTX é um assembly virtual que o driver pode compilar na hora do carregamento, just in time (JIT), para a GPU que encontrar. `nvcc -arch=sm_121` embute PTX e código de máquina para esse chip. O exemplo do manual para `sm_100` expande para `compute_100` mais `sm_100`, e `sm_121` segue a mesma regra. Sem nenhuma flag `-arch`, o padrão do manual é `sm_75`, então o código ainda pode rodar por recompilação do PTX, mas não usa o que o chip ganhou desde então.

```bash
nvcc -O3 -arch=sm_121 -lineinfo matmul.cu -o matmul-spark       # GB10, compute capability 12.1
nvcc -O3 -arch=sm_103 -lineinfo matmul.cu -o matmul-station     # GB300, compute capability 10.3
nvcc -O3 -gencode arch=compute_121,code=sm_121 \
        -gencode arch=compute_103,code=sm_103 matmul.cu -o matmul   # one binary, both machines
```

O CUTLASS, a biblioteca de templates C++ da NVIDIA para multiplicação de matrizes, lista na tabela de hardware da versão 4.8 o CUDA 13.0 como o toolkit mínimo que o próprio CUTLASS exige para as duas capabilities.

Um erro tentador é compilar numa máquina e copiar o binário para a outra. O `-arch=native` facilita isso: ele detecta a GPU visível e gera código de máquina para ela, sem PTX. Mas a causa da falha é a capability. Código para 12.1 não roda numa GPU 10.3, com ou sem PTX, então um build simples com `-arch=sm_121` também falha no Station.

O build de dois alvos acima dá código de máquina nativo nas duas máquinas. Um build que leve PTX `compute_100` também iniciaria nas duas por JIT, mas sem os recursos `a` descritos abaixo. A falta de PTX é um custo separado: um binário nativo também não passa para uma GPU posterior.

:::warning
Os sufixos estreitam o alvo. Um alvo `a`, como `sm_121a`, libera os recursos específicos de arquitetura, incluindo as instruções mais novas dos Tensor Cores, e o guia afirma que esse código roda apenas na compute capability exata para a qual foi compilado. Um alvo `f` cobre uma família: `compute_120f` roda em 12.0 e 12.1. Use o alvo menos específico que ainda tenha os recursos de que você precisa: simples primeiro, depois `f`, depois `a`.
:::

:::caveat
As listagens seguem os padrões do Programming Guide da NVIDIA, mas os autores do curso não as executaram numa GPU. Rode-as primeiro sob o `compute-sanitizer`. Os lançamentos são assíncronos, então um erro de um kernel pode aparecer na próxima sincronização. Chame `cudaGetLastError()` depois de um lançamento e verifique o resultado de `cudaDeviceSynchronize()`.
:::

Um programa CUDA, portanto, é uma regra para uma thread, um formato de lançamento e um alvo. A regra decide a correção, o padrão de acesso decide quantos bytes se movem e o alvo decide onde o binário roda. A aula 12.4 reescreve a multiplicação de matrizes para que menos bytes se movam.
