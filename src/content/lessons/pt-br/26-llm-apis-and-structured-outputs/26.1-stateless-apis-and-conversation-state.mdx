Quando alguém constrói seu primeiro chatbot, o bug mais surpreendente aparece logo no segundo turno: o modelo não tem ideia do que foi dito dez segundos antes. Isso não é esquisitice do SDK (*software development kit*, a biblioteca de código que um provedor fornece para chamar seu serviço) de uma empresa específica. **Endpoints** (endereços web num servidor que aceitam requisições automatizadas) sobre **HTTP** (*Hypertext Transfer Protocol*, o conjunto padrão de regras que navegadores e apps usam para trocar dados na web) são *stateless* (sem estado) por projeto, o que significa que cada requisição `POST` (uma chamada que envia dados ao servidor) não guarda memória de nenhuma chamada anterior. Para sustentar uma conversa, sua aplicação armazena a transcrição e reenvia o histórico relevante a cada requisição, pagando novamente por esses tokens salvo quando um cache acerta.

## Por que endpoints HTTP de LLM são stateless

Em [O que realmente acontece quando você aperta enviar](/pt-br/lessons/7-inference-and-efficiency/7.1-what-actually-happens-when-you-hit-send/), você viu que um transformer executa uma passagem direta sobre uma sequência de IDs de tokens e prevê o próximo token apenas a partir dessa sequência. Os pesos do modelo ficam congelados entre requisições; o motor não grava o nome do seu usuário nos parâmetros. Como define a RFC 9110 para interações HTTP sem estado, manter cada chamada autossuficiente permite que um **balanceador de carga** (um roteador de tráfego que distribui chamadas entre máquinas) envie o turno 1 ao cluster de **GPU** (*graphics processing unit*, o processador gráfico usado para rodar modelos) A e o turno 2 ao cluster B sem mover gigabytes de memória de sessão entre computadores do datacenter.

A consequência prática é uma fronteira clara de responsabilidade. Seu banco de dados ou armazenamento de sessão em memória—montado com listas e dicionários como em [Python, NumPy e PyTorch](/pt-br/lessons/0-orientation-and-foundations/0.7-python-numpy-pytorch/)—guarda a lista ordenada de mensagens. Cada mensagem traz um `role` (papel)—em geral `system` ou `developer`, `user`, `assistant` ou `tool`—e um `content`. Quando o usuário envia o turno $t$, o **backend** (o programa de servidor que roda atrás da interface do usuário) anexa a nova mensagem, **serializa** (converte para texto transmissível) a lista em **JSON** (*JavaScript Object Notation*, um formato de texto com chaves e valores rotulados), envia tudo por **HTTPS** (HTTP criptografado) e grava a resposta do assistente assim que a chamada termina.

Como sua aplicação controla essa lista de mensagens, a depuração permanece reproduzível. Se o turno 7 gerar uma resposta errada, basta salvar o JSON exato enviado naquele turno e fazer **replay** (reexecutar a mesma entrada) localmente contra um prompt ou modelo novo, sem depender de adivinhar estado oculto num servidor remoto.

## Crescimento quadrático de tokens no chat multi-turno

Reenviar o histórico parece barato no turno 2, mas o volume cresce mais depressa do que a maioria das equipes prevê. Veja um caso concreto de atendimento com 10 turnos antes da fórmula geral.

Suponha um prompt de sistema estático de `400` tokens, média de `100` tokens por mensagem do usuário e `200` tokens por resposta do assistente. Cada turno concluído adiciona `100 + 200 = 300` tokens ao histórico.

- O turno 1 envia `400 + 100 = 500` tokens de entrada.
- O turno 2 envia `500 + 300 = 800` tokens de entrada.
- O turno 3 envia `800 + 300 = 1.100` tokens de entrada.
- O turno 10 envia `400 + 100 + 9 × 300 = 3.200` tokens de entrada.

Somando as dez chamadas, você paga `500 + 800 + 1.100 + ... + 3.200 = 18.500` tokens de entrada na conversa, embora a transcrição final tenha apenas `3.400` tokens (`3.200` de entrada mais os `200` da última resposta). A uma tarifa de `USD 3,00` por milhão de tokens sem cache, dez turnos custam `USD 0,0555`; estenda o mesmo chat para 50 turnos e o total de entrada sem cache dispara para `392.500` tokens (`USD 1,18` por sessão).

De forma geral, em $N$ turnos com prompt de sistema $s$, mensagem do usuário $u$ e resposta do assistente $a$, cada turno soma um passo fixo, então o acumulado de tokens de entrada segue uma progressão aritmética:

$$T_{\text{in}}(N) = N \cdot (s + u) + (u + a)\frac{N(N - 1)}{2}$$

Substituindo $s = 400$, $u = 100$, $a = 200$ e $N = 10$, obtemos $10 \cdot 500 + 300 \cdot 45 = 5{,}000 + 13{,}500 = 18{,}500$. O primeiro termo soma o prompt de sistema e cada nova mensagem do usuário; o termo $N(N - 1)/2$ conta todos os turnos antigos reenviados repetidamente, de modo que dobrar os turnos aproximadamente quadruplica os tokens de entrada sem cache. O cache de prefixo—detalhado adiante nesta trilha—dá desconto sobre o trecho repetido, mas mesmo um desconto de 90% ainda bate no teto da janela de contexto se o histórico crescer sem freio.

:::insight
Dimensione produtos interativos pelo acumulado de tokens de entrada, não só pelo tamanho final do contexto. Um loop de agente com 30 passos que anexa 1.500 tokens de saída de ferramenta por passo pode ultrapassar 650.000 tokens acumulados numa única sessão.
:::

## Histórico no cliente versus threads no servidor

Vários provedores oferecem hoje endpoints com estado—como objetos de thread ou encadeamento via `previous_response_id`—nos quais você envia apenas a nova mensagem e um identificador do servidor. Por baixo desse **formato de rede** (os bytes exatos enviados na conexão), o transformer continua lendo os tokens acumulados em cada turno. A troca é operacional, não matemática:

- **Arrays gerenciados pelo cliente** mantêm uma fonte única da verdade no seu banco, permitem **failover** imediato (troca rápida para outro provedor ou modelo aberto em caso de queda) e facilitam editar ou **anonimizar** (remover dados sensíveis de) um turno antigo.
- **APIs com estado no servidor** reduzem a **largura de banda de upload** (o volume de dados que um celular ou navegador envia pela rede) e tiram de você o armazenamento do histórico, mas prendem a conversa ao ciclo de retenção e aos endpoints de exclusão de um único fornecedor.

Se o sistema exige portabilidade entre provedores, controle rigoroso de residência de dados ou replay offline em avaliações, guarde a transcrição canônica no seu banco e trate a API como **função pura** (uma operação cuja saída depende apenas das mensagens passadas na entrada, sem memória oculta).

## Como limitar o estado sem perder o fio da conversa

Como toda janela de contexto tem limite e históricos longos diluem a atenção e encarecem cada turno, aplicações em produção adotam uma política explícita de estado em vez de concatenar tudo indefinidamente.

1. **Janela deslizante por orçamento de tokens.** Mantenha o prompt de sistema fixo e empilhe turnos do mais recente para o mais antigo até atingir um teto (por exemplo, 8.000 tokens). Corte sempre em fronteiras completas de turno para nunca deixar uma resposta de ferramenta órfã sem sua chamada correspondente.
2. **Resumo periódico em lotes.** Quando turnos antigos passam de um limite (por exemplo, a cada 8 turnos), execute uma chamada dedicada que condensa os turnos 1 a 8 numa nota estruturada—fatos confirmados, decisões e restrições abertas—e substitua o bloco antigo de uma vez. Atualizar em lotes em vez de todo turno mantém o prefixo estável para cache.
3. **Compactação de artefatos.** Saídas de ferramentas—grandes **payloads** JSON (os dados carregados dentro de uma mensagem), resultados de busca ou **stack traces** (relatórios de erro impressos quando um programa falha)—costumam responder por 80% dos tokens do histórico. Salve o payload bruto em **armazenamento de objetos** (serviço em nuvem para guardar arquivos grandes) sob um ID, mantenha só os campos extraídos no array ativo e consulte de novo pelo ID se o usuário pedir detalhes.

:::warning
Nunca sobrescreva mensagens antigas no **log de auditoria** (o registro permanente de conformidade) ao compactar o contexto. Guarde uma tabela **imutável** (nunca alterada depois de gravada) com a transcrição bruta para depuração e conformidade, e gere a janela enviada ao modelo como uma **projeção derivada** (uma cópia resumida montada a partir desse log).
:::

## Persistência idempotente de turnos

Quedas de rede acontecem entre o servidor concluir a geração e o cliente gravar a resposta. Atribua a cada envio do usuário um `turn_id` gerado no cliente e salve a mensagem do usuário antes de chamar o LLM. Se a requisição HTTP atingir um **timeout** (estourar o tempo limite de espera) ou cair antes do registro da resposta, sua lógica de retry verifica se já existe resposta para aquele `turn_id` em vez de duplicar a mesma fala do usuário em `messages[]` (sua lista armazenada de mensagens). Tornar o registro **idempotente** (seguro para repetir sem gerar duplicatas) mantém a alternância limpa (`user` → `assistant` → `user`) e preserva a integridade do estado após falhas.
