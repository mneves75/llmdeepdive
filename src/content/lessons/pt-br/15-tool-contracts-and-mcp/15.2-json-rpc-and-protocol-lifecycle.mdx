O assistente de compras tem um pedido validado da [aula 15.1](/pt-br/lessons/15-tool-contracts-and-mcp/15.1-from-model-output-to-a-tool-request/): consultar o PO-1001. A consulta roda num programa separado, o servidor de compras, e os dois programas conversam por um par de pipes. O assistente pode ter várias perguntas em andamento ao mesmo tempo, e as respostas voltam pelo mesmo fluxo. Como ele sabe qual resposta pertence a qual pergunta? E se o servidor esperar outra versão da conversa? Esta aula constrói a camada de mensagens que responde às duas coisas: JSON-RPC 2.0, do jeito que o Model Context Protocol o usa.

## Quatro tipos de mensagem

O *Model Context Protocol* (MCP) é um protocolo aberto que permite a uma aplicação de IA, o *host*, se conectar a programas que oferecem ferramentas e dados, chamados *servidores*. Dentro do host, um *cliente* por servidor fala o protocolo. As mensagens do MCP são mensagens *JSON-RPC 2.0*: objetos JSON para chamar um método com nome em outro programa. Há quatro formatos:

- Uma *requisição* tem `"jsonrpc": "2.0"`, um `id`, um `method` e `params` opcionais. Ela espera exatamente uma resposta.
- Uma *resposta de resultado* traz o mesmo `id` e um `result`.
- Uma *resposta de erro* traz o mesmo `id` e um `error` com um `code` inteiro e uma `message`.
- Uma *notificação* é uma requisição sem `id`. A especificação do JSON-RPC diz: "The Server MUST NOT reply to a Notification" (o servidor não pode responder a uma notificação).

No transporte stdio, em que o cliente inicia o servidor como processo filho, cada mensagem é uma linha de JSON na entrada ou na saída padrão do servidor. O trecho abaixo é saída real do servidor deste curso, que recebeu cinco linhas na entrada padrão: descoberta (id 1), uma requisição com versão desconhecida (id 2), uma notificação de cancelamento para o id 2, uma consulta (id 3) e uma listagem de ferramentas (id 4). Voltaram quatro linhas:

```json
{"jsonrpc":"2.0","id":1,"result":{"resultType":"complete","supportedVersions":["2026-07-28"],"capabilities":{"tools":{"listChanged":true}},"_meta":{"io.modelcontextprotocol/serverInfo":{"name":"agentlab-purchasing","version":"0.1.0"}},"ttlMs":0,"cacheScope":"private"}}
{"jsonrpc":"2.0","id":2,"error":{"code":-32022,"message":"Unsupported protocol version","data":{"supported":["2026-07-28"],"requested":"1900-01-01"}}}
{"jsonrpc":"2.0","id":3,"result":{"resultType":"complete","content":[{"type":"text","text":"{\"po_id\": \"PO-1001\", \"supplier\": \"Supplier Alpha\", \"item\": \"M8 hex bolts, box of 500\", \"quantity\": 40, \"unit_price\": \"12.50\", \"currency\": \"USD\", \"status\": \"received\"}"}],"structuredContent":{"po_id":"PO-1001","supplier":"Supplier Alpha","item":"M8 hex bolts, box of 500","quantity":40,"unit_price":"12.50","currency":"USD","status":"received"},"isError":false}}
```

A quarta linha, a primeira página da listagem de ferramentas, é longa; a [aula 15.3](/pt-br/lessons/15-tool-contracts-and-mcp/15.3-tools-resources-prompts-and-discovery/) explica o que ela traz. Nada voltou para a notificação.

## Casando respostas com perguntas

O `id` é a única ligação entre uma resposta e sua pergunta. O MCP aperta o JSON-RPC aqui: um id é uma string ou um inteiro e "MUST NOT be `null`" (não pode ser `null`), e não pode repetir o id de nenhuma outra requisição que o remetente ainda não viu respondida. O cliente guarda os ids em espera num objeto `PendingCalls` e confere cada resposta contra ele:

```python
# file: examples/agent-engineering/src/agentlab/tools/jsonrpc.py
    def settle(self, response: dict) -> int | None:
        """Return the id this response answers, None for a cancelled request, or raise."""
        request_id = response.get("id")
        if not is_valid_id(request_id):  # also stops True from matching id 1
            raise ProtocolViolation(f"response without a usable id: {str(request_id)[:64]}")
        if request_id in self._waiting:
            self._waiting.remove(request_id)
            return request_id
        if request_id in self._cancelled:
            self._cancelled.remove(request_id)
            return None
        raise ProtocolViolation(f"response for id {request_id!r}, which is not waiting for one")
```

São três casos. Um id em espera é resolvido uma vez e removido, então uma segunda resposta à mesma requisição é uma violação. Um id que o cliente cancelou devolve `None`: o MCP diz que um cliente "SHOULD ignore any response to the cancelled request that arrives afterward" (deveria ignorar qualquer resposta à requisição cancelada que chegue depois). Qualquer outro id significa que o servidor respondeu a uma pergunta que ninguém fez, e o cliente deixa de confiar no fluxo. O comentário sobre `True` existe porque em Python `True == 1`, então um servidor que mandasse `"id": true` casaria, sem essa verificação, com a requisição 1.

## O lado que recebe e seus códigos de erro

O `Dispatcher` do servidor recebe uma linha e devolve as linhas a escrever de volta. O JSON-RPC fixa cinco códigos de erro, e o MCP acrescenta os seus numa faixa reservada:

| Código | Significado | Quando este servidor o envia |
|---|---|---|
| -32700 | Parse error | a linha não é JSON (o id é `null`, já que nenhum pôde ser lido) |
| -32600 | Invalid Request | valor errado em `jsonrpc`, sem método, id inválido ou um lote |
| -32601 | Method not found | um método desconhecido, e o `initialize` legado |
| -32602 | Invalid params | params não é objeto, falta `_meta`, ferramenta desconhecida |
| -32603 | Internal error | o handler quebrou |
| -32022 | Unsupported protocol version (MCP) | a requisição cita uma versão que este servidor não fala |

O MCP divide a faixa de erros de servidor do JSON-RPC: os códigos de -32020 a -32099 pertencem à especificação do MCP, e uma implementação não pode inventar os próprios ali. Um *lote* (*batch*), um array JSON com várias requisições, é JSON-RPC válido, mas a ligação stdio do MCP diz que cada linha é "a single JSON-RPC request, notification, or response" (uma única requisição, notificação ou resposta JSON-RPC), então o dispatcher recusa um array como uma única requisição inválida. Eis o miolo de `_reply`:

```python
# file: examples/agent-engineering/src/agentlab/tools/jsonrpc.py
        params = message.get("params", {})
        handler = self._methods.get(message["method"])
        try:
            if not isinstance(params, dict):
                raise RpcError(INVALID_PARAMS, "params must be an object")
            if handler is None:
                raise RpcError(METHOD_NOT_FOUND, f"Method not found: {message['method'][:64]}")
            result = handler(params, request_id, emit)
        except RpcError as error:
            return None if notification else error_response(request_id, error.code, error.message, error.data)
        except Exception:
            # Details go to the server's log (stderr), never to the peer.
            log.exception("handler for %s failed", message["method"][:64])
            return None if notification else error_response(request_id, INTERNAL_ERROR, "Internal error")
```

Toda saída confere `notification` primeiro, então nem uma notificação que falha recebe resposta. Uma quebra vira um simples "Internal error": os detalhes vão para a saída de erro padrão, que a ligação stdio reserva para logs. Um teste faz um handler levantar uma exceção cuja mensagem contém uma senha falsa e confere que a senha nunca chega ao cliente.

## Um ciclo de vida sem handshake

Se você já leu sobre MCP antes, talvez espere uma requisição `initialize` que abre uma sessão e fixa a versão. A especificação agora chama essas revisões, a 2025-11-25 e anteriores, de *legacy* (legadas). Na revisão 2026-07-28, "There is no negotiation handshake" (não há handshake de negociação). O MCP é stateless, sem estado entre requisições: "Servers MUST NOT rely on prior requests over the same connection to establish context" (servidores não podem depender de requisições anteriores na mesma conexão para estabelecer contexto). Em vez disso, toda requisição leva dois campos obrigatórios em `params._meta`: `io.modelcontextprotocol/protocolVersion` e `io.modelcontextprotocol/clientCapabilities`, os recursos do cliente com que esta requisição pode contar. O servidor confere os dois, em toda requisição:

```python
# file: examples/agent-engineering/src/agentlab/tools/server.py
def check_request_meta(params: dict) -> None:
    """Every request states its version and capabilities; the server remembers nothing between requests."""
    meta = params.get("_meta")
    if not isinstance(meta, dict) or not isinstance(meta.get(VERSION_KEY), str) or not isinstance(meta.get(CAPABILITIES_KEY), dict):
        raise RpcError(INVALID_PARAMS, "missing required _meta fields", {"required": [VERSION_KEY, CAPABILITIES_KEY]})
    if meta[VERSION_KEY] not in SUPPORTED_VERSIONS:
        raise RpcError(UNSUPPORTED_PROTOCOL_VERSION, "Unsupported protocol version", {"supported": SUPPORTED_VERSIONS, "requested": meta[VERSION_KEY][:64]})
```

O que sobra de ciclo de vida é curto. O cliente lança o processo do servidor. Ele pode chamar `server/discover`, que todo servidor precisa implementar, para saber as versões suportadas e as capacidades do servidor, como `tools`. Depois manda requisições. Para parar, fecha a entrada padrão do servidor, espera e, se o servidor não sair, escala para `SIGTERM` e depois `SIGKILL`; o servidor deveria sair assim que sua entrada fecha. Se o servidor morrer inesperadamente, o cliente o reinicia e tenta de novo. Nada se perde além das requisições em andamento, porque nada morava na conexão.

A especificação também pede que um servidor que só fala revisões modernas cite suas versões em qualquer erro que devolva a um `initialize`, porque clientes legados não teriam outra pista para seguir em frente. Este servidor responde ao `initialize` com -32601 e `"supported": ["2026-07-28"]` no data.
