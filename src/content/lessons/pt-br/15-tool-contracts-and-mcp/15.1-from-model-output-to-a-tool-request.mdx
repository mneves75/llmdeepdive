O assistente de compras está atendendo um comprador do tenant-a, uma das duas empresas fictícias dos dados do curso (um *tenant* é uma organização cliente cujos registros ficam separados dos de qualquer outra). O modelo responde com uma chamada de ferramenta: rodar `lookup_purchase_order` com os argumentos `{"po_id": "PO-2001"}`. O número do pedido parece certo. Ele também é um pedido do tenant-b. O código deve executá-lo? A resposta pede três perguntas separadas. O pedido está bem formado? Ele cita uma ferramenta que existe? Quem chama pode ver este registro? Esta aula transforma as duas primeiras num schema estrito e deixa a terceira à parte, porque nenhum schema consegue respondê-la.

## O que um modelo realmente entrega?

Uma *chamada de ferramenta* (*tool call*) é o pedido de um modelo para rodar uma função: o nome de uma ferramenta mais um objeto de argumentos. O modelo a produz como texto gerado em *JSON* (JavaScript Object Notation, um formato em texto puro para dados estruturados de chave e valor). O adaptador `OpenAICompatibleModel` do curso, o código que conversa com a API (Application Programming Interface, interface de programação) do modelo, faz o *parsing* desse texto — lê os campos estruturados a partir dos caracteres brutos — e o devolve como `ModelReply.tool_call`, um *dicionário* Python (uma tabela de pares chave-valor). Se o texto não for JSON válido, o adaptador devolve um erro que começa com `protocol:` em vez de adivinhar o que se quis dizer.

O modelo aprendeu a forma da ferramenta pela sua *definição*: um nome, uma descrição e um *schema* (uma especificação formal dos nomes de campos, tipos de dados e faixas aceitas), enviados junto com o prompt. Essas definições são texto que o modelo lê, então custam tokens como qualquer outra parte do prompt ([aula 1.4](/pt-br/lessons/1-text-to-tensors/1.4-sentencepiece-byte-level-token-counts/)). Ler um schema não prende o modelo a ele. O modelo ainda pode mandar uma *string* (texto) onde cabe um número, inventar um campo ou copiar um número de pedido de um e-mail de fornecedor não confiável. A especificação do Model Context Protocol (MCP), o protocolo das próximas aulas, diz sem rodeios que servidores "MUST validate all tool inputs" (precisam validar todas as entradas de ferramentas).

## Forma: um modelo de argumentos estrito

*JSON Schema* é um documento JSON padronizado que descreve quais valores JSON são aceitos: os tipos, quais campos são obrigatórios e a faixa permitida de um número. O MCP publica os argumentos de cada ferramenta como um JSON Schema chamado `inputSchema`. O projeto escreve cada schema uma vez usando *Pydantic*, uma biblioteca Python que confere dados contra uma classe declarada, e deixa o Pydantic gerar o JSON Schema a partir dela. No trecho abaixo, `Arguments` fixa três regras estritas de base (`ConfigDict`), `LookupPurchaseOrder` exige um número de pedido com quatro dígitos seguindo o padrão de expressão regular `^PO-[0-9]{4}$` (começa com `PO-`, seguido de quatro dígitos e nada mais) e `ListPurchaseOrders` restringe `status` e limita `limit`:

```python
# file: examples/agent-engineering/src/agentlab/tools/contracts.py
class Arguments(BaseModel):
    # Strict: "5" is not 5. Forbid: an extra field is an error, not ignored.
    model_config = ConfigDict(strict=True, extra="forbid", frozen=True)


class LookupPurchaseOrder(Arguments):
    po_id: str = Field(pattern=r"^PO-[0-9]{4}$", description="Purchase order number, for example PO-1001.")


class ListPurchaseOrders(Arguments):
    status: Literal["open", "received"] | None = None
    limit: int = Field(default=10, ge=1, le=50)
```

`Literal["open", "received"]` é um *enum*, um campo que só aceita uma lista fixa de valores. `ge=1, le=50` limita o número pelos dois lados (maior ou igual a 1, menor ou igual a 50). Imprimir `ListPurchaseOrders.model_json_schema()` gera o documento JSON abaixo, avisando ao modelo que propriedades extras são proibidas, `status` precisa ser `"open"`, `"received"` ou `null` (vazio), e `limit` precisa ser um inteiro (número sem casas decimais) de 1 a 50:

```json
{"additionalProperties": false, "properties": {"status": {"anyOf": [{"enum": ["open", "received"], "type": "string"}, {"type": "null"}], "default": null, "title": "Status"}, "limit": {"default": 10, "maximum": 50, "minimum": 1, "title": "Limit", "type": "integer"}}, "title": "ListPurchaseOrders", "type": "object"}
```

O contrato publicado e o contrato aplicado vêm da mesma classe, então não têm como se afastar um do outro. Um teste confirma que o schema diz `"additionalProperties": false` e um limite de 1 a 50.

## Por que o modo estrito importa

Por padrão, o Pydantic tenta *coagir* um valor, isto é, convertê-lo para o tipo declarado quando consegue. A documentação dá o exemplo da string `'123'` virando o inteiro 123. Isso é cômodo num formulário web e errado na saída de um modelo, porque um modelo que manda `"20"` leu mal o contrato, e consertar em silêncio esconde o erro. O modo estrito faz o Pydantic "error if the data is not of the correct type" (dar erro se o dado não for do tipo correto). Eis o que o Pydantic 2.13.5 fez com o campo `limit` quando esta aula foi escrita; a coluna do modo estrito é o que os testes conferem:

| Entrada | Modo padrão (lax) | Modo estrito |
|---|---|---|
| `"5"` | aceito como 5 | rejeitado: não é um inteiro válido |
| `5.0` | aceito como 5 | rejeitado: não é um inteiro válido |
| `true` | aceito como 1 | rejeitado: não é um inteiro válido |
| `51` | rejeitado: acima de 50 | rejeitado: acima de 50 |

A linha do *booleano* (`true`/`false`) é a surpreendente. Em Python, `True` é uma *subclasse* (um tipo especializado que herda o comportamento de um tipo pai) de `int` com valor 1, então a validação lax o deixa passar.

## Por que um campo desconhecido é um erro

A segunda configuração é `extra`. A documentação do Pydantic diz que, por padrão, um modelo ignora dados extras, e `extra="forbid"` transforma isso em erro. Imagine o modelo enviando `{"po_id": "PO-1001", "tenant_id": "tenant-b"}`. Ignorar o campo extra calha de ser seguro aqui, porque a ferramenta nunca o lê. Também significa que ninguém fica sabendo que o modelo tentou escolher um tenant. Proibi-lo transforma a tentativa numa rejeição visível, `tenant_id: Extra inputs are not permitted`, que um teste, um *log* (um registro contínuo de eventos do sistema) ou um revisor consegue ver.

Escolher um tenant não é tarefa do modelo. Nos registros compartilhados do projeto (`domain.py`), todo `RunState` (o estado salvo de uma execução do assistente) carrega um `Principal`: o usuário e o tenant que o *controlador* (o programa externo que conduz o laço entre usuário, modelo e ferramentas) montou a partir de uma entrada autenticada, como um login verificado, nunca da saída do modelo. Nenhum modelo de argumentos desta trilha tem um campo de tenant, então não há onde um modelo colocar um.

## Válido não é autorizado

A *autorização*, a decisão de se quem chama pode agir sobre um registro específico, precisa de fatos que o schema não tem: quem está chamando e de quem é o registro. Avance pelas três chamadas abaixo para ver onde o parsing, a validação estrita de forma e a autorização por tenant barram cada pedido ruim.

<Figure id="t15-shape-then-permission" />

A verificação de permissão fica em `authorize_record`. Se a busca não devolver registro, ou se o `tenant_id` do registro não bater com `principal.tenant_id`, a função levanta `ToolRejected` com a mesma mensagem de "não encontrado"; caso contrário, devolve o registro:

```python
# file: examples/agent-engineering/src/agentlab/tools/contracts.py
def authorize_record(principal: Principal, record: dict | None, po_id: str) -> dict:
    """Allow a record only if it belongs to the caller's tenant.

    Missing and forbidden get the same answer: saying "forbidden" would tell
    the caller that another tenant's order exists.
    """
    if record is None or record["tenant_id"] != principal.tenant_id:
        raise ToolRejected(f"purchase order {po_id} not found")
    return record
```

A mensagem idêntica importa. Se PO-9999 respondesse "não encontrado" e PO-2001 respondesse "proibido", um modelo ou um atacante poderia mapear quais números de pedido existem em outras empresas só perguntando. A [aula 15.4](/pt-br/lessons/15-tool-contracts-and-mcp/15.4-a-raw-postgres-mcp-server/) leva essa mesma regra para dentro da consulta ao banco, para que as linhas de outro tenant nem saiam do banco.

:::caveat
Nenhuma das duas verificações torna um pedido correto. Um comprador do tenant-a ainda pode pedir o pedido errado entre os do próprio tenant-a, e as duas verificações vão passar. Se a ação corresponde à intenção do usuário é uma pergunta para a aprovação (trilha 20) e para a avaliação (trilha 23).
:::

Uma rejeição não encerra a execução: o modelo recebe um erro e pode tentar de novo. Esse erro também é texto entrando no contexto do modelo, então o projeto o mantém curto. Ele lista nomes de campos e motivos, nunca o valor rejeitado, porque o valor pode ter 5.000 caracteres ou carregar uma *instrução injetada* (texto hostil escondido em dados externos para conduzir o modelo). As mensagens de `ToolRejected` têm no máximo 300 caracteres, e um teste manda um número de pedido hostil para conferir que o texto dele não volta.
