Até agora o servidor de compras rodou como processo filho na própria máquina do comprador, lançado pelo assistente com o tenant do comprador no ambiente. No próximo trimestre, a equipe quer um servidor compartilhado na rede, que os assistentes das duas empresas consigam alcançar. Chega uma requisição por HTTP com um token perfeitamente assinado, mas o token foi emitido para o servidor de agenda da empresa, não para o de compras. O servidor de compras deve responder? No stdio essa pergunta nunca apareceu, então esta aula começa perguntando quem está chamando em cada transporte.

## Quem chama, no stdio?

No transporte stdio, o host inicia o servidor e segura as duas pontas dos seus pipes. Nada na rede alcança esses pipes; outro programa precisaria de acesso aos próprios processos do host naquela máquina. O protocolo base do Model Context Protocol (MCP) tira a consequência: implementações que usam stdio "SHOULD NOT follow this specification, and instead retrieve credentials from the environment" (não deveriam seguir esta especificação e deveriam, em vez disso, obter as credenciais do ambiente). É o que o servidor de compras faz com `AGENTLAB_USER_ID` e `AGENTLAB_TENANT_ID` na [aula 15.4](/pt-br/lessons/15-tool-contracts-and-mcp/15.4-a-raw-postgres-mcp-server/). Essa identidade é configuração escolhida no lançamento e fixa durante toda a vida do processo. O servidor nunca a deduz de requisições anteriores, o que o protocolo stateless proíbe.

A confiança não desaparece. Ela passa para quem escreve o comando de lançamento. A orientação de segurança do MCP descreve um comprometimento de servidor local em que um atacante planta um comando de inicialização malicioso na configuração de um cliente. Quando um cliente oferece configurar um servidor local com um clique, a orientação diz que ele precisa "Show the exact command that will be executed, without truncation" (mostrar o comando exato que será executado, sem cortes) e "Require explicit user approval before proceeding" (exigir aprovação explícita do usuário antes de seguir). Ela também recomenda lançar servidores com acesso restrito ao sistema de arquivos e à rede, que é o assunto da trilha 17. Um servidor stdio roda com os privilégios do usuário que o lançou.

## Um servidor remoto verifica um token em toda requisição

O transporte Streamable HTTP envia cada mensagem como um POST HTTP para um único endpoint MCP, e qualquer um na rede pode enviar um. A especificação de autorização do MCP, construída sobre o OAuth 2.1, dá nome às partes. O servidor MCP é um *servidor de recursos* (*resource server*). O cliente é um *cliente* OAuth que age pelo usuário. Um *servidor de autorização* autentica o usuário, pede *consentimento*, a concordância explícita do usuário com o que o cliente pode fazer, e emite um *token de acesso*. O cliente envia esse token num cabeçalho `Authorization: Bearer`, em toda requisição e nunca na URL. Quatro das *claims* do token, as afirmações que ele faz sobre si mesmo, decidem cada requisição:

- `aud`, a *audiência*: para qual servidor o token é. Servidores MCP "MUST validate that access tokens were issued specifically for them as the intended audience" (precisam validar que os tokens de acesso foram emitidos especificamente para eles como audiência pretendida), segundo a RFC 8707 (uma RFC, ou Request for Comments, é um dos documentos de padrões numerados da IETF).
- `scope`: as permissões concedidas, como palavras separadas por espaços, por exemplo `purchases:read`.
- `exp`: o horário de expiração, em segundos desde 1970. A RFC 9068 diz que "The current time MUST be before the time represented by the 'exp' claim" (o horário atual precisa ser anterior ao horário representado pela claim exp).
- `jti`: o id único do token, que permite a um servidor reconhecer um token *revogado*, retirado antes da expiração.

Um token do servidor de agenda é recusado mesmo que seja autêntico. A especificação diz que servidores MCP "MUST NOT accept or transit any other tokens" (não podem aceitar nem repassar nenhum outro token), e a orientação de segurança dá nome à falha: *token passthrough*, em que um servidor aceita tokens feitos para outro e os repassa adiante, de modo que o serviço seguinte não consegue saber o que foi verificado.

## As quatro verificações como fixture

O curso não implementa OAuth à mão e não faz criptografia nenhuma. Verificar a assinatura, o emissor e o algoritmo de um token é tarefa de uma biblioteca mantida, usando as chaves do servidor de autorização. `remote_auth.py` começa depois desse ponto: recebe claims que uma biblioteca já verificou e toma as quatro decisões acima, com um relógio injetado e um conjunto injetado de ids revogados.

```python
# file: examples/agent-engineering/src/agentlab/tools/remote_auth.py
    audiences = [token.aud] if isinstance(token.aud, str) else token.aud
    if resource not in audiences:
        return _invalid("token was issued for another resource")  # the audience check MCP requires (RFC 8707)
    if token.exp <= int(now.timestamp()):
        return _invalid("token expired")
    if token.jti in revoked:
        return _invalid("token revoked")
    if not required_scopes <= set(token.scope.split()):
        needed = " ".join(sorted(required_scopes))
        return Decision(False, 403, "insufficient_scope", f'Bearer error="insufficient_scope", scope="{needed}"')
    return Decision(True, 200, subject=token.sub)
```

Os códigos de status vêm da especificação: "Invalid or expired tokens MUST receive a HTTP 401 response" (tokens inválidos ou expirados precisam receber uma resposta HTTP 401), e um escopo insuficiente recebe 403 com um cabeçalho `WWW-Authenticate` que cita o escopo necessário, como descreve a RFC 6750. O teste de escopo separa a string nos espaços e compara palavras inteiras, então `purchases:read-all-tenants` não satisfaz `purchases:read`. Com `now` às 12:00:00 UTC, os testes veem estas respostas:

| Token | Resposta |
|---|---|
| para este servidor, `purchases:read`, expira às 12:05:00 | 200 |
| `aud` é o servidor de agenda | 401 `invalid_token` |
| expira exatamente às 12:00:00 | 401 `invalid_token` |
| expira às 12:00:01 | 200 |
| `jti` na lista de revogados | 401 `invalid_token` |
| só o escopo `calendar:read` | 403 `insufficient_scope`, `scope="purchases:read"` |

A revogação precisa de uma fonte. Um token autocontido continua válido até expirar, a menos que o servidor pergunte a alguém. A RFC 7662 define a *introspecção de token*: o servidor de recursos pergunta ao servidor de autorização sobre um token e recebe de volta `active`, um booleano "indicator of whether or not the presented token is currently active" (que indica se o token apresentado está ativo neste momento). Expirações curtas limitam por quanto tempo um token que ninguém revogou continua útil. Depois que as quatro verificações passam, um servidor real ainda mapearia o sujeito do token para um `Principal` pelo próprio diretório de usuários, e as consultas da aula 15.4 então aplicariam o escopo desse tenant. A fixture para na decisão.

## Cancelamento e falhas de transporte

Cada transporte também sinaliza o cancelamento de um jeito. No stdio, o cliente envia `notifications/cancelled`; no Streamable HTTP, em que as respostas podem chegar como um fluxo SSE (Server-Sent Events), "Closing the SSE response stream is the cancellation signal" (fechar o fluxo SSE da resposta é o sinal de cancelamento), e o servidor precisa tratar uma desconexão como cancelamento. O cliente do curso envia `notifications/cancelled` quando uma requisição estoura o tempo e ignora qualquer resposta atrasada. O servidor trata uma requisição por vez, então nunca vê um cancelamento enquanto ainda há trabalho rodando. Esse é um dos recursos que este subconjunto não implementa. Quando o processo do servidor morre, o cliente levanta `TransportClosed` em vez de esperar para sempre, e um teste mata o processo para conferir.

## O que o subconjunto feito à mão deixa de fora

A docstring do servidor lista o que falta: recursos, prompts, completions, logging, progresso, requisições de várias idas e voltas, extensões, o transporte Streamable HTTP e sua autorização, cancelar trabalho em andamento, encerrar uma assinatura de forma ordenada no desligamento, cache além de `ttlMs: 0` e o handshake legado `initialize`. É uma implementação para aprender, não uma implementação compatível. A comparação a seguir vem da leitura do README e do código-fonte do SDK (software development kit) oficial de MCP para Python na tag v2.2.0 (lançada em 2026-09-07). O curso não instala nem roda o SDK, e a integração contínua (CI) do curso não o testa. O README diz que a v2 suporta a especificação 2026-07-28 "and every earlier revision" (e todas as revisões anteriores), e os transportes stdio, Streamable HTTP e SSE. Para autorização, o SDK define uma interface `TokenVerifier` que você implementa, por exemplo com uma biblioteca de JWT (JSON Web Token), devolvendo um `AccessToken` com o id do cliente, os escopos, a expiração, o recurso e o sujeito. O backend de autenticação bearer dele recusa tokens expirados e, quando configurado com a URL do próprio servidor, tokens emitidos para outro recurso; um `RequireAuthMiddleware` separado responde 403 `insufficient_scope` quando falta um escopo exigido. As decisões são as mesmas que a fixture desta aula toma, e a criptografia fica nas bibliotecas.
