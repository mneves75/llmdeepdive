Um modelo de linguagem trabalha com números, não com letras. Esta aula acompanha uma palavra do seu teclado até dentro do Qwen3.8-27B e de volta, e nomeia o que cada etapa do caminho promete. Isso importa porque cada etapa pode mudar ou descartar informação, e quando algo quebra em produção você precisa saber qual etapa foi.

## Por que a mesma palavra pode chegar como bytes diferentes?

Digite a palavra *café* numa caixa de chat e envie ao Qwen3.8-27B. Uma coisa perfeitamente banal de se fazer, e que esconde um problema que já quebrou sistemas em produção.

O Unicode, o padrão que dá um número a cada caractere, chama cada um desses números de **code point** (ponto de código). Existem duas formas padrão de escrever *café* em code points. Uma usa quatro, terminando num único caractere pré-composto para o e acentuado. A outra usa cinco, terminando num e simples seguido de um acento agudo combinante separado. Na tela, são indistinguíveis.

Computadores guardam code points como bytes, e o **UTF-8** é a regra padrão para isso: cada code point vira de um a quatro bytes. Serializada em UTF-8, a primeira grafia ocupa cinco bytes e a segunda, seis. O caractere acentuado custa dois bytes na primeira forma, enquanto o e sozinho mais o sinal combinante custam três na segunda.

O modelo nunca vê a sua tela. Seu tokenizer público (o programa que corta o texto em tokens) recebe uma string Unicode e, nesta versão fixada, primeiro aplica **NFC** (Normalization Form C, a forma de normalização C). O NFC é uma regra do Unicode que reescreve grafias que o Unicode declara equivalentes, chamadas **canonicamente equivalentes**, numa única forma composta padrão. Só depois começa o processamento byte-level. As duas grafias de *café* portanto convergem para a mesma string normalizada e os mesmos ids de token.

Outras distinções sobrevivem à normalização. Um espaço comum e um espaço não separável não são canonicamente equivalentes, então ainda produzem sequências diferentes. A questão não é que todo par visualmente idêntico difere. É que a política de normalização declarada pelo tokenizer decide quais distinções chegam ao modelo.

## O que a codificação garante?

Acompanhe o caminho inteiro, nomeando o que cada etapa promete e o que não promete. A primeira fronteira é a **codificação**: o Unicode atribui code points a um repertório imenso de elementos de texto, e o UTF-8 transforma cada code point em bytes. Um valor de byte sozinho não significa nada até você saber qual codificação o produziu.

Até a ideia de um caractere visível é escorregadia. Um emoji com modificador de tom de pele e um zero-width joiner (um code point invisível que cola os vizinhos num só símbolo) pode ocupar vários code points e ser desenhado como um único glifo. E o exemplo do *café* mostra que mesmo uma palavra latina com um acento tem mais de uma grafia legal em bytes.

A normalização pode forçar formas canonicamente equivalentes a coincidir, e o tokenizer fixado do Qwen3.8-27B aplica NFC explicitamente. Essa escolha tem um custo: identificadores, senhas e código-fonte muitas vezes precisam preservar distinções que texto em linguagem natural aceita perder de bom grado. O espaço em branco carrega o mesmo risco. Um espaço comum, um espaço não separável e um espaço estreito não separável parecem quase idênticos e são bytes completamente diferentes. Todas essas escolhas são feitas antes de qualquer modelo entrar em cena.

## Em que o tokenizer transforma o texto?

A segunda fronteira é a **tokenization** (tokenização). Um tokenizer corta o texto em **tokens**, as pequenas unidades que um modelo lê e escreve (o termo da [aula 0.1](/pt-br/lessons/0-orientation-and-foundations/0.1-what-is-a-language-model/)), e dá a cada um um id inteiro. O tokenizer do Qwen3.8-27B pega o texto normalizado, transforma em bytes UTF-8 e aplica **BPE** (byte-pair encoding, codificação por pares de bytes) byte-level, um método que constrói tokens fundindo pedaços vizinhos frequentes. A [aula 1.2](/pt-br/lessons/1-text-to-tensors/1.2-tokenization-i/) examina o que esse vocabulário contém e a [aula 1.3](/pt-br/lessons/1-text-to-tensors/1.3-bpe-step-by-step/) mostra como ele foi construído.

Os artefatos do Qwen3.8-27B expõem 248.077 ids mapeados. Esses ids indexam tensores (arrays multidimensionais de pesos) com 248.320 linhas, e as 243 linhas restantes não têm mapeamento no tokenizer publicado.

Os ids em si são rótulos, não quantidades. O token 900 não é maior, nem posterior, nem mais importante que o token 12, do mesmo jeito que uma chave de hash map não carrega significado próprio.

Como este tokenizer trabalha com bytes, ele tem uma consequência muito útil. Seu alfabeto byte-level representa cada byte UTF-8 produzido a partir de uma string Unicode normalizada válida, então ele não precisa de token "desconhecido" para esse texto. Isso não transforma a API pública de texto numa interface para dados binários arbitrários.

## Seguindo uma palavra pelo modelo, ida e volta

Rode a ida e volta mentalmente. Após a normalização NFC, qualquer das duas grafias de *café* vira a mesma sequência de bytes UTF-8 e depois a mesma lista curta de ids.

1. Cada id seleciona uma linha da **tabela de embeddings**, uma grande tabela de consulta com um vetor aprendido por id (cada um desses vetores é chamado de *embedding*). O resultado é um vetor de 5120 dimensões, como a [aula 0.4](/pt-br/lessons/0-orientation-and-foundations/0.4-vectors-matrices-dot-products/) descreveu.
2. Esses vetores atravessam 64 camadas, cada uma reescrevendo o estado.
3. A camada final emite 248.320 **logits** para a próxima posição: scores brutos, um por linha, que a softmax transforma em probabilidades.
4. Um token é escolhido, e o decoder mapeia os ids escolhidos de volta para bytes e então para texto legível.

Para ids produzidos ao codificar essa entrada normalizada, a decodificação reconstrói o texto normalizado. Isso inclui toda distinção que a normalização manteve. Ela não pode recuperar uma grafia canonicamente equivalente que o NFC substituiu, porque essa grafia nunca chegou ao modelo.

Texto gerado é outro caso. Ids arbitrários amostrados pelo modelo não correspondem a nenhuma entrada codificada, então não têm garantia NFC. Podem até formar fragmentos de bytes malformados, que o decoder precisa tratar com caracteres de substituição.

:::caveat
Esta aula deliberadamente não imprime os ids inteiros específicos que o Qwen atribui a *café*, e você deveria desconfiar de qualquer curso que faça isso de memória. A [aula 0.8](/pt-br/lessons/0-orientation-and-foundations/0.8-how-to-read-ml-paper/) fixou a regra: fatos arquiteturais só são afirmados quando um artefato primário os declara. O tamanho do vocabulário está no arquivo de configuração e é seguro citar. Ids individuais de token são uma propriedade dos arquivos do tokenizer, que você pode carregar e consultar em segundos, e que ninguém deveria parafrasear de lembrança.
:::

## Então de onde vem o significado?

Uma tabela de embeddings mapeia ids para vetores e, na inicialização, esses vetores não contêm definição alguma. O treino os remodela, junto com tudo que vem depois, para que as representações se tornem úteis para prever o próximo token.

Note que a *mesma* linha serve a toda ocorrência de um token. A palavra *manga* na fruteira e *manga* na camisa começam numa linha idêntica. São os tokens ao redor, misturados pelas camadas acima, que separam os dois estados. Então o significado, na medida em que a palavra se aplica, pertence a um estado que depende do contexto, não a uma entrada de vocabulário.

Sintaxe e semântica, portanto, não são entregues nem pelo Unicode nem pelo tokenizer. Elas emergem, imperfeitamente, de três fontes: padrões nos dados de treino, vieses embutidos na arquitetura e o objetivo de treino. Um modelo pode aprender que uma aspas de abertura prevê uma de fechamento mais adiante, que um sujeito restringe um verbo, ou que certos nomes coocorrem com certas profissões. Essas regularidades sustentam comportamento útil sem equivaler a uma gramática explícita nem a uma base de conhecimento verificada.

:::warning
Um erro comum é tratar uma ida e volta normalizada e estável como prova de compreensão. Ela demonstra que o tokenizer transporta consistentemente sua representação normalizada. Isso é propriedade do código do tokenizer, e valeria com a mesma perfeição se as 64 camadas do meio fossem substituídas por números aleatórios. Um transporte fiel não diz nada sobre a qualidade do que aconteceu durante o trajeto.
:::

## Que falhas cada fronteira explica?

A visão em camadas explica um catálogo de falhas reais:

- Bytes corrompidos quebram a decodificação antes de o modelo ser alcançado.
- Caracteres visualmente confundíveis podem esconder um identificador trocado no que parece texto comum.
- Um tokenizer azarado pode estilhaçar um idioma em muito mais posições que outro, o que a [aula 1.4](/pt-br/lessons/1-text-to-tensors/1.4-sentencepiece-byte-level-token-counts/) converte em dinheiro.
- Grafias raras recebem representações fracamente treinadas.
- Um modelo fluente ainda pode ligar o referente errado do mundo real, porque seu objetivo premiava continuação provável e não a checagem de fatos contra o mundo.

Computadores processam texto com grande sofisticação, e cada etapa desse processamento tem um contrato estreito o bastante para caber em uma linha. A normalização escolhe uma grafia entre as equivalentes. O UTF-8 mapeia símbolos normalizados para bytes. Tokenizers mapeiam essa representação para ids. Embeddings mapeiam ids para vetores. Camadas transformam vetores. A decodificação mapeia scores de volta para tokens. Manter essas seis fronteiras distintas impede o verbo vago *ler* de esconder onde a informação entrou, mudou ou se perdeu sem erro nenhum.
