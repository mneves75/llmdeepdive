Antes de um modelo ler texto, algo precisa cortar esse texto em **tokens**, as unidades que o modelo lê e escreve, e dar a cada um um id inteiro. Essa escolha de unidades parece encanamento, mas decide o comprimento de toda sequência, o tamanho das tabelas do modelo e quais strings o modelo consegue representar. Esta aula monta essa escolha a partir do zero.

## Quantas unidades uma palavra deveria custar?

Pegue a palavra inglesa *unbelievability* e faça uma pergunta de projetista: quantas unidades o modelo deveria gastar com ela? Três respostas já foram tentadas em produção, e vale trabalhar as consequências de cada uma antes de qualquer terminologia chegar.

**Um caractere por vez.** A palavra custa quinze unidades. O vocabulário necessário é minúsculo: algumas centenas de entradas cobrem quase todo texto em escrita latina, e nenhuma palavra fica irrepresentável. Mas agora toda frase se estica por cinco ou seis vezes mais posições (os lugares da sequência, um por token). Como a trilha 4 vai mostrar, o trabalho de um transformer cresce com as posições, não com os caracteres. Você deixou o modelo barato de armazenar e caro de rodar.

**Uma palavra inteira.** A palavra custa uma unidade, desde que alguém a tenha colocado no vocabulário. Se não colocou, o modelo recebe um símbolo "desconhecido", e a distinção entre *unbelievability* e *incomprehensibility* é destruída na porta de entrada. Nomes, flexões, jargão de domínio, erros de digitação e palavras inventadas terça-feira passada caem todos no mesmo buraco. Nenhuma lista finita de palavras dá conta de texto aberto, e aumentar a lista tem um preço próprio, ao qual chegamos mais abaixo.

**Pedaços de palavras.** Divida-a como *un*, *believ*, *abil*, *ity* e ela custa quatro unidades, com pedaços reutilizáveis em milhares de outras palavras. Isso é **tokenization por subpalavras** (*tokenization* é o termo em inglês para tokenização), e essencialmente todo modelo moderno a usa, o Qwen3.8-27B incluído. Strings frequentes ficam inteiras; as raras são compostas a partir de pedaços. Um algoritmo aprende os pedaços a partir de um corpus (uma grande coleção de texto de treino), e a [aula 1.3](/pt-br/lessons/1-text-to-tensors/1.3-bpe-step-by-step/) acompanha um desses algoritmos merge a merge (*merge* é cada fusão de dois pedaços num só).

## Como o Qwen consegue soletrar qualquer string?

A variante do Qwen desce mais um degrau. Seu tokenizer primeiro aplica normalização NFC (a regra do Unicode, vista na [aula 1.1](/pt-br/lessons/1-text-to-tensors/1.1-why-computers-cant-read/), que escolhe uma grafia entre as equivalentes). Depois um pré-tokenizador **ByteLevel** transforma o texto nos seus bytes UTF-8, e só então roda o BPE (byte-pair encoding, o algoritmo de fusões da aula 1.3).

Como as unidades base derivam de bytes, elas soletram todo byte UTF-8 produzido por uma string Unicode válida. Então escritas desconhecidas e emoji não precisam colapsar num token desconhecido. Dois limites mantêm essa afirmação honesta:

- Isso não é uma rota de fallback. Alguns tokenizers usam "byte fallback", quebrando um caractere em tokens de byte só quando ele falta no vocabulário. A configuração BPE publicada do Qwen diz `byte_fallback: false` e não declara token desconhecido. Os bytes já são a camada de base, então não há para onde recorrer.
- Isso não faz a API pública de texto aceitar dados binários arbitrários.

A cobertura de texto Unicode normalizado é ampla. A eficiência não: strings incomuns podem se expandir em cadeias longas de pedaços derivados de bytes.

## Por que as fronteiras de token são estatísticas, e não linguísticas?

Note que nenhuma dessas divisões é um fato sobre a língua. Até *palavra* é ambíguo. *Dá-lhe* é uma palavra ou duas? A pontuação gruda? O chinês não coloca espaço nenhum entre palavras. O alemão solda alegremente quatro conceitos num composto só.

Ainda assim, um tokenizer precisa devolver uma resposta determinística para toda string Unicode válida, inclusive strings que seus projetistas jamais imaginaram. Então as fronteiras que ele traça vêm da estatística, não da linguística. Uma divisão pode parecer absurda para uma pessoa e ainda assim ser a escolha certa de engenharia.

## O que o 248.320 da configuração conta?

Agora o número no arquivo de configuração, que é onde esta aula justifica seu lugar. O Qwen3.8-27B declara 248.320 linhas de vocabulário.

Há duas leituras erradas. A óbvia é *o modelo conhece 248.320 palavras*. A mais sutil, que pega quem já sabe melhor, é *o tokenizer pode emitir 248.320 tokens distintos*. Esse campo não garante nenhuma das duas. O que `vocab_size` governa é um shape de tensor (as dimensões de um array de pesos). Ele define o número de linhas da matriz de embeddings, a tabela que transforma cada id num vetor. Também define o número de colunas da projeção de saída, a matriz que produz os logits, os scores brutos por token da [aula 0.1](/pt-br/lessons/0-orientation-and-foundations/0.1-what-is-a-language-model/).

Os artefatos do tokenizer tornam a diferença mensurável. O modelo BPE contém 248.044 entradas, e 33 tokens adicionados ocupam ids até 248.076, totalizando 248.077 ids mapeados. A configuração do modelo define $\text{vocab\_size}=248{,}320$, então os tensores de embedding e saída reservam 243 linhas adicionais.

O shape é divisível por 512 — $248{,}320 = 512 \times 485$ —, algo conveniente para sharding, isto é, dividir uma matriz entre várias GPUs, muitas vezes em fatias iguais. Mas os artefatos publicados não informam por que esse tamanho exato foi escolhido, que sinal de treino as linhas não mapeadas receberam nem como todo servidor trata seus logits. A configuração de geração fixada não declara uma lista genérica de `suppress_tokens`. Inspecione o runtime real antes de afirmar que essas linhas são mascaradas.

:::insight
Este é um caso pequeno de um padrão que se repete pelo curso inteiro: um número na configuração de um modelo costuma ser a resposta a uma pergunta de hardware vestida com a fantasia de uma pergunta linguística. Quando encontrar uma constante estranhamente específica, pergunte por quanto ela divide antes de perguntar o que ela significa.
:::

## Quanto custa um vocabulário maior?

O tamanho do vocabulário tem um preço, e esse preço é fácil de subestimar. Cada linha é um vetor de 5120 números. Neste modelo, o embedding de entrada e a projeção de saída são matrizes separadas, e não uma matriz compartilhada, então cada linha adicional custa armazenamento duas vezes. A [aula 1.5](/pt-br/lessons/1-text-to-tensors/1.5-embeddings-meaning-as-geometry/) faz a contabilidade completa, e o total é surpreendente.

A tensão de projeto é, portanto, real. Mais entradas de vocabulário significam sequências mais curtas e attention mais barata. Também significam uma tabela maior para armazenar, carregar e multiplicar a cada passo de decodificação. Não existe resposta universalmente correta, só um ponto numa curva escolhido para um conjunto específico de idiomas, hardware e cargas de trabalho.

O tokenizer é fixado quando o treino começa, então ele faz parte do contrato do modelo, e não é uma conveniência de pré-processamento. A matriz de embeddings tem uma linha por entrada do vocabulário, e essas linhas aprenderam seus valores sob um mapeamento específico de texto para ids. Troque o tokenizer depois e todo id aponta para uma linha que aprendeu outra coisa. É por isso que você não pode misturar os pesos de um modelo com o tokenizer de outro, por mais parecidos que os dois pareçam.

:::warning
Tokens não carregam significados fixos de dicionário, mas é comum supor que carregam, de modo que uma divisão estranha seria uma falha de compreensão. Tokens são embalagem, não semântica. Um modelo lida perfeitamente bem com uma palavra picada em quatro fragmentos estranhos se as camadas acima aprenderam a remontá-la, e pode lidar mal com uma palavra que chegou como um token único e limpo. O que fronteiras de token determinam de forma confiável é *custo* e *comprimento*, não significado. Elas também têm efeitos de segunda ordem: aritmética fica mais difícil quando os dígitos se agrupam de forma inconsistente, e sequências de bytes incomuns dão a prompt injections onde se esconder.
:::

## Quatro perguntas para fazer a qualquer tokenizer

Quando você inspeciona um tokenizer, quatro perguntas resolvem a maior parte do que importa:

1. Ele consegue representar o texto válido que sua interface aceita?
2. Quantas linhas de tensor há, e quantos ids os artefatos do tokenizer mapeiam?
3. Quantos tokens o texto típico dos seus idiomas exige?
4. Os idiomas e domínios com que você se importa são divididos em pedaços com a mesma eficiência que os outros?

Essas perguntas mostram por que tokenization é mais que pré-processamento. Ela fixa o alfabeto disponível ao modelo e define o preço de toda sequência que esse modelo vai processar na vida.
