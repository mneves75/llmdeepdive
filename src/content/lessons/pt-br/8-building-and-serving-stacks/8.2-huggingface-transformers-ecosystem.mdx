Um colega relata que o Qwen3.8-27B "ignora o botão de thinking": ele desliga, o modelo raciocina mesmo assim, e a flag parece decorativa. Outro relata que o mesmo script dava respostas diferentes no mês passado e hoje dá outras, sem nenhuma mudança de código. Os dois bugs são reais, e nenhum está no modelo. Os dois vivem na fina camada de encanamento entre os pesos no Hub (o site da Hugging Face que hospeda modelos) e o texto na tela.

Essa camada tem quatro partes: quais bytes você baixou, como eles foram carregados, como sua conversa virou uma string e como os tokens foram amostrados. A [aula 8.1](/pt-br/lessons/8-building-and-serving-stacks/8.1-pytorch-the-reference-runtime/) deu o runtime; esta aula cobre tudo que está enrolado em volta dele.

## Quais bytes você realmente baixou?

Um repositório do Hub como `Qwen/Qwen3.8-27B` é um repositório git com arquivos grandes. Um identificador de repositório sozinho nomeia um branch, não um snapshot. Então carregar sem fixar uma revisão significa "o que quer que main aponte quando o cache de download falhar". É por isso que o mesmo script deriva ao longo dos meses: o fornecedor publica uma correção de tokenizer ou um ajuste de config, e o seu próximo download pega a mudança.

A correção é a mesma que você já usa para dependências. Fixe um hash de commit, registre-o ao lado dos seus resultados de avaliação e trate o diretório do modelo como um artefato com versão, exatamente como você faria com uma imagem de contêiner.

## Como o safetensors carrega 54 GB com segurança?

O Qwen3.8-27B é distribuído em safetensors bf16, e o safetensors é deliberadamente sem graça. Um arquivo é um header JSON listando cada tensor com seu dtype (tipo numérico), shape e faixa de bytes, seguido de um único blob contíguo de números brutos. Carregar é um mapeamento de memória (pedir ao sistema operacional que exponha o arquivo como memória, lendo as páginas só quando são tocadas) mais fatiamento. Nada é desserializado em objetos Python, então nenhum código do arquivo chega a rodar.

Os 54 GB de pesos em bf16 são divididos em vários arquivos chamados shards, com um arquivo de índice mapeando cada nome de tensor para o seu shard. Foi assim que a [aula 4.14](/pt-br/lessons/4-transformer/4.14-reading-real-weights/) conseguiu abrir pesos reais e encontrar `model.layers.31.mlp.gate_proj.weight` sem carregar os outros cinquenta gigabytes. Daí vêm três consequências práticas:

- O carregamento é rápido, porque as páginas chegam sob demanda.
- Um checkpoint malicioso não pode executar no load como um pickle pode. (Pickle é o formato de serialização de objetos do Python, e despicklar pode rodar código arbitrário.)
- Os nomes de tensor são uma interface pública estável. Scripts de conversão e adaptadores LoRA dependem deles.

## Como as mensagens viram tokens?

Agora a parte que causa o bug relatado. O Qwen3.8-27B é um modelo de chat, e modelos de chat são treinados sobre um layout de string muito específico: marcadores de papel, fronteiras de turno e os special tokens que marcam onde um bloco de thinking começa e termina. Esse layout não está embutido nos pesos e não está na config do modelo. É um template Jinja (uma linguagem de templates de texto) distribuído *junto com o tokenizer*, e `apply_chat_template` é a função que o renderiza.

Você entrega ao `apply_chat_template` uma lista de dicionários com papéis e conteúdos. Ele devolve exatamente a string que o modelo foi treinado a continuar, e tokenizar essa string dá os ids para o forward pass. O modelo nunca vê um papel. Ele vê tokens.

É aí que `enable_thinking` mora. É uma variável consumida pelo template. Não é um parâmetro do modelo e não é um argumento do loop de geração. Defini-la como false faz o template renderizar um prompt cujo andaime suprime o bloco de thinking; defini-la como true (o padrão) renderiza a versão que convida a um. Pesos idênticos, forward pass idêntico, tokens de entrada diferentes. Então a sequência é:

1. Monte as mensagens.
2. Chame o template com `add_generation_prompt=True` e sua escolha de thinking, e tokenize.
3. Desempacote o encoding devolvido em `generate()`.

```python
inputs = tok.apply_chat_template(
    messages,
    add_generation_prompt=True,
    enable_thinking=False,
    return_dict=True,
    return_tensors="pt",
).to(model.device)
out = model.generate(
    **inputs,
    do_sample=True,
    temperature=0.7,
    top_p=0.80,
    top_k=20,
    min_p=0.0,
    repetition_penalty=1.0,
    max_new_tokens=256,
)
```

Este trecho supõe que `tok` e um `model` em um único device foram carregados da mesma revisão fixada e que `messages` já está definido. No Transformers v5, `apply_chat_template(..., return_tensors="pt")` devolve um `BatchEncoding`, então passá-lo como argumento posicional `ids` falha; `**inputs` fornece tanto `input_ids` quanto `attention_mask`. `do_sample=True` também é necessário, senão temperature, top-p, top-k e min-p não têm efeito no decoding. O limite de comprimento fica explícito para que um exemplo copiado tenha uma fronteira finita.

:::warning
Montar a string do prompt na mão é a maneira mais comum de quebrar um modelo de chat, e nada avisa que isso aconteceu. Um prompt que é apenas *parecido* com o layout treinado ainda produz texto fluente, então nada quebra e nenhum erro aparece. O que você obtém é um modelo operando fora da distribuição em que foi instruction-tuned, com um botão de thinking que não faz nada porque nenhum template chegou a rodar. Renderize o template, depois logue a string renderizada uma vez e leia.
:::

## Trocar de template, e por que tool calls também são texto

Como o template é um arquivo, e não uma propriedade dos pesos, as pessoas também o **redistribuem e substituem**. Alguns repositórios não contêm peso nenhum, só um `chat_template.jinja` e uma nota sobre o que ele muda. O GGUF carrega o template no seu header de metadados, e conversões MLX o mantêm ao lado do tokenizer, então um único arquivo desses pode ser apontado para o mesmo modelo sob vários runtimes diferentes.

O que um template trocado compra é real, mas limitado. Ele pode mudar o enquadramento do system, o scaffolding em torno de um bloco de thinking e como as definições de tools são dispostas, de modo que pode encurtar respostas de forma mensurável ou mudar o formato delas. Ele não muda o que o modelo sabe. Trate uma economia de tokens alegada como a [aula 0.8](/pt-br/lessons/0-orientation-and-foundations/0.8-how-to-read-ml-paper/) ensina a tratar qualquer número de benchmark: pergunte qual modelo, qual harness, quantas amostras e contra qual template de base. Lembre também que trocar o template afasta o modelo do layout em que ele foi ajustado. Isso é uma troca, com um custo do outro lado.

O tool calling anda pelo mesmo mecanismo: o modelo emite texto estruturado e o seu harness o parseia. Renderização e parsing são onde a maioria dos bugs vive, mas não são o problema todo. Uma chamada de ferramenta em produção também exige validação semântica de argumentos, autorização, idempotência e tratamento de falhas, cobertos pela [aula 15.1](/pt-br/lessons/15-tool-contracts-and-mcp/15.1-from-model-output-to-a-tool-request/) e pela [aula 16.1](/pt-br/lessons/16-agent-security-and-guardrails/16.1-threat-model-the-assistant/). O ciclo aqui tem quatro passos, e todos são texto:

1. Você passa as definições de tools ao `apply_chat_template` junto com as mensagens.
2. O template as renderiza no layout exato de special tokens que o modelo foi treinado para responder.
3. O modelo emite uma chamada estruturada como tokens comuns.
4. O seu harness converte esse trecho de volta em nome de função e argumentos, confere se os argumentos fazem sentido e se quem chamou pode rodar essa ferramenta, executa e anexa o resultado como mais uma mensagem.

Nada no forward pass sabe que existe uma tool. Então, quando o tool calling se comporta mal, o bug quase sempre está na renderização ou no parsing, não no modelo. A [aula 8.5](/pt-br/lessons/8-building-and-serving-stacks/8.5-sglang/) cobre a metade complementar: restringir o decode para que a chamada emitida tenha parsing garantido.

## Presets de sampling e controles de thinking

O sampling é a segunda falha que não produz erro. Os ajustes abaixo são os botões da [aula 7.4](/pt-br/lessons/7-inference-and-efficiency/7.4-sampling/): a temperature remodela a distribuição de probabilidade, top_p, top_k e min_p cortam os tokens improváveis, e as penalidades desencorajam repetição.

- O preset instruct completo do model card atual é temperature 0.7, top_p 0.80, top_k 20, min_p 0, presence penalty 1.5 e repetition penalty 1.0.
- O thinking mode usa temperature 1.0, top_p 0.95, top_k 20, min_p 0, presence penalty 0 e repetition penalty 1.0.

A interface bruta de `generate()` do Transformers na revisão citada suporta os campos mostrados no trecho, mas não tem argumento de presence penalty. Portanto, o trecho é uma implementação parcial e declarada do preset do card. Defina todo campo suportado, registre os não suportados e logue a requisição efetiva. Não presuma que padrões omitidos casam com o card.

O thinking tem três controles independentes:

- `enable_thinking` decide se existe um bloco de raciocínio.
- `reasoning_effort` controla a profundidade e hoje assume `xhigh` por padrão no card oficial. Os rótulos são semântica de API e template, então inspecione o template efetivo antes de comparar runtimes.
- `preserve_thinking` hoje vem true e mantém os blocos de raciocínio de turnos anteriores. Isso pode ajudar um agente, mas também faz raciocínio antigo consumir tokens de prompt em cada turno. Meça tokens e tempo do job inteiro e decida deliberadamente se esse histórico pertence ao contexto.

## Por que isso ainda não é um servidor

Nada disso é um serving stack. As requisições rodam uma depois da outra, memória é alocada por chamada, não há paginação nem continuous batching (o jeito da [aula 7.8](/pt-br/lessons/7-inference-and-efficiency/7.8-pagedattention-and-continuous-batching/) de dividir a GPU entre muitas requisições), e um segundo usuário concorrente espera. Isso é uma virtude para trabalho de corretude e uma desqualificação para produção, e é por isso que a [aula 8.4](/pt-br/lessons/8-building-and-serving-stacks/8.4-vllm/) retoma o fio com o vLLM.

O que você leva adiante é a disciplina: fixe a revisão, carregue safetensors, renderize o template, defina o preset e saiba qual dos quatro está mentindo antes de culpar o modelo.
