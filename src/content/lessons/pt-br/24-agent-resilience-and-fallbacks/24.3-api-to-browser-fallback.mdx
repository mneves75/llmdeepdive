A API de relatórios do fornecedor respondia `GET /v1/reports/2026-03` com as linhas de compra de março. Neste mês ela responde 410 Gone, e o dono da API anunciou a aposentadoria meses atrás. O mesmo relatório continua no portal legado que a trilha 18 controlou: entrar, apertar "Download March 2026 CSV", checar o arquivo. O classificador da aula 24.1 já devolve um candidato `fallback` para essa rota. A pergunta desta aula é o que mais precisa ser verdade para que um navegador possa substituir uma API.

A regra tentadora é "se a API falhar, use o navegador". Cinco manhãs mostram por que ela está errada. Numa, a API responde 403 e a conta do portal ainda enxerga o relatório. Noutra, uma rota viva responde 404 para o pedido de outro tenant. Numa terceira, o envio de uma fatura estoura o tempo limite. Numa quarta, a conta do portal acaba sendo uma conta de administrador compartilhada. Na quinta, a execução pertence a um auxiliar que nunca teve permissão para ler relatórios. Um fallback pelo navegador em qualquer desses casos esconderia uma recusa, exporia um recurso, arriscaria uma segunda fatura, agiria com a autoridade de outra pessoa ou passaria da permissão da execução.

## Quando um desvio é permitido

Um fallback, uma segunda forma de fazer uma tarefa depois que a primeira falha, só é seguro quando faz a mesma tarefa. Num fallback da API para o navegador, isso significa que quatro coisas continuam iguais. O **escopo** da tarefa: a mesma leitura do mesmo relatório. A **identidade**: a sessão do portal age pela mesma pessoa, no mesmo tenant. As **permissões**: a sessão não tem nem mais nem menos do que a execução. A **pós-condição**, o que precisa ser verdade depois: a execução fica com as mesmas linhas verificadas que a API teria devolvido. Um fallback que mantém as quatro é um desvio para o mesmo lugar. Um que muda qualquer uma delas é outra ação, e chamá-lo de transparente esconde isso.

O gatilho precisa ser um fato conhecido. O 410 da RFC 9110 diz que o acesso "is no longer available", não está mais disponível, e que isso "is likely to be permanent", provavelmente é permanente. A RFC 8594 define um cabeçalho de resposta `Sunset`, que "indicates that a URI is likely to become unresponsive at a specified point in the future", indica que um URI deve parar de responder num momento definido no futuro, então um cliente pode saber de uma aposentadoria antes que ela aconteça. Qualquer um dos dois sinais é motivo para uma pessoa registrar a rota como aposentada e revisar um equivalente. Um 404 numa rota viva não é um sinal desses: a RFC 9110 deixa o servidor mandá-lo para esconder um recurso que quem chama não pode ver. Um navegador que enxerga mais do que a API transformaria esse recurso escondido num vazamento.

## O mesmo principal, não só a mesma empresa

O portal tem contas próprias, e a execução tem um `Principal` construído pelo controlador a partir de entrada autenticada (`agentlab.domain`). As duas precisam ser ligadas pelo runtime, nunca por um texto que um modelo escreveu, do mesmo jeito que a [aula 20.4](/pt-br/lessons/20-human-approval-and-durable-pauses/20.4-slack-and-teams-approval-adapters/) mapeou um usuário do Slack para um principal por meio de um diretório. Aqui o runtime guarda um mapa de conta do portal para principal, e a checagem exige que esse mapa devolva exatamente o principal da execução: mesmo usuário, mesmo tenant, mesmos papéis.

A igualdade importa nos dois sentidos. Uma conta do portal com menos papéis falharia no portal, o que é só um incômodo. Uma conta do portal com mais papéis, como uma conta de serviço compartilhada que também aprova faturas, deixaria a execução agir com uma autoridade que ela nunca teve. O teste `test_a_portal_account_with_more_permissions_is_refused` existe para esse caso.

## A checagem em código

<Figure id="fallback-gate" />

```python
# file: examples/agent-engineering/src/agentlab/resilience/fallback.py
def may_fall_back(verdict: Verdict, failure: Failure, *, principal: Principal, portal_account: str,
                  accounts: Mapping[str, Principal]) -> Decision:
    """Every condition must hold; the first one that fails is the reason given."""
    if verdict.action != "fallback":
        return Decision(False, f"24.1 said {verdict.action}: {verdict.reason}")
    equivalent = EQUIVALENTS.get(verdict.equivalent or "")
    if equivalent is None or equivalent.replaces != failure.route or failure.effect != "read":
        return Decision(False, f"no reviewed read equivalent for {failure.route}")
    acting = accounts.get(portal_account)
    if acting is None:
        return Decision(False, f"portal account {portal_account!r} is not mapped to a principal")
    if acting != principal:
        return Decision(False, "the portal session would act as a different principal (user, tenant or roles)")
    if equivalent.required_role not in principal.roles:
        return Decision(False, f"{principal.user_id} lacks {equivalent.required_role}, which the API route required too")
    return Decision(True, f"{equivalent.name} replaces {failure.route}", equivalent)
```

A primeira checagem reaproveita o veredito da aula 24.1, então um 401, um 403, um 404 numa rota viva e uma escrita incerta são todos recusados antes mesmo de se olhar a identidade. O motivo informado é o do próprio classificador, o que mantém o trace honesto sobre por que nenhum desvio foi tomado. A última checagem é a da tarefa proibida. O equivalente registra qual papel a rota da API exigia (`reports_reader`), e um principal sem ele não pode usar o portal para fazer o que a API teria recusado.

## Ação equivalente e a mesma pós-condição

O equivalente fixa a ação, além da permissão. `report_target("2026-03")` devolve exatamente um alvo, o botão chamado "Download March 2026 CSV", e o modelo não propõe nada. A trilha 18 deixava um modelo sugerir um papel e um nome porque estava explorando uma página desconhecida. Um fallback revisado não é exploração. Uma pessoa decidiu que esse único botão equivale à rota aposentada, e qualquer outra coisa seria uma ação que ninguém revisou.

A pós-condição é checada como a [aula 18.5](/pt-br/lessons/18-computer-use-and-gui-automation/18.5-recover-and-verify/) checou: `fetch_report` observa, fecha um diálogo conhecido, aperta o único botão e aceita o download só se `validate_report` concordar que ele é o relatório do período pedido. `read_report` devolve linhas do navegador só quando esse resultado é `done`. Caso contrário, não devolve resultado, e informa o motivo. No teste de navegador, a exportação de junho é um arquivo bem formado com as linhas de março: a checagem permite a tentativa, o portal entrega o arquivo, a verificação o rejeita, e a execução termina sem nada, em vez de terminar com o mês errado. O desvio foi percorrido e não chegou ao destino, então não conta.

## Por que escritas nunca usam o fallback

Uma escrita incerta é classificada como `reconcile` pela aula 24.1, então nunca chega a esta checagem como candidata. Uma rota de escrita aposentada também é recusada, mesmo que alguém tenha registrado um equivalente para ela. Dois motivos tornam essa regra fixa. Primeiro, a [aula 20.2](/pt-br/lessons/20-human-approval-and-durable-pauses/20.2-bind-approval-to-one-operation/) vinculou uma aprovação a uma operação: o id dela e a hash de um rascunho exato. Um formulário enviado pelo navegador é outra operação, e a aprovação não se estica para cobri-la. Segundo, um formulário de portal não tem chave de idempotência. Se o envio estourar o tempo limite, a execução não consegue perguntar ao portal o que ele registrou, como a reconciliação da aula 14.4 pergunta ao serviço de contas a pagar, então um retry poderia criar uma segunda fatura. Uma escrita que precisa mudar de canal pede uma integração nova, revisada por alguém, com aprovação própria. Enquanto ela não existir, uma pessoa faz o envio.

:::note
`read_report` não tenta de novo. Repetir a chamada à API é papel do `call_with_retries` da aula 24.2, que roda antes de um fallback sequer ser considerado, porque um 503 é motivo para esperar, não para pegar outra estrada.
:::

## Rode o exercício

A partir de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest tests/test_resilience_fallback.py`. A saída termina com `Ran 11 tests` e `OK`. Um navegador falso registra cada chamada, então cada teste de recusa confere que o navegador nunca foi acionado, e `test_a_retired_route_falls_back_to_the_fixed_button_as_the_same_principal` é o controle positivo que mostra que a checagem consegue abrir.

A metade de navegador roda o portal sintético de verdade no Chromium: `uv run --frozen python -m unittest discover -s tests_browser -p "test_resilience_fallback.py"` termina com `Ran 3 tests` e `OK`. `test_a_retired_route_is_served_by_the_portal_and_verified` compara as linhas com os registros de compra do tenant-a, `test_a_403_never_reaches_the_portal` confere que o portal não entregou nenhuma exportação, e `test_a_fallback_file_that_fails_its_checks_is_no_result` é o caso de junho.

Quebre o código: em `may_fall_back`, troque `if acting != principal:` por `if acting.tenant_id != principal.tenant_id:` e rode o arquivo da suíte principal. Os testes de outro usuário e de permissões a mais falham os dois, porque agora uma conta de serviço do mesmo tenant pode agir pela execução. Restaure a linha.
