O classificador da aula 24.1 diz que vale repetir um 503 numa leitura, e ele está certo. Mesmo assim, na simulação do curso, 26 tarefas chegam durante a queda, e cada uma faz 5 tentativas. Nas duas execuções, as tarefas que chegaram durante a queda falham e todas as tarefas depois dela dão certo. Os limites reduzem a carga sobre o provedor sem perder nenhum trabalho útil.

## Por que retries podem piorar uma queda

Um retry (nova tentativa) é uma aposta de que a falha foi breve. Durante uma falha longa, cada retry é carga extra num sistema que já está sobrecarregado, e essa carga pode mantê-lo fora do ar. O capítulo do Google sobre falhas em cascata, escrito por Mike Ulrich, mostra a multiplicação: se três camadas de uma pilha repetem 3 vezes cada, uma única ação do usuário pode virar 4 × 4 × 4 = 64 tentativas no banco de dados lá embaixo. O conselho do capítulo é "always use randomized exponential backoff", sempre usar backoff exponencial com aleatoriedade, "limit retries per request", limitar os retries por pedido, considerar "a server-wide retry budget", um orçamento de retries para o servidor inteiro, e evitar repetir em várias camadas.

O momento importa tanto quanto a quantidade. Clientes que falharam no mesmo instante e esperam o mesmo tempo repetem no mesmo instante, então o servidor vê o pico original de novo, e de novo. Essas ondas sincronizadas são o que se chama de tempestade de retries (*retry storm*).

## Backoff exponencial com full jitter

O backoff exponencial dobra a espera depois de cada falha, até um limite. O jitter acrescenta aleatoriedade para que os clientes se espalhem. O artigo de Marc Brooker no AWS Architecture Blog, de 2015, comparou variantes numa simulação e concluiu que o backoff sem jitter "is the clear loser", é o perdedor claro: ele "takes more work", dá mais trabalho, e "more time than the jittered approaches", leva mais tempo do que as abordagens com jitter. Entre as duas melhores variantes o veredito ficou dividido: o "Full Jitter" usa menos trabalho, mas um pouco mais de tempo, do que o "Decorrelated Jitter". O curso usa o full jitter porque é o mais simples dos dois. A fórmula, como está escrita no simulador do artigo, sorteia uma espera uniforme entre zero e o exponencial limitado:

```python
# file: examples/agent-engineering/src/agentlab/resilience/retry.py
def full_jitter(attempt: int, *, base_s: float, cap_s: float, rng: random.Random) -> float:
    """Seconds to wait before retry number ``attempt + 1``: uniform between zero and the capped exponential."""
    return rng.uniform(0.0, min(cap_s, base_s * 2**attempt))
```

Com `base_s=0.5`, a quarta tentativa (`attempt=3`) espera algo entre 0 e 4 segundos, cerca de 2 em média. O teste sorteia 1.000 esperas de um gerador com semente fixa e confere o intervalo, a média e que as esperas estão espalhadas. O gerador é passado como argumento, então a mesma semente sempre dá as mesmas esperas e o teste nunca depende de sorte.

Quando o servidor manda `Retry-After`, a espera é a maior entre o valor com jitter e o atraso pedido pelo servidor. Um servidor que pede mais do que a chamada pode esperar (`max_wait_s`, 60 segundos por padrão) encerra a chamada com stop em vez de dormir, porque uma execução com prazo não pode passar uma hora esperando.

## Um orçamento de retries para o processo inteiro

O limite de tentativas vale para uma chamada, enquanto um orçamento de retries vale para tudo o que um processo faz. O exemplo do capítulo de SRE é "only allow 60 retries per minute in a process", permitir só 60 retries por minuto num processo, e, passado isso, falhar o pedido em vez de repetir. `RetryBudget` guarda os horários dos retries recentes e recusa um novo quando `limit` retries já caem dentro da última `window`.

O orçamento pega uma falha que o breaker, mais abaixo, não pega. No teste do orçamento, o provedor falha uma chamada sim, outra não. Um breaker que conta falhas consecutivas nunca abre, porque cada sucesso zera a contagem. Com um orçamento de 3 retries por minuto, seis tarefas fazem três retries entre elas, e a quarta tarefa que precisa de um recebe um stop cujo motivo diz que o orçamento de retries acabou. Um minuto depois a janela andou e os retries voltam a ser permitidos.

## O circuit breaker

A descrição de Martin Fowler, de 2014, é curta: "You wrap a protected function call in a circuit breaker object, which monitors for failures", você envolve uma chamada protegida num objeto circuit breaker, que monitora as falhas. Quando as falhas chegam a um limite, "the circuit breaker trips", o breaker desarma, e as chamadas passam a falhar na hora, sem chegar à dependência. Depois de uma pausa o breaker fica "half open", meio aberto, pronto "to make a real call as trial to see if the problem is fixed", para fazer uma chamada real de teste e ver se o problema foi resolvido. Um teste bem-sucedido reinicia o breaker, e um teste que falha recomeça a pausa.

<Figure id="circuit-breaker-states" />

```python
# file: examples/agent-engineering/src/agentlab/resilience/retry.py
    def allow(self) -> bool:
        if self.state == "open" and self.opened_at is not None and self.clock() - self.opened_at >= self.open_for:
            self.state, self.trial_running = "half_open", False
        if self.state == "closed":
            return True
        if self.state == "half_open" and not self.trial_running:
            self.trial_running = True
            return True
        return False

    def record(self, *, ok: bool) -> None:
        if ok:
            self.state, self.failures, self.trial_running = "closed", 0, False
            return
        self.failures += 1
        if self.state == "half_open" or self.failures >= self.threshold:
            self.state, self.opened_at, self.trial_running = "open", self.clock(), False
```

Duas escolhas em `call_with_retries` importam. O breaker conta uma falha só quando o veredito da 24.1 é retry ou reconcile. Um 403 ou um 404 quer dizer que a dependência respondeu direito, então conta como saudável. E um breaker que recusa uma chamada devolve um stop cujo motivo começa com "circuit open", que quem chamou pode informar como degradado em vez de falho.

No teste da queda o breaker tem `threshold=5` e uma pausa de 30 segundos. A primeira tarefa faz cinco tentativas, gastando quatro retries do orçamento, e a quinta falha abre o breaker. As duas tarefas seguintes não fazem chamada nenhuma. Depois, a cada 30 segundos mais ou menos, uma tarefa faz uma única chamada de teste, que falha e reabre o breaker. São 9 testes somados às 5 primeiras falhas, 14 ao todo, e a primeira tarefa depois da recuperação dá certo. O breaker e o orçamento são objetos simples num processo, então vários processos de worker teriam cada um o seu. Compartilhar um entre processos exige estado compartilhado, o mesmo problema que a aula 24.4 resolve para o dinheiro.
