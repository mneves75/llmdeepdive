Rodar um modelo de linguagem no próprio computador ([aula 7.12](/pt-br/lessons/7-inference-and-efficiency/7.12-running-models-locally/)) executa o modelo de 27B do curso em hardware nativo — cortando custos de nuvem e mantendo rascunhos privados longe de servidores remotos, mas ainda pedindo instalação de binários ou uso de terminal. Trazer a inferência local para dentro de uma aba do navegador elimina qualquer instalação, ao custo de um modelo muito menor: em vez do modelo nativo de 27B da aula 7.12, este laboratório de navegador roda o **Qwen3-0.6B**, escolhido para caber na memória e no orçamento de download de uma única aba. Quem acessa clica em um link ou abre um arquivo HTML salvo, aguarda uma única vez o download dos pesos e conversa dentro da sandbox de segurança do próprio navegador, sem servidor de inferência nem chave de API.

Para entender como uma aba faz isso sem congelar nem vazar prompts, esta trilha percorre um aplicativo real completo no repositório: `examples/qwen-local-lab/`. Todos os números desta trilha descrevem esse sistema de navegador rodando o **Qwen3-0.6B** — um modelo compacto de 0,6 bilhão de parâmetros, com 28 camadas de transformer e dimensão oculta de 1.024, diferente do modelo muito maior Qwen3.8-27B usado como referência nas trilhas anteriores. Embora o Qwen3-0.6B suporte nativamente uma janela de contexto de 32.768 tokens, o laboratório configura deliberadamente **2.048 tokens** (`CONTEXT_SIZE = 2048`) para manter o cache KV controlável na memória do navegador.

## Por que uma aba se divide em cinco camadas

Uma página web não funciona como um programa de linha de comando dono da máquina inteira. Toda aba começa com uma única **thread principal** — uma fila sequencial encarregada de desenhar pixels, ouvir teclas e responder a cliques. Se você rodar multiplicações de matrizes nessa thread principal, o navegador não consegue redesenhar a tela nem perceber um clique em **Stop** até a conta terminar.

O diagrama abaixo mapeia as cinco camadas que mantêm o Qwen Local Lab fluido e auditável. Duas regras sustentam essa fronteira: `src/app.js` renderiza cada token gerado com `textContent` em vez de `innerHTML` (impedindo que a saída do modelo execute como HTML) e guarda o histórico só na memória da aba salvo quando o usuário marca **Remember this conversation** (`localStorage`), enquanto `src/inference-worker.js` isola o cálculo pesado atrás de chamadas RPC via `postMessage` marcadas com `id` inteiro e substitui `self.fetch` ao fim da carga para lançar erro diante de qualquer requisição `http:` ou `https:` durante a geração.

Dentro do artefato único de 15,66 MB (`dist/index.html`, 15.658.412 bytes), esse worker conduz dois runtimes embutidos — `wllama` 2.3.7 (compilação em WebAssembly do `llama.cpp`, que cria seu próprio worker interno de cálculo) e `WebLLM` 0.2.89 (WebGPU) — além do `hash-wasm` 4.13.0 para conferência de integridade. Os pesos do Qwen3-0.6B permanecem fora do HTML, entrando apenas após clique explícito em **Load model** ou pela File API do navegador, apoiados na Cache API de melhor esforço (que o navegador pode limpar quando falta espaço em disco).

## Inicializando código embutido sem servidor

Como o aplicativo inteiro é entregue em um único documento HTML autocontido, não existem arquivos `.js` ou `.wasm` avulsos ao lado dele em um servidor. Em vez disso, o build embute os cinco binários de terceiros e o código do worker como blocos de texto **base64** (uma codificação que representa bytes binários usando caracteres ASCII imprimíveis) dentro de elementos ocultos no HTML.

Antes de olhar o código abaixo, veja o papel das duas funções. `embeddedAssets()` decodifica cada motor embutido uma única vez para uma **URL `blob:`** temporária em memória (um endereço que aponta para bytes já presentes no navegador, sem tráfego de rede). `ensureWorker()` converte o script do worker embutido em sua própria URL `blob:`, inicia o Web Worker dedicado, conecta o recebimento de mensagens e garante uma limpeza segura caso o worker caia inesperadamente.

```js
// file: examples/qwen-local-lab/src/app.js
function embeddedAssets() {
  if (state.assets) return state.assets;
  state.assets = {
    wllama:blobFromBase64('asset-wllama','text/javascript'),
    webllm:blobFromBase64('asset-webllm','text/javascript'),
    singleWasm:blobFromBase64('asset-single-wasm','application/wasm'),
    multiWasm:blobFromBase64('asset-multi-wasm','application/wasm'),
    hashwasm:blobFromBase64('asset-hashwasm','text/javascript'),
  };
  return state.assets;
}

function ensureWorker() {
  if (state.worker) return state.worker;
  const workerURL = blobFromBase64('asset-worker','text/javascript');
  const worker = new Worker(workerURL,{type:'module',name:'qwen-local-inference'});
  worker.onmessage = event => { if (state.worker === worker) onWorkerMessage(event.data); };
  worker.onerror = event => {
    if (state.worker !== worker) return;
    event.preventDefault();
    const message = event.message || 'The inference worker stopped unexpectedly. Reload the model to retry.';
    if (state.current) finishGeneration(null, message);
    for (const pending of state.pending.values()) pending.reject(new Error(message));
    state.pending.clear();
    destroyWorker();
    showError(message);
    setPhase('error');
  };
  state.worker = worker;
  return worker;
}
```

Repare na guarda `if (state.worker === worker)` dentro de `onmessage` e `onerror`. O usuário pode clicar em **Unload** ou **Stop**, encerrando um worker antigo e criando um novo milissegundos depois. Conferir a identidade do objeto garante que um evento atrasado de um worker já encerrado nunca corrompa o estado da nova sessão.

## Por que os motores ficam no HTML e os pesos ficam fora

Uma primeira dúvida natural é por que o aplicativo empacota 15,66 MB de código dos motores dentro do `dist/index.html`, mas se recusa a empacotar os pesos do modelo no mesmo arquivo. A resposta aparece direto na aritmética de transferência.

Os cinco binários de runtime embutidos somam 11.659.803 bytes brutos (11,66 MB); depois da expansão em base64 e do código da interface, o `dist/index.html` chega a **15,66 MB** (15.658.412 bytes). Em contraste, o arquivo de CPU do Qwen3-0.6B (`Qwen3-0.6B-Q8_0.gguf`) tem **639,45 MB** (639.446.688 bytes), e o pacote de GPU do WebLLM (`Qwen3-0.6B-q4f16_1-MLC`) soma cerca de **335,37 MB** de fragmentos de pesos em 4 bits mais **11,42 MB** de tokenizer, configuração e biblioteca compilada (**346,79 MB** no total).

Na primeira carga fria de um visitante, o total de bytes que atravessa a rede é o HTML base somado apenas ao conjunto de pesos escolhido:

$$
T_{\text{CPU}} = 15.66 + 639.45 = 655.11\ \text{MB}
$$

$$
T_{\text{GPU}} = 15.66 + 335.37 + 11.42 = 362.45\ \text{MB}
$$

Manter os pesos fora do HTML traz dois ganhos práticos de engenharia. Primeiro, quem usa o modo GPU nunca baixa o arquivo CPU de 639,45 MB, e quem usa o modo CPU nunca baixa o pacote GPU de 346,79 MB. Segundo, o navegador precisa analisar um arquivo HTML inteiro como texto antes de rodar os scripts; embutir um binário de 639,45 MB em base64 somaria ~852,6 MB de texto à casca de 15,66 MB — gerando um arquivo HTML de cerca de 868 MB antes de qualquer código executar, como calcula em detalhe a [aula 34.2](/pt-br/lessons/34-a-model-in-your-browser/34.2-inside-the-gguf-file/).

## Onde a fronteira de rede realmente está

A frase "roda localmente no navegador" costuma gerar mal-entendidos, por isso convém traçar a fronteira com precisão. Ao abrir uma cópia hospedada do Qwen Local Lab e clicar em **Load model**, a aba **cruza sim** a rede para buscar os pesos fixados no Hugging Face (e, no modo GPU, uma biblioteca compilada fixada em `raw.githubusercontent.com`). A verificação SHA-256 de arquivo inteiro cobre o GGUF oficial de CPU (639,45 MB) e a `model_lib` WASM fixada de GPU (6,56 MB), enquanto os fragmentos de pesos de GPU, o tokenizer e a configuração do WebLLM são fixados por revisão via HTTPS em vez de re-hasheados pelo nosso worker. Depois de carregados no worker, a geração não faz nenhuma requisição HTTP — os prompts digitados e os tokens produzidos nunca saem do aparelho.

Duas ressalvas continuam valendo depois da carga. Primeiro, ao usar uma URL hospedada e ficar offline depois, conseguir reabrir a página depende de o navegador ter preservado o HTML e os pesos em cache; a remoção automática de cache fica fora do controle do aplicativo. Segundo, um fluxo sem rede — exportar a página limpa pelo botão **Save HTML**, guardar um arquivo `.gguf` compatível do Qwen3-0.6B ao lado dela no disco e reabri-lo e carregá-lo offline no modo CPU — está implementado no aplicativo, mas continua sem verificação ponta a ponta (veja a [aula 34.8](/pt-br/lessons/34-a-model-in-your-browser/34.8-measuring-browser-inference/)). As próximas três aulas abrem cada camada por dentro: o formato do arquivo GGUF de 639,45 MB, o seletor duplo de WebAssembly e WebGPU e o pipeline de SHA-256 em streaming que protege cada byte baixado.
