Navegadores rodam em máquinas muito diferentes entre si. Uma pessoa abre o seu link em um notebook recente com placa gráfica rápida; outra abre em um navegador corporativo restrito ou em uma máquina virtual na nuvem sem GPU alguma. Olhar a string `User-Agent` (o nome e a versão que o navegador declara) falha o tempo todo, porque drivers, ajustes de privacidade e cabeçalhos de hospedagem podem desligar recursos de hardware em qualquer navegador. Por isso, o Qwen Local Lab embarca dois motores completos na mesma aba — **WebLLM** para GPU e **wllama** para CPU — e escolhe entre eles testando capacidades reais em tempo de execução.

Ponto fundamental: CPU (`wllama`) e GPU (`WebLLM`) são **rotas alternativas mutuamente exclusivas** a cada carregamento, e não estágios sequenciais — cada clique em **Load model** inicializa apenas um motor e baixa apenas os pesos daquela rota. Embora o diagrama abaixo organize as checagens de capacidade da esquerda para a direita, a aba segue o ramo de GPU *ou* o ramo de CPU, nunca os dois em sequência.

## Testando SIMD e exceções do WebAssembly antes do download

**WebAssembly (WASM)** é um formato binário compacto de instruções que o navegador compila em código de máquina veloz para a CPU. Rodar o `llama.cpp` em WebAssembly depende de duas extensões específicas: **SIMD** (*Single Instruction, Multiple Data*, que permite a uma instrução de CPU multiplicar ou somar um vetor inteiro de números em paralelo) e **exceções WASM** (tratamento estruturado de erros compilado a partir de C++).

Em vez de baixar 639,45 MB de pesos GGUF só para travar em um navegador antigo, `validateWasmSupport()` chama `WebAssembly.validate()` em dois módulos WASM mínimos montados à mão — 31 bytes para SIMD e 28 bytes para exceções. Repare que ambos começam com `[0, 97, 115, 109]`, os bytes mágicos ASCII `\0asm` do WebAssembly. Se qualquer sonda retornar `false`, o modo CPU falha em menos de um milissegundo com uma mensagem clara.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
function validateWasmSupport() {
  const simd = [0,97,115,109,1,0,0,0,1,5,1,96,0,1,123,3,2,1,0,10,10,1,8,0,65,0,253,15,253,98,11];
  const exceptions = [0,97,115,109,1,0,0,0,1,4,1,96,0,0,3,2,1,0,10,8,1,6,0,6,64,25,11,11];
  if (typeof WebAssembly === "undefined" ||
      !WebAssembly.validate(new Uint8Array(simd)) ||
      !WebAssembly.validate(new Uint8Array(exceptions))) {
    throw new AppError("This browser does not support the WebAssembly SIMD and exception features required by CPU mode. Use an up-to-date desktop browser.", "WASM_UNSUPPORTED");
  }
}
```

## Por que cabeçalhos HTTP definem 1 thread de CPU contra 4

Passar pelo teste de SIMD permite que o modo CPU funcione, mas uma segunda regra de segurança do navegador controla quão rápido ele vai rodar. Inferência paralela em CPU precisa de **SharedArrayBuffer**, um bloco de memória compartilhada que várias threads WebAssembly leem ao mesmo tempo sem duplicar 639 MB de pesos para cada thread. Como temporizadores precisos sobre memória compartilhada podem ser abusados em ataques de canal lateral da classe Spectre, os navegadores só liberam `SharedArrayBuffer` sob **isolamento entre origens** (*cross-origin isolation*).

Uma página só entra em isolamento entre origens (`crossOriginIsolated === true`) quando o servidor web envia dois cabeçalhos HTTP reais na resposta: `Cross-Origin-Opener-Policy: same-origin` (COOP) e `Cross-Origin-Embedder-Policy: require-corp` (COEP). Tags `<meta>` no HTML não conseguem ativar esse estado — o navegador exige cabeçalhos HTTP. O Qwen Local Lab lê `crossOriginIsolated` e escolhe o número de threads de CPU de forma direta:

$$
n_{\text{threads}} = \begin{cases} \min(\text{hardwareConcurrency},\ 4) & \text{se } \text{crossOriginIsolated} = \text{true} \\ 1 & \text{se } \text{crossOriginIsolated} = \text{false} \end{cases}
$$

Com isolamento ativo, o `wllama` carrega seu binário embutido `multi-thread/wllama.wasm` (2.189.054 bytes) e limita o paralelismo a **4 threads** para que uma aba de chat em segundo plano nunca sufoque o restante do sistema operacional. Quando uma hospedagem estática comum omite cabeçalhos COOP/COEP, o worker recua para **1 thread** usando `single-thread/wllama.wasm` (2.158.740 bytes) em vez de quebrar.

## WebGPU, `shader-f16` e fixação da biblioteca compilada

Quando o dispositivo possui uma placa gráfica compatível, a **WebGPU** deixa o navegador executar matemática matricial paralela direto nos núcleos da GPU por meio de **shaders** de computação (pequenos programas executados em milhares de threads da GPU ao mesmo tempo). A rota de GPU do Qwen Local Lab roda `Qwen3-0.6B-q4f16_1-MLC` via WebLLM 0.2.89: cerca de **335,37 MB** de fragmentos de pesos quantizados em 4 bits mais **11,42 MB** de tokenizer, configuração e biblioteca compilada do modelo. A documentação de origem estima cerca de **1,4 GB** de memória de trabalho na GPU para contexto de 4.096 tokens; este laboratório configura 2.048 tokens, e o tamanho do download é sempre menor que a memória de trabalho ativa.

Uma checagem de hardware decide se o modo GPU pode iniciar: **`shader-f16`** (aritmética nativa de ponto flutuante de 16 bits dentro de shaders da GPU). Como `q4f16_1` desquantiza pesos de 4 bits para floats de 16 bits durante a multiplicação de matrizes, um adaptador sem `shader-f16` não consegue executar esses shaders. O modo Auto exige tanto um retorno válido de `requestAdapter()` quanto `adapter.features.has("shader-f16")`. Se a inicialização da GPU falhar depois que o usuário clica em Load, o aplicativo exibe o erro e oferece tentativa explícita em CPU em vez de iniciar em silêncio um segundo download de 639 MB.

Há também um detalhe de cadeia de suprimentos fácil de deixar passar no WebLLM 0.2.89. O registro pré-configurado do WebLLM busca a biblioteca WebAssembly compilada do modelo (`Qwen3-0.6B-q4f16_1_cs1k-webgpu.wasm`) no branch mutável `main` de `mlc-ai/binary-mlc-llm-libs`. Qualquer commit futuro enviado ao `main` alteraria silenciosamente código executável dentro da aba do usuário. No trecho abaixo, `loadGpu()` confere `navigator.gpu` e `shader-f16`, baixa a biblioteca do commit imutável `5b7251f3bdce957be2a7bf73a6f6c560d9874df4` por `obtainModelLibrary()` — que confirma exatamente **6.561.594 bytes** (~6,56 MB) e o SHA-256 fixado (`b277797f...`) — e entrega esses bytes exatos ao WebLLM por uma URL `blob:` temporária, revogando a URL assim que `reload()` termina.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
  if (!navigator.gpu) {
    throw new AppError("WebGPU is unavailable in this browser. Select CPU / WebAssembly mode, or use a supported browser over HTTPS or localhost.", "GPU_UNAVAILABLE");
  }
  const adapter = await navigator.gpu.requestAdapter({ powerPreference: "high-performance" });
  assertActive(op);
  if (!adapter || !adapter.features.has("shader-f16")) {
    throw new AppError("This GPU does not expose the shader-f16 feature required by the embedded Qwen3 GPU model. Select CPU / WebAssembly mode.", "GPU_UNAVAILABLE");
  }
  progress(op, 0.01, "Preparing the GPU runtime. First load downloads about 350 MB of model assets.");
  const library = await obtainModelLibrary(op, message.assets);
  const webllm = await getWebllm(message.assets);
  assertActive(op);
  // WebLLM fetches a non-http(s) model_lib with plain fetch() and skips its URL-keyed cache,
  // so it runs exactly the bytes verified above.
  const libraryUrl = URL.createObjectURL(new Blob([library], { type: "application/wasm" }));
  webllmConfig.model_list[0].model_lib = libraryUrl;
  runtime = new webllm.MLCEngine({
    appConfig: webllmConfig,
    logLevel: "SILENT",
    initProgressCallback(report) {
      progress(op, report.progress, report.text);
    },
  });
  backend = "webgpu";
  try {
    await runtime.reload(GPU_MODEL_ID, { context_window_size: CONTEXT_SIZE });
  } finally {
    URL.revokeObjectURL(libraryUrl);
  }
```

## O que esse roteamento muda na prática

Medições em ambientes específicos registradas em `examples/qwen-local-lab/VERIFICATION.md` em 26/11/2026 ilustram por que vale manter os três caminhos — encare estes números como observações por ambiente, não como benchmarks universais:

- **Chromium na nuvem, 1 thread WASM (sem COOP/COEP)**: o decode rodou entre **2,8 e 3,4 tokens por segundo**, lento o suficiente para acompanhar palavra por palavra, mas ainda totalmente funcional sem cabeçalhos especiais no servidor.
- **Apple M5 Pro, 4 threads WASM (isolamento entre origens ativo)**: o decode saltou para **43,7 a 52,1 tokens por segundo**, ritmo confortável de leitura rodando só em CPU.
- **Apple M5 Pro, WebGPU Metal-3 (`shader-f16`)**: o turno 1 rodou a **14,0 tokens por segundo** com shaders frios; no turno 2, numa continuação curta já aquecida, chegou a **133,7 tokens por segundo** (observações em dispositivo único, e não benchmarks isolados de compilação ou de regime permanente).

Ter os dois motores dentro da mesma aba transforma a diversidade de hardware em degradação elegante, em vez de uma tela quebrada. A seguir, a [aula 34.4](/pt-br/lessons/34-a-model-in-your-browser/34.4-streaming-and-verifying-weights/) mostra como o worker transmite 639,45 MB para a Cache API e verifica cada byte sem materializar um `ArrayBuffer` contíguo de 639,45 MB na memória JavaScript.
