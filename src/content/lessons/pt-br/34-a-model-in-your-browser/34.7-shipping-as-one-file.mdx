A maioria das aplicações web espalha seu código por dezenas de arquivos num servidor ou numa rede de entrega de conteúdo (CDN). Esse desenho funciona bem num site online, até alguém clicar em **Save HTML** para guardar uma cópia portátil do aplicativo de chat — ou um servidor estático perder um pedaço versionado e quebrar a página.

Em `examples/qwen-local-lab/`, o build gera um único documento determinístico, `dist/index.html`, reunindo toda a interface, os dois motores de inferência, os dois binários WebAssembly de CPU, o calculador SHA-256 em streaming e todos os avisos de licença de terceiros, usando apenas a biblioteca padrão do Python. Esta aula percorre a aritmética de bytes, a reprodução verificada de dependências, o embutimento em leitura única e a geração dupla de Content Security Policy por trás desse artefato.

## A conta do base64 nos 15,66 MB—e por que os pesos ficam de fora

HTML é um formato textual, enquanto binários WebAssembly compilados (`.wasm`) contêm bytes arbitrários que quebrariam o analisador HTML se colados direto numa tag `<script>`. Para guardar cargas binárias com segurança dentro do HTML, `scripts/build.py` codifica cada recurso embutido em **base64**, uma codificação textual que converte cada 3 bytes (24 bits) em 4 caracteres ASCII imprimíveis (6 bits cada).

Essa conversão impõe um fator exato de $\frac{4}{3} \approx 1.333$ (+33,3% de acréscimo). Como detalhado na pilha acima, os cinco binários fixados em `vendor/lock.json` (`webllm.js`, os binários WASM multi- e single-thread do `wllama`, o `wllama.js` com patch e o `hash-wasm.js`) somam **11.659.803 bytes** (**11,66 MB**) brutos. Multiplique por $\frac{4}{3}$:

$$
11{,}659{,}803 \times \frac{4}{3} \approx 15{,}546{,}404\ \text{B} \approx 15.55\ \text{MB}
$$

Como cada um dos cinco binários é codificado e preenchido em base64 separadamente até um múltiplo de 4 bytes, esses cinco blocos ocupam **15.546.408** bytes em base64 dentro do `dist/index.html` de **15.658.412 bytes** (**15,66 MB**), junto com cerca de **0,11 MB** de HTML UTF-8 puro, CSS, `src/app.js`, `src/inference-worker.js` em base64, avisos de licença e a tag `<meta>` de CSP. A pintura inicial da página não decodifica esses binários; em vez disso, `app.js` decodifica cada `<script type="application/octet-stream">` via `atob()` apenas em **Load** (dentro de `embeddedAssets()`) e entrega URLs `blob:` locais ao worker.

Agora aplique a mesma conta aos **639,45 MB** (`639.446.688` bytes) dos pesos Q8_0 GGUF do Qwen3-0.6B vistos na [aula 34.4](/pt-br/lessons/34-a-model-in-your-browser/34.4-streaming-and-verifying-weights/):

$$
639.45\ \text{MB} \times \frac{4}{3} \approx 852.6\ \text{MB}
$$

Somar esses ~852,6 MB de pesos em base64 aos ~15,7 MB dos runtimes e da interface inflaria o `dist/index.html` completo para cerca de **868 MB** — um documento HTML que navegadores penam para transformar em árvore DOM e duplicam em strings JavaScript durante `atob()`. Manter o *runtime* dentro de `dist/index.html` e os pesos na Cache API ou num arquivo GGUF local entrega portabilidade sem estourar a memória do navegador.

## Reconstruindo arquivos de terceiros sem npm install

Builds JavaScript tradicionais rodam `npm install`, trazendo centenas de dependências indiretas e scripts de instalação para a máquina. Como o `qwen-local-lab` precisa apenas de três bibliotecas pré-compiladas para navegador (`@wllama/wllama@2.3.7`, `@mlc-ai/web-llm@0.2.89` e `hash-wasm@4.13.0`), `scripts/fetch_vendor.py` baixa cada pacote compactado (*tarball*) direto de `https://registry.npmjs.org/` e confere seu resumo criptográfico **sha512** do npm antes mesmo de abrir o arquivo.

A função `check_integrity` calcula o hash SHA-512 em base64 dos bytes baixados e aborta na hora se um único bit diferir de `vendor/lock.json`.

```python
# file: examples/qwen-local-lab/scripts/fetch_vendor.py
def check_integrity(data, integrity, label):
    expected = integrity.removeprefix('sha512-')
    actual = base64.b64encode(hashlib.sha512(data).digest()).decode('ascii')
    if actual != expected:
        raise VendorError(f'{label}: tarball integrity mismatch (expected sha512-{expected}, got sha512-{actual})')
```

Depois de autenticar o pacote, `read_members` extrai apenas os arquivos regulares listados explicitamente — recusando caminhos absolutos, travessia com `..`, links simbólicos ou entradas duplicadas.

Um arquivo extraído precisa de ajuste pontual: o `wllama 2.3.7` original resolve URLs com `new URL(relativePath, document.baseURI)`, o que lança erro dentro de um Web Worker onde `document` não existe. O patch de uma linha `vendor/patches/wllama-worker-base-url.patch` troca isso por `typeof document === "undefined" ? self.location.href : document.baseURI`, sem tocar em nenhuma matemática de inferência. Para impedir que uma mudança futura aplique a edição no lugar errado, `apply_patch` exige que cada trecho case **exatamente uma vez**.

```python
# file: examples/qwen-local-lab/scripts/fetch_vendor.py
def apply_patch(text, patch_text, label):
    for old, new in parse_hunks(patch_text, label):
        count = text.count(old)
        if count != 1:
            raise VendorError(f'{label}: patch hunk matches {count} times; it must match exactly once')
        text = text.replace(old, new)
    return text
```

Por fim, `build_outputs` confere o tamanho exato em bytes e o SHA-256 de cada arquivo extraído (e ajustado) em memória contra `vendor/lock.json` antes de `run()` gravar um único arquivo em `vendor/`. Se qualquer validação falhar, o script termina com status 1 sem escrever nada.

## Uma leitura verificada em memória evita troca no meio do caminho

Quando um script de build verifica um arquivo no disco (`hash(open(path))`) e abre o mesmo caminho uma segunda vez para embuti-lo (`encode(open(path))`), cria-se uma janela de **Time-Of-Check to Time-Of-Use (TOCTOU)** — uma condição de corrida em que um arquivo adulterado poderia ser trocado entre a verificação e a montagem.

`scripts/build.py` elimina essa janela lendo cada arquivo listado para a memória uma única vez dentro de `vendor_files()`, conferindo seu SHA-256 contra `vendor/lock.json` e entregando exatamente esses bytes já em memória ao codificador base64.

```python
# file: examples/qwen-local-lab/scripts/build.py
def vendor_files(root):
    """Return the lock's verified asset bytes and notice texts, failing if any file is absent or altered."""
    lock = json.loads((root / 'vendor/lock.json').read_text(encoding='utf-8'))
    assets, notices = {}, []
    for package in lock['packages']:
        for entry in package['files']:
            path = root / 'vendor' / entry['output']
            if not path.is_file():
                raise BuildError(f'vendor/{entry["output"]} is missing; run scripts/fetch_vendor.py')
            data = path.read_bytes()
            if hashlib.sha256(data).hexdigest() != entry['sha256']:
                raise BuildError(f'vendor/{entry["output"]} does not match vendor/lock.json; run scripts/fetch_vendor.py')
            if entry['embed'] == 'notice':
                notices.append((path.name, data.decode('utf-8')))
            else:
                assets[entry['embed']] = data
    return assets, notices
```

## Gerando hashes do script e estilos para dois alvos de CSP

Como `dist/index.html` embute `src/app.js` e o CSS direto no documento, uma Content Security Policy descuidada recorreria a `'unsafe-inline'` — permitindo que qualquer tag `<script>` injetada rodasse. Em vez disso, `content_security_policy()` calcula o SHA-256 exato do único `<script type="module">` e de cada `<style>` inline e trava a política nesses resumos exatos.

```python
# file: examples/qwen-local-lab/scripts/build.py
def content_security_policy(html):
    """Return (header policy, meta policy) allowing exactly the inline blocks in html."""
    scripts = INLINE_SCRIPT.findall(html)
    if len(scripts) != 1:
        raise BuildError(f'expected exactly one inline module script, found {len(scripts)}')
    styles = ' '.join(dict.fromkeys(source_hash(style) for style in INLINE_STYLE.findall(html))) or "'none'"
    directives = [
        "default-src 'none'",
        f"script-src {source_hash(scripts[0])} blob: 'wasm-unsafe-eval'",
        'worker-src blob:',
        f'connect-src blob: {MODEL_HOSTS}',
        f'style-src {styles}',
        'img-src data:',
        "object-src 'none'",
        "base-uri 'none'",
        "form-action 'none'",
    ]
    # Browsers ignore frame-ancestors in a <meta> policy and log an error for it.
    return '; '.join(directives + ["frame-ancestors 'none'"]), '; '.join(directives)
```

Observe os dois retornos. `build.py` grava a primeira política — incluindo `frame-ancestors 'none'` — em `dist/_headers` ao lado de `Cross-Origin-Opener-Policy: same-origin` e `Cross-Origin-Embedder-Policy: require-corp` (os cabeçalhos HTTP que liberam WebAssembly multi-thread). A segunda vai para `<meta http-equiv="Content-Security-Policy">` dentro de `dist/index.html`, garantindo que até uma cópia salva sem arquivo de cabeçalhos mantenha as restrições de script, estilo, worker e rede. Retirar `frame-ancestors 'none'` da tag `<meta>` segue a especificação de CSP: navegadores ignoram essa diretiva em meta tags e exibem erro no console quando ela aparece ali.

## Quando um HTML único vence—e quando vários arquivos são melhores

Empacotar tudo num único arquivo é uma escolha deliberada de engenharia, não um padrão universal:

- **Onde um HTML único vence:** zero caminhos quebrados ao salvar via **Save HTML**, publicação atômica (sem descompasso entre um HTML antigo e um worker novo) e um único SHA-256 reproduzível para toda a aplicação.
- **Onde um build em vários arquivos vence:** transferência inicial menor (sem os 33,3% de inflação do base64, baixando só o motor escolhido em vez de `wllama` e `WebLLM` juntos), cache independente de bibliotecas inalteradas entre atualizações do app e zero custo de `atob()` ao clicar em Load.

Na [aula 34.8](/pt-br/lessons/34-a-model-in-your-browser/34.8-measuring-browser-inference/), colocamos o artefato pronto em máquinas reais, medimos a velocidade efetiva e traçamos uma linha nítida entre o que os testes provam e o que continua sem verificação.
