Baixar um modelo de 639,45 MB para dentro de uma aba do navegador chega perto do teto de memória de notebooks e celulares comuns. Se você pular a verificação de integridade, uma resposta truncada de proxy ou um cache corrompido pode entregar pesos quebrados ao WebAssembly. Por outro lado, conferir um arquivo de 639 MB do jeito mais imediato — usando a função nativa `crypto.subtle.digest()` da **WebCrypto** do navegador — pode derrubar a aba por falta de memória antes mesmo de o modelo iniciar.

## Por que o `digest()` de passada única da WebCrypto é arriscado em 639 MB

Um **hash criptográfico** como o **SHA-256** calcula uma impressão digital fixa de 256 bits para um arquivo: basta inverter um único bit em qualquer ponto dos 639.446.688 bytes para que o resumo hexadecimal de 64 caracteres mude por completo. Navegadores já trazem SHA-256 nativo em `crypto.subtle.digest()`, então por que o Qwen Local Lab embute a biblioteca `hash-wasm` 4.13.0 (216.120 bytes brutos)?

O motivo é o formato da API. `crypto.subtle.digest('SHA-256', buffer)` é uma função de **passada única**: ela exige manter toda a entrada de 639,45 MB em um único **ArrayBuffer** contíguo (um bloco contínuo de RAM). Chamar `await blob.arrayBuffer()` sobre um download de 639,45 MB materializa esse buffer contíguo inteiro de 639,45 MB em memória ao lado do `Blob` do download — antes mesmo de o `wllama` alocar sua heap WebAssembly e o cache de contexto.

O **streaming** resolve isso processando pequenos blocos de bytes conforme chegam da rede, sem esperar o arquivo inteiro caber na RAM. O Qwen Local Lab canaliza `response.body` por um **TransformStream** (um estágio de pipeline do navegador que inspeciona cada pedaço e o repassa intacto) ligado ao `createSHA256()` incremental da `hash-wasm`.

Antes de ler o código abaixo, observe as quatro proteções que rodam dentro de `hashingStream()` e `assertModelDigest()`. Cada pedaço verifica se o usuário clicou em Cancelar (`assertActive`), impõe um teto rígido de bytes para que um servidor defeituoso não envie além de `CPU_MODEL_SIZE` (639.446.688 bytes), atualiza o estado incremental do SHA-256 em memória constante minúscula e limita os avisos de progresso a cerca de uma vez a cada 120 ms antes de encaminhar o pedaço para `new Response(body).blob()`, deixando o navegador montar o `Blob` fora da heap JavaScript.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
// Hash the model chunk by chunk as it streams, so verification never holds a second model-sized buffer.
function hashingStream(op, hasher, onProgress) {
  let loaded = 0;
  let lastUpdate = 0;
  return new TransformStream({
    transform(chunk, controller) {
      assertActive(op);
      loaded += chunk.byteLength;
      if (loaded > CPU_MODEL_SIZE) {
        throw new AppError("The model download has an unexpected size. Please retry.", "INVALID_MODEL");
      }
      hasher.update(chunk);
      const now = performance.now();
      if (now - lastUpdate > 120 || loaded === CPU_MODEL_SIZE) {
        lastUpdate = now;
        onProgress(loaded);
      }
      controller.enqueue(chunk);
    },
  });
}

function assertModelDigest(hasher) {
  if (hasher.digest("hex") !== CPU_MODEL_SHA256) {
    throw new AppError("The model file does not match the official SHA-256 checksum, so it was not used. Download it again.", "INVALID_MODEL");
  }
}
```

A própria requisição de rede fixa a URL do commit exato no Hugging Face (`23749fef...`) e define `credentials: "omit"`, `cache: "no-store"` e `referrerPolicy: "no-referrer"` para que cookies, caches HTTP antigos e cabeçalhos de referência nunca interfiram no download. Somente depois que `validateGguf()` confirma 639.446.688 bytes e os bytes mágicos `"GGUF"` **e** `assertModelDigest()` confirma `9465e63a...` é que `obtainCpuModel()` chama `cache.put()`. Um download corrompido é recusado e nunca gravado na Cache API do navegador.

## Refazendo o hash dos pesos em cache antes de cada reuso

Mesmo depois de um arquivo verificado chegar à Cache API, o armazenamento em disco e os caches do navegador podem sofrer corrupção ou remoção parcial. Em vez de confiar cegamente em uma entrada salva, `obtainCpuModel()` faz cada acerto de cache atravessar de volta o mesmo `hashingStream()` até um `WritableStream` de descarte. Se tamanho, bytes mágicos ou SHA-256 falharem, o worker apaga a entrada danificada (`cache.delete(CPU_MODEL_URL)`) e segue para um novo download limpo — preservando o cancelamento do usuário por meio de `assertActive(op)`.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
    if (globalThis.caches) {
      cache = await caches.open(MODEL_CACHE_NAME);
      const saved = await cache.match(CPU_MODEL_URL);
      if (saved) {

        const blob = await saved.blob();
        const hasher = await sha256Hasher(assets);
        assertActive(op);

          await validateGguf(blob, CPU_MODEL_SIZE);

          assertModelDigest(hasher);
          modelCacheStatus = 'hit';
          modelCacheWarning = '';
          progress(op, 0.8, "Cached model verified. Preparing the CPU runtime…");
          return blob;
        } catch {
          assertActive(op);
          await cache.delete(CPU_MODEL_URL);
        }
      }
```

Recalcular o hash de 639,45 MB parece caro, mas o SHA-256 em WebAssembly corre perto da velocidade do armazenamento local. Na execução de verificação em um Apple M5 Pro (`VERIFICATION.md`, 26/11/2026), a carga fria de CPU (download de rede, SHA-256 em streaming, gravação na Cache API e inicialização em 4 threads) levou **40,93 s**, enquanto a recarga quente (leitura da Cache API, nova verificação SHA-256 completa de 639,45 MB e inicialização em 4 threads com zero requisições HTTP) levou **1,89 s**.

## Calculando o tempo do primeiro download

Como uma carga fria precisa mover centenas de megabytes pela conexão do visitante, a largura de banda domina a primeira espera. Converta o tamanho $S$ em bytes para bits ($S \times 8$) e divida pela velocidade efetiva $B$ em bits por segundo para obter o tempo idealizado de transferência:

$$
t = \frac{S \times 8}{B}
$$

Em uma conexão de 50 Mbps ($B = 50 \times 10^6\ \text{bit/s}$), compare o GGUF de CPU de 639,45 MB com o pacote GPU MLC de ~346,79 MB (~335,37 MB de pesos mais ~11,42 MB de tokenizer, configuração e biblioteca compilada):

$$
t_{\text{CPU}} = \frac{639{,}446{,}688 \times 8}{50 \times 10^6} \approx 102.3\ \text{s}
$$

$$
t_{\text{GPU}} = \frac{346{,}790{,}000 \times 8}{50 \times 10^6} \approx 55.5\ \text{s}
$$

Em 100 Mbps esses tempos idealizados caem pela metade, para cerca de 51,2 s (CPU) e 27,7 s (GPU); em 10 Mbps apenas o arquivo de CPU leva 511,6 s (mais de 8,5 minutos). Cargas reais somam sobrecarga de protocolo, gravação em disco e inicialização do motor — motivo pelo qual o Qwen Local Lab nunca inicia um download ao abrir a página e sempre exige um clique explícito em **Load model**.

## A fronteira honesta de integridade

Boa engenharia documenta o que um sistema verifica **e** onde suas checagens terminam. Nos três caminhos pelos quais pesos entram no Qwen Local Lab, a garantia de integridade varia por rota:

- **GGUF CPU Q8_0 oficial (639,45 MB)**: verificado por tamanho exato (639.446.688 bytes), bytes mágicos `"GGUF"`, SHA-256 do arquivo inteiro (`9465e63a...`) tanto no download quanto em cada acerto na Cache API, além da validação pós-carga de arquitetura, camadas e largura oculta do Qwen3-0.6B.
- **Rota GPU WebLLM (~346,79 MB no total)**: a `model_lib` WASM compilada de 6.561.594 bytes é fixada no commit `5b7251f3...`, verificada por SHA-256 (`b277797f...`) no download e no cache e entregue ao WebLLM por uma URL `blob:`. Já os fragmentos de pesos GPU (~335,37 MB), o tokenizer e a configuração vêm fixados na revisão `8c14ce481d4c692769976ad52afea453a102df19` do Hugging Face via HTTPS e ficam no cache do próprio loader do WebLLM; o nosso worker envoltório **não** refaz o hash desses fragmentos.
- **Importação de GGUF local**: arquivos escolhidos pelo usuário pulam o SHA-256 oficial do Q8_0 e o tamanho fixo para que outras quantizações compatíveis funcionem offline; recebem apenas o filtro da interface, os bytes mágicos `"GGUF"` e a verificação pós-carga de identidade do Qwen3-0.6B.

Deixar essas fronteiras explícitas permite que revisores e usuários saibam exatamente o que cada rota comprova — e onde o sistema se apoia em HTTPS, fixação de commit ou confiança no disco local.
