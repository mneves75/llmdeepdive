Quando uma aba do navegador recebe um arquivo binário de 639,45 MB — seja baixado de um servidor remoto ou escolhido no disco do usuário —, entregar bytes às cegas para um motor WebAssembly gera desperdício de memória e falhas difíceis de diagnosticar. Um proxy de rede pode devolver uma página HTML de erro no lugar dos pesos, um download pode parar na metade ou alguém pode escolher outra família de modelo por engano. Como o formato **GGUF** ([aula 8.7](/pt-br/lessons/8-building-and-serving-stacks/8.7-llama-cpp-and-gguf/)) reúne assinatura fixa, metadados estruturados e pesos quantizados em um único arquivo, o worker do navegador consegue inspecionar o que recebeu antes de gastar computação.

## Como um arquivo binário GGUF é organizado

Um **arquivo binário** é uma sequência contínua de bytes brutos (números de 0 a 255), e não texto legível por humanos. Pela especificação GGUF, o arquivo oficial de CPU do Qwen Local Lab, `Qwen3-0.6B-Q8_0.gguf` (**639.446.688 bytes**, ou 639,45 MB), reúne cinco partes seguidas: um **cabeçalho** (iniciando com os quatro **bytes mágicos** ASCII `71, 71, 85, 70` que soletram `"GGUF"`, versão do formato e contagens), **pares chave-valor de metadados** (arquitetura, hiperparâmetros e tabela do tokenizer para que o `wllama` dispense arquivos JSON separados), um **diretório de informações de tensores** (nome, forma, tipo de quantização e deslocamento de cada tensor), **preenchimento de alinhamento** (*alignment padding*) e, por fim, os **dados dos tensores quantizados**.

A pilha abaixo condensa esse formato nas três faixas principais sobre as quais o worker do navegador atua. Quase todos os 639,45 MB são pesos comprimidos da rede neural: como vimos na [aula 7.9](/pt-br/lessons/7-inference-and-efficiency/7.9-quantization-i-int8-int4-the-basics/) e na [aula 7.10](/pt-br/lessons/7-inference-and-efficiency/7.10-quantization-ii-gptq-awq-gguf-qat/), a **quantização** `Q8_0` de 8 bits reduz cada peso para inteiros menores acompanhados de fatores de escala por bloco, ficando em pouco mais de 1 byte por parâmetro nos ~0,6 bilhão de pesos ao incluir escalas e tabelas de *embedding*.

## Duas checagens: quatro bytes antes da carga, identidade depois

Antes de alocar memória WebAssembly, o worker executa `validateGguf()`. A função confere se a entrada é um **Blob** do navegador (uma referência a dados binários brutos no disco ou na memória), verifica se há pelo menos 16 bytes e se o tamanho bate com `expectedSize` quando informado, e lê apenas os bytes 0 a 3 com `blob.slice(0, 4)` para confirmar `"GGUF"`. Ler quatro bytes não custa quase nada de memória, mesmo em um arquivo de 639 MB.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
async function validateGguf(blob, expectedSize = null) {
  if (!(blob instanceof Blob) || blob.size < 16 ||
      (expectedSize !== null && blob.size !== expectedSize)) {
    throw new AppError("The model file is incomplete or has an unexpected size. Download the GGUF again.", "INVALID_MODEL");
  }
  const magic = new Uint8Array(await blob.slice(0, 4).arrayBuffer());
  if (magic[0] !== 71 || magic[1] !== 71 || magic[2] !== 85 || magic[3] !== 70) {
    throw new AppError("The selected file is not a GGUF model. Select a Qwen3-0.6B .gguf file.", "INVALID_MODEL");
  }
}
```

Passar pelos bytes mágicos prova apenas que o arquivo é *algum* modelo GGUF — não que ele é o Qwen3-0.6B. O usuário poderia escolher um modelo Llama ou um checkpoint Qwen de 4 bilhões de parâmetros, que espera outro formato de prompt ou estouraria a memória da aba. Somente depois que `runtime.loadModel()` retorna é que `validateCpuIdentity()` lê os metadados já interpretados do `wllama`, confere três campos e lança `WRONG_MODEL` se qualquer um divergir.

```js
// file: examples/qwen-local-lab/src/inference-worker.js
function validateCpuIdentity(engine) {
  const metadata = engine.getModelMetadata();
  if (metadata.meta?.["general.architecture"] !== "qwen3" ||
      Number(metadata.hparams?.nLayer) !== 28 ||
      Number(metadata.hparams?.nEmbd) !== 1024) {
    throw new AppError("This page supports Qwen3-0.6B GGUF models. The selected model has a different architecture or size.", "WRONG_MODEL");
  }
}
```

Note a diferença intencional entre um download oficial e um arquivo local importado pelo usuário. Quando o worker baixa `Qwen3-0.6B-Q8_0.gguf` do Hugging Face (ou o relê da Cache API), ele passa `expectedSize = 639446688` e também verifica o resumo criptográfico SHA-256 do arquivo inteiro ([aula 34.4](/pt-br/lessons/34-a-model-in-your-browser/34.4-streaming-and-verifying-weights/)). Quando o usuário clica em **Use a local GGUF file**, `loadCpu()` chama `validateGguf(message.file)` com `expectedSize = null` e pula o digest SHA-256 oficial de propósito. Assim, quem visita pode importar outra quantização compatível do Qwen3-0.6B offline — como um GGUF menor de 4 bits — continuando protegido pelo filtro de extensão e tamanho da interface (`1.024` bytes a `1.500 × 1.024 × 1.024` bytes — **1 KiB a 1.500 MiB** — e `.gguf`), pela checagem dos 4 bytes `"GGUF"` e pela verificação pós-carga em `validateCpuIdentity()`. O limite honesto é que uma importação local recebe validação de formato e de identidade do modelo, nunca o checksum SHA-256 do arquivo Q8_0 oficial.

## Por que não dá para embutir 639 MB em base64 no HTML

Na [aula 34.1](/pt-br/lessons/34-a-model-in-your-browser/34.1-what-runs-where/), vimos que o Qwen Local Lab embute 11,66 MB de motores WebAssembly e JavaScript dentro do `dist/index.html` usando **base64**. Por que não dar um passo além e embutir também o `Qwen3-0.6B-Q8_0.gguf` para que o HTML dispense qualquer download separado?

O base64 codifica cada 3 bytes brutos (24 bits) em 4 caracteres ASCII imprimíveis (6 bits cada), inflando qualquer conteúdo binário na razão exata de $4/3$ (+33,3%):

$$
S_{\text{base64}} = 639{,}446{,}688 \times \frac{4}{3} = 852{,}595{,}584\ \text{bytes} \approx 852.60\ \text{MB}
$$

Somando os 15,66 MB dos motores e da interface, o resultado seria um único documento HTML de cerca de **868 MB**. Isso quebra navegadores de três formas ao mesmo tempo:

- **Trava o parser de HTML**: o navegador precisa ler e tokenizar o documento inteiro como texto antes de executar qualquer script.
- **Dispara o pico de memória**: decodificar uma string base64 de 852,60 MB com `atob()` força o JavaScript a manter o texto, a cópia binária decodificada e o `Blob` resultante em memória ao mesmo tempo — mais de 1,5 GB antes de o modelo alocar um único tensor ou cache KV.
- **Impede download seletivo de backend**: quem roda em GPU ainda teria de baixar 852,60 MB de pesos de CPU que nunca vai usar.

Manter os pesos em um arquivo GGUF binário separado respeita o modo como navegadores lidam com volumes grandes: como fluxos brutos fora do parser de HTML. Em seguida, a [aula 34.3](/pt-br/lessons/34-a-model-in-your-browser/34.3-two-engines-one-tab/) mostra como uma única aba escolhe entre WebAssembly na CPU e WebGPU na placa gráfica depois que os motores iniciam.
