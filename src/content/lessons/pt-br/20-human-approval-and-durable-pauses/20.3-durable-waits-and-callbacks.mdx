O pedido de aprovação da [aula 20.2](/pt-br/lessons/20-human-approval-and-durable-pauses/20.2-bind-approval-to-one-operation/) sai na segunda-feira às 09:00, com validade de três dias. O aprovador está viajando e pode responder na quarta, ou nunca. Enquanto isso a empresa faz dois deploys (publica novas versões do software que reiniciam os programas em execução), e um worker cai. Como a execução espera três dias?

A primeira ideia que vem à mente é um laço num processo worker (um programa rodando em segundo plano): dormir, ver se chegou resposta, dormir de novo. Esse processo segura memória e uma thread (uma linha ativa de execução) por três dias. Um deploy o reinicia e esquece a espera. Uma queda a perde. Duas cópias do processo podem acordar ao mesmo tempo. A solução é a ideia por trás da [aula 14.3](/pt-br/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/): guardar a espera como dado gravado, não como um programa rodando.

## O que precisa sobreviver a três dias de espera?

Uma *espera durável* é uma espera registrada onde sobrevive a reinícios: pelo que estamos esperando, até quando, e o que acontece quando a resposta chega. Três coisas precisam persistir: o próprio pedido (com sua hash e validade), o prazo (para que algo encerre a espera se ninguém responder) e a decisão quando chegar. Nenhum processo precisa continuar vivo; qualquer processo que comece depois consegue ler a espera gravada e continuar.

Algo também precisa acordar a espera. Um *callback* é uma chamada para dentro do nosso sistema, vinda de fora, quando algo acontece. Aqui, o clique do aprovador chega como uma requisição HTTP (Hypertext Transfer Protocol, o formato padrão de pedido e resposta da web) do Slack ou do Teams. A *fronteira da transação*, o conjunto de mudanças que são gravadas juntas ou não são gravadas, decide o que uma queda pode deixar para trás. Esta aula constrói a mesma espera duas vezes, uma com a biblioteca padrão do Python (as ferramentas que já vêm prontas no Python) e outra com o Temporal.

## Uma espera como uma linha

A versão do core guarda cada pedido como uma linha no mesmo arquivo SQLite (um banco de dados leve guardado num único arquivo em disco) dos checkpoints e do outbox (a tabela de ações de saída aguardando entrega) da trilha 14. `open` insere a linha com status `pending`, e o worker da execução pode sair. Nada dorme. Dentro de uma transação travada do banco, `decide` lê a linha, para se o pedido não existir, já estiver decidido, estiver fora do prazo ou vier de alguém sem permissão e, caso contrário, grava a decisão.

```python
# file: examples/agent-engineering/src/agentlab/approval/store.py
    def decide(self, approval_id: str, approver: Principal, *, approve: bool, now: datetime) -> Outcome:
        """Record one person's decision, once, before the deadline."""
        with self._transaction():
            found = self._read(approval_id)
            if found is None:
                return Outcome(False, "unknown", f"no approval {approval_id}")
            request, status, _run = found
            if status != "pending":
                return Outcome(False, status, f"already {status}")
            if now >= request.expires_at:
                self._move(approval_id, "pending", "expired", now)
                return Outcome(False, "expired", "the decision arrived after the deadline")
            who = check_approver(request, approver)
            if not who.allowed:
                return Outcome(False, status, who.reason)
            to = "approved" if approve else "denied"
            self._move(approval_id, "pending", to, now, decided_by=approver.user_id)
            return Outcome(True, to, who.reason)
```

`_transaction` abre o `BEGIN IMMEDIATE` do SQLite. A documentação do SQLite diz que ele faz a conexão "start a new write immediately", começar uma escrita na hora, e só uma transação de escrita pode estar ativa por vez. Assim a leitura e a mudança de status não se sobrepõem passo a passo às de outro worker. `_move` é um compare-and-swap, uma atualização que só tem sucesso se a linha ainda tiver o status que quem chamou leu, como nos checkpoints da aula 14.3.

Três caminhos encerram uma espera: uma decisão, o prazo vencido (percebido por `decide` ou por um *varredor*, `expire_due`, que um agendador — um serviço de relógio que dispara tarefas em horários marcados — pode chamar a cada poucos minutos) ou um cancelamento na [aula 20.5](/pt-br/lessons/20-human-approval-and-durable-pauses/20.5-deny-expire-revoke-and-resume/). Todo método recebe `now` de quem o chama. Esse é o *controle do relógio* de que os testes dependem: um teste passa `T0 + timedelta(days=2, hours=23)` e recebe a resposta que uma quinta-feira de verdade às 08:00, uma hora antes do prazo, receberia, sem esperar nada.

## A mesma espera no Temporal

A [aula 14.5](/pt-br/lessons/14-agent-architecture-and-state/14.5-langgraph-and-temporal/) mostrou o histórico de eventos e os timers duráveis do Temporal. O Temporal também tem três tipos de mensagem para um workflow em execução. A documentação define Queries como pedidos de leitura, Signals como "asynchronous write requests" (escritas assíncronas, enviadas sem esperar resposta ou erro: "you cannot await any response or error") e Updates como "synchronous, tracked write requests" (escritas síncronas e rastreadas cujo remetente pode aguardar resposta ou erro: "can wait for a response on completion or an error on failure"). Um Update também pode ter um *validador*: uma função que levanta exceção para rejeitar o Update "before it is written to History", antes que seja escrito no histórico.

O exercício usa um Update, porque o adaptador que entrega um clique deveria saber na hora se ele contou. A etapa de espera do workflow abaixo calcula quanto tempo falta até `expires_at`, retorna `expired` na hora se não sobrar nada e, nos demais casos, pausa até chegar uma decisão ou o tempo esgotar.

```python
# file: examples/agent-engineering/src/agentlab/approval/temporal.py
    @workflow.run
    async def run(self, request_json: str) -> str:
        started = workflow.now()
        remaining = self.request.expires_at - started
        if remaining <= timedelta(0):
            return "expired"
        try:
            await workflow.wait_condition(lambda: self.decision is not None, timeout=remaining)
        except asyncio.TimeoutError:
            return "expired"
```

`wait_condition` retorna quando sua função fica verdadeira. Na versão 1.34.0 do SDK (Software Development Kit, o kit de desenvolvimento) do Temporal, um timeout a faz levantar `asyncio.TimeoutError`, e sua docstring (comentário de documentação no código) observa que um timeout cria um timer do Temporal. Esse timer mora no servidor, então nenhum worker precisa ficar vivo durante a espera. Antes de o Temporal gravar um Update no histórico, o validador abaixo confere quatro condições em ordem — nenhuma decisão ainda, decisão igual a `approve` ou `deny`, hash do rascunho igual e permissão dada por `check_approver` — levantando erro para rejeitar chamadas inválidas na hora.

```python
# file: examples/agent-engineering/src/agentlab/approval/temporal.py
    @decide.validator
    def check_decision(self, approver_json: str, decision: str, content_sha256: str) -> None:
        """Raising here rejects the Update before it reaches the history."""
        if self.decision is not None:
            raise ValueError(f"already {self.decision}")
        if decision not in ("approve", "deny"):
            raise ValueError(f"unknown decision {decision!r}")
        if content_sha256 != self.request.content_sha256:
            raise ValueError("the approver saw a different draft")
        who = check_approver(self.request, Principal.model_validate_json(approver_json))
        if not who.allowed:
            raise ValueError(who.reason)
```

O argumento `approver_json` é dado do runtime: o adaptador o monta a partir de um callback autenticado. Nunca é um texto que um modelo escreveu. O trabalho do Temporal é a espera e seu histórico; decidir quem pode aprovar continua no nosso código.

## O que os testes provam, e o que não provam

O teste do Temporal exercita o caminho de queda e reconstrução acima com `env.sleep(timedelta(days=1))` no ambiente de teste com avanço de tempo, que, segundo a documentação, "will manually advance time by the duration you specify", avança o tempo manualmente pela duração indicada. Depois de desligar o primeiro worker e pular um dia simulado sem nenhum worker ativo, um segundo worker sobe com `max_cached_workflows=0` (forçando a reconstrução completa pelo histórico) e recebe três Updates: quem pediu aprovando, um aprovador com a hash errada e uma aprovação válida. Os dois primeiros levantam `WorkflowUpdateFailedError`. O resultado começa com `AP-0001 approved by u-approver after 1 day`, o histórico tem exatamente um evento `WORKFLOW_EXECUTION_UPDATE_ACCEPTED` e o timer é cancelado. Um segundo teste avança três dias simulados sem decisão e confirma que o workflow devolve `expired` e não envia nada.

Esses são testes de fixture (testes autocontidos com entradas simuladas e relógio controlado). Mostram que a espera sobrevive a um reinício de worker e termina certo no prazo. Não mostram o comportamento numa espera real de três dias com deploys de verdade. O SDK também oferece `WorkflowEnvironment.start_local()`, onde, nas palavras da documentação, "any Timers will wait the actual amount of time", os timers esperam o tempo real. Uma execução ali com uma validade real curta, digamos dez minutos, é um exercício opcional. O CI (Continuous Integration, o executor automatizado de testes) do curso não a roda, porque ela prenderia uma máquina de testes pela espera inteira.

## Rode o exercício

O código do core está em `src/agentlab/approval/store.py`, e seus testes em `tests/test_approval_wait.py`. A partir de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest discover -s tests -p "test_approval_wait.py"`. A saída esperada termina com `Ran 7 tests` e `OK`. O teste de reinício fecha o store, abre um novo sobre o mesmo arquivo, encontra o pedido em `waiting()` e o aprova dois dias e 23 horas depois de aberto, uma hora antes do prazo.

O passo a passo do Temporal está em `src/agentlab/approval/temporal.py` e `tests_frameworks/test_approval_temporal.py`, no grupo opcional `frameworks`. Rode `uv run --frozen python -m unittest discover -s tests_frameworks -p "test_approval_temporal.py"`. A saída esperada termina com `Ran 3 tests` e `OK`. Linhas de log acima disso são esperadas: registros de erro de Java (stack traces) enquanto um servidor de teste lento sobe, e avisos de heartbeat do worker. A primeira execução baixa esse servidor, então precisa de rede uma vez.

Quebre as duas versões. Em `store.py`, troque `if now >= request.expires_at:` dentro de `decide` por `if False:`: `test_a_late_decision_is_refused_and_the_wait_expires` fica vermelho, porque um clique depois do prazo aprovaria. Em `temporal.py`, troque `if content_sha256 != self.request.content_sha256:` por `if False:`: o primeiro teste do Temporal falha com `WorkflowUpdateFailedError not raised`, porque a aprovação de outro rascunho seria aceita. Restaure as duas linhas.
