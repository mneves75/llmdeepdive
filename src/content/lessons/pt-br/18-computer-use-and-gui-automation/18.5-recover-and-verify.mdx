Quatro manhãs com a mesma tarefa, "baixar o relatório de março de 2026". Na segunda-feira um aviso de manutenção cobre a página, e o clique no botão de março estoura o prazo. Na terça o portal foi redesenhado, com os mesmos botões numa nova arrumação. Na quarta, outro redesenho renomeou todos os botões de exportação para "Export". Na quinta alguém aponta a execução para junho por engano: o clique funciona, um arquivo chega, o aviso diz que terminou, e o arquivo tem as linhas de março.

Uma execução que trata as quatro do mesmo jeito, tentando de novo até algo acontecer, cedo ou tarde clica na coisa errada. Esta aula separa os problemas que a execução sabe nomear e dos quais se recupera, os problemas que ela precisa passar a uma pessoa, e a verificação que decide quando ela terminou.

## Problemas esperados e problemas desconhecidos

Antes de cada clique, o Playwright confere que o elemento está visível, estável, habilitado e que "Receives Events, as in not obscured by other elements", recebe eventos, isto é, não está encoberto por outros elementos. Se as verificações não passam a tempo, a "action fails with the TimeoutError", a ação falha com o TimeoutError. O aviso de segunda é uma camada que cobre a página inteira, então o botão de março nunca recebe eventos e o clique simples estoura o prazo. O teste de navegador mostra exatamente isso.

Essa falha é esperada. O aviso é um diálogo com um botão chamado "Dismiss", e fechá-lo é reversível, inofensivo e faz parte do trabalho da execução. O redesenho de terça também é esperado: a [aula 18.1](/pt-br/lessons/18-computer-use-and-gui-automation/18.1-observe-before-acting/) escolheu alvos por papel e nome justamente para que uma nova arrumação não mude nada. A página de quarta é de outra natureza. O alvo da execução não existe mais, e "Export" encontra cinco botões. Qualquer escolha entre eles é um chute sobre uma página da qual ninguém falou à execução. A regra é se recuperar só de problemas que o código sabe nomear e escalar todo o resto.

## O laço de recuperação

`fetch_report`, em `browser.py`, põe essas decisões em ordem:

```python
# file: examples/agent-engineering/src/agentlab/gui/browser.py
        while True:
            budget.spend("observe")
            state = classify_page(page.url, observe(page), portal_origin)
            trace.record("gui.page", url=page.url, state=state)
            if state != "ready":
                return Outcome(state, f"stopped on {page.url}: {state}")
            dialog = page.get_by_role("dialog")
            if dialog.count():
                dismiss = dialog.get_by_role("button", name="Dismiss", exact=True)
                if dismiss.count() != 1:
                    return Outcome("needs_human", "a dialog without a known way to close it")
                budget.spend("dismiss")
                dismiss.click()
                trace.record("gui.dismiss", target="button:Dismiss")
                continue  # the page changed: observe again before acting
            button = resolve(page, target)
            if button is None:
                return Outcome("needs_human", f"no single {target.role} named {target.name!r}: the layout is not one this run knows")
            budget.spend("click")
            trace.record("gui.click", target=f"{target.role}:{target.name}")
            return download_report(page, lambda: button.click(timeout=timeout_ms), period=period, folder=folder, trace=trace, timeout_ms=timeout_ms)
```

Cada volta começa com uma observação nova, porque uma ação muda a página e o snapshot antigo descreve uma página que não existe mais. Uma página que não está pronta (uma sessão expirada, um desafio, outra origem, todos da [aula 18.3](/pt-br/lessons/18-computer-use-and-gui-automation/18.3-login-and-session-state/)) encerra a execução com esse estado. Um diálogo só é fechado pelo botão conhecido, e um diálogo sem ele escala. O alvo precisa corresponder a exatamente um elemento, ou a execução escala com um motivo que nomeia o problema de layout. Não há ramo que clique por coordenadas quando falta o alvo semântico: recorrer a um chute é como a quarta-feira vira um download errado.

## Um orçamento de ações

E se fechar o aviso o fizesse voltar? O laço observaria, fecharia e observaria para sempre. `ActionBudget` conta cada ação, e a que passa do limite lança `BudgetExhausted`, que `fetch_report` transforma em `needs_human`:

```python
# file: examples/agent-engineering/src/agentlab/gui/control.py
    def spend(self, action: str) -> None:
        if len(self.spent) >= self.limit:
            raise BudgetExhausted(f"{self.limit} actions spent ({', '.join(self.spent)}); not taking '{action}'")
        self.spent.append(action)
```

O orçamento é conferido antes de cada ação, então a execução para antes de tomar a ação que não pode pagar. Com limite 2 e o aviso na tela, a execução observa, fecha o diálogo e para antes da segunda observação, e o portal não serve nada. A lista spent também serve de trace compacto do que a execução fez.

## Verifique o resultado, não o clique

A execução de quinta faz tudo certo mecanicamente. O clique acerta, o portal serve `/export?period=2026-06`, o navegador salva o arquivo e o aviso comemora. `validate_report`, da [aula 18.4](/pt-br/lessons/18-computer-use-and-gui-automation/18.4-download-a-csv-from-a-legacy-portal/), então lê as linhas e encontra `line 2 is for period 2026-03, not 2026-06`, então o resultado é `failed` e a cópia é apagada. "Concluído" é uma propriedade do resultado no ambiente, as linhas certas na pasta da execução, nunca das ações que levaram até ali. A trilha 23 constrói suas avaliações sobre a mesma regra, a começar pela [aula 23.1](/pt-br/lessons/23-agent-evaluation-and-ci/23.1-define-success-and-capture-traces/).

## Comparações de capturas com máscaras

A comparação visual é uma verificação extra útil: a página parecia igual antes e depois de um passo que não deveria mudar nada? A página de relatórios tem um relógio que muda a cada 50 milissegundos, então duas capturas cruas nunca batem. O `screenshot` do Playwright aceita uma lista `mask`, e os elementos mascarados são "overlaid with a pink box `#FF00FF`", cobertos por uma caixa rosa, que "completely covers its bounding box", cobre por completo o retângulo do elemento:

```python
# file: examples/agent-engineering/src/agentlab/gui/browser.py
    image = page.screenshot(mask=[page.get_by_role("timer")], animations="disabled", caret="hide")
    return hashlib.sha256(image).hexdigest()
```

O teste controla o relógio da página, adianta-o um segundo e confere três coisas. As capturas cruas diferem. Os digests mascarados são iguais. Um aviso novo ainda muda o digest mascarado. Comparar digests SHA-256 significa que qualquer pixel mudado conta. Isso funciona para um navegador numa máquina, mas capturas de outra máquina ou de outra versão do navegador podem diferir na renderização das fontes e precisam de uma tolerância. As capturas continuam sendo evidência de apoio. As verificações semânticas, o diálogo sumido e exatamente um alvo resolvido, são aquilo sobre o que o laço age.

:::note
Um caminho pelo navegador também pode substituir uma API aposentada, mas só quando age com a mesma identidade e as mesmas permissões e seu resultado é verificado deste jeito. A [aula 24.3](/pt-br/lessons/24-agent-resilience-and-fallbacks/24.3-api-to-browser-fallback/) discute quando esse recurso alternativo é permitido.
:::
