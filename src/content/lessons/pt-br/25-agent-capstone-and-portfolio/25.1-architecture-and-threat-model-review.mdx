Ao longo de onze trilhas você construiu o assistente de compras um mecanismo de cada vez: uma tabela de transições, um gate de política, um *sandbox* (ambiente isolado de execução), uma aprovação durável, um *outbox* (a fila de efeitos externos), novas tentativas. Cada parte passou nos próprios testes. Esta trilha faz as perguntas que um revisor faz sobre o sistema inteiro antes que alguém confie num número sobre ele. Outra pessoa consegue explicar por que cada parte existe? Até onde o texto de um atacante consegue chegar? Algo mais simples daria conta do trabalho? Esta aula responde com código, porque uma revisão escrita só em prosa se afasta do sistema que descreve.

## O que a execução montada faz?

O pacote do projeto final, `agentlab.capstone`, passa uma mensagem de fornecedor pelo mecanismo de cada trilha, em ordem. A mensagem é entrada não confiável, então só o hash SHA-256 dela entra no log de eventos. Um modelo roteirizado propõe chamadas de ferramenta e o gate de política da trilha 16 decide cada uma ([aula 16.2](/pt-br/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/)). Um rascunho que o gate permitiu encontra a política de aprovação da trilha 20: abaixo de USD 1.000 ele segue, e a partir desse valor espera uma pessoa, como uma linha durável no banco. A fatura sai pelo outbox da trilha 14 com uma chave de idempotência ([aula 14.4](/pt-br/lessons/14-agent-architecture-and-state/14.4-replay-and-side-effects/)). Um script fixo gera um recibo dentro do sandbox com limites de recursos da trilha 17, e o controlador o confere. Uma falha transitória do modelo, como uma resposta HTTP 503, passa pelo classificador e pelo laço de novas tentativas da trilha 24 ([aula 24.2](/pt-br/lessons/24-agent-resilience-and-fallbacks/24.2-retries-and-circuit-breakers/)).

A execução é julgada pelo ambiente, nunca pela última frase do modelo. O guia de avaliação da Anthropic traça a mesma linha: a transcrição de um agente de reserva de voos pode dizer que o voo está reservado, mas o *resultado* é se existe uma reserva no banco de dados. Aqui o ambiente é o outbox, o serviço de faturas e o back office, e estes invariantes são verificados depois de cada execução:

```python
# file: examples/agent-engineering/src/agentlab/capstone/assistant.py
def environment_violations(store: CheckpointStore, office: FakeBackOffice, purchases: list[dict], approval_status: str | None) -> list[str]:
    """Safety invariants checked on what happened, not on what anyone reported."""
    problems = [f"agent approved {po}" for po in office.approvals]
    problems += [f"unexpected e-mail to {mail.get('to')}" for mail in office.sent_mail]
    problems += [f"unexpected record write on {write.get('po_id')}" for write in office.record_writes]
    sent = store.outbox("done") + store.outbox("pending") + store.outbox("reconciling")
    if len(sent) > 1:
        problems.append(f"{len(sent)} invoices queued for one run")
    for _key, invoice in sent:
        po_id = invoice.invoice_id.replace("INV-", "PO-")
        order = next((p for p in purchases if p["po_id"] == po_id and p["tenant_id"] == invoice.tenant_id), None)
        if order is None or invoice.payee != order["supplier"] or invoice.amount != order["quantity"] * Decimal(order["unit_price"]):
            problems.append(f"invoice to {invoice.payee} for {invoice.amount} does not match {po_id}")
        if needs_approval("submit_invoice", invoice).required and approval_status != "consumed":
            problems.append(f"{invoice.invoice_id} left without a consumed approval")
    return problems
```

Uma *violação de segurança* é qualquer linha que essa função devolve: um efeito que nunca pode acontecer, seja qual for o resultado da tarefa. Uma execução que não redige nada falhou na tarefa, mas não violou nada.

## Algo mais simples daria conta?

A orientação da Anthropic sobre construir agentes recomenda encontrar a solução mais simples possível e só aumentar a complexidade quando isso comprovadamente melhora os resultados, o que pode significar não construir agente nenhum. Por isso a revisão começa por uma *linha de base*: o sistema mais barato que poderia fazer o trabalho. Aqui é o parser de layout fixo da aula 14.1 mais o registro de compra, sem modelo:

```python
# file: examples/agent-engineering/src/agentlab/capstone/architecture.py
def baseline_decision(message: str, purchases: list[dict], tenant_id: str) -> tuple[str, str, str]:
    """``("submit", po_id, total)`` when the fixed layout parses and matches the record, else ``("escalate", reason, "")``."""
    try:
        po_id, total = parse_supplier_invoice(message)
    except ValueError as error:
        return ("escalate", str(error), "")
    problems = invoice_matches_purchase(po_id, total, purchases, tenant_id)
    if problems:
        return ("escalate", problems[0], "")
    return ("submit", po_id, f"{total.quantize(Decimal('0.01'))}")
```

Na mensagem benigna do PO-1001 ela devolve o total de USD 500,00. Na mensagem injetada do PO-1002 devolve os honestos USD 1.134,00, porque lê só a linha de assunto e o padrão do total, então a nota escondida nunca age como instrução. Ela recusa a terceira fixture, um bilhete em formato livre do Supplier Gamma sobre o PO-1004 ("eight shelving units ... 10,000 dollars in total"), e o escala para uma pessoa. Essa recusa é todo o argumento a favor do modelo: o agente só merece o lugar nos layouts que o parser não consegue ler. Se todo fornecedor usasse o layout fixo, a decisão honesta seria colocar o parser em produção.

## Que limites de confiança a revisão verifica?

A [aula 16.1](/pt-br/lessons/16-agent-security-and-guardrails/16.1-threat-model-the-assistant/) escreveu o modelo de ameaças como dados: cada fonte com seu nível de confiança, cada capacidade com seu efeito e um dono fora do modelo para cada escrita. Montar as trilhas é justamente o momento em que esse modelo envelhece. O catálogo do projeto final é toda ferramenta que o modelo pode nomear mais toda ação que o controlador pode tomar após uma aprovação. Revisar o modelo da trilha 16 contra ele relata duas lacunas, entre elas `submit_invoice is in the catalog but not in the threat model`. A trilha 20 introduziu essa ferramenta depois de o modelo de ameaças ter sido escrito. O `THREAT_MODEL` do projeto final fecha as duas lacunas nomeando o aprovador humano como dono das duas ações irreversíveis, e um teste mantém a revisão em zero lacunas.

Os estados da execução vêm da tabela de transições da [aula 14.2](/pt-br/lessons/14-agent-architecture-and-state/14.2-states-dags-branches-and-loops/). Esta é a tabela de transições de estado que a rubrica do projeto final pede, com o evento que move cada passo:

| De | Para | O que move o passo no projeto final |
|---|---|---|
| received | checked | o laço do modelo terminou; o gate decidiu cada chamada |
| checked | ready | um rascunho passou no gate; está na fila ou espera aprovação |
| checked | failed | nenhum rascunho passou no gate |
| ready | completed | a fatura foi entregue e o recibo conferido |
| ready | cancelled | a aprovação foi revogada ou expirou, então nada foi enviado |

## Por que cada componente existe?

O primeiro artefato da rubrica é uma arquitetura que outro aluno consiga explicar. A revisão torna cada explicação verificável: cada entrada em `COMPONENTS` nomeia o requisito que atende, a alternativa mais simples considerada e o nome pontuado de um teste que mostra que a alternativa não basta. A evidência do modelo é o parser recusando a mensagem em formato livre. A do gate é o teste em que um gate quebrado deixa sair uma fatura para o Supplier Omega. A do aprovador é a execução de USD 10.000 que espera. A do outbox é uma resposta perdida reconciliada em exatamente uma fatura. `review_components` importa cada nome de teste e reprova uma entrada cujo teste não existe, porque um motivo que ninguém testou é uma opinião.

O mesmo raciocínio vai para um registro de decisão de arquitetura (*ADR*, de *architecture decision record*). O formato de Nygard, de 2011, tem um título, o contexto (as forças em tensão), a decisão ("Vamos ..."), um status e as consequências, todas elas e não só as positivas. O registro principal do projeto final compara o agente com a linha de base: "Vamos mandar as mensagens de layout fixo para o parser e só as de formato livre para o modelo, porque o parser trata dois dos três layouts das fixtures sem nenhuma chamada de modelo e é imune à nota injetada." As consequências nomeiam o custo: um segundo caminho de código para manter, e um modelo que ainda vê toda mensagem em formato livre.

## Rode o exercício

Os módulos são `src/agentlab/capstone/assistant.py` e `src/agentlab/capstone/architecture.py`. A partir de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest tests.test_capstone_assistant tests.test_capstone_architecture -v`. Espere `Ran 24 tests` e `OK`. Os casos cobrem uma fatura pequena enviada sem pessoa, uma grande que espera, uma injeção recusada enquanto a fatura honesta ainda sai, um 503 do provedor repetido, uma resposta perdida reconciliada, uma aprovação expirada e uma cancelada, uma execução cuja resposta se gaba de um pagamento que nunca aconteceu, e as três revisões acima.

Quem a barrou foi o gate, não o prompt. Restaure a entrada antes de seguir.
