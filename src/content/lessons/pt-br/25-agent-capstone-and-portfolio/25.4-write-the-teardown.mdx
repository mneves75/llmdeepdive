Você tem um relatório de benchmark da [aula 25.2](/pt-br/lessons/25-agent-capstone-and-portfolio/25.2-a-reproducible-benchmark/) e postmortems da [aula 25.3](/pt-br/lessons/25-agent-capstone-and-portfolio/25.3-failure-analysis/). Outra pessoa, em outra máquina, conseguiria pegar o seu texto e chegar aos mesmos números? Se não conseguir, os números são uma afirmação sobre o seu notebook. Esta aula escreve o *relatório técnico* (em inglês, *teardown*), o documento que permite a uma segunda pessoa rodar e conferir o trabalho, e testa que um processo limpo de fato o reproduz.

## O que uma segunda pessoa precisa

O checklist de artigos da NeurIPS diz o que os revisores esperam de qualquer resultado experimental, e os itens dele se encaixam em seis seções:

- **Preparação.** O checklist pede o código, os dados e instruções com "o comando exato e o ambiente necessários para rodar e reproduzir os resultados". Aqui isso é `uv sync --frozen` e o comando do benchmark, mais as versões registradas do Python, do Pydantic e do agentlab.
- **Metodologia.** Os cenários, o número de tentativas, a semente, um ambiente novo por tentativa, o tipo de evidência e o que conta como sucesso. Aqui sucesso quer dizer que o ambiente terminou no estado esperado sem violação de segurança, e as palavras do modelo não são avaliadas.
- **Resultados.** Todo número do relatório, com o intervalo, as falhas pelo nome e uma tabela por cenário. O checklist pede para dizer quais resultados são reproduzíveis, se só alguns forem.
- **Limitações.** O checklist pede uma seção separada sobre suposições fortes, como a independência, e sobre quão robustos são os resultados quando essas suposições falham. Também pergunta pelo alcance, como ter testado com poucas execuções.
- **Manifesto de artefatos.** O digest do relatório, o manifesto de fixtures e um SHA-256 para cada arquivo de entrada, para que o leitor saiba se tem as mesmas entradas.
- **Licenças.** O checklist pede a versão e o nome da licença de cada recurso usado. O projeto final lê as duas coisas dos metadados dos pacotes instalados: agentlab e Pydantic são MIT, e três das quatro dependências do Pydantic também.

O Framework de Gestão de Riscos de IA do NIST diz o mesmo pelo lado da governança. A função MEASURE dele diz que conjuntos de teste, métricas e detalhes das ferramentas usadas em teste, avaliação, verificação e validação ficam documentados. O framework acrescenta que a documentação pode aumentar a transparência, melhorar a revisão humana e reforçar a responsabilização. O relatório técnico é essa documentação para um sistema pequeno.

## Gere, não redigite

Um relatório técnico digitado à mão se afasta do relatório que descreve: um número é arredondado de outro jeito, ou uma falha fica de fora porque era constrangedora. `render_teardown` monta o Markdown a partir do próprio relatório, então todo número do texto é o número do JSON. A seção de Limitações é um texto fixo que diz o que essa evidência não consegue mostrar. Toda execução usou um modelo roteirizado. Com um modelo roteirizado, três tentativas não podem discordar. O relógio foi injetado. Dez cenários com três tentativas cada são uma verificação didática, não uma estimativa de confiabilidade em produção.

Uma limitação é útil quando nomeia uma suposição, o que a quebra e o que isso faria com o resultado. "Os resultados podem variar" não nomeia nada. "O intervalo supõe tentativas independentes; as três tentativas de um cenário roteirizado são idênticas, então o intervalo é mais estreito do que a evidência sustenta" nomeia as três coisas. O checklist traz um ponto que vale copiar. Os revisores são orientados a não penalizar a honestidade sobre limitações, e o texto avisa que um desfecho pior é um revisor descobrir uma limitação que o artigo não reconheceu. Escreva as limitações que você conhece antes que outra pessoa as encontre.

`review_teardown` então verifica o que o leitor precisa encontrar. Cada uma das seis seções tem que existir e ter texto. O tipo de evidência, `fixture-tested`, tem que estar declarado. O digest do relatório tem que aparecer. Um teste troca o tipo de evidência pela palavra mais vaga "tested" e confere que a revisão reclama.

## Um processo limpo reproduz o relatório?

Reprodução é uma comparação, não uma impressão. O teste que decide isso inicia um novo processo Python com `-I`, que ignora as variáveis de ambiente `PYTHON*` e o diretório atual, num diretório temporário vazio, e conta com o Python salgando os hashes de strings de um jeito diferente em cada processo novo. Roda o benchmark ali. Depois compara o digest com uma execução no próprio processo. O guia de avaliação da Anthropic pede o mesmo isolamento por tentativa: estado compartilhado entre execuções, como arquivos que sobraram, pode causar falhas correlacionadas ou inflar as notas.

Quando os digests diferem, um simples "o hash é diferente" não diz a ninguém onde olhar. `reproduces` nomeia o que mudou:

```python
# file: examples/agent-engineering/src/agentlab/capstone/teardown.py
def reproduces(expected: dict, actual: dict) -> list[str]:
    """Empty when the deterministic parts match; otherwise the digest and every run that differs."""
    if expected["digest"] == actual["digest"] and expected["deterministic"] == actual["deterministic"]:
        return []
    problems = [f"digest differs: {expected['digest'][:12]} vs {actual['digest'][:12]}"]
    key = lambda run: f"{run['case_id']}.t{run['trial']}"
    theirs = {key(run): run for run in actual["deterministic"]["runs"]}
    for run in expected["deterministic"]["runs"]:
        other = theirs.get(key(run))
        if other != run:
            changed = "missing" if other is None else ", ".join(name for name in run if run[name] != other.get(name))
            problems.append(f"{key(run)}: {changed}")
    if expected["deterministic"]["fixture_manifest"] != actual["deterministic"]["fixture_manifest"]:
        problems.append("fixture manifest differs: the runs read different fixture files")
    return problems
```

Um relatório adulterado com um sucesso invertido produz `digest differs` seguido de `ordinary-po1001.t1: success`, que são a execução e o campo a inspecionar.

O teste de processo novo é mais estreito que uma máquina limpa, e a diferença importa. Ele reaproveita o ambiente instalado. A verificação completa é sua, e a CI do curso não a roda. Clone o repositório num diretório novo, rode `uv sync --frozen` e o benchmark a partir de `examples/agent-engineering/`, e compare o digest do relatório novo com o do seu relatório técnico. Uma segunda pessoa fazendo exatamente isso, na máquina dela, é o teste de aceitação desta aula.

## Rode o exercício

O módulo é `src/agentlab/capstone/teardown.py` e os testes estão em `tests/test_capstone_teardown.py`. A partir de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest tests.test_capstone_teardown -v`. Espere `Ran 7 tests` e `OK`. Os testes geram o relatório técnico a partir de um relatório novo, conferem as seis seções e os dois fatos obrigatórios, apontam uma seção ausente e uma vazia, leem a tabela de licenças dos metadados instalados, reproduzem o digest num processo novo e nomeiam a execução num relatório adulterado.

Para ver o teste de processo novo mostrar seu valor, troque `trial_seed` em `assistant.py` para devolver `hash((seed, case_id, trial))`. Todo teste de `test_capstone_benchmark.py` continua passando, porque duas execuções num mesmo processo compartilham o mesmo sal de hash. `test_a_fresh_process_in_an_empty_directory_reproduces_the_digest` falha, porque o processo novo aplica outro sal aos hashes de texto e sorteia tempos diferentes. Restaure a semente em texto antes de seguir.
