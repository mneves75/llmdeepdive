O controlador precisa de um resumo de CSV produzido por código não confiável. Ele manda o arquivo de compras e o script do modelo, e quer de volta um `summary.json` curto com os totais por fornecedor. A [aula 17.1](/pt-br/lessons/17-sandboxed-agent-execution/17.1-what-isolation-protects/) mostrou que um processo com limites não consegue manter esse script longe dos arquivos do host, então esta aula põe o script atrás de uma máquina virtual. Ela começa pela parte que não muda quando o limite muda: o contrato entre o controlador e o que quer que rode o código.

:::note
A parte de microVM desta aula precisa de uma máquina Linux x86_64 em que seu usuário leia e escreva em `/dev/kvm`, como um servidor bare-metal. macOS, contêineres comuns e runners de CI hospedados típicos não servem. Sem uma, você ainda pode rodar os testes de contrato abaixo e estudar os comandos, mas não pode declarar o marco da microVM. A CI do curso não executa nenhum comando de microVM desta aula.
:::

## Comece pelo contrato, não pela VM

Um *backend* é qualquer coisa que recebe um pedido e devolve uma resposta sob as mesmas regras. O projeto define os dois lados como registros estritos, usando a base `Record` de `agentlab.domain`, que rejeita campos desconhecidos e tipos errados:

```python
# file: examples/agent-engineering/src/agentlab/sandbox/interpreter.py
class InputFile(Record):
    # A bare name: no directory, no "..", and never main.py, so an input cannot overwrite the script.
    name: str = Field(pattern=r"^[a-z0-9_-]{1,40}\.csv$")
    content: str = Field(max_length=1_000_000)


class InterpreterRequest(Record):
    request_id: str = Field(pattern=r"^[A-Za-z0-9-]{1,64}$")
    code: str = Field(min_length=1, max_length=20_000)
    files: tuple[InputFile, ...] = Field(default=(), max_length=8)
```

Cada limite tem um motivo. Nomes de arquivo não conseguem subir para fora da workspace nem substituir o script. Os tamanhos têm teto antes de qualquer coisa começar. O id do pedido aceita só letras, dígitos e hífens, até 64 caracteres, que é exatamente o que o jailer do Firecracker aceita como id de VM. Assim o mesmo id pode nomear a microVM e, depois, os recursos exatos a remover.

A resposta traz o código de saída, se o relógio disparou, stdout e stderr limitados, o `memory_limited` da [aula 17.2](/pt-br/lessons/17-sandboxed-agent-execution/17.2-resource-and-filesystem-limits/), os artefatos coletados com seus hashes SHA-256 e uma lista das saídas recusadas. Os bytes dos artefatos viajam como base64 no JSON, então a resposta atravessa um socket sem mudar. Um teste comprova essa ida e volta.

## Coletar resultados sem confiar neles

O convidado escreve seus resultados em `out/`, e o convidado pode ser hostil. Coletá-los é, portanto, um problema de validação de entrada, e o laço trata cada entrada como suspeita:

```python
# file: examples/agent-engineering/src/agentlab/sandbox/interpreter.py
        try:
            # O_NOFOLLOW: a symlink fails instead of being read through.
            # O_NONBLOCK: a FIFO the guest left behind cannot hang the controller.
            fd = os.open(out / name, os.O_RDONLY | os.O_NOFOLLOW | os.O_NONBLOCK)
        except OSError:
            rejected.append(f"{name}: not a regular file")
            continue
        with os.fdopen(fd, "rb") as file:
            info = os.fstat(file.fileno())
            if not stat.S_ISREG(info.st_mode):
                rejected.append(f"{name}: not a regular file")
                continue
            if info.st_size > budget:
                rejected.append(f"{name}: over the artifact size budget")
                continue
```

Um *symlink* é um arquivo que aponta para outro caminho. Sem `O_NOFOLLOW`, um convidado poderia ligar `out/report.txt` a um arquivo do host, e "colete meus resultados" viraria "leia os segredos do host". Uma *FIFO* é um pipe com nome, e abrir uma bloqueia até aparecer quem escreva, então `O_NONBLOCK` impede que um pipe esquecido congele o controlador. Antes do laço, a função também recusa um `out` que seja ele mesmo um symlink, e limita o número de artefatos e o tamanho total.

O backend de subprocesso executa os cinco passos da figura. Um bloco `with tempfile.TemporaryDirectory(...)` cria a workspace e remove esse diretório exato em caso de sucesso, de timeout e de exceção.

## O backend de microVM

O segundo backend mantém o contrato e troca o subprocesso por uma microVM Firecracker. Este é o projeto; o curso não o implementa:

- **A imagem do convidado** é um sistema de arquivos raiz somente leitura com Python e todas as dependências já instaladas, construída antes ([aula 17.3](/pt-br/lessons/17-sandboxed-agent-execution/17.3-network-egress-and-secrets/)). Um pequeno *agente convidado* dentro dela recebe o pedido, roda o mesmo bootstrap com limites num diretório gravável em memória e devolve a resposta.
- **Nenhum dispositivo de rede.** A configuração não lista interface de rede, então o convidado não tem rota para lugar nenhum.
- **Um canal.** *vsock* é um socket virtual entre host e convidado. O Firecracker o mapeia para um socket Unix no host, então o controlador se conecta ali, manda `CONNECT <porta>`, escreve o JSON do pedido e lê o JSON da resposta.
- **O jailer.** Em produção, o Firecracker roda dentro do seu jailer, que cria um chroot para o id da VM, reduz privilégios para um usuário dedicado, aplica limites de recursos e limpa o ambiente.

## Comandos na v1.17.0, não executados pela CI do curso

Tudo abaixo segue a documentação do Firecracker na tag v1.17.0. Precisa de um host com KVM, então é uma ilustração que a CI do curso não executa. Primeiro, verifique se seu usuário pode usar o KVM. A linha vem do guia de primeiros passos:

```bash
[ -r /dev/kvm ] && [ -w /dev/kvm ] && echo "OK" || echo "FAIL"
```

Um arquivo de configuração define cada recurso de antes do boot com os mesmos nomes da API. Este não tem interfaces de rede. Ele usa um drive raiz somente leitura e dá boot com `8250.nr_uarts=0`, que o guia de produção recomenda porque o convidado consegue inundar o console serial:

```json
{
  "boot-source": {
    "kernel_image_path": "vmlinux.bin",
    "boot_args": "reboot=k panic=1 8250.nr_uarts=0"
  },
  "drives": [
    {
      "drive_id": "rootfs",
      "path_on_host": "python-guest.ext4",
      "is_root_device": true,
      "is_read_only": true
    }
  ],
  "machine-config": { "vcpu_count": 1, "mem_size_mib": 512 },
  "network-interfaces": [],
  "vsock": { "guest_cid": 3, "uds_path": "./v.sock" }
}
```

A documentação do jailer diz que os arquivos que a VM usa precisam ser ligados por hard link ou copiados para dentro do jail antes. Coloque `vmlinux.bin`, `python-guest.ext4` e `vm.json` em `/srv/jailer/firecracker/req-1/root/`, legíveis pelo usuário dedicado, e então inicie:

```bash
sudo jailer --id req-1 \
  --exec-file /usr/bin/firecracker \
  --uid 10001 --gid 10001 \
  --resource-limit fsize=268435456 --resource-limit no-file=1024 \
  --new-pid-ns --daemonize \
  -- --config-file vm.json
```

Os argumentos depois de `--` vão para o Firecracker. Configurar com `--config-file` já inicia a VM, então nada disputa corrida entre chamadas de configuração. A sequência de API do guia de primeiros passos precisa de um `sleep` entre as chamadas e pula o jailer, e por isso o guia se declara "not intended for production" (não destinado à produção).

## O que continua sendo trabalho do controlador

Uma microVM move o limite. Ela não tira as tarefas do controlador:

- **Limpeza.** A documentação do jailer diz "It's up to the user to handle cleanup after running the jailer" (cabe ao usuário cuidar da limpeza depois de rodar o jailer). O controlador mata o processo indicado em `/srv/jailer/firecracker/req-1/root/firecracker.pid` e remove `/srv/jailer/firecracker/req-1`, mais qualquer cgroup criado para `req-1`. A aula 17.5 explica por que a remoção precisa nomear exatamente esse id.
- **Saída limitada.** O convidado consegue fazer crescer os logs e a saída serial do Firecracker, e o guia de produção pede armazenamento limitado para os dois. O canal de resposta precisa dos mesmos limites do subprocesso.
- **vsock estreito.** Uma conexão que o convidado abre para a porta 52 é encaminhada para `./v.sock_52` no host, se algo estiver escutando ali. Escute só na porta de que o protocolo precisa.
- **Vivacidade.** O guia de produção recomenda um processo vigia que mate processos Firecracker que pararam de responder. O timeout de relógio faz esse papel aqui.

## Rode o exercício

O módulo é `src/agentlab/sandbox/interpreter.py`; os testes estão em `tests/test_sandbox_interpreter.py`. A partir de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest tests.test_sandbox_interpreter -v`. Espere `Ran 7 tests` e `OK`.

O controle positivo envia as compras sintéticas do tenant-a como CSV e recebe `summary.json` com Supplier Alpha em 1.634,00 (40 × 12,50 + 6 × 189,00), Supplier Beta em 780,00 e Supplier Gamma em 10.000,00. Os casos hostis são um symlink para um arquivo do host, um diretório `out` trocado por um symlink, uma FIFO e saídas demais. Cada um é recusado enquanto os arquivos legítimos ao lado continuam sendo coletados. Para ver uma captura real, tire `os.O_NOFOLLOW` da chamada a `os.open`: `test_a_symlinked_artifact_is_not_followed` falha porque o conteúdo do arquivo do host volta como artefato. Restaure antes de seguir.
