A equipe precisa escolher onde o gerador de relatórios roda. Cinco nomes voltam sempre à conversa: E2B, gVisor, WebContainers, "só um contêiner" e Docker-in-Docker. Cada um é oferecido como "uma sandbox", como se fossem intercambiáveis. Não são. Cada um põe o limite em outro lugar, protege outra pessoa e precisa de outra máquina. Esta aula os compara pelas cinco exposições da [aula 17.1](/pt-br/lessons/17-sandboxed-agent-execution/17.1-what-isolation-protects/) e depois faz duas coisas que nenhuma tabela comparativa faz: mede o backend que você de fato configurou e limpa o que ele deixou.

## Seis opções, seis limites diferentes

A tabela acrescenta a referência Firecracker do curso aos cinco candidatos. A coluna "Rede" lista só o que a documentação citada afirma.

| Opção | Onde o código do convidado roda | O que fica entre ele e o seu host | Rede |
|---|---|---|---|
| E2B | a nuvem do provedor | a sandbox do provedor; seu controlador chama a API dele | saída aberta por padrão |
| gVisor (`runsc`) | o seu host Linux | um kernel de aplicação em espaço de usuário | definida pelo runtime de contêiner |
| WebContainers | a aba do navegador do visitante | o navegador | as regras do navegador |
| Contêiner sem privilégio | o seu host Linux | namespaces, cgroups, seccomp; kernel compartilhado | definida pelo runtime |
| Docker-in-Docker | o seu host Linux | em geral nada: roda com `--privileged` | definida pelo runtime |
| Referência Firecracker | o seu host Linux com KVM | um kernel convidado e um VMM enjaulado | nenhuma: sem dispositivo de rede |

Leia cada linha e as diferenças aparecem. A **E2B** tira o convidado das suas máquinas, o que também torna o provedor parte do seu plano de controle: seu controlador precisa de acesso de rede até ele, além da conta e do consentimento do próprio aluno. O **gVisor** mantém o convidado no seu host, respondendo às chamadas de sistema dele com o Sentry em vez do kernel do host. Ele não é uma VM. Os **WebContainers** rodam Node.js "entirely inside your browser tab" (inteiramente dentro da aba do navegador), então protegem a máquina de um visitante contra uma demonstração de código e não fazem nada por Python ao lado dos seus dados. Um **contêiner sem privilégio** divide o kernel do host, e o Docker observa que namespaces de usuário estão "available but not enabled by default" (disponíveis, mas não habilitados por padrão). O **Docker-in-Docker** é o caso de uso que a referência do `docker run` dá para o `--privileged`.

## Configurações que removem o limite

Um limite é uma configuração, e três configurações comuns o desfazem:

- **`--privileged`.** A referência do `docker run` diz que ele habilita todas as capabilities, dá acesso a todos os dispositivos do host, desliga os perfis padrão de seccomp e AppArmor e "is not a securely sandboxed process" (não é um processo em sandbox segura).
- **Um socket do Docker montado.** O daemon do Docker "requires `root` privileges unless you opt-in to Rootless mode" (exige privilégios de root, a menos que você opte pelo modo rootless). A página do Docker sobre proteger o daemon diz que quem tem as chaves "can give any instructions to your Docker daemon" (pode dar qualquer instrução ao seu daemon), o que significa root no host dele. Um convidado que alcança o socket pode iniciar um contêiner com o `/` do host montado, que a página de segurança do Docker diz que "can alter your host filesystem without any restriction" (pode alterar o sistema de arquivos do host sem nenhuma restrição).
- **Padrões deixados ligados.** A documentação da E2B, lida em 2026-10-18, diz "Every sandbox has outbound access to the internet by default" (toda sandbox tem acesso de saída à internet por padrão). Regras de permissão "always take precedence" (sempre têm precedência) sobre as de negação, e a filtragem por domínio só cobre HTTP na porta 80 e TLS na porta 443. Um padrão não examinado também é uma decisão.

Nenhuma das opções está livre de vulnerabilidades, e nenhuma afirma estar. A documentação do gVisor até lista onde ele "does not help" (não ajuda): ataques antes de a sandbox começar, canais laterais no estilo Spectre e exploits dentro do próprio workload, em que "the attacker will still have access to whatever the sandbox is configured to have access to" (o atacante ainda terá acesso a tudo aquilo a que a sandbox está configurada para ter acesso).

## Meça, não descreva

A página de um fornecedor descreve um produto. O que roda é a sua configuração dele. Então o projeto mede um backend com sondas pequenas, cada uma um script convidado cuja saída o controlador compara com o marcador que significa "o convidado conseguiu fazer isto":

```python
# file: examples/agent-engineering/src/agentlab/sandbox/boundary.py
def probe_boundary(backend: Backend) -> dict[str, bool]:
    with tempfile.TemporaryDirectory(prefix="agentlab-probe-") as host:
        # A file the guest was never given, outside any workspace.
        secret = Path(host) / "host-secret.txt"
        secret.write_text("host-only data", encoding="utf-8")
        probes = {
            "reads_host_file": (f"print(open({str(secret)!r}).read())", "host-only data\n"),
            "inherits_environment": ("import os\nprint('PATH' in os.environ or 'HOME' in os.environ)", "True\n"),
            "starts_processes": (FORK, "started\n"),
        }
        report = {name: _stdout(backend, name, code) == marker for name, (code, marker) in probes.items()}
    report["output_bounded"] = len(_stdout(backend, "output", f"import sys\nsys.stdout.write('x' * {FLOOD})")) < FLOOD
    return report
```

Para o backend de subprocesso, rodando como usuário comum, o relatório medido é `reads_host_file=True`, `inherits_environment=False`, `starts_processes=False` e `output_bounded=True`. Três controles se sustentam e um limite está ausente, exatamente o que as aulas 17.1 e 17.2 previram. Um controle positivo roda as mesmas sondas contra uma configuração mais frouxa e obtém respostas diferentes, então as sondas conseguem mesmo distinguir configurações. Sondas de rede ficaram de fora de propósito: elas precisam de um destino que você controla e de um firewall para testar, e o aviso da E2B de que conexões bloqueadas podem parecer abertas vale para elas.

## Limpe exatamente o que a execução possui

Toda execução cria recursos: uma workspace, um grupo de processos e, no caminho da microVM, um diretório de jail e um cgroup. A limpeza remove esses recursos, nomeados pelo que a execução registrou ao criá-los. Ela nunca remove "tudo o que parece nosso". `rm -rf /tmp/agentlab-sandbox-*` apagaria a workspace de outra execução no meio do trabalho. Um `pkill python` atingiria processos de outras pessoas.

O projeto segue essa regra em cada camada. A workspace é o caminho exato que `TemporaryDirectory` devolveu. A morte mira o grupo de processos que o filho lidera. No caminho da microVM, o id do jailer nomeia o chroot `/srv/jailer/firecracker/<id>` e o cgroup, e a documentação do jailer deixa essa limpeza com você. A limpeza também precisa rodar na falha: depois de um timeout e depois de o convidado travar os próprios arquivos com `chmod 0`.

## Registre a decisão

Um *registro de decisão de arquitetura* (ADR, *architecture decision record*) é um documento curto que declara uma decisão, seu contexto e as alternativas rejeitadas, para que a próxima pessoa saiba o porquê. Para uma sandbox, ele precisa guardar valores medidos, não adjetivos. O modelo abaixo é uma ilustração para você preencher. A CI do curso não o verifica, porque só você conhece seu modelo de ameaças e suas máquinas:

```markdown
# ADR: Execution boundary for the report generator

Status: proposed
Context: model-written Python over one tenant's purchase CSV; the script is untrusted.
Threat model: what the guest must never reach (files, credentials, network, other tenants).
Decision: the backend chosen, and its exact configuration.
Measured limits: probe_boundary output, with date, commit and host.
Unsupported platforms: where this cannot run, and what learners there do instead.
Failure cleanup: which resources a run creates, and how each is removed by its id.
Rejected alternatives: each option considered, and the exposure that ruled it out.
```

## Rode o exercício

O módulo é `src/agentlab/sandbox/boundary.py`; os testes estão em `tests/test_sandbox_boundary.py`. A partir de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest tests.test_sandbox_boundary -v`. Espere `Ran 5 tests` e `OK`. Rodando como root, o teste do relatório medido é pulado, porque o `RLIMIT_NPROC` não vale para o root.

Os testes de limpeza põem um diretório vizinho chamado `agentlab-sandbox-neighbour` ao lado das workspaces. Depois de uma execução normal, de um timeout e de um convidado que travou os próprios arquivos, só o vizinho sobra. Para vê-los pegar um vazamento, acrescente `delete=False` à chamada `TemporaryDirectory(...)` em `SubprocessBackend.run`. Os três testes de limpeza falham, listando a workspace deixada para trás. As execuções das sondas, que usam o diretório temporário do sistema, também deixam oito workspaces lá. Restaure a linha e depois remova exatamente esses oito diretórios, pelos nomes que a saída da falha e o seu diretório temporário mostram.
