O assistente de compras pode produzir um pequeno relatório. O modelo escreve um script Python que soma as compras do tenant-a por fornecedor, e o controlador o executa. No caminho, o modelo leu a mensagem do fornecedor, e na [aula 16.2](/pt-br/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) essa mensagem trazia instruções para ele. Então o script é *código não confiável*: ninguém o revisou, e um atacante pode tê-lo moldado. Esta trilha responde a uma pergunta em cinco partes. Quando esse script roda, o que ele alcança, e o que o impede?

## O que um script que você não escreveu consegue alcançar?

Rode-o do jeito que o controlador mais simples faria: `subprocess.run(["python", "report.py"])` a partir do processo do worker. O processo filho começa com tudo o que o pai tem, menos a memória do pai:

- **Arquivos.** Ele roda como o mesmo usuário do sistema operacional, então pode abrir todo arquivo que esse usuário lê: o banco de checkpoints da [aula 14.3](/pt-br/lessons/14-agent-architecture-and-state/14.3-checkpoints-and-serialization/), uma chave privada no diretório pessoal, os registros do outro tenant.
- **Credenciais.** Um filho herda as *variáveis de ambiente* do pai por padrão. Se o worker tem `MODEL_API_KEY`, o script também tem.
- **Rede.** Ele pode abrir uma conexão para qualquer endereço que o host alcança. Numa máquina de nuvem, isso inclui o serviço de metadados em `169.254.169.254`, que pode entregar as credenciais da própria máquina ([aula 17.3](/pt-br/lessons/17-sandboxed-agent-execution/17.3-network-egress-and-secrets/)).
- **Recursos.** Ele pode girar a CPU, alocar memória, encher o disco e iniciar processos até a máquina penar.
- **O kernel.** O *kernel* é o núcleo do sistema operacional: toda abertura de arquivo, socket e processo novo é uma *chamada de sistema*, um pedido que o programa faz ao kernel. As chamadas de sistema do script vão para o mesmo kernel que roda todo o resto do host, então um bug nesse kernel é uma saída.

São cinco exposições separadas. Uma sandbox (ambiente isolado) só vale o que vale sua resposta a cada uma delas, e sandboxes diferentes respondem a subconjuntos diferentes.

## Quem é confiável: o plano de controle e o convidado

Dois papéis aparecem em todo projeto desta trilha. O *plano de controle* é o código confiável em volta da sandbox: decide o que roda, guarda credenciais, define limites, recebe e valida resultados e destrói a sandbox depois. O *workload convidado* é o código não confiável lá dentro. O documento de design do Firecracker adota a visão mais estrita do convidado: todas as suas threads de CPU virtual "are considered to be running malicious code as soon as they have been started" (são consideradas como rodando código malicioso desde o momento em que começam).

Manter os papéis separados evita uma confusão comum. O controlador pode precisar de rede, para chamar o modelo ou a API de um provedor de sandbox, enquanto o convidado não precisa de nenhuma. "Sem rede" é uma propriedade do convidado, não do sistema inteiro. O mesmo vale para segredos: o controlador guarda a chave de API, e o convidado nunca deve recebê-la.

## Quatro limites, quatro respostas diferentes

Um *limite* (*boundary*) é o mecanismo que fica entre o convidado e o que ele não pode alcançar. Quatro tipos são comuns, e a figura abaixo empilha cada um entre o script e o host.

<Figure id="isolation-layers" />

Um **processo com limites de recursos** limita quanto o script usa. A aula 17.2 constrói um. Ele não muda nada sobre o que o script alcança: mesmo usuário, mesmos arquivos, mesma rede, mesmo kernel.

Um **contêiner** acrescenta *namespaces*, que dão ao processo sua própria visão de arquivos, processos e interfaces de rede. Acrescenta também *cgroups*, que definem cotas de CPU, memória e número de processos. As chamadas de sistema continuam indo para o kernel do host, que é compartilhado. A documentação de segurança do Docker avisa que as capabilities e montagens padrão "may provide incomplete isolation" (podem dar isolamento incompleto), sozinhas ou "in combination with kernel vulnerabilities" (combinadas com vulnerabilidades do kernel).

Um **kernel em espaço de usuário** coloca um programa entre o convidado e o kernel do host. A documentação do gVisor o chama de "an application kernel, not a virtual machine hypervisor or a system call filter" (um kernel de aplicação, não um hipervisor de máquina virtual nem um filtro de chamadas de sistema). Seu componente Sentry reimplementa o Linux em Go e roda em espaço de usuário, e "gVisor never passes through any system call to the host" (o gVisor nunca repassa nenhuma chamada de sistema ao host). Ele não é uma microVM.

Uma **máquina virtual** dá ao convidado um kernel próprio, rodando sobre hardware emulado. Uma *microVM* é uma máquina virtual com um conjunto deliberadamente pequeno de dispositivos emulados, para que ela inicie rápido e exponha menos código ao convidado. O Firecracker constrói microVMs sobre o KVM, o módulo de virtualização do kernel Linux.

| Limite | As chamadas de sistema do convidado chegam a | Ainda precisa de controles separados para |
|---|---|---|
| Processo com limites | o kernel do host | arquivos, rede, segredos, o kernel |
| Contêiner | o kernel do host, filtrado | política de rede, segredos, bugs do kernel |
| gVisor | o Sentry | política de rede, segredos |
| MicroVM | o seu próprio kernel convidado | filtragem de saída no host, limpeza |

A última coluna nunca fica vazia. Até uma microVM deixa a filtragem de rede para o host: o documento de design do Firecracker diz que ele "does not perform any network traffic filtering" (não faz nenhuma filtragem de tráfego de rede). Esse é o ponto do laboratório na analogia. Uma parede forte não filtra o ar.

:::warning
Uma configuração pode remover um limite inteiro. A referência do `docker run` diz que um contêiner iniciado com `--privileged` "is not a securely sandboxed process" (não é um processo em sandbox segura) e que esses contêineres "can get a root shell on the host" (podem obter um shell root no host). A aula 17.5 trata disso e de um socket do Docker montado, que tem o mesmo efeito.
:::

## Um runtime de navegador é outro lugar, não uma VM menor

Os WebContainers, da StackBlitz, rodam aplicações Node.js "entirely inside your browser tab" (inteiramente dentro da aba do navegador). O código roda na máquina do visitante, dentro do navegador dele, e nunca no seu servidor. Isso é útil para uma página interativa de programação, mas responde a outra pergunta. Ele não roda um interpretador CPython ao lado do seu controlador e dos seus dados, então não substitui uma microVM com Python. A aula 17.5 o compara com os outros.

## Rode o exercício: limites não são isolamento

O módulo é `src/agentlab/sandbox/process.py`, que a [aula 17.2](/pt-br/lessons/17-sandboxed-agent-execution/17.2-resource-and-filesystem-limits/) explica linha por linha. Aqui você só o usa. O teste cria um arquivo fora do diretório de trabalho do script e nunca o passa para dentro:

```python
# file: examples/agent-engineering/tests/test_sandbox_isolation.py
    def test_the_same_process_reads_a_host_file_it_was_never_given(self):
        # The file lives outside the working directory; nobody passed it in.
        code = f"print(open({str(self.secret)!r}).read(), end='')"
        result = run_python(code, Path(self.workdir.name))
        self.assertEqual(result.stdout, b"host-only data\n")
```

A partir de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest tests.test_sandbox_isolation -v`. Espere `Ran 3 tests` e `OK`. Os três testes valem juntos. `test_the_limits_are_applied` mostra que um laço ocupado é morto pelo limite de CPU, não pelo relógio. O teste do arquivo do host mostra que o mesmo processo ainda lê um arquivo que nunca recebeu. O controle positivo mostra que um caminho inexistente falha de verdade, então a leitura acima encontrou o arquivo real.

Para ver o primeiro teste pegar uma regressão, apague a linha que define `RLIMIT_CPU` no bootstrap dentro de `process.py`. O laço passa a rodar até o timeout de relógio, `result.timed_out` vira verdadeiro e o teste falha. Restaure a linha. O teste do arquivo do host não tem correção dentro deste módulo: fechar essa exposição exige outro limite, que as aulas 17.4 e 17.5 constroem e medem.
