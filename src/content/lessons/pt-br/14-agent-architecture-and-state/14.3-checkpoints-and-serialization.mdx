Um processo worker está rodando o assistente de compras no PO-1001. Ele já conferiu a fatura, então o status da execução é `checked`. Aí um deploy reinicia o worker. Quando o processo novo sobe, o que ele sabe sobre run-1? Se a resposta é "o que estava na memória do processo antigo", ele não sabe nada. Vai recomeçar a execução em `received`, e nada vai avisá-lo de que a conferência já aconteceu. Esta aula faz o estado sobreviver ao reinício. Depois trata o caso mais difícil: dois workers que acham, cada um, que são donos da execução.

## Um snapshot em memória é um checkpoint?

Um *snapshot* é uma cópia do estado num momento. Onde ele mora decide ao que ele sobrevive. Um objeto Python, ou um banco SQLite aberto como `":memory:"`, vive dentro de um processo e some com ele. A própria documentação do LangGraph diz o mesmo dos seus savers em memória: "When the process restarts, all checkpoints are lost" (quando o processo reinicia, todos os checkpoints se perdem).

Um *checkpoint*, neste curso, é um snapshot gravado em *armazenamento durável*: um arquivo ou banco de dados que dura mais que o processo e pode ser lido pelo próximo. O `CheckpointStore` do projeto guarda uma linha por execução num arquivo SQLite. O SQLite é um motor de banco de dados da biblioteca padrão do Python que guarda um banco inteiro num único arquivo.

## Serialização: o estado como texto

*Serialização* transforma um objeto em bytes que você pode guardar ou enviar. *Desserialização* faz o caminho de volta. O projeto serializa o `RunState` em JSON com o `model_dump_json` do Pydantic. Esta é a linha que o exercício grava depois do primeiro passo:

```json
{"schema_version":1,"run_id":"run-1","principal":{"user_id":"u1","tenant_id":"tenant-a","roles":[]},"status":"checked","step":1,"max_steps":12,"version":1,"evidence":[]}
```

Por que JSON? É texto puro, então você pode abrir o banco e ler com os próprios olhos o estado de uma execução travada. Qualquer linguagem o interpreta. Carregá-lo também não executa código. O formato `pickle` do Python também guardaria o objeto, mas sua documentação avisa que fazer unpickling de dados não confiáveis pode executar código arbitrário. Um checkpoint é lido de volta por um processo posterior, talvez depois de alguém mal-intencionado ter mexido no arquivo, então esse risco importa aqui.

Dois campos existem por causa do armazenamento. `schema_version` diz qual formato de registro é este. Quando uma versão futura do código mudar o formato, as linhas antigas ainda dirão `1`, e o carregador pode recusar uma versão que não entende. Chutar seria pior. O `load` transforma essa recusa num erro claro:

```python
# file: examples/agent-engineering/src/agentlab/state/checkpoints.py
    def load(self, run_id: str) -> RunState | None:
        """The last committed state, or None. An unknown schema raises instead of being guessed."""
        row = self._db.execute("SELECT body FROM run_state WHERE run_id = ?", (run_id,)).fetchone()
        if row is None:
            return None
        try:
            return RunState.model_validate_json(row[0])
        except ValidationError as error:
            raise ValueError(f"stored state for {run_id} does not match schema version 1") from error
```

O outro campo, `version`, conta as escritas confirmadas. Ele é a chave das duas últimas seções.

## Transações: tudo ou nada

Uma *transação* é um grupo de mudanças no banco que dá certo ou falha como uma unidade. A documentação do SQLite descreve o commit atômico como "either all database changes within a single transaction occur or none of them occur" (ou todas as mudanças de uma transação acontecem, ou nenhuma). Ela também diz que as transações "appear to be atomic even if the transaction is interrupted by an operating system crash or power failure" (parecem atômicas mesmo se interrompidas por uma queda do sistema operacional ou de energia). `BEGIN IMMEDIATE` abre uma transação que pega o lock de escrita na hora. `COMMIT` torna as mudanças permanentes, e `ROLLBACK` as descarta.

O store abre a conexão com `isolation_level=None`, o que diz ao módulo `sqlite3` do Python para não abrir transações por conta própria. Toda transação de `save(state, expected_version, effects=())` fica então visível no seu corpo, que grava `state` como versão `expected_version + 1` ou levanta `StaleWrite`:

```python
# file: examples/agent-engineering/src/agentlab/state/checkpoints.py
        new = RunState.model_validate({**state.model_dump(), "version": expected_version + 1})
        self._db.execute("BEGIN IMMEDIATE")
        try:
            if expected_version == 0:
                cursor = self._db.execute(
                    "INSERT INTO run_state (run_id, version, body) VALUES (?, 1, ?) ON CONFLICT (run_id) DO NOTHING",
                    (new.run_id, new.model_dump_json()),
                )
            else:
                cursor = self._db.execute(
                    "UPDATE run_state SET version = ?, body = ? WHERE run_id = ? AND version = ?",
                    (new.version, new.model_dump_json(), new.run_id, expected_version),
                )
            if cursor.rowcount != 1:
                raise StaleWrite(f"{new.run_id} is no longer at version {expected_version}")
            for key, draft in effects:
                self._db.execute(
                    "INSERT INTO outbox (idempotency_key, run_id, payload, status) VALUES (?, ?, ?, 'pending')",
                    (key, new.run_id, draft.model_dump_json()),
                )
            self._db.execute("COMMIT")
        except BaseException:
            self._db.execute("ROLLBACK")
            raise
        return new
```

Ignore `effects` por enquanto; a [aula 14.4](/pt-br/lessons/14-agent-architecture-and-state/14.4-replay-and-side-effects/) explica. A transação já faz um trabalho aqui. Um teste inicia um processo filho de verdade que chama `save` e se mata com `os._exit(1)` depois do `UPDATE` e da primeira inserção no outbox, antes do `COMMIT`. Quando o processo pai reabre o arquivo, a execução continua na versão 1, em `checked`, e o outbox está vazio. Uma queda no meio de um passo deixa o último checkpoint confirmado e nada escrito pela metade.

## Dois escritores, uma execução: compare-and-swap

A durabilidade cria um problema novo. Suponha que os workers A e B carreguem run-1 na versão 3. A decide `ready` e salva. B, ainda com a versão 3, decide `needs_info` e salva. Se a escrita de B substituir a linha, a decisão de A se perde sem erro nenhum. Essa falha se chama *atualização perdida*.

O *compare-and-swap* (CAS, comparar e trocar) evita isso: grave o valor novo só se o valor guardado ainda for o que você leu. Aqui o valor comparado é o número da versão. O `UPDATE` leva `WHERE run_id = ? AND version = ?`, então só muda uma linha se ninguém confirmou nada desde que este escritor carregou o estado. `cursor.rowcount` informa quantas linhas casaram. Zero quer dizer que alguém chegou antes, e o store levanta `StaleWrite`. B precisa então recarregar a versão 4 e decidir de novo a partir do que A fez.

Esse estilo se chama *controle de concorrência otimista*, a partir do artigo de 1981 de Kung e Robinson, "On optimistic methods for concurrency control". Os workers fazem o trabalho sem segurar locks, e os conflitos são detectados na hora do commit. Ele serve para execuções em que dois escritores na mesma execução são raros, mas possíveis.

:::caveat
O CAS rejeita a escrita desatualizada. Ele não decide o que B deve fazer depois. Recarregar e decidir de novo costuma ser o certo para uma máquina de estados. Se B já tivesse enviado um e-mail antes de a gravação falhar, porém, esse e-mail já está no mundo, e nenhum rollback o traz de volta. Efeitos fora do banco são o assunto da próxima aula.
:::
