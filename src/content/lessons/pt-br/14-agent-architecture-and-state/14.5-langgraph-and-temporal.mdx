Você construiu a execução de compras à mão: uma tabela de transições, checkpoints em SQLite com compare-and-swap e um outbox com chaves de idempotência. Dois frameworks muito usados empacotam essas ideias. Cada um responde do seu jeito à pergunta da [aula 14.4](/pt-br/lessons/14-agent-architecture-and-state/14.4-replay-and-side-effects/): depois de uma queda, o que roda de novo? Esta aula reconstrói a execução no LangGraph 1.2.12 e no SDK Python do Temporal 1.34.0, as versões que o projeto de exercícios fixa. Cada parte termina com um teste que mostra exatamente o que se repete.

## A mesma execução como grafo do LangGraph

O LangGraph monta uma execução como um `StateGraph`: os nós são funções Python que devolvem atualizações para um estado compartilhado, e as arestas dizem qual nó roda em seguida. Uma *aresta condicional* chama uma função de roteamento para escolher entre vários nós. É a ramificação e o laço da [aula 14.2](/pt-br/lessons/14-agent-architecture-and-state/14.2-states-dags-branches-and-loops/). Esta é a ligação dos nós no `frameworks.py` do projeto:

```python
# file: examples/agent-engineering/src/agentlab/state/frameworks.py
    builder = StateGraph(GraphState)
    builder.add_node("receive", receive)
    builder.add_node("check", check)
    builder.add_node("ask_supplier", ask_supplier)
    builder.add_node("complete", complete)
    builder.add_edge(START, "receive")
    builder.add_edge("receive", "check")
    builder.add_conditional_edges("check", route, ["ask_supplier", "complete"])
    builder.add_edge("ask_supplier", "check")
    builder.add_edge("complete", END)
    return builder.compile(checkpointer=SqliteSaver(conn))
```

O `checkpointer` é o que torna a execução durável. O `SqliteSaver`, do pacote `langgraph-checkpoint-sqlite`, grava checkpoints num arquivo SQLite. Cada execução é uma *thread*, identificada pelo `thread_id` da config, e os checkpoints são guardados por thread.

## O que um reinício do LangGraph repete?

A documentação do LangGraph diz que ele "creates a checkpoint at each super-step boundary" (cria um checkpoint em cada fronteira de super-step). Um *super-step* é um tique do grafo, em que roda todo nó agendado para aquele tique. Nós que rodam um depois do outro ficam em super-steps separados. A documentação acrescenta que "you can only resume execution from a checkpoint" (só dá para retomar a execução de um checkpoint). Então um nó que cai no meio roda de novo desde o início.

O exercício prova isso. O nó `check` cai na primeira chamada. O teste então abre um novo objeto de grafo sobre o mesmo arquivo, como faria um processo reiniciado, e chama `invoke(None, config)` para retomar a thread:

```python
# file: examples/agent-engineering/tests_frameworks/test_state_frameworks.py
    def test_a_restart_resumes_after_the_last_checkpoint(self):
        check, received = FlakyCheck(), []
        with self.assertRaises(RuntimeError):
            self.open_graph(check, received.append).invoke({"status": "received", "supplier_answered": True}, self.config, durability="sync")
        # A new graph object over the same file, as after a process restart.
        final = self.open_graph(check, received.append).invoke(None, self.config, durability="sync")
        self.assertEqual(final["status"], "completed")
        self.assertEqual(len(received), 1)  # finished before the crash: not run again
        self.assertEqual(check.calls, 2)  # interrupted mid-step: runs again
```

`receive` rodou uma vez e `check` rodou duas. Se `check` tivesse criado uma fatura antes de cair, a fatura seria criada duas vezes. Um checkpoint do framework não muda isso. Efeitos colaterais dentro de um nó ainda precisam da chave da aula 14.4.

O teste passa `durability="sync"`. O LangGraph oferece três modos de durabilidade. Com `"sync"`, ele persiste cada checkpoint "synchronously before the next step starts" (de forma síncrona, antes de o próximo passo começar). Com `"async"`, persiste "while the next step executes" (enquanto o próximo passo roda), e a documentação avisa que ele "does not write checkpoints if the process crashes during execution" (não grava checkpoints se o processo cair durante a execução). No código fixado, `"async"` é o padrão. Escolha `"sync"` quando uma queda nunca puder perder um passo terminado.

## O orçamento de passos é o recursion_limit

O LangGraph conta super-steps e levanta `GraphRecursionError` quando uma execução passa do seu `recursion_limit`. O exercício define o limite como 8 na config. Um fornecedor que nunca responde então fica no laço `check → ask_supplier → check` até o erro pará-lo. Um fornecedor que responde termina em três super-steps.

Por que defini-lo explicitamente? A página da Graph API diz que o padrão é de 1.000 passos desde a versão 1.0.6. O código na tag 1.2.12 define `DEFAULT_RECURSION_LIMIT` como `10007`, a partir da variável de ambiente `LANGGRAPH_DEFAULT_RECURSION_LIMIT`. Um laço medido contra o pacote instalado parou em 10.007 passos. Quando documentação e código discordam, vale o código que você roda, e um orçamento definido por você evita a dúvida por completo.

## A mesma execução como workflow do Temporal

O Temporal divide uma execução em duas partes. Um *workflow* é o código de orquestração. Uma *activity* é uma função que mexe no mundo: uma chamada de API, uma escrita em banco, uma chamada ao modelo. O servidor do Temporal registra um *histórico de eventos* para cada workflow, um log do que o workflow pediu e do que voltou. Se um worker morre, outro worker reconstrói o workflow *reproduzindo* esse histórico (o replay): roda o código do workflow de novo desde o começo, e cada activity já registrada como concluída devolve o resultado guardado sem rodar de novo.

O replay só funciona se o código do workflow fizer "the same Workflow API calls in the same sequence, given the same input" (as mesmas chamadas à API de workflow, na mesma sequência, com a mesma entrada). Por isso o código do workflow não pode ler o relógio, sortear números nem fazer I/O diretamente. Isso pertence às activities, ou a chamadas do SDK cujos resultados ficam guardados no histórico. Este é o workflow do projeto e sua activity de fatura:

```python
# file: examples/agent-engineering/src/agentlab/state/frameworks.py
    @activity.defn
    async def create_invoice(self, draft_json: str) -> str:
        info = activity.info()
        # Temporal's recommended key: the same on every retry, unique per workflow run.
        key = idempotency_key(info.workflow_run_id, info.activity_id)
        return self.service.create(key, InvoiceDraft.model_validate_json(draft_json))


@workflow.defn
class InvoiceWorkflow:
    """Deterministic orchestration: no clock, no I/O, only activities and timers."""

    @workflow.run
    async def run(self, draft_json: str) -> str:
        await workflow.execute_activity_method(
            InvoiceActivities.check_purchase, draft_json, start_to_close_timeout=timedelta(seconds=30)
        )
        await workflow.sleep(timedelta(days=3))  # a durable timer: the supplier's dispute window
        return await workflow.execute_activity_method(
            InvoiceActivities.create_invoice,
            draft_json,
            start_to_close_timeout=timedelta(seconds=30),
            retry_policy=RetryPolicy(initial_interval=timedelta(seconds=1), maximum_attempts=5),
        )
```

`workflow.sleep` cria um *timer durável*. A documentação do Temporal diz que os timers são persistidos e que "Workers consume no additional resources while waiting for a Timer to fire" (os workers não consomem recursos extras enquanto esperam um timer disparar). A espera sobrevive a um reinício do worker. O bloco de imports no topo de `frameworks.py` fica dentro de `workflow.unsafe.imports_passed_through()`. O Temporal reimporta o módulo do workflow dentro de um sandbox, um ambiente isolado, e esse bloco lhe diz para reutilizar os módulos do LangGraph e do projeto que já estão carregados.

## O que um reinício do Temporal repete, e o que prova a conclusão?

O teste inicia o workflow num primeiro worker e espera até o histórico mostrar que o timer começou. Então desliga esse worker. Um segundo worker assume, e o teste espera o resultado. O ambiente de teste com avanço de tempo do Temporal pula os três dias. Seu SDK baixa o servidor de teste no primeiro uso, então a primeira execução precisa de acesso à rede. O sistema de contas perde a resposta da primeira tentativa de `create_invoice`.

As asserções mostram o que aconteceu. `check_purchase` rodou uma vez: terminou antes do reinício, e o replay devolveu o resultado registrado. `create_invoice` rodou duas vezes, porque o timeout fez a primeira tentativa falhar e o Temporal a repetiu. A documentação do Temporal avisa que uma activity "may be executed multiple times" (pode ser executada várias vezes), mesmo que "will be observed as completed exactly once" (seja vista como concluída exatamente uma vez). O sistema de contas ainda guarda uma única fatura, graças à chave. O histórico traz `TimerFired` pelo menos três dias depois de `TimerStarted` e termina com `WorkflowExecutionCompleted`. Ele não traz nenhum evento `ActivityTaskFailed` para a tentativa repetida.

Então dois registros respondem "terminou?". O histórico prova que o workflow terminou e viu um resultado. Só o registro do sistema de contas sob a chave prova que existe uma única fatura.

:::note
Os workers definem `max_cached_workflows=0`. Um valor diferente de zero faz o worker guardar workflows em cache e usar "sticky task queues" (filas de tarefas fixas), que mandam a próxima tarefa de um workflow de volta ao worker que o rodou por último. Nos nossos ensaios com o cache ligado, a passagem para o segundo worker travou até o teste estourar o tempo limite de 30 segundos. Com o cache desligado, toda tarefa reproduz o histórico em qualquer worker que a pegar, que é o comportamento que este exercício existe para mostrar.
:::

## Rode o exercício

O código está em `src/agentlab/state/frameworks.py` e os testes em `tests_frameworks/test_state_frameworks.py`. Eles precisam do grupo de dependências opcional `frameworks`. A partir de `examples/agent-engineering/`, rode `uv sync --frozen --group frameworks` e depois `uv run --frozen python -m unittest discover -s tests_frameworks -p "test_state_frameworks.py"`.

A saída esperada termina com `Ran 4 tests` e `OK`. Acima dela aparece um traceback que termina em `OutcomeUnknown: reply lost`. É o SDK registrando a falha injetada na primeira tentativa, e faz parte do teste. Para ver a chave fazer diferença, acrescente `info.attempt` à parte de operação da chave em `create_invoice`, para que cada tentativa ganhe uma chave diferente. O teste do Temporal então falha com `'AP-0002' != 'AP-0001'`: agora existe uma segunda fatura. Escolha o LangGraph quando quiser um grafo de passos de modelo e ferramenta dentro de um processo. Escolha o Temporal quando uma execução precisar esperar dias, sobreviver a reinícios de worker e repetir activities sob o controle de um servidor. Nos dois casos, a chave na escrita externa é trabalho do seu código.
