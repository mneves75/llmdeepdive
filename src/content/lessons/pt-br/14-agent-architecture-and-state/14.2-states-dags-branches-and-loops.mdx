O pedido de compra PO-1003 é de 25 pacotes de luvas de segurança. A fatura do fornecedor chega sem a quantidade, então o assistente pede essa informação, o fornecedor responde, a fatura é conferida de novo e desta vez passa. Essa execução foi `received → checked → needs_info → checked → ready → completed`. A pergunta desta aula é como escrever esses movimentos para que o código recuse um movimento sem sentido e pare um laço que nunca se resolve. A palavra que você vai ouvir para isso é "grafo", e ela esconde três ideias diferentes.

## Que tipo de grafo é uma execução?

Um *grafo dirigido* é um conjunto de nós ligados por setas. Ele aceita quaisquer setas, inclusive as que levam de volta ao ponto de partida.

Um *DAG* (directed acyclic graph, grafo dirigido acíclico) é um grafo dirigido "with no path that starts and ends at the same vertex" (sem nenhum caminho que comece e termine no mesmo vértice), nas palavras do Dictionary of Algorithms and Data Structures do NIST. As aulas deste curso formam um: cada aula lista seus pré-requisitos, e a verificação `content:graph` do repositório, que roda no CI, falha se essas ligações formarem um ciclo. Um ciclo ali significaria que alguma aula nunca poderia ser alcançada.

A execução acima não é um DAG. O caminho `checked → needs_info → checked` volta ao início. Isso é um *ciclo*, e não há problema: um grafo de execução pode ter laços, enquanto o grafo de pré-requisitos não pode. Mantenha os dois separados: chamar um workflow com laços de "DAG" esconde justamente a propriedade que você mais precisa controlar.

A terceira ideia é a que a execução usa. Uma *máquina de estados finitos* é, na definição do NIST, um modelo com "a set of states, a start state, an input alphabet, and a transition function" (um conjunto de estados, um estado inicial, um alfabeto de entrada e uma função de transição). Aqui os estados são os status da execução, o estado inicial é `received`, e a função de transição é uma tabela que diz qual status pode seguir qual. Os nós de um DAG costumam ser trabalhos separados, cada um feito uma vez. Os nós de uma máquina de estados são as condições de uma execução, e uma execução pode visitar o mesmo nó muitas vezes.

## A tabela de transições da execução

O projeto escreve a tabela como um dicionário que leva cada status ao conjunto de status permitidos em seguida:

```python
# file: examples/agent-engineering/src/agentlab/state/transitions.py
TERMINAL = frozenset({"completed", "failed", "cancelled"})

# No row leads to ``awaiting_approval``: track 20 keeps approval status on its own row (agentlab.approval.store).
TRANSITIONS: dict[str, frozenset[str]] = {
    "received": frozenset({"checked", "cancelled", "failed"}),
    "checked": frozenset({"needs_info", "ready", "cancelled", "failed"}),
    "needs_info": frozenset({"checked", "cancelled", "failed"}),
    "ready": frozenset({"completed", "cancelled", "failed"}),
    "completed": frozenset(),
    "failed": frozenset(),
    "cancelled": frozenset(),
}
```

Quatro características aparecem nela. A *ramificação* é a linha de `checked`: a execução vai para `needs_info` ou para `ready`. O *laço* é `needs_info`, cuja linha leva de volta a `checked`. A *pausa* também é `needs_info`, porque a execução espera ali pelo fornecedor. Os *estados terminais* têm linhas vazias, então nada sai de `completed`, `failed` ou `cancelled`. Todo status ativo também pode ir para `cancelled`, quando uma pessoa interrompe a execução, ou para `failed`, quando há um erro.

Por que uma tabela, e não uma cadeia de `if` espalhada pelo código? Porque a tabela é um dado que se lê numa tela só. Quem revisa vê todos os movimentos legais de uma vez, e uma mudança nas regras aparece como uma diferença de uma linha na revisão. Um teste também consegue percorrer cada linha, o que é bem mais difícil quando as regras ficam escondidas nas funções que fazem o trabalho. As trilhas seguintes partem da mesma ideia. A trilha 23, por exemplo, julga uma execução por seu caminho ter sido permitido, e não por ter seguido uma única sequência "de ouro" fixa de passos.

## Por que um laço precisa de orçamento?

Um laço com saída é código correto. O risco é um laço cuja saída depende de algo fora do seu controle, como um fornecedor que nunca responde ou um modelo que continua propondo `needs_info`. O guia da Anthropic observa que agentes costumam incluir "stopping conditions (such as a maximum number of iterations) to maintain control" (condições de parada, como um número máximo de iterações, para manter o controle). O registro `RunState` do projeto traz um contador `step` e um limite `max_steps`, e `advance` aplica os dois:

```python
# file: examples/agent-engineering/src/agentlab/state/transitions.py
def advance(state: RunState, to: str) -> RunState:
    """Return the next state, or raise ``IllegalTransition``.

    The new record is validated again, because ``model_copy`` would accept a
    status the record does not allow.
    """
    if to not in TRANSITIONS.get(state.status, frozenset()):
        raise IllegalTransition(f"{state.status} -> {to} is not in the table")
    step = state.step + 1
    if step >= state.max_steps and to not in TERMINAL:
        to = "failed"  # the budget is spent and the run has not finished
    return RunState.model_validate({**state.model_dump(), "status": to, "step": step})
```

Leia a regra do orçamento assim: o movimento que usaria o último passo sem terminar a execução a encerra em `failed`. Com `max_steps=5` e um fornecedor que nunca responde, os movimentos 1 a 4 vão para `checked`, `needs_info`, `checked`, `needs_info`. O movimento 5 propõe `checked`, mas a execução não pode terminar nesse movimento, então ela falha no passo 5.

## O modelo propõe e a tabela decide

Num agente, o modelo escolhe o próximo status. Neste projeto ele nunca define o status diretamente. O laço condutor pede uma proposta e a passa por `advance`:

```python
# file: examples/agent-engineering/src/agentlab/state/transitions.py
def run_until_terminal(state: RunState, decide: Callable[[RunState], str]) -> RunState:
    """Ask ``decide`` for each next status until the run reaches a terminal state.

    The loop always ends: every move adds a step, and the budget turns the
    last one into ``failed``.
    """
    while state.status not in TERMINAL:
        state = advance(state, decide(state))
    return state
```

Nos testes, `decide` lê a resposta de um `ScriptedModel`, o modelo offline do projeto que repete respostas fixas. Quando o roteiro responde `completed` com a execução em `checked`, `advance` levanta `IllegalTransition`. A tabela não consegue julgar se `ready` é uma escolha *sensata* quando falta informação. Ela só garante que a execução anda por rotas que alguém escreveu e revisou.
