O assistente de compras que você vai construir ao longo destas trilhas começa com um trabalho comum. Um fornecedor manda por e-mail a fatura do pedido de compra PO-1001: quarenta caixas de parafusos a USD 12,50, total de USD 500,00. Seu código precisa ler o total, conferi-lo com o pedido e registrar a fatura. Esse trabalho precisa de um agente? É tentador recorrer a um. Esta aula dá um jeito de decidir, e um teste que depois diz se qualquer execução, com agente ou sem, de fato fez o seu trabalho.

## Três jeitos de ler uma fatura

Aqui está o começo da mensagem do fornecedor, um dos fixtures sintéticos (dados de teste inventados) do projeto de exercícios:

```text
# file: examples/agent-engineering/src/agentlab/fixtures/supplier_messages/benign.txt
Subject: Invoice for PO-1001

Hello,

The 40 boxes of M8 hex bolts on purchase order PO-1001 were delivered on
Tuesday. Please find our invoice attached: 40 x USD 12.50 = USD 500.00.
```

Três tipos de sistema poderiam lê-la.

**Um parser determinístico.** "Determinístico" quer dizer que a mesma entrada sempre dá a mesma saída. Esse fornecedor sempre escreve a linha de assunto e a linha "quantidade x USD preço = USD total" do mesmo jeito, então uma expressão regular (um padrão de texto) encontra as duas:

```python
# file: examples/agent-engineering/src/agentlab/state/workflow.py
SUBJECT = re.compile(r"^Subject: Invoice for (PO-\d{4})$", re.MULTILINE)
TOTAL = re.compile(r"(\d+) x USD ([\d,]+\.\d{2}) = USD ([\d,]+\.\d{2})")


def parse_supplier_invoice(text: str) -> tuple[str, Decimal]:
    """Return (purchase order id, invoice total) from the supplier's fixed layout.

    Raises ``ValueError`` on any other layout: a parser that guesses would turn
    a format change into a wrong payment instead of an error someone sees.
    """
    subject, total = SUBJECT.search(text), TOTAL.search(text)
    if subject is None or total is None:
        raise ValueError("not the expected invoice layout")
    return subject.group(1), Decimal(total.group(3).replace(",", ""))
```

Rodar não custa nada, a resposta é sempre a mesma e ele recusa o que não reconhece. Sua fraqueza é o outro lado dessa força: um layout novo faz o parser falhar.

**Uma chamada ao modelo.** Quando quarenta fornecedores escrevem cada um do seu jeito, um padrão por fornecedor deixa de ser prático. Um modelo de linguagem ([aula 0.1](/pt-br/lessons/0-orientation-and-foundations/0.1-what-is-a-language-model/)) consegue ler texto livre e devolver o pedido de compra e o total em JSON. Seu código continua decidindo todo o resto: valida o JSON, confere o total e registra a fatura. O modelo preenche uma única caixa numa sequência fixa.

**Um agente.** O guia de engenharia da Anthropic traça a linha que este curso usa. Um *workflow* orquestra modelos e ferramentas "through predefined code paths" (por caminhos de código predefinidos). Um *agente* é um sistema em que os modelos "dynamically direct their own processes and tool usage" (dirigem dinamicamente seus próprios processos e seu uso de ferramentas). Imagine uma entrega contestada: o fornecedor cobrou 40 caixas, o depósito registrou 36. O próximo passo depende do que o anterior encontrou. Consultar o pedido, perguntar ao fornecedor, talvez dividir a fatura. Nenhum caminho fixo cobre todos os casos. O mesmo guia diz que agentes servem para problemas abertos em que não dá para prever o número de passos.

O guia também recomenda "finding the simplest solution possible, and only increasing complexity when needed" (achar a solução mais simples possível e só aumentar a complexidade quando necessário). Cada degrau acima custa mais por execução e é mais difícil de testar. Também dá ao modelo mais espaço para errar.

## O que trafega entre as partes?

Qualquer que seja o sistema, suas partes trocam mensagens. Dois formatos aparecem em todas as trilhas seguintes.

**JSON** (JavaScript Object Notation, RFC 8259) é texto que codifica objetos (`{"key": value}`), arrays (`[1, 2]`), strings, números, `true`, `false` e `null`. Toda linguagem lê e escreve JSON, e é por isso que modelos, ferramentas e serviços o usam para trocar dados.

**HTTP** (RFC 9110) é o protocolo de requisição e resposta por trás das APIs web. Uma requisição leva um *método* (`GET` para ler, `POST` para criar), um *caminho* (`/v1/chat/completions`), *cabeçalhos* (metadados como `Content-Type: application/json`) e um *corpo*. A resposta leva um *código de status*: 200 é sucesso, 4xx quer dizer que a requisição estava errada e 5xx quer dizer que o servidor falhou. Esse invólucro costuma ser chamado de *envelope*, e o JSON dentro dele de *payload* (a carga útil).

O próximo bloco é uma ilustração do payload que o adaptador `OpenAICompatibleModel` do projeto envia numa chamada ao modelo. O CI do curso roda esse adaptador só contra um servidor falso local em `tests/test_core.py`, nunca contra um modelo real, então trate os valores como exemplo:

```json
{
  "model": "local-test",
  "messages": [{"role": "user", "content": "find PO-1001"}],
  "tools": [{"type": "function", "function": {"name": "lookup_po", "parameters": {"type": "object"}}}]
}
```

Um caso não pertence a nenhuma família de status: resposta nenhuma. Uma requisição que estoura o tempo limite pode ou não ter surtido efeito no servidor. A [aula 14.4](/pt-br/lessons/14-agent-architecture-and-state/14.4-replay-and-side-effects/) trata exatamente dessa lacuna.

## Como saber se uma execução deu certo?

Uma execução produz duas coisas. A *transcrição* é o que o sistema disse e fez pelo caminho. O *resultado* é o estado do mundo quando ela terminou. O guia de avaliação da Anthropic dá o exemplo de um agente que diz "Your flight has been booked" (sua passagem foi reservada): o resultado é se a reserva existe no banco de dados. O mesmo vale para faturas.

Por isso a *asserção de sucesso da tarefa* do projeto ignora o que a execução relata. Ela recalcula o total esperado a partir do registro de compra confiável:

```python
# file: examples/agent-engineering/src/agentlab/state/workflow.py
def invoice_matches_purchase(po_id: str, total: Decimal, purchases: list[dict], tenant_id: str) -> list[str]:
    """The task success assertion: problems found, or an empty list.

    It compares the claimed total with quantity x unit price from the
    purchase record of the run's own tenant, so another tenant's order is
    treated as missing.
    """
    record = next((p for p in purchases if p["po_id"] == po_id and p["tenant_id"] == tenant_id), None)
    if record is None:
        return [f"{po_id} is not a purchase order of {tenant_id}"]
    expected = record["quantity"] * Decimal(record["unit_price"])
    if total != expected:
        return [f"total {total} but the purchase order expected {expected}"]
    return []
```

Um *tenant* é um cliente cujos dados precisam ficar separados dos de todos os outros clientes. Os fixtures têm dois. O PO-2001 pertence ao `tenant-b`, então uma execução do `tenant-a` o trata como inexistente, mesmo que o registro exista.

:::caveat
Os fixtures incluem uma segunda mensagem cujo comentário HTML escondido manda "the AI assistant" trocar o beneficiário e aumentar o valor para USD 11.340,00. O parser acima só lê a linha do total, então devolve USD 1.134,00. Um modelo que recebesse a mensagem inteira leria o comentário como parte da entrada. A trilha 16 trata desse problema; a asserção de sucesso daqui ainda pegaria o total inflado.
:::

## Escolhendo o sistema menos complexo

| Tarefa | Sistema menos complexo | Por quê |
|---|---|---|
| Faturas de um fornecedor com layout fixo | Parser determinístico | Mesma entrada, mesma resposta; um layout desconhecido falha de forma visível |
| Faturas em texto livre de muitos fornecedores | Uma chamada ao modelo dentro de código fixo | A extração varia; os passos ao redor dela não |
| Uma entrega incompleta contestada | Agente com orçamento de passos | O próximo passo depende do que o anterior encontrou |

Toda linha usa a mesma asserção de sucesso. O sistema que produziu o total não muda o jeito de julgá-lo.

## Rode o exercício

O módulo é `src/agentlab/state/workflow.py` e seus testes estão em `tests/test_state_workflow.py`, dentro de `examples/agent-engineering/`. A partir desse diretório, rode `uv run --frozen python -m unittest discover -s tests -p "test_state_workflow.py"`.

A saída esperada termina com `Ran 6 tests` e `OK`. O teste que mais importa entrega à asserção um total de USD 5.000,00 para o PO-1001 e espera um problema, "expected 500.00". Troque `if total != expected:` por `if False:` e esse teste fica vermelho: uma execução que relata o total errado passaria como sucesso. Restaure a linha antes de seguir para a [aula 14.2](/pt-br/lessons/14-agent-architecture-and-state/14.2-states-dags-branches-and-loops/), que dá ao caso do agente uma estrutura da qual ele não consegue sair.
