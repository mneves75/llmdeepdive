Uma mudança no assistente de compras está pronta. Os casos de desenvolvimento passam. É seguro fazer o merge? Mais tarde, com um modelo novo por trás, o assistente acerta 24 de 30 execuções. Isso é bom, e é melhor do que no mês passado? São duas perguntas diferentes, respondidas por dois tipos diferentes de execução. Esta aula separa as duas e depois relata uma taxa de sucesso do jeito que um leitor consegue conferir: com o tamanho da amostra, a incerteza e o custo.

## Replay e execuções reais respondem a perguntas diferentes

Um *replay* roda os casos com respostas gravadas do modelo: o `ScriptedModel` por trás de cada caso da [aula 23.3](/pt-br/lessons/23-agent-evaluation-and-ci/23.3-build-a-100-case-corpus/). O controlador, o gate, as ferramentas e os avaliadores são o código real. Só as palavras do modelo estão fixas. Nada varia entre execuções, então uma falha sempre significa que o código mudou, e a suíte pode rodar a cada commit. O CI do curso roda `tests/` assim, no job `examples`.

Uma *execução com modelo real* (*live trial*) roda um caso contra um modelo de verdade. As respostas mudam de uma execução para outra. O guia de 2026 da Anthropic sobre avaliação de agentes dá o motivo das repetições com clareza: "Because model outputs vary between runs, we run multiple trials to produce more consistent results", como as saídas do modelo variam entre execuções, rodam-se várias tentativas para ter resultados mais consistentes. Uma execução real custa dinheiro ou tempo de hardware e precisa de um servidor de modelo, então o CI do curso não roda nenhuma.

As duas produzem tipos diferentes de evidência, que o README do projeto mantém separados. Um replay aprovado é *fixture-tested*: a lógica de controle funciona contra respostas roteirizadas. Uma execução real aprovada é *live-model-tested*, para o modelo e a revisão registrados. Uma não substitui a outra.

## Um replay que barra toda mudança

`regressions` reproduz cada caso de desenvolvimento executado e devolve uma linha por problema. Uma lista vazia significa que a mudança pode entrar:

```python
# file: examples/agent-engineering/src/agentlab/evals/trials.py
def regressions(cases: Sequence[Case], gate: Gate = authorize) -> list[str]:
    """Replay every executed development case; return one line per problem. Empty means the change may merge."""
    failures = []
    for case in cases:
        if case.split != "dev" or not executed(case):
            continue
        result = run_assistant_case(case, gate=gate) if case.setup["runner"] == "assistant" else run_case(case)
        failures += [f"{case.case_id}: {problem}" for problem in result.problems]
    return failures
```

Ele roda 64 casos e nunca um reservado, porque os reservados são para candidatos a release. O exercício injeta uma regressão plausível: uma "refatoração" do gate que confere cada pedido contra o tenant que for dono dele. A suíte, sem nenhuma mudança, pega o defeito em cinco casos, com 11 linhas de problema: três rascunhos para o pedido de outro tenant que agora passam, e dois ataques de exfiltração cujas leituras do pedido de outro tenant agora funcionam. A suíte também aceita uma alternativa válida. O caso `ord-001` foi gravado como consulta seguida de rascunho; um modelo que cria o rascunho direto passa nele sem mudança, porque os avaliadores das aulas [23.1](/pt-br/lessons/23-agent-evaluation-and-ci/23.1-define-success-and-capture-traces/) e [23.2](/pt-br/lessons/23-agent-evaluation-and-ci/23.2-evaluate-valid-paths/) conferem efeitos e regras, não um caminho.

## Tentativas repetidas e o que relatar

Rode um caso $k$ vezes, com chance de sucesso por tentativa $p$. Dois resumos do guia respondem a perguntas diferentes. *pass@k* é a chance de que ao menos uma das $k$ tentativas dê certo; serve para uma tarefa em que uma pessoa escolhe a tentativa boa. *pass^k* é a chance de que todas as $k$ deem certo; serve para um assistente que precisa funcionar toda vez que um comprador pede. O τ-bench (Yao et al., 2024) criou o pass^k para medir essa consistência e relatou que até os agentes de chamada de função mais fortes que testou eram inconsistentes, com pass^8 abaixo de 25% no domínio de varejo.

Se as tentativas forem independentes, pass@k é $1 - (1 - p)^k$ e pass^k é $p^k$. Com $p = 0.8$ e $k = 3$, pass@3 é 0,992 e pass^3 é 0,512. O mesmo agente parece quase perfeito ou pouco melhor que uma moeda, conforme a pergunta que você faz. A independência é uma suposição: as tentativas de um caso difícil tendem a falhar juntas, então relate os resultados por caso, além do total.

## Um intervalo, não uma porcentagem solta

Trinta tentativas com 24 sucessos dão uma taxa de 80%. A taxa real pode ser menor ou maior; quanto? O intervalo de score de Wilson (Wilson, 1927) responde, e o exercício o calcula com a biblioteca padrão:

```python
# file: examples/agent-engineering/src/agentlab/evals/trials.py
def wilson_interval(successes: int, n: int, z: float = 1.959964) -> tuple[float, float]:
    """Wilson's (1927) score interval for a success rate; z = 1.959964 gives 95%.

    Unlike rate ± z·sqrt(rate·(1 - rate)/n), it stays inside [0, 1] and does
    not collapse to a zero-width interval at 0 or n successes.
    """
    if n <= 0 or not 0 <= successes <= n:
        raise ValueError("need at least one trial and 0 <= successes <= n")
    rate = successes / n
    denominator = 1 + z * z / n
    center = (rate + z * z / (2 * n)) / denominator
    half = z * math.sqrt(rate * (1 - rate) / n + z * z / (4 * n * n)) / denominator
    return max(0.0, center - half), min(1.0, center + half)
```

Para 24 de 30, ele dá cerca de 62,7% a 90,5%. São os números que a calculadora de custo por sucesso da [aula 25.2](/pt-br/lessons/25-agent-capstone-and-portfolio/25.2-a-reproducible-benchmark/) usa, e um teste confere a função em Python contra eles. A fórmula mais simples citada na docstring dá cerca de 65,7% a 94,3% para os mesmos dados e afirma que 30 de 30 são exatamente 100%, sem incerteza nenhuma; o Wilson dá cerca de 88,7% a 100%.

Intervalos mantêm as comparações honestas. A versão B, com 27 de 30, tem um intervalo de cerca de 74,4% a 96,5%, que se sobrepõe ao da versão A em quase toda a largura: trinta tentativas de cada não conseguem separá-las. Com 300 tentativas de cada, e as mesmas taxas, os intervalos ficam em 75,1% a 84,1% e 86,1% a 92,9%, e a diferença é real. A sobreposição é uma leitura aproximada, não um teste formal, mas um relatório que traz os intervalos deixa o leitor vê-la.

`run_trials` junta tudo isso. Ele roda cada caso um número escolhido de vezes, cada vez a partir de um back office novo, e relata execuções, sucessos, o intervalo de Wilson, chamadas ao modelo, um custo estimado (chamadas × um preço por chamada que você informa), o custo por sucesso, o rótulo de evidência e cada falha por caso e por tentativa. O custo por sucesso conta também as execuções que falharam, e é por isso que ele passa do custo de uma execução; a aula 25.2 acrescenta o sandbox e o tempo de revisão.

## Rodando execuções reais por conta própria

Uma execução real troca o modelo roteirizado por `OpenAICompatibleModel`, envolvido em `LiveAdapter`. O adaptador importa: o laço do assistente da [aula 16.2](/pt-br/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) nunca envia definições de ferramentas, então o adaptador acrescenta a cada chamada os JSON schemas das duas ferramentas concedidas. Ele também conta as chamadas, guarda cada erro `transport:`, `http:` ou `protocol:` como falha daquela tentativa e registra o nome de modelo que o servidor informou, que é uma alegação do servidor e não prova dos pesos por trás dele.

O trecho a seguir é uma ilustração que o CI do curso não roda, porque precisa de um servidor de modelo que você mesmo inicia (llama-server, o servidor do mlx-lm ou um provedor que você escolher):

```python
from decimal import Decimal

from agentlab.evals.corpus import build_corpus
from agentlab.evals.trials import run_trials
from agentlab.model import OpenAICompatibleModel

held_out = [c for c in build_corpus() if c.split == "held_out" and c.category in ("ordinary", "injection")]
model = OpenAICompatibleModel("http://127.0.0.1:8080/v1", model="local-model")
report = run_trials(held_out, lambda case, trial: model, trials=3, cost_per_call=Decimal("0"))
print(report.successes, report.runs, report.low, report.high, report.evidence, report.served_by)
```

São 9 casos reservados × 3 tentativas = 27 execuções. Os casos de falha de ferramenta ficam só no replay, e `run_trials` os recusa: o oráculo deles exige que o gate recuse uma chamada errada roteirizada, que um modelo real talvez nunca faça. Um relatório só recebe o rótulo `live-model-tested` quando toda tentativa usou um modelo servido e algum servidor respondeu; uma única tentativa roteirizada o torna `fixture-tested`, e uma rodada que nenhum servidor respondeu recebe o rótulo `no-model-answered`.

:::warning
Uma rodada real pequena é uma verificação didática, não uma estimativa de confiabilidade. Vinte e sete execuções sobre dados sintéticos dizem pouco sobre o tráfego de produção. Relate o modelo, a revisão, a data, o hardware ou o provedor, todos os resultados e os intervalos, e nunca misture aprovações de replay na contagem real.
:::

## Rode o exercício

O módulo é `src/agentlab/evals/trials.py`; os testes ficam em `tests/test_evals_trials.py`. De dentro de `examples/agent-engineering/`, rode `uv run --frozen python -m unittest tests.test_evals_trials`. A saída termina com `Ran 14 tests` e `OK`. Os testes conferem o intervalo de 24 em 30, pass@3 e pass^3, a suíte de replay e a regressão injetada, um caminho alternativo válido, 30 tentativas roteirizadas das quais seis alegam sucesso sem criar o rascunho, os rótulos de evidência e o adaptador enviando os schemas das ferramentas.

Para ver por que a fórmula do intervalo importa, troque a linha que calcula `half` em `wilson_interval` por `center, half = rate, z * math.sqrt(rate * (1 - rate) / n)`. Dois testes falham, `test_24_of_30_is_80_percent_between_about_62_7_and_90_5` e `test_thirty_scripted_trials_report_rate_interval_and_cost`: o limite inferior passa a cerca de 65,7%, um intervalo que exagera o que 30 tentativas conseguem mostrar. Restaure a linha antes de seguir. A [aula 24.5](/pt-br/lessons/24-agent-resilience-and-fallbacks/24.5-recovery-drills/) reaproveita este replay para ensaiar recuperações.
