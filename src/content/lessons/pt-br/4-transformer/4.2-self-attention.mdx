## Por que um token precisa do seu contexto?

O embedding de um token (o vetor que o modelo busca para cada id de token, [aula 1.5](/pt-br/lessons/1-text-to-tensors/1.5-embeddings-meaning-as-geometry/)) é uma consulta sem contexto. O token "banco" recebe o mesmo vetor inicial em "banco do rio" e em "conta no banco", mas um modelo útil precisa tratar essas duas ocorrências de forma diferente. Esse é o problema concreto: transformar uma identidade estática de token numa representação que dependa da sequência ao redor.

**Self-attention** (autoatenção) é a operação que faz isso: cada posição decide quanta informação vai buscar em cada outra posição permitida. As próprias posições são saídas do tokenizador da [aula 1.2](/pt-br/lessons/1-text-to-tensors/1.2-tokenization-i/). No Qwen3.8-27B cada uma delas é um vetor de 5120 números, o **hidden size** do modelo (a largura do vetor que cada token carrega de uma camada para a outra).

## Queries, keys e values

Represente a sequência como uma matriz $X$: uma linha por posição de token, 5120 features por linha. A camada de attention aprende três matrizes de projeção, $W_Q$, $W_K$ e $W_V$. Uma **projeção**, aqui, é uma multiplicação de matrizes aprendida que transforma cada linha num vetor novo, possivelmente de outro comprimento. A camada produz

$$
Q = XW_Q,\qquad K = XW_K,\qquad V = XW_V.
$$

Os nomes descrevem papéis, não entradas diferentes:

- **Queries** (consultas) expressam o que cada posição receptora está procurando.
- **Keys** (chaves) descrevem como cada posição disponível deve ser encontrada.
- **Values** (valores) contêm a informação que pode ser transferida.

Toda posição cria as três a partir da sua representação atual. Um hash map é uma boa primeira imagem: você busca algo com uma query e recebe de volta um value. A diferença é que attention nunca escolhe uma única key exata. Ela compara a query com todas as keys e devolve uma mistura de todos os values, ponderada por quanto cada key casou.

## Attention em três tokens, à mão

Pegue uma query e três posições, cada uma com vetores de 2 dimensões para a conta caber na cabeça. Seja a query $q = [2, 0]$ e as keys $k_1 = [1, 0]$, $k_2 = [0, 1]$, $k_3 = [0.5, 1]$.

1. **Pontue cada key** com um produto escalar (multiplique as componentes correspondentes e some, [aula 0.4](/pt-br/lessons/0-orientation-and-foundations/0.4-vectors-matrices-dot-products/)). Um produto escalar maior significa direções mais compatíveis. Os scores são $[2, 0, 1]$.
2. **Transforme scores em pesos** com o softmax, a função da [aula 0.3](/pt-br/lessons/0-orientation-and-foundations/0.3-probability-you-need/) que exponencia cada score e divide pelo total. Isso dá aproximadamente $[0.67, 0.09, 0.24]$: positivos, somando um, com a maior parte do peso no melhor casamento.
3. **Misture os values** com esses pesos. Se os values forem $v_1 = [10, 0]$, $v_2 = [0, 10]$, $v_3 = [5, 5]$, a saída é cerca de

   $$
   0.67 \cdot [10, 0] + 0.09 \cdot [0, 10] + 0.24 \cdot [5, 5] \approx [7.9, 2.1].
   $$

A saída é um vetor novo para essa posição, construído principalmente com o que a posição 1 ofereceu. A attention real também divide os scores pela raiz quadrada da dimensão de head antes do softmax; este exemplo de brinquedo pula esse passo, e a [aula 4.3](/pt-br/lessons/4-transformer/4.3-scaled-dot-product-attention/) explica por que ele é necessário.

Fazer isso para todas as queries de uma vez são três operações matriciais. Todos os pares de uma vez formam a matriz de scores $QK^\top$. Escale pela raiz quadrada da dimensão de head $d_k$ e normalize cada linha com softmax:

$$
\operatorname{Attention}(Q,K,V)
= \operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right)V.
$$

As saídas do softmax são os pesos de attention: não negativos, cada linha somando um. Multiplicar por $V$ dá a cada posição de query uma soma ponderada de vetores de value. Essa separação é o coração do projeto: keys decidem *onde ler*, values determinam *o que é lido*. Se keys e values fossem forçados a ser os mesmos vetores, endereçamento e conteúdo compartilhariam uma única representação e cada um comprometeria o outro.

Considere "O chef adicionou sal porque a sopa estava sem graça." A query em "graça" pode casar com as keys de "sopa" e "estava" mais fortemente do que com a key de "chef". Sua nova representação então mistura informação de value dessas posições. Em outra frase o mesmo token parte do mesmo embedding, mas termina em outro lugar. Essa é a mistura contextual que nos propusemos a construir.

## Os shapes reais no Qwen3.8-27B

<Figure id="attention-projection-shapes" />

Agora o exemplo trabalhado com shapes reais. Um primeiro palpite razoável, e o clássico palpite errado, é que cada projeção mapeia o hidden size nele mesmo: $5120 \to 5120$, uma matriz quadrada. A configuração do Qwen3.8-27B refuta isso.

**Queries.** As camadas de Gated Attention do modelo usam 24 query heads, cada uma de dimensão 256 (um **head** é uma cópia independente do cálculo de attention; a [aula 4.5](/pt-br/lessons/4-transformer/4.5-multi-head-attention/) explica por que existem vários). A projeção de query precisa produzir todas elas, então o query state é o número de heads vezes a dimensão de head:

$$
24 \times 256 = 6144 \neq 5120.
$$

Esses 6144 são a largura do *query state*, e ela é genuinamente não quadrada: $6144 - 5120 = 1024$ mais larga do que uma matriz quadrada seria.

**A porta.** A matriz de pesos que produz as queries é mais larga ainda. Estas são camadas de attention **com porta** (`attn_output_gate` na config), e a porta está fundida na mesma projeção: `q_proj` emite número de heads vezes dimensão de head **duas vezes**, $24 \times 256 \times 2 = 12288$. Acompanhe a divisão com cuidado, porque ela é por head, não ao meio:

- A saída é vista como 24 heads de $256 \times 2$, e o último eixo de cada head é cortado em 256 valores de query e 256 de porta.
- Junte as metades de query e você tem o query state de 6144.
- Junte as metades de porta e você tem um segundo 6144 que nunca entra na matriz de scores. Em vez disso, depois que a atenção roda, sua saída é escalada elemento a elemento por $\sigma(\text{porta})$ e só então projetada. Aqui $\sigma$ é a sigmoide ([aula 2.3](/pt-br/lessons/2-neural-network-fundamentals/2.3-activation-functions/)), que espreme qualquer número na faixa de 0 a 1, então cada valor de porta funciona como um botão de volume sobre um número da saída.

Em disco, portanto, o tensor é $5120 \to 12288$; só metade dele vira query.

**Keys e values** são ainda mais estreitos. O modelo tem apenas 4 KV heads (um projeto grouped-query, em que vários query heads compartilham um mesmo head de key e value, coberto na [aula 7.6](/pt-br/lessons/7-inference-and-efficiency/7.6-mqa-gqa-and-mla/)), então

$$
4 \times 256 = 1024,
$$

e tanto a projeção de key quanto a de value são $5120 \to 1024$.

**Saída.** Depois que os heads calculam suas saídas e são concatenados de volta à largura 6144, uma projeção de saída mapeia $6144 \to 5120$ para que o resultado caiba de novo no residual stream (o vetor corrente por token ao qual cada camada soma sua contribuição, [aula 4.10](/pt-br/lessons/4-transformer/4.10-residuals-pre-norm-post-norm/)).

Quatro retângulos, nenhum quadrado: $q: 5120 \to 12288$ (queries e porta juntas), $k: 5120 \to 1024$, $v: 5120 \to 1024$, $o: 6144 \to 5120$. Note que a entrada de $o$ tem 6144 de largura, não 12288: o que chega até ela é a *saída* da atenção concatenada e escalada pela porta, que por acaso tem a mesma largura do query state. A porta é aplicada elemento a elemento logo antes de $o$, então escala o que $o$ recebe sem alargá-lo.

:::warning
É tentador achar que as projeções de attention "precisam" preservar a largura do hidden state, e que portanto 24 heads de 256 dimensões "deveriam" ser corrigidos para caber em 5120. Não deveriam. Número de heads × dimensão de head é uma escolha de projeto independente; a projeção de saída é o que reconcilia isso com o residual stream. Se algum dia você inspecionar os pesos desse modelo e vir uma projeção de query que não é nem 5120 nem 6144, e sim 12288, isso também é a arquitetura: a porta viaja na mesma matriz, intercalada head a head, e a [aula 4.14](/pt-br/lessons/4-transformer/4.14-reading-real-weights/) mostra exatamente essa forma em um checkpoint real.
:::

## O que a self-attention deixa para as próximas aulas

A palavra **self** significa que queries, keys e values vêm de uma única sequência. Modelos decoder-only como o Qwen3.8-27B acrescentam um **causal mask** (máscara causal): a posição $i$ não pode ler posições depois de $i$, tema que a [aula 4.4](/pt-br/lessons/4-transformer/4.4-causal-masking/) desenvolve. E um único cálculo de attention não é encarregado de capturar todas as relações: as projeções são divididas nos 24 heads paralelos mencionados acima, assunto da aula 4.5. O bloco completo acrescenta conexões residuais, normalização e uma rede feed-forward; attention é a operação de roteamento dentro desse sistema maior.

Duas propriedades computacionais importam mais adiante:

- Todos os scores por pares são operações matriciais, então o treinamento processa as posições em paralelo.
- A matriz de scores tem uma entrada para cada par de posições, gerando crescimento quadrático no comprimento da sequência. A aula 4.3 quantifica essa conta no comprimento de contexto real desse modelo, e a trilha 7 trabalha para reduzi-la.

## O que os pesos de attention mostram, e o que não mostram

Pesos de attention são evidência sobre roteamento, não prova de raciocínio. Um peso alto mostra que um head transferiu informação de value por uma aresta, numa camada. Residual streams, outros heads e camadas posteriores podem amplificar ou cancelar isso.

O modelo mental durável é o de uma consulta diferenciável: cada posição escreve uma pergunta, veste um crachá e oferece um conteúdo. "Diferenciável" quer dizer que uma pequena mudança numa query ou key muda a saída um pouco, em vez de virá-la de uma vez, então o treinamento pode usar gradientes (como o erro muda quando cada peso muda, [aula 0.6](/pt-br/lessons/0-orientation-and-foundations/0.6-derivatives-gradients/)) para aprender as projeções que definem os três, de ponta a ponta.
