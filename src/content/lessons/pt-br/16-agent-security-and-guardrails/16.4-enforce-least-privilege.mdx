Até aqui um agente só lia a mensagem do fornecedor e redigia a fatura. Divida esse trabalho em três. Um *leitor de e-mail* lê as mensagens dos fornecedores e informa de que pedido e de que total cada uma trata. Um *redator de faturas* cria os rascunhos. Um *responsável pelos registros* atualiza o status de um pedido quando a mercadoria chega. O leitor de e-mail lê texto escrito por atacantes o dia inteiro, então é o papel com mais chance de ser manipulado. Suponha que ele seja manipulado por completo e emita um pedido de formato perfeito. O próximo bloco é uma ilustração dos campos desse pedido, não código que a CI do curso roda; o teste mais abaixo monta o mesmo pedido em Python:

```json
{"tool": "write_purchase_record", "arguments": {"po_id": "PO-1003", "status": "received"}}
```

O PO-1003 é um pedido aberto real do próprio tenant da execução. Marcá-lo como recebido esconderia uma entrega que nunca chegou. O gate deveria permitir?

## Menor privilégio, uma concessão por papel

O princípio do *menor privilégio* de Saltzer e Schroeder diz que todo programa "should operate using the least set of privileges necessary to complete the job" (deve operar com o menor conjunto de privilégios necessário para o trabalho), e que isso "limits the damage that can result from an accident or error" (limita o dano que um acidente ou erro pode causar). A entrada da OWASP sobre prompt injection dá o mesmo conselho para modelos: "restrict the model's access privileges to the minimum necessary for its intended operations" (restrinja os privilégios de acesso do modelo ao mínimo necessário para as operações previstas). Para os três papéis, isso significa três concessões:

```python
# file: examples/agent-engineering/src/agentlab/security/privilege.py
ROLE_GRANTS: dict[str, frozenset[str]] = {
    "mail_reader": frozenset({"lookup_po"}),
    "invoice_drafter": frozenset({"lookup_po", "create_invoice_draft"}),
    "records_clerk": frozenset({"lookup_po", "write_purchase_record"}),
}
```

O gate da [aula 16.2](/pt-br/lessons/16-agent-security-and-guardrails/16.2-indirect-prompt-injection/) confere a concessão antes de tudo, então o pedido perfeito do leitor de e-mail é recusado com "write_purchase_record is not granted to this agent". O formato nunca importou. O mesmo pedido vindo do responsável pelos registros é permitido: esse é o controle positivo, e sem ele um gate que recusasse tudo também passaria no teste.

Ajuda listar o que um leitor de e-mail totalmente enganado ainda consegue fazer com essa concessão. Ele consegue ler os pedidos do próprio tenant, de que precisa para o trabalho, e consegue informar um pedido ou um total errado. Ele não consegue ler pedidos de outro tenant, porque a verificação de tenant continua rodando, e não consegue escrever nada. Essa lista curta é o objetivo do menor privilégio: o dano de um ataque bem-sucedido é limitado pela concessão, e não pelo quanto o ataque foi convincente.

Essa é a diferença entre *validação* e *autorização*. A validação pergunta se um pedido está bem formado; os testes centrais do projeto já mostram um pedido de formato perfeito para a fatura de outro tenant passando na validação. A autorização pergunta se quem chama pode fazer essa coisa com esse objeto. Um modelo que leu o schema da ferramenta sempre consegue produzir um pedido válido, então a validade nunca pode ser a permissão.

## Campos tipados entre papéis

Como o redator descobre qual fatura redigir? Não pelo texto livre do leitor de e-mail, que poderia levar adiante as frases do atacante. A única saída do leitor de e-mail é um registro com dois campos:

```python
# file: examples/agent-engineering/src/agentlab/security/privilege.py
class ExtractedInvoice(Record):
    """What the mail reader may report about a message: two fields, nothing else."""

    po_id: str = Field(pattern=r"^PO-\d{4}$")
    total: Decimal = Field(gt=0, max_digits=12, decimal_places=2)
```

O registro é estrito e proíbe campos desconhecidos, então uma resposta que acrescenta `"payee": "Supplier Omega"` ou `"approved": true` não passa na leitura. Os campos preferidos do atacante não têm onde cair. Isso é *extração tipada*. Ela tem um limite que vale dizer com todas as letras: um tipo valida a estrutura, não o sentido. O leitor de e-mail ainda pode informar o total errado, então o gate do redator continua comparando o total com o registro de compra. Tipos estreitam o que pode ser repassado; verificações contra fontes confiáveis decidem se é verdade.

## Segredos que o agente nunca vê

O back office precisa de uma chave. O desenho tentador põe a chave onde o agente consegue usá-la: no prompt, numa variável de ambiente que uma ferramenta lê, ou como argumento de ferramenta. Aí um agente manipulado pode imprimi-la ou mandá-la para outro lugar. Um *intermediário de credenciais* (*credential broker*) guarda o segredo e o anexa ele mesmo, só para as chamadas da lista dele:

```python
# file: examples/agent-engineering/src/agentlab/security/privilege.py
@dataclass
class CredentialBroker:
    """Holds one secret and the only destinations it may be sent to."""

    routes: dict[str, str]  # tool name -> fixed URL; the model cannot choose the destination
    secret: str = field(repr=False)
    transport: Transport = field(repr=False)

    def call(self, tool: str, arguments: dict) -> JsonValue:
        url = self.routes.get(tool)
        if url is None:
            raise PermissionError(f"no credential route for {tool}")
        reply = self.transport(url, {"Authorization": f"Bearer {self.secret}"}, arguments)
        text = json.dumps(reply)
        # A service that echoes the header (in a debug field or an error) must not leak it onward.
        return json.loads(text.replace(self.secret, "[redacted]")) if self.secret in text else reply
```

Três propriedades importam. O agente nunca tem a chave, então nenhum prompt consegue extraí-la. O destino é fixo por ferramenta, então o modelo não escolhe para onde a chave vai. E uma resposta que devolve a chave, num campo de depuração ou num erro, é ocultada antes de chegar ao modelo. Os campos com `repr=False` mantêm o segredo fora de logs e de mensagens de falha dos testes, a mesma escolha que `OpenAICompatibleModel` faz para a chave de API dele.

:::note
O guia de segurança do MCP proíbe o antipadrão parecido de *token passthrough*: um servidor que repassa o token de um cliente a uma API mais adiante. A regra dele é que servidores MCP "MUST NOT accept any tokens that were not explicitly issued for the MCP server" (não podem aceitar tokens que não foram emitidos explicitamente para o servidor MCP). Ele também recomenda escopos mínimos, ampliados aos poucos, em vez de um único token amplo. A [aula 15.5](/pt-br/lessons/15-tool-contracts-and-mcp/15.5-transport-and-authorization-boundaries/) trata dessas fronteiras de autorização.
:::

## Mostre texto de fora como texto inerte

O último ativo da tabela da aula 16.1 é a tela de quem revisa. A resposta do assistente costuma repetir trechos da mensagem do fornecedor, então também é texto de fora. Se a tela de quem revisa renderiza HTML ou Markdown, a resposta pode trazer marcação que executa, ou uma imagem cujo endereço leva dados ao servidor do atacante no instante em que a página carrega. `render_untrusted` remove todo destino de link e de imagem e então escapa o resto:

```python
# file: examples/agent-engineering/src/agentlab/security/privilege.py
def render_untrusted(text: str) -> str:
    """Return HTML-safe text with every link and image target removed.

    Escaping stops markup; removing targets stops a reviewer's browser from
    fetching an attacker's URL, which could carry data in its query string.
    """
    text = MARKDOWN_LINK.sub(lambda match: f"{match.group(1)} [link removed]", text)
    return html.escape(BARE_URL.sub("[link removed]", text))
```

O rótulo sobrevive como texto ("status [link removed]"), para quem revisa ainda ver que havia algo ali. Só escapar não bastaria: a sintaxe de imagem do Markdown não tem nenhum caractere que o escape de HTML altere.

## Rode o exercício

O módulo é `src/agentlab/security/privilege.py` e seus testes estão em `tests/test_security_privilege.py`, dentro de `examples/agent-engineering/`. A partir desse diretório, rode `uv run --frozen python -m unittest discover -s tests -p "test_security_privilege.py"`.

A saída esperada termina com `Ran 11 tests` e `OK`. `test_the_mail_reader_cannot_write_records_even_with_a_perfect_request` e seu controle `test_the_same_request_passes_for_the_role_that_owns_the_write` provam que quem decide é a concessão, não o schema. `test_the_secret_reaches_the_service_for_an_allowlisted_call` confere que a chave está no cabeçalho que o serviço recebeu. `test_the_secret_never_reaches_the_model` faz uma consulta pelo intermediário contra um serviço falso que devolve a chave e então confere que a chave não está em nada do que o modelo, o resultado da execução ou o `repr` do intermediário mostram. Troque a última linha do intermediário por `return reply` e esse teste fica vermelho. Restaure-a. A aula 16.5 ataca todos esses controles de uma vez.
